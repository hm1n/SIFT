## 1. P1 — 재질문 횟수가 unknown 이후의 질문 횟수가 아닙니다

위치는 `src/features/experience-block/progress.ts:65`, `:88`, `:98`, `:150`입니다.

`recordResponse`는 unknown 이력을 저장하지 않고 전체 `askedCount >= 2`일 때 `reaskUsed`를 켭니다. 따라서 같은 요소에서 provided 다음 처음 unknown을 받으면 재질문을 한 번도 하지 않았는데 소진 처리합니다. 반대로 unknown 뒤 실제 재질문에 unanswered를 받으면 소진하지 않아 다시 물을 수 있습니다. R1과 R2로 두 방향을 재현했습니다.

관련 결함도 있습니다. `selectNextTarget`의 입력에는 다른 구체적인 단서나 이전 질문에 사용한 근거가 없고, 질문 생성에 보내는 focus에도 없습니다. 따라서 “다른 단서가 있을 때만”이라는 조건을 확인하지 않고 질문 횟수와 블록 평가만으로 재질문합니다. 요소를 고정 ID로 만든 것만으로 이 조건이 구현되지는 않습니다.

최초 unknown을 받은 상태와 그 이후 실제 질문 제시를 구분해 기록해야 합니다. 재질문이 제시되면 응답 종류와 무관하게 사용 여부를 기록해야 합니다. 새로운 단서 조건도 질문 선택 또는 질문 후보 검증에 연결해야 합니다. 코드만으로 단서의 의미적 적합성까지 보장할 수 있다고 해석하지 않습니다.

기존 테스트는 unknown→unknown과 unanswered→unanswered만 검사합니다. 수정 시 R1·R2와 단서 없는 재질문 방지 사례를 회귀 테스트로 넣어야 합니다. 반복 질문 제한이라는 핵심 요구사항 위반이므로 P1입니다.

## 2. P1 — 답변별 미반영 상태가 없어 실패한 답변이 복구 대상에서 사라집니다

위치는 `src/features/experience-block/use-experience-interview.ts:93`, `:124`, `:132`, `:204`, `:222`와 `src/features/interview/block-prompt.ts:82`입니다.

미반영 턴을 단일 슬롯에 보관하고, 어느 턴이든 성공하면 슬롯을 지웁니다. t1 실패 후 t2만 성공해도 t1의 실패 표시와 재시도 대상이 사라집니다. 연속 실패하면 앞 실패를 뒤 실패가 덮습니다. 프롬프트는 “이전 턴의 답변은 이미 주장에 반영되어 있으므로 다시 추가하지 않습니다”라고 하므로 전체 이력이 남아 있다고 자동 복구되는 것도 아닙니다. R3에서 t1이 null로 지워지는 것을 확인했습니다. 대화 원문은 남지만 블록에 반영되지 않은 정보를 회수할 처리 상태가 유실됩니다.

같은 원인이 종료에도 드러납니다.

- 처리 중 사용자 종료는 호출을 abort하지만, abort를 미반영 상태로 등록하지 않아 마지막 저장 답변이 블록에 반영되지 않은 채 끝납니다. R6으로 확인했습니다. 기존 테스트는 오히려 이때 미반영 ID가 null이어야 한다고 기대합니다.
- 10턴 자동 종료는 외부 래퍼 대신 `inner.endInterview()`를 직접 호출합니다. 마지막 턴 실패에 대한 정리 경로를 거치지 않습니다. R9에서 갱신 호출이 10회에서 멈추는 것을 확인했습니다. 이 경우에는 미반영 ID와 수동 재시도 함수가 남아 있지만 설계의 종료 시 정리 시도는 없습니다.

답변별 처리 상태를 보관하고 성공한 답변만 반영 완료로 바꿔야 합니다. 사용자 종료와 상한 종료는 공통 정리 정책을 사용해야 하며, 중단한 요청과 미반영 답변을 구분해야 합니다. 과거 답변을 현재 상태에 재처리할 때 이후 정정을 되돌리지 않도록 원문 순서도 함께 검사해야 합니다.

실측 `merged-problem-chain-t1`에서도 평가 누락 때문에 문제와 해결 정보가 모두 반영되지 않았고, t2에서 복구되지 않았습니다. 평가 누락을 거절하는 가드는 맞습니다. 이를 해결하려고 변경된 블록에 이전 평가를 그대로 채워 넣으면 낡은 평가 문제가 재발합니다. 검증을 약화하는 대신 실패 답변의 복구 경로를 보장해야 합니다. 실제 정보 누락이므로 기존 backlog 2번의 “P2, 관측 가능한 오동작 없음” 판정은 현재 구현에는 맞지 않습니다.

수정 시 R3·R6·R9와 연속 실패, 과거 답변 재처리 뒤 최신 정정 유지 사례가 필요합니다.

## 3. P1 — 비동기 작업의 취소와 상태 적용 경계가 분리되어 있습니다

위치는 `src/features/experience-block/use-experience-interview.ts:109`, `:124`, `:209`와 `src/features/interview/use-interview-stream.ts:440`, `:455`입니다.

`applyTurn`은 이전 요청을 abort한 뒤 새 요청을 시작하지만, 응답을 적용할 때 요청 ID·기준 버전·signal 상태를 검사하지 않습니다. 서버가 준 상태를 그대로 교체합니다. R4에서는 t1 재처리의 JSON 완료를 지연시키고 t2 응답을 먼저 반영한 뒤 t1 응답을 풀었습니다. 상태 버전이 2에서 1로 되돌아갔습니다. 이 재현은 취소 후에도 응답 완료가 전달되는 fetch 대체 구현을 사용해 적용 가드 부재를 드러냅니다. 모든 네이티브 fetch가 이 순서로 동작한다는 뜻은 아닙니다.

화면 이탈은 더 직접적인 문제입니다. 외부 훅에 블록 갱신을 중단하는 unmount cleanup이 없고, 내부 훅 cleanup은 스트림만 끊습니다. `onBeforeQuestion`이 나중에 끝나면 이미 내려간 화면에서도 `start()`를 호출합니다. R5에서는 unmount 뒤 블록 요청의 signal이 여전히 살아 있었고 질문 호출 수가 1에서 2로 늘었습니다.

작업 세대 또는 요청 ID, 기준 상태 버전으로 적용을 보호하고, 이탈 시 블록 갱신과 다음 질문 continuation을 함께 무효화해야 합니다. 재처리 버튼도 진행 중인 답변 처리와 같은 작업 경계를 사용해야 합니다. 현재 구조에서는 재처리가 진행 중 갱신을 끊고 그 continuation이 이전 평가로 다음 질문을 선택하는 경로도 열려 있습니다.

R4·R5가 기존 테스트에 없었습니다. 종료·unmount·재처리 경쟁을 한 묶음으로 검증해야 합니다. 정보 덮어쓰기와 이탈 후 API 호출이므로 P1입니다.

## 5. P1 — 평가 결과와 실패·충돌 맥락이 다음 질문 생성에 연결되지 않습니다

입력 전체를 무조건 늘리기보다 해당 질문에 필요한 충돌·실패·재질문 맥락을 전달하고, 그 입력을 사용하는 운영 경로의 실제 질문을 검증해야 합니다. 첫 질문은 focus를 보내지만 focus 처리 규칙이 FOLLOW_UP_RULES에만 있다는 점도 함께 정리해야 합니다. 자동 회귀로는 실패 상태 인계와 충돌 대상 인계를, 실호출 평가로는 충돌을 사실로 전제하지 않는 질문을 검사해야 합니다.

## 7. P2 — 충분성과 반응 분류의 성공 판정이 과도합니다

이번 원본에서 운영 변형인 merged의 23턴은 sufficient=true를 한 번도 내지 않았습니다. 표본에 부정·철회 사례가 많으므로 이것만으로 판정 오류율을 계산할 수는 없습니다. 다만 `multi-block-t1`의 대안에는 SSE와 WebSocket이라는 선택지와 단방향 전송이라는 선택 이유가 있는데도 충분하지 않다고 평가합니다. `recall-t1`에는 관찰한 변화와 개발 화면에서의 확인 방법이 모두 있는데 수치 미측정을 이유로 not_done으로 닫습니다.

반응 분류도 “오류 없음”으로 확정하기 어렵습니다. `problem-chain-t5`의 대상 요소는 “이 작업을 시작하게 만든 상황”인데 답변은 결과와 확인 방법만 말합니다. 실제 targetResponse는 provided입니다. 계약의 “이번 요소에 대한 반응” 기준이라면 unanswered 검토 대상입니다. 이 사례는 새 결과 정보를 버리지 않으면서 대상 요소 반응만 따로 분류해야 하는 경계 사례입니다.

| 답변 처리 시작부터 질문 첫 조각 | 전체 중앙 3.419초, 최대 10.298초입니다. |
| 블록 출력 최대 | 631토큰입니다. |

세션 로그의 $0.0239는 현재 폴더 전체 합과 다릅니다. 어떤 부분집합에서 나온 값인지는 확정하지 못했습니다. 원본에 `withQuestion=true`가 있고 실제 질문과 지연이 있으므로 블록 호출만 했다고 취급해서도 안 됩니다.

하네스의 `failure=0`은 정상 반영 46/46을 뜻하지 않습니다. 두 번 검증에 실패해도 예외가 없으면 `failure=null`로 기록합니다. 검증 성공 여부와 전송·실행 실패 수를 별도로 집계해야 합니다.

운영 경로는 `applyBlockUpdate` 거절 시 즉시 502를 반환합니다. SDK의 maxRetries는 이 외부 검증 실패를 재시도하지 않고, 클라이언트에도 자동 재시도가 없습니다. 하네스의 두 번 시도는 수동 재처리까지 성공적으로 수행한 상황을 모사할 뿐 “운영 경로와 같은 자동 복구”가 아닙니다. 운영 변형 merged에서 최초 거절률과 최종 거절률을 별도로 봐야 합니다.

또 하네스는 다음 질문을 생성하면서 `selectNextTarget`과 targetBlock·targetElement를 사용하지 않습니다. 실제 생성된 질문을 다음 턴 질문으로 쓰지도 않고 다음 합성 질문으로 진행합니다. 따라서 보고서의 합성 질문과 실제 생성 질문을 구분해야 합니다. 블록 유지·수정의 실호출 검증은 유효하지만 재질문 정책, 10턴 완주, 운영 질문 품질의 검증은 아닙니다. raw fetch와 운영 SDK의 캐시 경계 차이도 이미 문서화된 미확인 항목입니다.

## 9. 확인된 구현과 미구현 범위

주장과 표시 문장이 분리되어 있고, add·revise·retract·conflict가 서버 리듀서에 있습니다. SHA·파일·주장 참조 검증, 미해소 충돌 문장 제외, 변경된 블록의 평가 누락 거절, 마지막 10번째 답변을 수용하는 이력 상한은 구현되어 있습니다. 합성 실호출에서 다중 블록 정보 보존, 정정, 철회, 주입 지시 거부 사례도 확인됩니다.

인용 대상의 실재와 문장의 의미적 진실성을 구분한 한계 설명은 적절합니다. 이 리뷰는 모든 의미 오류를 순수 함수로 검증하라고 요구하지 않습니다.

화면은 여전히 `InterviewStreamView`에서 `useInterviewStream`을 사용하고 `useExperienceInterview`는 테스트 외 소비자가 없습니다. 블록 패널 연결은 이슈 D로 명시적으로 미뤄진 범위이므로 별도 결함으로 세지 않았습니다. 다만 현재 사용자 화면을 통해 PAAR 전체 흐름이 운영된다고 볼 수는 없습니다.

## 10. 검증과 재현

기존 작업 트리에서 `npm test`는 68개 파일·1,094개 테스트 통과, `npm run lint`와 `npm run typecheck`는 종료 코드 0이었습니다. 그 뒤 검토용 테스트 9개를 추가해 9개 모두 설계상 기대와 다른 결과를 확인했습니다. 해당 테스트는 정상 테스트 실행을 깨뜨리지 않도록 `2026-09-11-PAAR-리뷰-재현.test.tsx.txt`로 보관합니다. 제품 코드와 기존 테스트는 바꾸지 않았습니다.

재현하려면 저장소 루트에서 다음 명령을 사용합니다. 목적지에 같은 파일이 이미 있으면 덮어쓰지 말고 먼저 확인합니다.

```powershell
Copy-Item -LiteralPath 'llm-wiki/output/2026-09-11-PAAR-리뷰-재현.test.tsx.txt' -Destination 'src/features/experience-block/paar-review.repro.test.tsx'
rtk proxy npx vitest run src/features/experience-block/paar-review.repro.test.tsx
Remove-Item -LiteralPath 'src/features/experience-block/paar-review.repro.test.tsx'
```

R1·R2는 재질문, R3·R6·R9는 미반영 답변과 종료 정리, R4·R5는 비동기 경계, R7은 보충 답변, R8은 예약 정책입니다. 수정할 때는 해당 테스트를 정식 회귀로 옮기고 각 묶음 안의 나머지 실패 경로도 함께 검사해야 합니다.
