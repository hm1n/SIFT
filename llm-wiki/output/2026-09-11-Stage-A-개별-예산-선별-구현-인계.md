# Stage A 개별 예산 선별 구현 인계

## 목표

Stage A 이전 선별에서 동점 그룹을 통째로 제외하는 규칙을 없애고, 남은 입력 예산에 들어가는 WorkUnit을 개별적으로 선택합니다. 0점도 예산이 허용하면 Stage A에 전달합니다. 점수는 제한된 예산에서 처리 우선순위를 정하며, 경험의 유무나 설명 가치를 확정하지 않습니다.

이 문서는 구현 요청을 위한 설계입니다. 이 문서 작성 과정에서 제품 코드 수정이나 신규 실측은 수행하지 않았습니다.

## 배경과 확인된 근거

PR 묶음과 단일 커밋을 함께 입력하는 기능 및 후보 0개 허용은 이미 구현됐습니다. 이를 다시 구현하지 않습니다. 현재 체크아웃의 계약을 우선 확인하고 작업합니다.

[이슈 #101 측정 기록](../raw/2026-09-11-이슈101-프롬프트교체-편향측정-session-log.md)에 따르면 Algorithm은 435개 중 인프라 추가 신호가 있는 1점 커밋 하나만 선별됐습니다. 나머지 0점 커밋 434개는 하나의 동점 그룹으로 묶였고, 이미 한 개가 선택된 상태라 그룹 분할이 금지되어 모두 제외됐습니다. 전체 입력이 0개였던 것은 아닙니다.

혼합 저장소에서 PR 평균은 2.00점, 단일 커밋 평균은 0.78점이었지만 해당 표본은 전부 입력됐습니다. 이 차이는 규모 신호의 영향을 보여주며, 새로운 가중치나 점수식의 효과를 검증한 결과는 아닙니다.

관련 설계 배경은 [커밋 묶음 실험 위키](../wiki/2026-09-10-PR-없는-저장소-커밋-묶음-방식-실험.md)와 [이번 논의 기록](../raw/2026-09-11-Stage-A-개별-예산-선별-설계-session-log.md)에 있습니다.

## 구현 범위

- `work-unit-selection.ts`의 동점 그룹 일괄 포함·제외를 개별 WorkUnit 예산 검사로 바꿉니다.
- 기존 점수 계산, 신호와 가중치, 개수 상한 200개 및 바이트 상한 110,000바이트를 유지합니다.
- 단일 커밋 가산점, PR·커밋별 할당 비율, 새로운 LLM 전처리, 자동 커밋 블랙리스트는 추가하지 않습니다.
- 기존 WorkUnit 및 Stage A 식별자 계약, PR 구성 규칙, 후보 0개 허용, 응답 검증과 복구 계약을 유지합니다.

## 선별 계약

1. 기존 함수로 각 WorkUnit의 점수와 요약 바이트를 계산합니다.
2. 점수 내림차순으로 정렬하며 동점은 입력 순서를 유지합니다. 선별 함수에서 별도의 날짜 정렬을 추가하지 않습니다.
3. 정렬된 항목을 하나씩 순회합니다. 단독 요약이 전체 바이트 상한을 초과하면 `over_byte_budget`으로 제외합니다.
4. 그 외 항목은 개수 상한과 남은 바이트 예산을 동시에 만족하면 선택합니다. 그렇지 않으면 `over_input_budget`으로 제외합니다. 이 사유에는 남은 바이트 부족도 포함됩니다.
5. 한 항목이 들어가지 않아도 뒤 항목을 계속 확인합니다. 높은 점수의 큰 항목이 빠지고 낮은 점수의 작은 항목이 들어갈 수 있습니다. 따라서 선택 결과를 점수 합격선으로 설명하지 않습니다.
6. 선택된 항목을 줄바꿈으로 연결한 실제 요약 바이트를 반환합니다. 첫 항목에는 구분자가 없고, 이후 선택 항목마다 줄바꿈 바이트 하나를 더합니다. 제외된 항목은 바이트 합계에 더하지 않습니다.
7. 입력의 모든 항목은 선택 또는 제외 중 정확히 한 곳에 들어가야 합니다. 제외 항목의 식별자, 점수, 신호와 사유를 보존합니다.

`allowSplit`, 동점 그룹 구성, 첫 예산 초과 이후 선택을 차단하는 `budgetExhausted`는 필요 없어집니다. 빈 입력 또는 모든 항목이 단독 상한을 넘는 경우에는 빈 선택을 반환하고 기존 빈 상태 흐름을 유지합니다. 상한을 넘는 항목을 억지로 되살리지 않습니다.

바이트 예산이 충분한 Algorithm 표본의 기대 결과는 200개 선택과 235개 제외입니다. 이는 조건부 기대값이며 실제 캐시의 바이트를 다시 재야 합니다. 가능한 조합을 탐색해 개수나 점수 합을 최대화하는 최적화 알고리즘은 구현하지 않습니다.

## 호출부와 화면 정합성

주요 확인 대상은 다음과 같습니다. 구현 전에 실제 참조를 검색하고 동일 데이터 흐름을 함께 확인합니다.

- `src/features/experience-candidates/work-unit-selection.ts`와 대응 테스트를 수정합니다.
- `candidate-client.ts`에서 입력 순서, 요청 예산 검사, 선택·제외 결과 전달을 확인합니다.
- `experience-candidate-list.tsx` 및 저장소 분석 화면에서 제외 사유와 빈 상태를 확인합니다.
- `thresholdScore`의 모든 참조를 확인합니다. 호환성을 위해 필드를 유지한다면 선택된 최저 점수라는 통계로만 사용합니다. 화면의 “이번 판단의 점수 경계” 문구는 제거하거나 실제 선별 방식 설명으로 바꿉니다. 필드가 불필요하면 타입·호출부·테스트에서 함께 제거하되 무관한 리팩터링은 하지 않습니다.

안내 예시는 “분석 가능한 분량 안에서 점수순으로 선택했습니다. 같은 점수에서는 입력 순서를 따릅니다.”입니다. 호출부가 WorkUnit을 최신순으로 제공한다는 사실을 확인한 경우에만 사용자 문구를 최신순으로 구체화합니다. 최신순은 동점 처리 기준이며 경험 가치의 근거가 아닙니다.

기존 Loading·Empty·Error 흐름을 유지합니다. 예산으로 분석하지 못한 항목과 모델이 판단한 뒤 미추천한 항목을 혼동하지 않습니다.

## 회귀 테스트

기존 동점 그룹 전체 제외 기대값은 새 계약에 맞게 바꿉니다. 아래 항목을 기존 테스트 하네스로 검증합니다.

| 사례 | 기대 결과 |
| --- | --- |
| 1점 1개와 0점 434개를 충분한 바이트 예산으로 처리합니다. | 200개를 선택하고 235개를 입력 예산 사유로 제외합니다. |
| 모든 항목이 0점이며 개수 상한을 넘습니다. | 입력 순서대로 상한까지 선택합니다. |
| 전체 입력이 두 예산 안에 들어갑니다. | PR·단일 커밋·점수와 관계없이 모두 선택합니다. |
| 일부 선택 후 다음 항목이 남은 바이트에 들어가지 않고 뒤의 작은 항목은 들어갑니다. | 큰 항목만 제외하고 뒤 항목을 선택합니다. 낮은 점수 항목에 대해서도 확인합니다. |
| 한 항목이 단독으로 전체 바이트 상한을 초과합니다. | `over_byte_budget`으로 분류하고 뒤 항목을 계속 확인합니다. |
| 단독으로는 들어가지만 남은 개수 또는 바이트 예산이 부족합니다. | `over_input_budget`으로 분류합니다. |
| 바이트 합계가 상한과 정확히 같거나 줄바꿈 때문에 초과합니다. | 구분자를 포함해 경계를 정확히 지킵니다. UTF-8 다중 바이트 문자도 확인합니다. |
| 같은 입력을 반복 실행합니다. | 선택 순서와 제외 결과가 일정합니다. 동점 입력 순서를 바꾸면 경계에서 선택 집합이 달라질 수 있습니다. |
| 빈 입력 또는 모든 항목이 단독 상한을 초과합니다. | 빈 선택을 반환하며 Stage A를 불필요하게 호출하지 않습니다. |

각 경우에서 선택·제외 누락 및 중복이 없고, 반환 바이트가 실제 선택 요약 렌더 결과와 일치하는지도 확인합니다. 화면에는 점수 합격선으로 오해할 문구가 남지 않아야 합니다.

## 실측과 완료 기준

기존 캐시와 측정 스크립트를 재사용해 Algorithm 및 PR·커밋 혼합 표본의 변경 전후 선택 수, 제외 수·사유, 선택 바이트를 기록합니다. Algorithm이 정확히 200개 선택되지 않는다면 실제 바이트와 제외 사유로 설명합니다. 입력 기회 확대가 후보 품질 향상을 입증하지는 않습니다.

기존 Algorithm 후보 0개 결과는 입력 한 개에 대한 측정이므로 확대된 입력에도 그대로 적용하지 않습니다. 실제 Stage A 연결 검증 시에는 전수 응답 계약, 소요 시간, 토큰 사용량 및 정상적인 후보 0개 처리를 확인합니다. 후보가 나왔다면 자동 커밋이라는 이유만으로 오답으로 처리하지 말고 실제 코드 근거를 확인합니다. 측정을 실행하지 못하면 미검증으로 기록합니다.

완료 조건은 다음과 같습니다.

- 동점 그룹 때문에 남은 예산을 사용하지 못하는 문제가 재현 테스트에서 해결됩니다.
- 두 상한, 결정적인 동점 처리, 정확한 제외 사유와 화면 안내가 유지됩니다.
- 기존 PR 및 혼합 입력의 예산 내 항목이 유지됩니다.
- 관련 회귀 테스트와 저장소의 `npm test`, `npm run lint`, `npm run typecheck`가 통과합니다. 실행 명령은 프로젝트 RTK 규칙을 따릅니다.
- 변경·실측 결과를 `llm-wiki/raw/`와 관련 위키에 기록하고 `log.md`를 갱신합니다. 과거 raw 기록은 수정하지 않습니다.
- PR 본문과 연결된 기능 정의서에 동점 일괄 제외 또는 점수 경계 설명이 있다면 새 계약으로 맞춥니다. 실제 변경 대상과 접근 불가 항목을 보고합니다. 이슈 #101에서 선별 정책 변경이 범위 밖이었다는 기존 기록을 이번 후속 변경으로 구분합니다.

## 후속 판단

PR·커밋 평균 점수 차이는 이번 변경만으로 해소되지 않습니다. 예산 초과 혼합 저장소에서 제외된 단일 커밋 표본을 별도로 판단해 유효 후보 누락을 확인한 뒤 점수식 또는 종류별 예산 정책을 검토합니다. 이번 구현에 추정으로 가중치나 비율을 넣지 않습니다.
