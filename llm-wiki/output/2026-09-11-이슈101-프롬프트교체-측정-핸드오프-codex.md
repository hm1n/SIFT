## 2. 검토가 필요한 설계 판단 하나

`src/features/experience-candidates/stage-a.ts`의 `modelFacingUnitId` 함수는 단일 커밋
단위의 식별자를 SHA 앞 7자리로 잘라 모델과 주고받습니다. 모델이 실제로 보는 텍스트
(`renderWorkUnitSummary`)에 7자리만 노출되기 때문입니다. 이 선택은 측정하지 않은 트레이드오프를
남깁니다. 한 번의 판단(최대 200단위) 안에서 SHA 앞 7자리가 우연히 겹치면 잘못 매칭됩니다.
확률은 무시할 만하다고 판단했지만 실측한 적은 없습니다. 아래 3절 측정에서 `unknown_sha`나
`schema_validation` 오류가 비정상적으로 나오는지 함께 확인하세요. 근거는
`raw/2026-09-11-이슈101-WorkUnit-판별유니온-구현-session-log.md` 3절에 있습니다.

## 3. 다음 작업: 프롬프트 교체와 측정 (이슈 Tasks 3번)

### 무엇을 바꾸는지

`src/features/experience-candidates/stage-a.ts`의 `createStageAGenerate` 시스템 프롬프트
중 이 문단(현재 434번째 줄 부근, 함수 안에서 `grep -n "이미 저장소 전체에서"`로 찾으세요)을
바꿉니다.

바꾸기 전(현재 문구):

> 입력으로 들어온 묶음은 이미 저장소 전체에서 점수로 걸러낸 상위 후보입니다. 따라서 고를 것이
> 없는 입력이 아닙니다. recommended가 true이거나 기여 항목에 맞는 묶음을 합쳐서 최소 1개,
> 최대 ${payload.candidateLimit}개 고르세요. 이 상한은 고르는 개수에만 걸립니다. decisions
> 배열의 길이를 줄이는 데 쓰면 안 됩니다. 나머지 묶음은 전부 '${UNCLASSIFIED_LABEL}'로
> 담으세요. 고를 때는 규모가 큰 묶음보다 설명할 거리가 있는 묶음을 앞세우세요.

바꾼 뒤(사용자가 이미 확정한 문구, 이슈 #101 Approach 3번 그대로):

> 각 입력은 PR 묶음 또는 단일 커밋입니다. 하나의 완결된 경험이라고 가정하지 마세요. 제공된
> 정보에서 기술적 선택이나 문제 해결을 확인할 단서가 있는 항목을 후속 diff 검토 대상으로
> 추천하세요. 변경 규모나 커밋 수만으로 설명 가치를 판단하지 마세요. 제공되지 않은 문제 상황,
> 선택 이유, 성과를 추정하지 마세요.

이 확정 문구는 "최소 1개" 하한과 "이미 점수로 걸러낸 상위 후보" 문장을 없애 추천 0개를
정상 출력으로 허용하는 것이 목적입니다. 다만 이 확정 문구에는 `candidateLimit` 상한 안내와
`UNCLASSIFIED_LABEL` 처리 지시가 빠져 있습니다. 서버는 `selectStageACandidates`에서
`candidates.length > input.candidateLimit`이면 여전히 오류를 던지므로(이 검사는 바꾸지
않습니다), 모델이 상한을 넘겨 고르지 않도록 안내하는 문장은 남겨야 합니다. 예를 들어 확정
문구 뒤에 "추천 개수는 최대 ${payload.candidateLimit}개까지입니다. 이 상한은 고르는
개수에만 걸리며 decisions 배열의 길이를 줄이는 데 쓰면 안 됩니다. 추천하지 않는 나머지는
'${UNCLASSIFIED_LABEL}'로 담으세요." 같은 문장을 붙이는 식입니다. 정확한 문구는 재량이지만,
사용자가 확정한 위 인용문 자체는 바꾸지 말고 그 앞이나 뒤에 상한 안내만 보태세요. 서버의
`candidateLimit >= 1` 검사(`route.ts`의 `isStageAInput`)는 그대로 둡니다.

바로 위 문단(`가장 중요한 규칙입니다...`)의 unitId 형식 지시와 그 앞 문단(`각 묶음의 판정은
이렇게 씁니다...`)은 이번 교체 대상이 아닙니다. 건드리지 마세요.

### 측정 방법

`scripts/measure-pipeline.ts`의 `stage-a` phase를 씁니다. 사용법은 파일 맨 위 주석에
있습니다.

```
GITHUB_TOKEN=$(gh auth token) npx tsx --env-file=.env scripts/measure-pipeline.ts <owner> <repo> stage-a --cache=<경로>
```

측정 대상은 두 저장소입니다.

- `hm1n hm1n.github.io` — PR과 직접 커밋이 섞인 실제 저장소(주 측정 대상). 층 0 실측에서
  전체 29커밋 중 21개가 상세 조회 대상이었고 PR 3개, 나머지는 PR 없는 직접 커밋입니다.
- `hm1n Algorithm` — PR이 하나도 없고 BaekjoonHub 자동 커밋 435건이 전부 블랙리스트를
  통과하는 저장소(음성 대조군). 이번 변경 전에는 Stage A에 아예 도달하지 못했던 입력입니다.
  자동 채점 커밋에서 Stage A가 없는 경험을 지어내지 않는지 확인하는 것이 이 저장소의 목적
  입니다. 근거: `raw/2026-09-10-커밋-묶음-방식-층0-구조지표-실측.md`.

두 저장소 모두 프롬프트 교체 전후로 5회씩 돌리세요(`STAGE_JUDGMENT_TEMPERATURE`가 이미
고정되어 있어 온도는 신경 쓸 필요 없습니다, `llm-provider.ts` 참고). `--cache=`로 상세 조회
결과를 저장소 밖에 캐시해 두면(예: `--cache=/tmp/hm1n-github-io.json`) 5회 반복에서 같은
입력을 재사용해 순수하게 모델 출력 분산만 봅니다. 콘솔 출력의 `[stage-a] 모델 응답
decision=N/N 고유=... 누락=... 계약충족=...`과 `[stage-a] 후보=X/Y 미분류=... 판단불가=...`
줄을 기록하세요. 확인할 것:

- 전수 응답 계약(`decision=N/N`, `계약충족=true`)이 교체 전후로 유지되는지
- 추천 후보 수 분포가 0을 포함해 자연스럽게 나오는지(교체 목적이 0개 허용이므로 5회 전부
  0개가 아니어야 하고, 반대로 5회 전부 이전과 동일하게 강제로 채워지지도 않아야 함)
- `Algorithm`에서 자동 채점 커밋을 설명 가치 있는 경험으로 잘못 추천하지 않는지(콘솔에
  찍히는 후보의 커밋 제목을 직접 확인)
- `unknown_sha`/`schema_validation` 오류가 2절의 SHA 7자리 트레이드오프 때문에 발생하는지

측정 기록은 `llm-wiki/raw/2026-09-11-이슈101-프롬프트교체-측정-실측.md`처럼 새 파일로
남기세요(기존 `raw/2026-09-01-Stage-A-후보-선정-분산-측정.md`이 같은 성격의 측정이라 형식을
참고하면 됩니다). 결론이 나오면 `wiki/2026-09-10-PR-없는-저장소-커밋-묶음-방식-실험.md`나
새 wiki 문서에 반영하세요.

측정이 오래 걸리거나 결과가 애매해 프롬프트를 더 다듬어야 하면, 이슈 #101의 "분리 조건"에
따라 지금까지 반영한 부분(위 커밋 3개)만으로 별도 이슈를 새로 만들어 이 프롬프트 작업을
분리해도 됩니다.
