## 1. P1: 재처리가 현재 답변을 취소하면서 미반영 목록에서 누락시킵니다

위치는 `src/features/experience-block/use-experience-interview.ts:162`, `:186`, `:205`입니다. 이전 P1-2·P1-3과 같은 비동기 처리 흐름이며, Map과 callSeq 도입으로도 전체 경계가 해결되지 않았습니다.

재현 S3은 t1 갱신 실패 후 t2 답변을 처리하는 동안 미반영 재처리를 실행합니다. t1 재처리가 t2 요청을 abort하고 inFlight를 덮어씁니다. t2의 AbortError 경로는 미반영 Map에 등록하지 않고 반환합니다. t1 재처리까지 성공하면 미반영 ID가 null이 됩니다. 기대값은 t2입니다. 원래 대화 이력은 남아 있지만 t2는 명시적인 블록 반영 및 종료 시 재처리 대상에서 빠집니다. 이후 모델이 이력에서 우연히 회수할 가능성을 복구 보장으로 볼 수 없습니다.

같은 큐의 취소 경계도 불완전합니다. S4는 t1·t2 미반영 상태에서 재처리를 시작하고 첫 요청 도중 unmount합니다. 현재 요청은 취소되지만 루프가 다음 항목을 실행해 화면 이탈 후 네 번째 네트워크 요청을 시작합니다. 기대 호출 수는 세 번입니다. 응답 적용 가드만으로 요청 시작을 막지는 못합니다. 이 증상만 보면 비용 낭비에 가깝지만, 현재 턴 누락과 함께 같은 실행·취소 흐름에서 정리해야 합니다.

재처리와 현재 답변 처리가 서로 취소되지 않도록 직렬 실행하거나, 중단되는 턴의 소유권을 미반영 큐로 확실히 넘겨야 합니다. 큐 진입 및 각 항목 실행 전에 취소 여부도 확인해야 합니다. 기존 backlog 3번의 “중복 호출만 생기고 상태 훼손은 없다”는 설명은 이 조합에 적용되지 않습니다. 훅 공개 API로 재현했으며 실제 화면에서 버튼을 잠그는지는 이번 검증 범위 밖입니다.

## 2. P1: 완료 안내에 대한 보충 답변이 질문 예산을 차감합니다

위치는 `src/features/interview/use-interview-stream.ts:493`과 `src/features/experience-block/use-experience-interview.ts:219`, `:234`입니다. 완료 안내를 question 역할로 추가한 직전 수정의 회귀입니다.

S5에서 실제 질문 한 번과 답변 후 모든 블록이 충분해집니다. 완료 안내에 보충 답변을 제출하면 질문 생성 호출은 여전히 한 번인데 turnsUsed는 2가 됩니다. 안내를 반복해서 받으며 보충하면 상한에 도달해 자동 종료되는 경로도 열립니다. 서버 이력 교대 문제는 고쳤지만, 안내와 실제 질문을 턴 계산에서 구별하지 않았습니다.

설계 6-1절은 “안내 메시지, 재시도, 종료 후 정리 호출은 턴에 포함하지 않습니다”라고 규정합니다. 턴 상한을 10에서 늘려도 이 불일치는 남습니다. 보충 답변에 별도 비용 제한을 두고 싶다면 명시적으로 계약을 바꿔야 합니다. 현재 계약을 유지하려면 안내를 구분하고 실제 질문·답변일 때만 turnsUsed를 늘려야 합니다. 보충 답변이 직전 target을 그대로 받는 경로도 함께 검토해야 합니다.

## 3. P1: 재질문 뒤 평가가 실패하면 소진된 요소를 다시 고릅니다

위치는 `src/features/experience-block/progress.ts:75`, `:111`과 `src/features/experience-block/use-experience-interview.ts:181`입니다. 이전 P1-1의 미해결 예외 경로입니다.

첫 unknown을 기준으로 계산하도록 바뀐 점은 맞습니다. 하지만 reaskUsed는 recordAsked가 아니라 성공한 평가 뒤 recordResponse에서만 갱신됩니다. unknown 뒤 허용된 재질문을 이미 했어도 그 답변의 블록 갱신이 실패하면 재질문 소진이 기록되지 않습니다.

S6은 problem.b의 재질문을 소진하고 다른 세 블록을 충분 상태로 둡니다. problem.a도 unknown 뒤 재질문했지만 평가 실패로 recordResponse가 호출되지 않은 상태에서 다음 대상을 고르면, 기대하는 done 대신 problem.a를 다시 고릅니다. 모델 호출 실패가 사용자에게 같은 요소를 추가로 묻는 허가가 됩니다.

이미 unknown이 확인된 요소의 재질문 예산은 질문 실행에 연결해야 합니다. 평가 성공 여부와 분리하고, 질문 생성 실패·재시도 때 중복 차감하지 않는 경계까지 함께 정해야 합니다. “다른 단서가 있을 때” 조건은 별개로 여전히 미구현이며 설계 12절에도 명시돼 있습니다. 이는 이번에 새로 발견한 결함은 아니지만 원래 요구사항 전체가 충족됐다는 결론은 낼 수 없습니다.

## 반영이 확인된 사항과 실측의 한계

- provided 이후 첫 unknown에서 바로 소진되던 문제는 수정됐습니다. 추가 대조 테스트 C1도 통과했습니다.
- 일반적인 t2 성공이 기존 t1 미반영 기록을 지우던 문제는 수정됐습니다. C2가 통과했습니다. 겹치는 재처리는 위 1번의 별도 실패 경로입니다.
- callSeq와 unmount 가드, 종료 시 미반영 재처리, 완료 대기의 질문·답변 교대, lastOutcome 전달이 코드에 반영됐습니다. 기본 경로 테스트 통과를 동시 실행 전체의 보장으로 확대해서는 안 됩니다.
- StrictMode에서 종료 및 첫 블록 반영을 확인한 S1·S2는 통과했습니다. 검토 중 의심했지만 재현되지 않았으므로 지적으로 포함하지 않습니다.
- 다른 답변에서 이미 평가받은 블록을 미확인 예약에서 제외하는 수정과 정성적 결과를 수치 없음만으로 not_done 처리하지 않도록 한 프롬프트 변경을 확인했습니다.
- `.measurements/block-update-2026-09-11-p2`의 46개 결과를 재집계하면 블록 비용은 $0.02689094, 질문 비용은 $0.069333, 합계는 $0.09622394입니다. 새 raw의 반올림 수치와 일치합니다. 이 합계는 시나리오 전체 비용이며 사용자 한 명의 한 경험 비용이 아닙니다.
- 하네스는 focus·lastOutcome을 전달하지만 다음 대상은 여전히 합성 시나리오에서 가져옵니다. selectNextTarget이 고른 대상과 실제 생성된 질문을 이어 쓰는 전체 인터뷰 실측은 아닙니다. 따라서 10턴 충분성이나 1인당 비용은 아직 확정할 수 없습니다.
- 정성적 결과 프롬프트 수정 뒤 recall 재실측 성공은 raw에 기록돼 있으나 해당 재실측 폴더는 삭제됐다고 기록되어 있습니다. 현재 파일만으로 그 개선 결과를 다시 검산할 수 없습니다. targetElement 밖 답변의 provided 오분류도 기록대로 미해결입니다.
