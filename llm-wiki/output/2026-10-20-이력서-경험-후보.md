정리일 2026-10-20. `wiki/`의 결정 문서와 `raw/` 세션 로그, `output/2026-08-25-Stage-A-B-트러블슈팅-발표정리.md`를 근거로 이력서에 넣을 만한 경험을 문제, 해결, 결과 한 줄씩으로 정리했습니다. 수치는 모두 근거 문서에 적힌 값입니다. 각 항목 끝에 근거 위치를 남겼습니다.

## A. AI 스트리밍 대화 렌더링과 프론트엔드

### 1. 스트리밍 렌더링을 측정해 보고 최적화 대상 정하기

- 문제: Markdown과 코드 블록이 섞인 긴 스트리밍 대화에서 리렌더 범위, DOM 누적, 하이라이팅 비용 중 무엇이 병목인지 알지 못했습니다.
- 해결: Node와 Playwright로 반복 측정 스크립트를 만들었습니다. 측정 결과에 따라 완료된 메시지는 `memo`로 고정하고, 청크는 rAF 단위로 모아 반영하고, 하이라이팅은 코드 펜스가 닫힌 뒤 한 번만 하도록 정했습니다. 가상 스크롤은 측정 근거가 없어 넣지 않았습니다.
- 결과: 청크당 비용이 6.75ms에서 0.13ms로 51.7배 줄었습니다. DOM이 160배 늘어도 append 비용은 0.30ms에서 0.50ms로만 늘어, 병목이 DOM이 아니라 JS 재파싱임을 확인했습니다.
- 근거: `wiki/2026-08-25-스트리밍-렌더링-측정과-전송-계약.md`

### 2. SSE 전송 계약과 실패 주입 검증

- 문제: 스트림이 `done`으로 끝나면 완료로 봤기 때문에 중간 청크가 빠져도 알 수 없었습니다. 잘못된 키(401)와 없는 모델(404)도 빈 응답 정상 종료로 분류되고 있었습니다.
- 해결: SSE를 `fetch`와 `ReadableStream`으로 직접 파싱하고 `seq`로 단절을 판정했습니다. 오류 분류는 `Record` 타입으로 강제하고, 실패를 일부러 주입해 분류마다 실제로 도달하는지 확인했습니다.
- 결과: 숨어 있던 provider 오류 오분류를 찾아 고쳤습니다. 한도 초과 실패에 걸리는 시간도 6.5초에서 2.4초로 줄었습니다.
- 근거: `wiki/2026-08-25-스트리밍-렌더링-측정과-전송-계약.md`, `wiki/2026-08-25-첫-질문-생성-provider-실측과-재개-방침.md`

### 3. React Strict Mode에서 첫 답변 뒤 인터뷰가 멈추던 버그

- 문제: 답변을 보내면 화면이 `connecting`에 멈추고 요청이 하나도 나가지 않았습니다. 기존 테스트 1,339건은 이 버그를 잡지 못했습니다.
- 해결: effect가 setup, cleanup, setup 순서로 다시 실행될 때 언마운트 ref가 true로 남는 것이 원인이었습니다. setup에서 ref를 false로 되돌리고, 실제 결함을 막고 있는 가드는 남겼습니다.
- 결과: `StrictMode` wrapper를 씌운 회귀 테스트 2건을 추가했고, 수정 전에는 실패하고 수정 후에는 통과하는 것을 확인했습니다.
- 근거: `wiki/2026-09-15-Strict-Mode-언마운트표시-잔류.md`, `raw/2026-09-15-경험채팅-첫답변-로딩멈춤-session-log.md`

### 4. 3열 레이아웃의 높이 전달 결함 수정

- 문제: 인터뷰 화면 높이가 64px로 찌그러졌습니다. 이를 고치자 메시지가 창 높이만큼 늘어났고, 긴 diff를 열면 body가 16,254px까지 커졌습니다.
- 해결: 래퍼 display, grid의 `align-content`, body 높이라는 세 원인을 차례로 고쳤습니다. 같은 패턴을 쓰는 곳을 전수 조사해 함께 수정했습니다.
- 결과: 화면 높이가 64px에서 731px로 돌아왔고 body는 900px로 고정됐습니다. diff가 12,000줄이어도 부모 높이는 변하지 않습니다. 3열 전환 뒤 렌더 비용 차이는 0.08ms 이하로 회귀가 없었습니다.
- 근거: `wiki/2026-09-14-인터뷰-3열-워크스페이스.md`, `raw/2026-09-14-채팅-UI-디자인-대조와-높이-보정-session-log.md`

### 5. 클라이언트 입력 검증 단위를 서버와 일치시키기

- 문제: 화면은 답변을 글자 수로 쟀고 서버는 JSON 직렬화 바이트로 쟀습니다. 줄바꿈이 많은 코드 답변은 화면을 통과한 뒤 서버에서 413으로 거절됐습니다.
- 해결: 화면도 서버와 같은 직렬화 함수를 써서 입력 단계에서 막도록 했습니다.
- 결과: 4,500자 기준이면 통과했을 6,750바이트 입력을 회귀 테스트로 고정했습니다.
- 근거: `wiki/2026-09-08-꼬리질문-답변입력-대화누적-화면.md`

## B. LLM 파이프라인 설계

### 6. 판단 단위를 커밋에서 PR 묶음으로 전환

- 문제: 입력이 분당 토큰 한도 8,000을 넘었습니다. 게다가 커밋 단위로 보면 의미 있는 작업도 `console.log 제거` 같은 잡무 커밋으로만 보였습니다.
- 해결: 이미 조회하고 있던 PR 소속 정보로 커밋을 묶었습니다. 경로나 시간 기반 클러스터링도 실측했지만 순도가 최대 77%라 채택하지 않았습니다.
- 결과: 추가 API 비용 없이 페이로드가 81~83% 줄었습니다. 커밋 18개짜리 PWA 작업 같은 큰 경험이 후보로 잡히기 시작했습니다.
- 근거: `wiki/2026-08-24-경험-판단단위-PR-묶음-전환-검토.md`, `output/2026-08-25-Stage-A-B-트러블슈팅-발표정리.md` 1-4절

### 7. 모델이 응답을 빠뜨리던 원인 찾기

- 문제: 모델이 입력 묶음 중 일부에만 답했습니다. 측정 지표가 커밋 기준으로 남아 있어 실제 누락이 지표에 묻혀 보이지 않았습니다.
- 해결: 지표를 묶음 기준으로 고치자 누락 개수가 매번 후보 상한과 같다는 패턴이 드러났습니다. 원인은 상충하는 두 지시를 한 문단에 붙인 프롬프트였고, 이 문단을 분리했습니다.
- 결과: 15개를 모두 답한 시도가 4회 중 0회에서 3회로 늘었습니다. 복구 호출이 사라져 전체 소요가 29.5초에서 17.9초로 줄었습니다.
- 근거: `wiki/2026-08-25-Stage-A-청크-폐기와-점수-선별-전환.md`, `output/2026-08-25-Stage-A-B-트러블슈팅-발표정리.md` 1-6절과 3절

### 8. 입력 상한을 실측 한계로 재설정하고 청크 구조 제거

- 문제: 옛 한도에서 역산한 바이트 상한 때문에 재현율이 15%였습니다. 실제와 다른 "분량 초과" 사유로 묶음 다수가 제외되고 있었습니다.
- 해결: 전수 응답 계약이 깨지는 지점을 직접 쟀고, 상한을 바이트 대신 묶음 개수 200으로 정했습니다.
- 결과: 400묶음까지 계약이 유지됐고 두 저장소의 제외 묶음이 0이 됐습니다. 필요 없어진 청크와 재개 코드를 걷어내 806줄을 지우고 244줄을 추가했습니다.
- 근거: `wiki/2026-09-01-네-경로-LLM-모델-확정.md` 7-3~7-5절, `wiki/2026-08-27-Stage-A-전량투입-정렬-전환-검토.md`

### 9. 동점 묶음 일괄 제외 버그와 PR 없는 저장소 지원

- 문제: PR을 쓰지 않는 저장소는 후보가 0개였습니다. 선별 예산이 200자리 중 199자리 남았는데도 0점 커밋 434개가 한꺼번에 제외됐습니다.
- 해결: 정답 기준을 실험 전에 고정하고 묶음 규칙 10여 개를 비교했습니다. 그 결과 PR 없는 커밋은 커밋 단위로 판단하는 판별 유니온으로 정했고, 예산 검사를 항목별로 바꿨습니다.
- 결과: 선별 입력이 1개에서 200개로 늘고 제외가 434개에서 235개로 줄었습니다. 20회 실행 모두 계약을 지켰습니다.
- 근거: `wiki/2026-09-10-PR-없는-저장소-커밋-묶음-방식-실험.md`, `raw/2026-09-11-Stage-A-개별-예산-선별-구현-session-log.md`

### 10. Stage B diff 예산 배분 수정

- 문제: patch 예산을 앞쪽 후보가 다 써서 후보의 55%가 diff를 한 글자도 받지 못했습니다. 모델은 근거가 없는 그 후보들을 근거 있다고 판단해 선정했습니다.
- 해결: 총량은 그대로 두고 후보별 균등 배분과 이월 방식으로 바꿨습니다.
- 결과: 후보 20개가 모두 patch를 받았고, 이후 모든 선정이 실제 diff를 근거로 삼았습니다.

### 11. 후보가 0개로 나오는 문제와 비결정성

- 문제: 모델 전환 뒤 계약은 지키면서 후보를 0개 골라 사용자에게 빈 화면이 나갔습니다(4/4회). 같은 입력에서도 후보 집합이 4가지로 갈렸습니다.
- 해결: 가설 셋을 차례로 배제한 뒤 프롬프트에 "최소 1개" 하한과 입력의 성격을 명시했습니다. 온도는 0으로 고정했습니다.
- 결과: 후보 0개 응답이 4/4회에서 0/5회로 줄었고, 같은 입력 8회가 모두 같은 5개를 골랐습니다.

## C. LLM 운영: 모델 선정, 비용, 오류 분류

### 12. 측정으로 provider 전환과 모델 선정

- 문제: Groq 무료 등급의 분당 토큰 한도에 막혔습니다. Gemini 일부 모델은 한 줄짜리 요청에도 119초가 걸렸습니다.
- 해결: 원인이 등급인지 모델인지 갈라서 확인했습니다. 투표로 고른 후보를 운영 크기의 입력으로 직접 쟀고, 배치 경로는 총 지연으로, 스트리밍 경로는 첫 청크 지연으로 판정했습니다.
- 결과: Stage B가 55초 시간 초과로 실패하던 것이 4.2초로 줄었습니다. 첫 질문은 첫 청크 1.2~1.6초에 인용 위반 0건이 됐고, 근거를 지어내던 이전 모델의 P1도 해소됐습니다.
- 근거: `wiki/2026-08-26-Stage-A-B-Gemini-확정-고도화-설계.md`, `wiki/2026-09-01-네-경로-LLM-모델-확정.md`, `raw/2026-08-28-Gemini-anyOf-지연-실측.md`

### 13. 실측 기반 LLM 비용 산정과 비용 상한 증명

- 문제: 호출 결과의 usage를 버리고 있어 비용이 전부 추정치였습니다. 10달러로 가능한 분석 횟수 추정도 442회와 310회로 갈렸습니다.
- 해결: 프로덕션과 같은 호출 경로에 usage 통로를 넣었습니다. 경로별 입력 상한에서 최악 비용도 유도했습니다.
- 결과: 분석 1회 비용 $0.0218, 10달러로 458회를 확정했고 최악의 경우에도 261회가 보장됩니다. 비용의 79.9%가 Stage B에서 나온다는 것도 확인했습니다.
- 근거: `wiki/2026-09-02-LLM-비용-산정.md`

### 14. 꼬리 질문과 블록 갱신의 비용과 근거 원칙 트레이드오프

- 문제: 매 턴 근거를 다시 실으면 비용이 늘고, 빼면 모델이 근거 없는 사실을 지어낼 자리가 생깁니다. 블록 갱신 호출은 캐시 경계가 잘못 잡혀 캐시 히트가 0이었습니다.
- 해결: 비용보다 근거 원칙을 택해 근거를 전량 재전송하기로 했습니다. 암묵 캐싱이 실제로 걸리는지 실측했고, 블록 갱신에는 명시적 캐시 경계를 두었습니다.
- 결과: 인터뷰 10턴 비용이 추정 $0.039~0.046에서 실측 $0.034로 내려갔습니다. 블록 갱신은 회당 $0.0020에서 $0.0003이 됐고, 40건에서 근거 없는 창작이 0건이었습니다.
- 근거: `wiki/2026-09-03-꼬리질문-대화-프롬프트-전략.md`, `wiki/2026-09-10-블록갱신-모델-확정.md`, `raw/2026-09-08-꼬리질문-근거-재전송-비용-재측정-session-log.md`

### 15. 도달하지 못하던 LLM 오류 분류 바로잡기

- 문제: AI SDK가 재시도한 실패를 `RetryError`로 감싸 429, 413, 503이 모두 일반 실패로 뭉개졌습니다. 그래서 하루 20요청 한도 소진을 모델 과부하로 오진했습니다.
- 해결: `RetryError.lastError`를 벗겨 분류하도록 고쳤습니다. 413은 응답 본문을 보고 한도 초과와 요청 과대를 갈랐습니다.
- 결과: 재시도해도 풀리지 않는 한도를 정확히 알리게 됐고, 쿼터만 태우던 재시도 낭비를 없앴습니다.
- 근거: `output/2026-08-25-Stage-A-B-트러블슈팅-발표정리.md` 2-3절

### 16. LLM이 만드는 경험 블록을 주장 단위 연산과 리듀서로 관리

- 문제: 화면 문장을 다음 갱신의 유일한 기억으로 쓰자, 허술한 답변이 들어오면 모델이 블록을 비웠습니다(20건 중 5건).
- 해결: 모델이 블록 전체를 다시 쓰지 않고 `add`, `revise`, `retract` 같은 연산만 출력하게 했습니다. 서버와 클라이언트는 같은 순수 리듀서로 연산을 검증하고, 버전으로 오래된 응답을 거절합니다.
- 결과: 116건에서 근거 없는 창작이 0건이었습니다. 지연은 중앙값 2.9초, 회당 비용은 약 $0.0005입니다.
- 근거: `wiki/2026-09-11-PAAR-경험블록-설계-개정.md`, `raw/2026-09-11-PAAR-경험블록-턴진행-실측-session-log.md`

## D. 신뢰성과 운영 준비

### 17. GitHub 간헐 500과 502의 원인을 계층별 측정으로 확정

- 문제: 분석 중 커밋 상세 조회가 26초 만에 500이나 502로 실패했는데, 재현이 일정하지 않았습니다.
- 해결: DNS, TCP, TLS를 나눠 쟀습니다. DNS가 약 11초 멈추는 동안 10초 연결 제한이 먼저 걸리는 구조를 찾았고, 전송 실패일 때만 1회 재시도하도록 했습니다.
- 결과: DNS p90이 11,074ms라는 근거를 확보했고 500과 502가 갈리는 이유도 설명했습니다. 403, 404, 409, 422, 429는 재시도하지 않는다는 회귀 테스트 5건을 넣었습니다.
- 근거: `raw/2026-09-15-GitHub-간헐실패-DNS-원인확정-session-log.md`, `raw/2026-09-15-GitHub-전송실패-재시도-session-log.md`

### 18. Sentry 관측성 구축과 계측 비용 측정

- 문제: 배포 후에도 서버 오류가 0건으로 잡혔습니다. 원인은 SDK 부재, 오류를 삼키는 try/catch 구조, 전역 오류 바운더리 부재였습니다. 기본 설정으로는 스트리밍 중 일어나는 CLS도 잡히지 않았습니다.
- 해결: 응답 status가 500 이상인 경우만 수집하도록 13개 파일 18곳에 배선했습니다. 처음 만든 자체 전송 장치는 번들이 분리돼 동작하지 않아 SDK를 직접 부르는 방식으로 되돌렸습니다. CLS는 standalone span으로 켰습니다.
- 결과: 4xx는 수집 0건, 5xx는 1건이고 민감 헤더 유출이 0건임을 확인했습니다. 코드는 110줄 줄었습니다. init 비용 26ms와 번들 증가 18.9%는 측정값으로 기록했습니다.
- 근거: `wiki/2026-09-16-sentry-서버-계측.md`, `wiki/2026-09-08-sentry-클라이언트-계측.md`

### 19. 사용자별 일일 분석 상한으로 비용 방어

- 문제: 사용자 제한이 전혀 없어 회당 $0.022인 분석을 무제한 반복할 수 있었습니다.
- 해결: 서버가 비용 천장을 보장하는 분석에 하루 3회 상한을 걸었습니다. 검사와 증가는 `insert … on conflict … where` 한 문장으로 만들어 동시 요청 경쟁을 막았고, 날짜 경계는 한국 시간 자정으로 정했습니다.
- 결과: 1인당 하루 최대 $0.115로, 혼자 10달러 예산을 비우려면 87일이 걸립니다. 운영 준비 체크리스트의 P0 하나를 닫았습니다.
- 근거: `wiki/2026-09-22-분석-횟수-상한.md`, `wiki/2026-09-18-운영-준비-체크리스트.md`

### 20. AI 코드리뷰 반영 절차 재설계

- 문제: PR 하나에서 리뷰가 6라운드 반복되고 코멘트가 24개 쌓였습니다. "빈 저장소"라는 한 원인을 매 라운드 한 단면씩만 고친 것이 원인이었습니다.
- 해결: 지적을 근본 원인별로 묶고, 묶음 하나를 커밋 하나로 만들고, 지적마다 회귀 테스트를 붙였습니다. P0와 P1만 merge blocker로 두고 재검증은 1회로 한정하는 종료 기준을 정했습니다.
- 결과: 바로 다음 이슈부터 2라운드에 수렴했고, 이후 PR 대부분이 1~2라운드에 끝났습니다. 4라운드가 걸린 이슈 #79 같은 반례도 기록돼 있습니다.
- 근거: `wiki/2026-08-20-코드리뷰-전략.md`, `log.md`
