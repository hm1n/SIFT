## 1. 시작 상태 확인

사용자가 이슈 파악과 작업 계획을 요청해 먼저 이슈 본문과 실제 코드를 대조했습니다. 이슈 본문이 전제한 상태와 저장소의 상태가 네 군데 달랐습니다.

- 이슈는 "Technical topics 섹션이 안내문만 표시하고 있습니다"라고 썼지만 그 시점에 #97은 머지되지 않았고 섹션 자체가 없었습니다. `SCHEMA_GAP_NOTICE` 문자열도 저장소에 없었고 이슈가 근거로 든 위키 문서도 없었습니다.
- `feature/stage-b-max-candidate` 브랜치(#108)가 `schema.ts` 133줄, `stage-b.ts` 117줄을 이미 고쳐 두고 있어 #110이 손댈 파일과 정면으로 겹쳤습니다.
- 디자인 원본 `App.tsx`를 열어 보니 이슈가 목록 행 근거로 든 623행은 목록 행이 아니라 상세 하단 바였고, 쓰는 값도 `CANDIDATE_TOPICS`가 아니라 `Candidate.tags`였습니다. 디자인 목록 행(636~644행)에는 토픽이 없습니다.
- 디자인의 `Candidate`는 `title`과 `summary`를 둘 다 갖는데 화면에는 `title`만 쓰고 `summary`는 어디에도 렌더링하지 않습니다. 이슈가 "한 문장 `summary`를 제목 자리에"라고 한 것은 디자인과 이름이 반대로 맞물립니다.

이 네 가지를 보고 "#108 머지 → #97 → #110" 순서를 제안했습니다. 사용자가 #97까지 머지했다고 알려 와 다시 확인해 보니 #108도 함께 닫혀 있었고, `114d76b`(PR #111)이 develop에 들어가 있었습니다. 작업 브랜치를 그리로 fast-forward하고 시작했습니다.

머지된 코드를 다시 읽으면서 이슈 전제 두 개가 더 낡은 것을 확인했습니다. #108이 `LOCAL_OUTPUT_CONTRACT_HINT_TEXT`를 지워 프롬프트 갈래가 하나로 합쳐졌고, 후보 상한이 3에서 20으로 올랐습니다.

## 2. 사용자에게 물은 세 가지

혼자 정하면 작업 결과가 달라지는 항목만 골라 물었고 셋 다 제가 추천한 쪽으로 정해졌습니다.

- `summary`의 형태는 한 문장이 아니라 디자인 `title`과 같은 짧은 명사형 구로 정했습니다. 접은 대안은 이슈 원문대로 한 문장을 생성하는 것입니다. 260px 목록 행에서 CSS로 잘려 뒷부분이 보이지 않는 것이 이유입니다.
- 빈 값은 스키마에서 거부하지 않고 화면이 폴백·정규화하기로 했습니다. 접은 대안은 `evidence`처럼 `minLength: 1`을 거는 것입니다.
- 토픽 앞 두 개는 목록 행 셋째 줄에 넣기로 했습니다. 접은 대안은 두 가지였습니다. 하나는 디자인대로 목록 행을 건드리지 않고 상세 칩만 두는 것이고, 다른 하나는 디자인 623행 위치인 상세 하단 바 왼쪽에 넣는 것입니다. 뒤쪽은 그 자리를 #97이 "Choose a different repository" 버튼에 이미 내줘서 footer 레이아웃을 다시 손대야 합니다.

## 3. 구현 순서

묶음 네 개를 커밋 네 개로 만들었습니다. `stage-b.test.ts`는 계약 픽스처와 프롬프트 회귀 테스트가 한 파일에 섞여 있어, 파일 단위로 넣지 않고 diff를 훅 단위로 갈라 `git apply --cached`로 나눠 담았습니다.

타입에 필수 필드를 추가하자 후보 리터럴을 만드는 11개 파일 32곳에서 typecheck가 한 번에 깨졌습니다. 스크립트로 일괄 삽입한 뒤 여러 줄 리터럴은 줄로 나누고 타입 순서에 맞게 다시 정렬했습니다.

### 접은 대안: 픽스처의 `summary`를 어떻게 채울지

`experience-selection.test.tsx`는 테스트 12개가 행을 커밋 제목으로 찾고 있었습니다. 후보 팩토리에 의미 있는 `summary`를 넣으면 선택자 12개를 전부 바꿔야 했습니다. 그 파일의 관심은 확정 전이와 근거 스냅샷이고 제목의 출처가 아니라서, 팩토리의 `summary`를 빈 문자열로 두고 제목이 커밋 제목으로 떨어지게 하는 쪽을 골랐습니다. 제목 계약 자체는 목록·상세 테스트가 봅니다.

`experience-candidate-list.test.tsx`는 반대로 했습니다. 행을 찾는 이름이 곧 제목 계약이라 각 테스트에 `summary`를 명시적으로 넘기고 선택자는 그대로 뒀습니다.

## 4. 측정

### 첫 실행이 실패했습니다

사용자가 `.env`를 워크트리에 복사해 준 뒤 `hm1n/SIFT`로 전체 파이프라인을 돌렸습니다. Stage A는 4,468밀리초에 후보 5개를 뽑았지만 Stage B가 10,593밀리초 만에 `unknown_file_path`로 실패했습니다. 모델이 `src/features/experience-candidates/work.ts`처럼 입력에 없는 경로를 인용했습니다.

`stage-b.ts`의 `outputContractText` 주석에 프롬프트 문장을 바꿨더니 같은 저장소에서 6회 중 5회가 이 오류로 실패한 전례가 적혀 있었습니다. 제가 그 함수 안에 문단을 끼워 넣었으므로 원인일 수 있었습니다.

### 입력을 고정해 비교했습니다

Stage A를 매번 다시 돌리면 후보 묶음이 달라져 개편 전후를 비교할 수 없습니다. `--cache`로 상세 조회 결과를 고정하고 `--skip-stage-a`로 Stage A를 건너뛰어 입력을 커밋 30개, 판단 단위 7개로 묶었습니다.

개편 전 기준선은 develop `114d76b`의 `src/features/experience-candidates/`를 `git checkout`으로 꺼내 같은 캐시로 돌린 뒤 되돌리는 방식으로 만들었습니다. 별도 워크트리를 만드는 방법은 `node_modules` 설치가 필요해 접었습니다.

캐시를 쓴 첫 실행도 `unknown_file_path`로 실패했고, 이어서 개편 후 12회를 더 돌려 11회 성공 1회 실패였습니다. 합쳐서 13회 중 2회 실패입니다. 개편 전은 13회 중 1회 실패였습니다. 이 표본에서 두 비율은 구분되지 않아, 프롬프트 문단 추가가 이 실패를 만든 것은 아니라고 판단했습니다.

소요는 개편 전 성공 3,828~9,908밀리초, 개편 후 성공 7,282~13,046밀리초였습니다. 출력 토큰은 개편 전 783~3,654, 개편 후 2,378~4,089입니다. 입력 토큰은 38,825에서 38,933으로 108개만 늘었습니다.

### 상한 상수는 건드리지 않았습니다

관측 최대 13,046밀리초가 `STAGE_B_TOTAL_BUDGET_MS` 55,000밀리초와 `STAGE_B_MIN_LLM_BUDGET_MS` 20,000밀리초 양쪽 안에 들어와, 두 상수를 조정할 이유가 없었습니다. 측정 전에 미리 준비했던 대안인 `MAX_TECHNICAL_TOPICS`를 6보다 낮추는 안도 쓰지 않았습니다.

### 토픽 문구를 여섯 번 고쳤습니다

지연 측정이 끝난 뒤 사용자가 "톤을 조정해야 할 수도 있으니 실데이터를 직접 보겠다"고 해서 생성된 `summary`와 `technicalTopics`를 뽑아 봤습니다. `measure-pipeline.ts`는 머리에 "응답 원문은 출력하지 않습니다"라는 정책이 적혀 있어 그 파일을 고치지 않고 `scripts/dump-summaries.mts`를 따로 만들었습니다. 확인이 끝나고 지웠습니다.

이 스크립트를 처음 돌렸을 때 "실패: unknown"만 찍혔습니다. `selectStageBCandidates`에 묶음 대표 SHA만 넘긴 것이 원인이었습니다. `buildStageBPayload`가 커밋마다 `candidateBySha.get(commit.sha)!.source`를 읽으므로 `expandCandidatesToCommits`가 펼친 커밋 전부를 넘겨야 합니다.

실데이터를 보니 토픽이 전부 `TypeScript`·`Vitest`·`React`였습니다. 어휘 7개가 49개 목록을 채우고 있어 목록 행이 모든 후보에서 같아집니다. 제가 쓴 "실제로 나타난 기술 이름만"이라는 문구가 스택 라벨을 부른 것이었습니다. 여기서부터 8회씩 돌려 가며 문장을 고쳤고, 회차별 수치와 결론은 위키 9절에 있습니다.

고치는 동안 두 번 되돌렸습니다.

하나는 사용자가 "요약은 커밋·PR 내용을 그대로 적어도 상관없다, 그게 작업의 핵심이니까"라고 해서, 준비했던 summary 쪽 제약 추가를 접었습니다. 제가 후퇴로 본 항목이 사용자 기준으로는 문제가 아니었습니다.

다른 하나는 `여러 개념을 '및'으로 묶지 말고 항목을 나누세요`입니다. 토픽을 짧게 만들려고 넣었는데 `schema_validation`이 14회 중 3회 났습니다. 처음에는 원인을 몰랐는데, grep 패턴에서 `cause=` 줄을 제가 걸러 버린 것이었습니다. 다시 찍어 보니 `AI_NoObjectGeneratedError: response did not match schema.`였고, 이 스키마에 걸린 유일한 배열 제약이 `technicalTopics`의 `maxItems: 6`입니다. 항목을 나누라는 지시가 개수를 상한 너머로 밀고 있었습니다. 문장을 빼자 이후 8회에서 0회입니다.

### 접은 대안: 토픽 길이를 상한으로 조이기

항목이 길어졌을 때 처음 떠올린 것은 프롬프트에 글자 수 상한을 거는 것이었습니다. 접었습니다. 같은 실행에서 짧게 나온 항목들이 정확히 `문서화`·`코드 공통화`·`웹 접근성`처럼 일반론으로 되돌아간 것들이었기 때문입니다. 구체성과 길이가 같은 축에 있어서, 길이를 조이면 처음 문제로 돌아갑니다. 대신 일반론을 직접 금지하는 문장을 넣었습니다.

목록 행의 `ROW_TOPIC_COUNT`를 2에서 1로 줄이는 안도 준비했다가 쓰지 않았습니다. 항목이 4~8자로 줄면서 앞 두 개를 이어도 한 줄에 들어갔습니다.

## 5. PR #118 CodeRabbit 1차 리뷰

지적 2건이고 라운드 1회입니다.

**묶음 1(P1).** `technicalTopics`의 JSON Schema `maxItems: 6`이 화면 정규화 계약을 앞지릅니다. 토픽이 7개면 Gemini가 응답 전체를 거부해 후보 최대 20개가 함께 사라지고, 이슈 Constraint를 직접 위반합니다. 4절에서 같은 경로로 14회 중 3회가 실패한 것을 제가 이미 관측했는데, 그때 프롬프트 문장만 빼고 스키마 쪽 원인을 남겨 뒀습니다. 증상이 사라진 것을 원인이 사라진 것으로 본 판단 착오입니다.

반영 전에 `buildCandidateOutputJsonSchema`의 제약을 런타임 검증과 전부 대조했습니다. `sha`·`evidence`의 `minLength`, `relatedShas`·`citedFilePaths` 원소의 `minLength`, `additionalProperties`와 `required`는 런타임과 일치합니다. 어긋나는 곳은 지적된 `technicalTopics.maxItems` 하나뿐이었습니다. `candidates.maxItems`도 응답 전체를 버리지만 `validateExperienceCandidateOutput`이 같은 조건으로 함께 거부하는 의도된 기존 계약(이슈 #108)이라 이번 범위 밖으로 뒀습니다.

**묶음 2(P2, 예외 적용).** 프롬프트 끝의 `한국어로 답하세요.`가 `outputContractText` 뒤에 붙어 있어 마지막 지시가 됩니다. 영어 저장소에서 두 필드의 언어 규칙을 덮을 수 있습니다. merge blocker는 아니지만 수정 비용이 문장 하나이고 이 PR이 스스로 세운 계약을 위반하므로 같은 PR에서 반영했습니다.

지적되지 않은 같은 성격의 결함이 하나 있었습니다. 언어 규칙이 `technicalTopics` 문단 안에만 있어 `summary`에는 아예 걸려 있지 않았습니다. 같은 프롬프트, 같은 데이터 흐름이라 함께 고쳐 두 필드 공통 규칙으로 올리고 우선순위를 명시했습니다.

영어 저장소에서 실제로 영어가 나오는지는 확인하지 못했습니다. `hm1n/SIFT`의 커밋이 전부 한글이라 실데이터가 없습니다. 회귀 테스트는 문구의 존재와 전역 지시보다 앞에 오는 순서까지만 잠급니다.
