# 세션 사용자 번호 도입 세션 로그

이슈 #114의 구현 부분입니다. 환경 설정 경위는 `2026-09-14-Neon-접속환경-설정-session-log.md`에 있습니다. 도달한 결론은 `wiki/2026-09-14-Neon-접속계층과-세션-사용자번호.md`에 있습니다.

## 시작 전에 정한 세 가지

핸드오프가 시작 전에 확인받으라고 한 항목이 셋이었습니다.

저장 계층 인터페이스와 테스트 대체 방식은 저장소에 이미 선례가 있어서 그대로 따르기로 했습니다. `experience-block` 라우트가 `handleExperienceBlockUpdate(request, generate = defaultGenerate)`로 의존성을 매개변수로 받고 테스트가 가짜를 직접 넘깁니다. `vi.mock`으로 모듈을 가로채지 않습니다. 연산이 여러 개라 함수 하나가 아니라 객체 하나를 넘기는 것만 다릅니다.

스키마 적용은 마이그레이션 도구 없이 SQL 파일과 작은 스크립트로 가기로 했습니다.

옛 쿠키 처리는 사용자 결정이 필요해서 A(다시 로그인), B(조용히 채움), C(없는 채로 둠) 셋을 근거와 함께 설명했습니다. 판단에 결정적이었던 사실은 `GITHUB_SESSION_MAX_AGE_SECONDS`가 28800초, 즉 8시간이고 서버가 평문의 발급 시각으로 직접 만료를 판정한다는 점입니다. 옛 형식은 배포 후 8시간이면 저절로 사라집니다. 사용자가 A를 골랐습니다.

접은 대안의 이유입니다. B는 세션 토큰을 읽는 라우트 8곳을 모두 고쳐야 하고, 쿠키를 다시 구울 때 발급 시각을 원래 값으로 보존하지 않으면 요청마다 8시간이 처음부터 다시 시작해 세션이 영원히 만료되지 않습니다. 이슈가 손대지 말라고 못 박은 부분이 정확히 거기였습니다. C는 사용자 번호 타입이 영구히 nullable이 되고, "저장이 안 되는 세션"을 화면에 설명하는 일이 #115로 넘어갑니다. 지금 기존 로그인 화면 한 번이면 끝날 일이 나중에 새 상태와 새 문구가 됩니다.

## 형식 번호를 넣게 된 경위

처음에는 평문에 사용자 번호 8바이트만 끼워 넣으려 했습니다. 그런데 옛 형식 쿠키가 복호화에 실패하지 않는다는 것을 확인했습니다. 키가 같고 GCM 인증 태그도 맞아서 유효한 값으로 통과하고, 바이트를 자르는 위치만 달라집니다. 그러면 토큰 앞부분을 사용자 번호로 읽고 잘린 토큰으로 GitHub을 호출해 401이 납니다. 사용자에게는 이유를 알 수 없는 로그인 실패로 보입니다.

그래서 평문 맨 앞에 형식 번호 1바이트를 두었습니다. 이 판단은 A·B·C 선택과 독립입니다. 어느 쪽을 골라도 옛 형식을 알아보는 수단은 필요합니다.

회귀 테스트로 옛 형식 쿠키를 테스트 안에서 직접 만들어(`[발급 시각 8바이트][토큰]`) `auth_revoked`가 되는지, 잘린 토큰이 새어 나오지 않는지 둘 다 확인했습니다.

## 콜백의 오류 분류를 나눈 것

`fetchAuthenticatedUser`를 기존 try 블록 안에 그냥 넣었다가 문제를 발견했습니다. 그 블록의 catch는 `server_error`를 `config_missing`으로 보냅니다. 원래는 암호화 키가 없을 때만 나오는 값이라 맞는 분류였는데, `/user` 조회도 `server_error`를 낼 수 있습니다. 그러면 GitHub이 잠시 답하지 않는 상황에 사용자가 "서버에 GitHub 로그인 설정이 없습니다"라는 안내를 받습니다.

토큰 교환과 사용자 조회를 앞 단계로 묶고 쿠키를 굽는 단계를 뒤로 분리했습니다. `config_missing`은 우리 OAuth 설정과 암호화 키가 없을 때만 씁니다. `/user`의 500과 429와 `id` 없는 응답 세 가지가 `exchange_failed`가 되고 쿠키를 굽지 않는지 회귀 테스트로 고정했습니다.

## 테스트 고정값이 실제 응답과 달랐던 것

`fetchAuthenticatedUser`에 `id` 검증을 넣자 기존 테스트 21건이 깨졌습니다. `mockRepoAndBranch` 같은 `/user` 고정값이 `{ login: "octocat" }`뿐이고 `id`가 없었습니다. 실제 GitHub 응답에는 항상 있는 값이라 고정값을 실제 모양에 맞췄습니다. 검증을 무르지 않았습니다.

`.mts` 파일 하나를 빠뜨렸습니다. 처음 호출처를 찾을 때 `--include=*.ts --include=*.tsx`로만 훑어서 `question-generation.measure.mts`가 빠졌고 typecheck에서 잡혔습니다.

## 스크립트 실행 방식

기존 측정 스크립트는 `npx tsx --env-file=...`로 돕니다. `apply-schema.mts`는 Node가 `.mts`를 그대로 실행하게 했습니다. tsx를 받아오지 않아도 되고 의존성도 늘지 않습니다. 대신 Node의 타입 제거가 확장자 붙은 지정자를 요구해서 `tsconfig.json`에 `allowImportingTsExtensions`를 켰습니다. `noEmit`이 이미 켜져 있어 추가 조건은 없었습니다.

환경변수는 `process.loadEnvFile`로 읽습니다. Node 24라 플래그도 의존성도 필요 없습니다.

## 첫 스키마 적용이 한 번 실패한 것

첫 `npm run db:schema`가 `ConnectTimeoutError`로 죽었습니다. 대상 호스트는 `api.c-2.us-east-2.aws.neon.tech:443`이었습니다. 같은 호스트로 직접 `fetch`를 해 보니 1077ms에 400이 돌아와서 호스트는 살아 있는 것을 확인했습니다. 다시 돌리니 그대로 적용됐습니다. 일시적인 문제였습니다.

적용 결과 표 두 개(`repository_analysis`, `interview_session`)가 만들어졌고, 한 번 더 돌려도 결과가 같은 것을 확인했습니다.

## 정의서 SQL을 한 군데 고친 것

정의서의 `create index on ...`에는 인덱스 이름이 없습니다. 이름이 없으면 Postgres가 자동으로 붙이고 `if not exists`를 쓸 수 없어 재실행이 실패합니다. 인덱스 둘에 이름을 붙였습니다. 표 정의는 그대로입니다.

## 범위에서 뺀 것

Neon 구현체(`neonStore()`)를 만들지 않았습니다. 핸드오프가 실제 저장과 복원, 목록, 삭제를 #115와 #116의 범위로 못 박았기 때문입니다. 그래서 이번 PR에는 프로덕션 구현이 없는 인터페이스가 남습니다. 접속 계층 자체는 `apply-schema.mts`가 `getSql()`을 통해 실제 Neon을 상대로 검증합니다.
