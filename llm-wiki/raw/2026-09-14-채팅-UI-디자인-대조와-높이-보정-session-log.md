# 채팅 UI 디자인 대조와 높이 보정 세션 로그 (2026-09-14)

사용자가 dev 서버에서 화면을 열어 놓고 요소를 하나씩 짚어 준 데서 이어진 작업입니다. 레이아웃 높이
결함 셋, 채팅 UI 구조 개편, 그리고 그 과정에서 드러난 무증상 결함 하나를 다뤘습니다. 도달한 결론은
`wiki/2026-09-14-인터뷰-3열-워크스페이스.md` 10~13절에 있습니다.

앞 작업은 `raw/2026-09-14-레거시-팔레트와-화면-문구-영어화-session-log.md`입니다.

## 1. 높이가 세 번에 걸쳐 드러났습니다

이 주제의 핵심은 **한 번에 다 못 찾았다**는 것입니다. 순서대로 적습니다.

### 1차 — `.content`가 블록 컨테이너였습니다

사용자가 "자식 컴포넌트의 높이가 부모를 꽉 채우게 해 달라"고 했습니다. `repository-analysis.module.css`의
`.content`가 `flex: 1; min-height: 0`은 있는데 `display` 선언이 없어 블록이었습니다. 자신은 787px을
제대로 받았지만 그 안의 인터뷰 `.screen`이 가진 `flex: 1`을 받아 줄 flex 부모가 없었습니다.

`display: flex; flex-direction: column`을 더했습니다. 실측으로 인터뷰 `.screen`이 64px(헤더만)에서
731px로, `.workspace`가 20px에서 687px로 바뀌었습니다.

### 2차 — grid의 기본값이 메시지를 늘리고 있었습니다

높이가 제대로 내려가자 다음 결함이 드러났습니다. 사용자가 "화면 높이를 조정하면 메시지 블록 높이도
같이 조정된다"고 지적했습니다.

`.log`가 grid 컨테이너이고 grid의 `align-content` 기본값은 `stretch`입니다. **남는 높이를 자동 크기
행에 나눠 줍니다.** 그전까지는 `max-height: 60vh`만 있어 컨테이너가 내용만큼만 자랐고 남는 높이가
없어 드러나지 않았습니다. 이슈 #98이 `flex: 1; min-height: 0`으로 바꾸면서 남는 높이가 생겼습니다.
**#98이 만든 회귀입니다.**

`align-content: start`를 더했습니다. 지적받은 줄만 고치지 않는다는 규칙에 따라 `display: grid`와
`flex: 1`을 함께 쓰는 자리를 전부 찾았더니 셋이었고, `experience-candidate-detail.module.css`의
`.body`에도 같은 결함이 있었습니다. 한 줄짜리 문단이 268px이었습니다. 함께 고쳤습니다.
(`.candidateList`는 이미 `start`였습니다.)

### 3차 — 진짜 출발점은 `body`였습니다

사용자가 코드 패널에서 큰 파일(`package-lock.json`, +8576 −1923)을 고르니 화면 전체가 늘어난다고
했습니다. 셸 콘텐츠가 1203px이었습니다.

재현해 보니 body가 16254px까지 자랐습니다. 원인은 `globals.css`의 `body { min-height: 100% }`입니다.
**`min-height`는 아래 한계만 정합니다.** 내용이 뷰포트를 넘으면 body가 같이 자라고, body가 자라면
그 아래로 `flex: 1; min-height: 0`을 줄줄이 걸어 둔 칸들이 줄어들 이유를 잃습니다.

1차에서 고친 `.content`는 사슬 **중간**이었습니다. 출발점이 `min-height`인 한 내용이 짧을 때만
맞았습니다.

`height: 100%`로 바꿨습니다. body 16254px → 900px, `.diffBody` 9912px → 393px, 문서 스크롤 사라짐.
diff를 5줄·800줄·12000줄로 바꿔 가며 재도 부모 높이가 모두 같고 `.diffBody`만 자체 스크롤합니다.

셸을 쓰지 않는 로그인 화면이 깨지는지 먼저 확인했습니다. `overflow-x: hidden` 때문에 body의
`overflow-y`가 `auto`로 계산되므로 내용이 넘치면 body가 스크롤합니다. 뷰포트 380px에 600px 카드를
넣어 스크롤 유지와 잘림 없음을 확인한 뒤 적용했습니다.

**규칙으로 남겼습니다.** `flex: 1; min-height: 0`은 위에서 확정된 높이가 내려올 때만 뜻이 있습니다.

## 2. 측정 방식에서 두 번 헛짚었습니다

첫 시도에서 probe 페이지의 바깥 높이를 주지 않아 `.content`가 120px로 나왔습니다. 고치기 전과 후가
똑같이 나와 "차이 없음"으로 읽힐 뻔했습니다. 실물에서 잰 787px을 셸 높이로 명시하고 다시 쟀습니다.

두 번째로, dev 서버가 HTTP로 내려주는 CSS 청크가 **디스크 산출물보다 오래된** 경우가 있었습니다.
6777자 대 10.8K였습니다. 그걸 모르고 재서 "메시지 배치가 여전히 block"이라는 잘못된 결과를 한 번
얻었습니다. 이후 측정은 전부 `.next/dev/static/chunks/`의 파일을 직접 읽는 방식으로 바꿨습니다.

## 3. 디자인 원본이 세션 중에 바뀌어 있었습니다

사용자가 "채팅 UI가 참고 파일과 전혀 다르다"고 해서 대조하려고 파일을 다시 열었더니 세션 초반에
읽은 것과 달랐습니다. 116.9K → 137K, 갱신 시각 2026-09-11 18:28 → **2026-09-14 15:00**입니다.

추가된 것은 **한국어·영어 전환**입니다. `LangSelector`, `TRANSLATIONS.ko`/`.en`, `localStorage`,
그리고 로케일별 타이포그래피 토큰(`.locale-ko`에서 Pretendard가 UI 기본 폰트가 됩니다)입니다.

이건 같은 날 앞에서 한 "화면 문구 전부 영어 고정"과 정면으로 부딪힙니다. 대조 보고에 이 사실을
먼저 적고 방향부터 정해 달라고 했습니다. 사용자는 **로케일 전환은 무시하고 로케일과 무관한 구조만
맞추기로** 결정했습니다.

인계 문서에 "디자인 파일은 저장소 밖에 있고 사용자가 계속 수정한다. 작업 전 갱신 시각을 확인한다"는
항목이 있었는데, 세션 초반에 확인한 뒤 다시 확인하지 않은 것이 이번에 드러났습니다.

## 4. 채팅 UI를 구조만 맞췄습니다

로케일과 무관한 것만 골랐습니다. 메시지 행을 세로 쌓기에서 44px 고정 라벨 칸 + 본문 칸 가로 배치로,
로그를 카드에서 전체 폭으로, 입력부를 흩어진 요소 넷에서 테두리 하나 안의 입력 + 푸터 줄로
바꿨습니다. `rows=1` 자동 증가(상한 140px), `⌘/Ctrl+↵` 단축키, 생성 중 순환 표시를 더하고 줄바꿈을
`overflow-wrap: anywhere`에서 `word-break: keep-all`로 바꿨습니다.

### 순환 표시를 CSS로 돌린 이유

디자인 원본 `ThinkingRow`는 `setInterval`로 400ms마다 React 상태를 바꿉니다. 그대로 옮겼더니 lint가
`react-hooks/set-state-in-effect`로 막았습니다. `prefers-reduced-motion` 분기에서 effect 안에 setState를
호출했기 때문입니다.

우회하는 대신 방식을 바꿨습니다. keyframe 셋으로 같은 모양을 만들면 렌더가 0이고
`prefers-reduced-motion`도 CSS에서 함께 처리됩니다. 스트리밍 중 리렌더 범위를 줄이는 것이 이 화면의
핵심 제약이라 이쪽이 맞습니다. 칸마다 **차는** 시점은 다르고 **비는** 시점은 같아서
`animation-delay` 하나로는 만들 수 없고 keyframe이 셋 필요했습니다.

### 맞추지 않은 것

메시지 시각, `● EVIDENCE / 파일명` 칩, 질문 위 PAAR 타깃 라벨, 입력부 푸터 왼쪽의 블록 진행
상태입니다. 앞 둘은 질문 스트림 계약에 정보가 없고 뒤 둘은 블록 계약이 #89~#91입니다.

### 지우지 않은 것

디자인은 목업이라 실패와 접근성을 다루지 않습니다. 상태 낭독 문단, 새 메시지 안내, 오류 상자와
재시도, 이력 절단 안내, 종료 확인, `role="log"`의 `aria-live="off"` 낭독 경계를 남겼습니다. 대조
보고에 이 목록을 따로 적어 "차이니까 지운다"가 되지 않게 했습니다.

## 5. 무증상 결함 하나가 사용자 질문으로 드러났습니다

사용자가 화면의 `Answer` 라벨을 가리키며 "이 타이틀은 참고 파일에 있는 거야?"라고 물었습니다.
디자인에 없는 것이 맞는데, **그게 보인다는 것 자체가 버그**였습니다.

라벨을 `styles.visuallyHidden`으로 감췄는데 `interview-stream-view.module.css`에 그 선언이 없었습니다.
다른 모듈에 있어서 있으려니 했습니다. `styles.visuallyHidden`이 `undefined`가 되고
`className={undefined}`는 속성을 통째로 지웁니다. **타입도 lint도 테스트도 전부 통과합니다.**
감추려던 것이 안 감춰진 경우라 눈으로 보기 전에는 드러나지 않습니다. 같은 경로로 생성 중 표시의
대체 문장도 드러나 있었습니다.

선언을 더해 고치고 `src/css-module-class-reference.test.ts`를 새로 넣었습니다. 모든 컴포넌트의
`styles.X` 참조를 그 컴포넌트가 import한 모듈의 선언과 맞춰 봅니다. jsdom은 레이아웃을 계산하지
않아 "감춰졌는지"를 렌더로 확인할 수 없어서 렌더 대신 소스를 읽습니다.

**테스트가 실제로 잡는지 선언 이름을 일부러 바꿔 확인했습니다.** 파일과 이름을 정확히 짚어
실패했습니다. 저장소 전체에서 어긋난 참조는 이 하나뿐이었습니다.

## 6. 초점 표시와 답변 안내

사용자가 "textarea focus 시 border 하이라이트되지 않게" 해 달라고 했습니다. 재 보니 **두 가지가
동시에** 걸리고 있었습니다. composer의 `focus-within` 테두리 변화(`#e5e5e5` → `#a3a3a3`)와 textarea의
`2px solid #0a0a0a` outline입니다. outline이 `outline-offset: -2px`라 테두리 선 바로 위에 그려져
테두리가 굵어진 것처럼 보였습니다.

처음 잰 값에서 테두리가 안 바뀐 것으로 나와 헷갈렸는데, `transition: border-color .12s` 때문에
전이 도중 값을 읽은 것이었습니다. 300ms 기다린 뒤 다시 쟀습니다.

둘 다 걷고 `outline: none`을 명시했습니다. 이 칸의 초점은 글자 커서만 알립니다. 되돌리려는 사람이
나올 수 있어 위키에 왜 뺐는지 적었습니다.

이어서 답변 안내 문단도 디자인에 없다고 빼 달라고 했습니다. **통째로 지우지는 않았습니다.** 답변
칸의 `aria-describedby`가 이 요소를 가리키고, 같은 요소가 상한 초과 오류도 보여 줍니다. 평소에는
시각적으로만 감추고 상한을 넘은 동안에만 보이게 했습니다. 푸터 정렬도 `space-between`에서
`margin-left: auto`로 바꿨습니다. 왼쪽이 비면 `space-between`이 남은 항목을 왼쪽으로 보냅니다.

## 7. 회귀 테스트를 넣은 것과 못 넣은 것

넣은 것은 jsdom에서 확인 가능한 셋입니다. 보조 키와 함께면 전송·Enter만이면 줄바꿈·보낼 수 없는
상태면 단축키도 무시, `aria-describedby`가 두 상태 모두에서 실재하는 요소를 가리킴, CSS Module 참조
일치입니다.

못 넣은 것은 배치와 높이입니다. jsdom은 레이아웃을 계산하지 않습니다. 그 사실과 이유를 위키 10~13절에
각각 적었습니다. 대신 컴파일된 CSS를 Playwright에 물려 같은 DOM을 만들고 고치기 전 선언만 되돌려
비교하는 방식으로 매번 확인했습니다.
