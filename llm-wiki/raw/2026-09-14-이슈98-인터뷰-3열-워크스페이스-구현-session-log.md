# 이슈 #98 인터뷰 3열 워크스페이스 구현 세션 로그 (2026-09-14)

이슈 #98과 이슈 #97에서 넘어온 인계 문서를 받아 인터뷰 화면을 3열 워크스페이스로 개편하고 코드 근거
패널을 만든 경위입니다. 도달한 계약은 `wiki/2026-09-14-인터뷰-3열-워크스페이스.md` 1~7절에 있습니다.

같은 날 이어진 세 주제는 각각 다른 파일입니다. `raw/2026-09-14-한글-폰트-스택-session-log.md`,
`raw/2026-09-14-레거시-팔레트와-화면-문구-영어화-session-log.md`,
`raw/2026-09-14-채팅-UI-디자인-대조와-높이-보정-session-log.md`입니다.

## 1. 착수 전에 이슈와 코드의 충돌 네 가지를 확인받았습니다

인계 문서의 첫 항목이 "다른 이슈가 정한 Constraint는 디자인 선호보다 우선한다. 판단이 갈리면 먼저
묻는다"였습니다. 이슈 본문과 현재 코드를 대조해 네 가지가 갈린다고 보고 사용자에게 물었습니다.

1. **코드 패널의 상태 3종.** 이슈 Goal은 `LOADING EVIDENCE`, `NO EVIDENCE`, `ERROR / EVIDENCE(Retry)`를
   요구하는데 셋 중 둘이 현재 구조에서 도달 불가로 보였습니다.
2. **확인 가능 여부 안내의 자리.** 디자인의 `CodePanel`에는 자리가 없고 이슈 Constraint는 제거하지
   말라고 합니다.
3. **`InterviewStreamView`의 높이.** 손대지 말라는 Constraint가 있는데 `max-height: 60vh`가 3열 배치와
   맞지 않습니다.
4. **렌더링 비용 측정.** 기존 측정 스크립트는 합성 페이지를 `setContent`로 띄우므로 배치를 바꿔도
   정의상 같은 값이 나옵니다.

사용자 답은 각각 **도달 가능한 것만 구현**, **둘 다 시각적으로 숨김**, **CSS 높이만 수정**,
**3열 컨테이너 재현을 측정에 추가**였습니다. 이 네 가지가 이후 구현의 기준이 되었습니다.

접은 대안을 적어 둡니다. 1번에서 "시간 기반으로 가짜 LOADING을 잠깐 보여 주는" 방법을 검토했다가
버렸습니다. 상태를 직접 나타내지 않는 대리 지표를 쓰지 않는다는 기존 결정(`experience-selection.ts`)에
걸립니다. 2번에서 `aria-label`로 이름만 주는 방법도 버렸습니다. DOM에서 사라지면 스크린리더에서도
사라지고, 그것이 이슈 #47 PR #52 1차 리뷰의 P1이었습니다.

## 2. 순수 변환을 먼저 떼어 냈습니다

화면부터 만들지 않고 데이터 변환 둘을 먼저 분리했습니다. 근거는 이 둘이 화면 없이 검증 가능한
반면 섞어 두면 diff 파싱 오류를 화면 버그로 오인하게 된다는 점입니다.

- `evidence-files.ts`: 스냅샷의 `커밋 → 파일`을 `파일 → 커밋`으로 뒤집습니다.
- `diff-patch.ts`: unified diff를 줄 단위로 파싱합니다.

여기서 결정 둘이 나왔습니다. **여러 커밋에 걸친 파일은 언제나 `modified`로 둡니다.** 스냅샷에 커밋
시간 순서가 없어 added 뒤 deleted인지 그 반대인지 재구성할 수 없습니다. 순서를 모르는 채 한쪽을
고르면 실제와 어긋난 상태를 단정하게 됩니다. **절단된 patch를 정상 입력으로 다룹니다.** hunk 헤더
없이 시작하거나 줄 가운데서 끊긴 입력이 실제로 들어오므로, 파싱 실패로 빈 화면을 그리지 않고 아는
것만 붙이고 모르는 줄 번호는 `null`로 둡니다. 접두어까지 잘려 나간 줄은 버리지 않고 문맥 줄로
남깁니다. 버리면 사용자가 보는 diff가 조용히 짧아집니다.

테스트 27건을 붙이고 그 위에 화면을 얹었습니다.

## 3. 첫 커밋이 PowerShell 때문에 깨졌습니다

`git commit -m @'...'@` 형태로 PowerShell here-string을 쓰려다 제목이 `@ feat: 근거 스냅샷의 파일
기준 구조 변환 추가`로 들어갔습니다. `@`가 제목에 남았습니다. bash heredoc으로 바꿔
`git commit --amend -F - <<'EOF'`로 고쳤고, 이후 모든 커밋에 같은 방식을 썼습니다.

이 세션에서 셸 관련 실패가 몇 번 더 있었습니다. 백틱이 든 Python `-c` 문자열을 bash에 넘기면
명령 치환이 일어나 코드 블록이 통째로 사라집니다. 위키에 절을 추가할 때 실제로 코드 블록 두 개가
비었고, 나중에 Edit 도구로 복구했습니다. 긴 스크립트는 파일로 쓴 뒤 실행하는 쪽이 안전했습니다.

`interview-screen.tsx`를 3열로 다시 쓰고 나니 9개가 깨졌습니다. 전부 문구와 구조가 바뀐 것이
원인이었습니다. `AI 인터뷰`, `← 후보 목록으로`, `대표 커밋 aaaaaaa`, `이 질문의 근거` region,
metrics `li` 조회, 한국어 절단 문구입니다. `interview-screen.test.tsx`와
`experience-selection.test.tsx`를 새 구조에 맞췄습니다.

metrics 태그를 확인하던 단언은 지우지 않고 **AI 선택 안내를 확인하는 단언으로 바꿨습니다.** PR #57
1차 리뷰 P2가 만든 태그 경계를 이 테스트가 지키고 있었는데, 그 경계는 이제 후보 상세 화면이

이어서 `repository-flow.test.tsx` 2개가 더 깨졌습니다. `"AI 인터뷰"` 문자열을 인터뷰 화면에 도달한
표시로 쓰고 있었습니다. `getByRole("region", { name: "Code / Evidence" })`로 바꿨습니다. 문구가 아니라
구조를 가리키게 한 것입니다.

## 5. 측정은 배치 변형을 새로 만들어야 했습니다

기존 2부는 합성 페이지를 `page.setContent`로 띄웁니다. 실제 앱을 로드하지 않으므로 그대로 다시
돌리면 배치를 바꿔도 같은 값이 나옵니다. 그래서 한 열 배치와 3열 배치를 같은 코퍼스로 각각 재는
변형을 넣었습니다. 두 배치의 차이는 로그가 놓이는 자리뿐이고 메시지 HTML과 측정 절차와 viewport는
같게 뒀습니다. viewport는 3열이 성립하는 1440x900입니다.

결과는 **회귀 없음**입니다. 로그 폭이 1231px에서 609px로 줄어드는데 append 비용 차이가 최대
0.08ms입니다. 같은 배치를 두 번 돌렸을 때의 차이(160개 append가 0.33ms와 0.40ms)보다 작습니다.
자동 스크롤은 두 배치 모두 모든 크기에서 0.000ms입니다.

1부는 배치와 무관한 순수 JS 비용인데 실행 사이 편차가 컸습니다. 같은 날 두 실행에서 메시지 80개
전체 리렌더가 165.98ms와 155.26ms, `createHighlighter` 최초 1회가 449.38ms와 97.81ms였습니다.
**이 수치로 배치 변경의 영향을 판단하지 않기로 했습니다.** 편차가 측정하려는 차이보다 큽니다.

## 7. 계획 밖에서 판단한 것

완료 보고에 목록으로 넣은 것들입니다.

- `ResizeHandle`에 `role="separator"`, 화살표 키, pointer events(터치)를 넣었습니다. 디자인 원본은
  마우스 전용입니다.
- 탭 모드에서 비활성 열을 `display: none`이 아니라 `visibility: hidden`으로 감춥니다. 대화 열을
  떼면 스트림이 끊기고, 높이가 0이 되면 자동 스크롤이 하단을 놓칩니다.
- 탭을 `role="tab"` 대신 `aria-pressed` 버튼 셋으로 만들었습니다. 제대로 된 tablist는 roving
  tabindex까지 필요한데 얻는 것이 없었습니다.
- diff 줄 번호는 추가 줄에 변경 후 번호를 씁니다. 디자인은 변경 전 번호만 써서 추가 줄의 번호 칸이
  빕니다.
- 색인 실패 커밋에 "무엇을 확인할 수 없는지" 안내를 새로 넣었습니다. 기존 패널에 있던 안내가
  디자인에는 없어 그냥 빠질 뻔했습니다.
- FILES와 diff 사이 세로 크기 조절 손잡이는 넣지 않았습니다. 접기로 같은 목적을 달성합니다.
