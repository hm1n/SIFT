# diff 추가·삭제 색 구분 세션 로그 (2026-09-14)

사용자가 dev 서버에서 코드 패널의 diff 본문을 짚으며 "참고 파일에서는 `+`가 green, `-`가 red인데
우리 코드베이스엔 적용이 안 되어 있다"고 한 데서 시작한 작업입니다. 도달한 결론은
`wiki/2026-09-14-인터뷰-3열-워크스페이스.md` 15절에 있습니다.

앞 작업은 `raw/2026-09-14-채팅-UI-디자인-대조와-높이-보정-session-log.md`입니다.

## 1. 이슈 #98이 명시적으로 하지 않기로 한 항목이었습니다

작업 전에 이슈 본문을 다시 읽었습니다. Non-goal에 이렇게 적혀 있었습니다.

> diff에 semantic 색을 넣는 결정. 우선 배경 대비와 +/- 기호, 왼쪽 표시선으로만 구분하고, 읽기
> 어렵다는 실측이 있을 때만 극히 절제된 색을 검토합니다.

`code-panel.module.css` 머리 주석에도 같은 말이 근거와 함께 박혀 있었습니다. 즉 이 작업은 신규
구현이 아니라 **이미 내린 결정을 뒤집는 것**입니다.

뒤집는 근거는 "읽기 어렵다는 실측"이 아니라 사용자가 실물을 보고 내린 판단입니다. 이슈를 쓸 때는
색 없이도 읽힐 것이라고 봤는데 실제로 화면에 띄워 놓고 보니 아니었다는 것입니다. 결정을 내린
사람이 같은 사람이므로 그대로 진행했습니다. 다만 이 성격이므로 CSS 주석·위키·PR 본문 셋 다에
경위를 남기기로 했습니다. 나중에 주석만 읽는 사람이 Non-goal과 코드가 어긋나 보이는 것을 막기
위해서입니다.

## 2. 디자인 원본에서 색이 쓰이는 자리를 먼저 셌습니다

`App.tsx`(133.8K, 세션 중 수정 없음)에서 `16a34a|dc2626`을 찾아 9곳이 나왔습니다.

| 줄 | 자리 |
| --- | --- |
| 982 | `DiffLineRow`의 `+`/`−` 기호 |
| 1002~1003 | `FileRow`의 `+adds` / `-dels` |
| 1182~1184, 1200~1201 | diff 헤더의 집계 |
| 1695~1696, 1723 | 메시지 안에 끼워 넣는 근거 블록 |

마지막 것은 우리 쪽에 대응물이 없습니다(#98 Non-goal의 `EVIDENCE / SHA 태그`). 나머지 셋은 우리
`code-panel.tsx`에도 그대로 있습니다. `diffMark|additions}|deletions}`로 다시 세어 5곳, 전부
`code-panel.tsx` 안이었습니다. 한 파일로 닫힙니다.

**기호 색만 넣으려다 배경까지 넣기로 바꾼 이유**가 여기서 나왔습니다. 기존 `.diffLine[data-type="add"]`
는 이미 `background: var(--color-muted)`(회색)를 갖고 있었습니다. 기호만 초록으로 칠하면 초록 기호에
회색 배경이라는, 원본에도 없고 기존 설계에도 없는 조합이 됩니다. 원본의 `#f0fdf4`·`#fef2f2`를 함께
가져왔습니다.

## 3. 색이 없던 시절의 대체 표시 둘을 걷어냈습니다

이건 사용자가 지시한 범위 밖이라 판단이 필요했습니다. 걷어낸 것은 둘입니다.

**add 줄의 왼쪽 세로 표시선.** 원본에서 `border-l-2`는 `line.focused`를 표시하는 자리입니다.
우리에겐 `focused` 개념이 없어서(질문이 참조하는 줄 정보가 스트림 계약에 없음, #98 Non-goal) 그
자리를 추가·삭제 구분에 전용하고 있었습니다. 색이 그 일을 하게 되면 표시선은 원본에 없는 장식으로
남습니다. `border-left: 2px solid transparent`는 정렬 때문에 남겼습니다.

**del 줄 본문의 취소선.** `text-decoration: line-through`는 원본에 없습니다. 코드에 취소선이 그어지면
글자를 가로지르는 선이 `-`, `_`, `=` 같은 문자와 섞여 읽기가 나빠집니다. 색 없이 삭제를 표시해야
했던 제약이 만든 것이라 함께 걷었습니다.

둘 다 "색을 넣었으므로 필요 없어진 것"이지 "색으로 대체한 것"이 아닙니다. 지시 범위 밖이므로 완료
보고에 따로 적었습니다.

## 4. 접근성 판정 — 색만으로 가르지 않습니다

색으로 정보를 전달하면 색각 이상과 흑백 출력에서 정보가 사라집니다. 여기서는 걷어내지 않은 것이
그 역할을 합니다.

- `+`/`−` 기호가 `.diffMark`에 그대로 남습니다(`aria-hidden="true"`이지만 시각적으로는 보입니다)
- 줄 번호가 add는 새 번호, del은 옛 번호를 보여 줍니다
- DOM에는 `data-type="add|del"`이 그대로 있습니다

따라서 색은 **덧붙이는 신호**이고 유일한 신호가 아닙니다. 이 판정을 테스트로 고정했습니다(6절).

## 5. 집계 숫자는 `+`와 `−`가 같은 클래스였습니다

```tsx
<span className={styles.fileStat}>+{file.additions}</span>
<span className={styles.fileStat}>−{file.deletions}</span>
```

`:first-child`/`:last-child`로 가르는 방법도 있었지만 접었습니다. `.filename` 뒤에 붙는 순서에
의존하게 되고, 사이에 무엇이 하나 들어오면 조용히 어긋납니다. `data-kind="add|del"`을 붙였습니다.
diff 줄이 이미 `data-type`을 쓰고 있어 표현 방식도 맞습니다.

diff 헤더 쪽은 `.diffStats` 안의 익명 `<span>`이라 `.diffStats [data-kind="add"]`로 받았습니다.

## 6. jsdom이 CSS Module을 적용하지 않아 테스트 방식을 바꿨습니다

처음에는 렌더 결과에서 `getComputedStyle`로 색을 읽으려 했는데, 이 프로젝트의 vitest 설정에서
CSS Module은 클래스 이름만 남기고 선언은 적용되지 않습니다. 렌더로는 색을 확인할 수 없습니다.

`src/css-module-class-reference.test.ts`가 같은 제약 때문에 소스를 읽는 방식을 이미 쓰고 있어서
그 선례를 따랐습니다. 다만 **무엇을 고정할지**를 좁혔습니다.

- `#16a34a`라는 값 자체는 고정하지 않습니다. 값이 바뀌는 것은 결함이 아닙니다.
- 고정하는 것은 둘입니다. 추가와 삭제가 **서로 다른** 토큰을 가리키는지, 그리고 색을 지웠을 때
  남는 `+`/`−` 기호가 여전히 DOM에 있는지.

두 번째가 특히 중요합니다. 이 결정이 한 번 뒤집혔으므로 다음 사람이 "색이 있으니 기호는 지워도
되겠다"로 갈 수 있습니다. 그때 걸리게 해 뒀습니다.

## 7. 테스트가 실제로 잡는지 확인했습니다

테스트를 쓰고 통과시키는 것만으로는 그 테스트가 무엇을 잡는지 알 수 없습니다. `.diffMark`의 add 색
선언을 `var(--color-muted-foreground)`로 되돌려 놓고 돌렸습니다.

```
FAIL  CodePanel diff 색 > 추가와 삭제가 서로 다른 색 토큰을 가리킨다
AssertionError: expected '/*\r\n * 인터뷰 워크스페이스의…' to match /\.diffLine\[data-type="add"\] \.diffM…/
Tests  1 failed | 18 passed (19)
```

잡습니다. 되돌렸습니다.

이때 백업 파일을 `/tmp`에 뒀는데 이 환경에서는 스크래치패드를 쓰라는 지침이 있습니다. 다음부터
스크래치패드에 둡니다.

보조 회색 2종뿐이었고 의미를 담은 색은 처음입니다. 오류 색(`#a3272c`)은 아직

후보입니다. 이번 범위가 아니라 손대지 않았습니다.
