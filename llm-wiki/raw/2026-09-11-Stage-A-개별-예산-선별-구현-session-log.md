# Stage A 개별 예산 선별 구현 세션 로그

`output/2026-09-11-Stage-A-개별-예산-선별-구현-인계.md`와 `raw/2026-09-11-Stage-A-개별-예산-선별-설계-session-log.md`를 이어받아 구현했습니다. 처음에는 별도 GitHub Issue(#103)를 만들었으나, 사용자가 이슈를 새로 파지 않고 이슈 #101에 병합해 같은 세션에서 이어가기로 결정해 #103을 삭제하고 #101 본문에 이번 범위를 추가했습니다.

## 구현

`work-unit-selection.ts`의 `selectWorkUnitsForStageA`를 동점 그룹 단위 일괄 처리에서 개별 항목 순회로 다시 작성했습니다. 점수 내림차순 정렬과 동점 시 입력 순서 유지는 그대로 두고, `allowSplit`·`budgetExhausted` 플래그와 그룹 구성 로직을 삭제했습니다. 정렬된 항목을 하나씩 확인해 항목 하나가 혼자 바이트 상한을 넘으면 `over_byte_budget`, 개수·바이트 예산에 들어가면 선택, 아니면 `over_input_budget`으로 분류하고 다음 항목을 계속 확인합니다.

`thresholdScore` 필드는 인계 문서가 열어 둔 두 선택지 중 유지하는 쪽을 택했습니다. `candidate-client.ts`, `repository-analysis.ts`와 관련 테스트까지 20곳 넘게 참조하고 있어 제거하면 이번 변경 범위를 넘는 무관한 리팩터링이 됩니다. 의미만 "선택된 항목 중 최저 점수" 통계로 재정의하고 계산식은 그대로 두었습니다(선택 항목이 여전히 점수 내림차순으로 쌓이므로 `selected.at(-1)?.score`가 새 알고리즘에서도 성립합니다).

`experience-candidate-list.tsx`의 제외 안내 문구에서 "이번 판단의 점수 경계는 N점이었습니다" 문장을 지웠습니다. 선택이 개별 항목 단위로 이뤄지면서 점수 높고 큰 항목이 빠지고 점수 낮고 작은 항목이 들어가는 비단조 결과가 정상이 되어, 단일 점수 경계로 설명하면 사실과 다르기 때문입니다. "저장소가 커서 전체 N묶음 중 점수 상위 M묶음만 판단했습니다"에서도 "점수 상위"를 지웠습니다. 대체 문구는 "분석 가능한 분량 안에서 점수순으로 선택했고, 같은 점수에서는 최신 커밋을 우선했습니다."로 정했습니다. "최신 커밋"으로 구체화한 근거는 `work-unit.ts` 90행 주석("호출자가 넘긴 커밋 순서(현재는 최신 순)를 단위 수준에서도 유지")으로, 구현 전에 실제로 최신순이 유지되는지 코드로 확인한 뒤 반영했습니다.

`thresholdScore`를 화면에서 더 이상 쓰지 않게 되면서 `StageAExclusions` 컴포넌트의 구조 분해에서 뺐습니다. 인터페이스 필드 자체는 다른 호출부 호환을 위해 유지했습니다.

## 테스트

`work-unit-selection.test.ts`에서 동점 무리 일괄 처리를 전제로 한 기존 테스트 2건을 재작성했습니다.

- "같은 점수 무리는 예산에 다 들어갈 때만 넣는다" → "동점 항목도 개별로 확인해 예산에 드는 만큼만 선택한다"로 바꿔 부분 선택을 검증합니다.
- "점수가 높은 묶음부터 고르고 나머지는 사유와 함께 남긴다" → "점수 높은 항목 다음이 예산에 안 들어가도 그 뒤 낮은 항목은 계속 확인한다"로 바꿔, 중간 점수 항목이 못 들어가도 그보다 점수가 낮은 항목이 남은 예산에 들어가면 선택되는 회귀를 재현합니다.

신호를 함께 돌려주는 기존 테스트는 매직 넘버 400바이트 대신 `unitBytes()`로 계산한 예산을 쓰도록 바꿔, 실제 렌더 크기와 무관하게 결정적으로 통과하게 했습니다.

새 회귀 테스트 4건을 추가했습니다. 동점 다수가 개수 상한을 넘을 때 입력 순서대로 상한까지만 선택하는지(0점 단일 커밋 20개, 개수 상한 5개로 축소 재현), 전체 입력이 예산 안에 들면 PR·단일 커밋·점수 관계없이 모두 선택하는지, 같은 입력을 반복 실행하면 결과가 그대로인지, 동점 입력 순서를 바꾸면 예산 경계에서 선택 집합이 달라지는지를 확인합니다.

기존 UI 텍스트 어서션 5건이 깨졌습니다(`experience-candidate-list.test.tsx` 3건, `repository-analysis-view.test.tsx` 2건). "점수 상위"와 "이번 판단의 점수 경계는 N점이었습니다" 문구를 참조하고 있어 새 문구에 맞게 고쳤습니다.

`npm run typecheck`, `npm run lint`, `npm run test -- --run`을 실행해 전부 통과를 확인했습니다(56 files / 967 tests, 이전 926에서 41개 늘었습니다: WorkUnit 판별 유니온 구현분 37개 + 이번 신규 4개).

## 실측

`.env`를 메인 체크아웃(`C:/Users/user/orca/demian/.env`)에서 이 워크트리로 복사해 실제 Gemini 호출로 검증했습니다. 이전 세션이 만든 캐시(`hm1n.github.io`, `Algorithm` 상세 조회 결과)를 그대로 재사용해 프롬프트 교체 검증과 이번 검증이 같은 입력을 봅니다.

`hm1n.github.io`는 12묶음 전체가 이미 바이트 예산 안에 들어오는 저장소라 이번 변경으로 결과가 바뀌지 않았습니다(선별 입력묶음=12, 제외묶음=0, 후보 4개는 프롬프트 교체 검증 때와 동일). 이 저장소는 애초에 동점 무리 일괄 제외 버그의 영향을 받지 않았습니다.

`Algorithm`은 이번 변경의 핵심 검증 대상입니다. 3회 반복 모두 다음과 같이 동일했습니다.

| 지표 | 이전(동점 그룹 일괄 처리) | 이후(개별 항목 예산 검사) |
| --- | --- | --- |
| 선별 입력묶음 | 1 | 200 |
| 제외묶음 | 434(전부 `over_input_budget`) | 235(전부 `over_input_budget`) |
| Stage A `decision` 계약 | 1/1, 충족 | 200/200, 3회 모두 충족 |
| 후보 | 0(미분류 1) | 2(미분류 198) |

인계 문서가 조건부로 예상한 "200개 선택, 235개 제외"와 정확히 일치했습니다. 새로 늘어난 후보 `0759fe2` `Change default branch from 'master' to 'main'`은 BaekjoonHub 자동 채점 커밋이 아니라 실제로 배포 브랜치 설정을 바꾼 직접 커밋입니다. 이전 편향 측정(`raw/2026-09-11-이슈101-프롬프트교체-편향측정-session-log.md`)에서 이미 "예산이 허용했다면 질문할 단서가 있다고 받아들일 수 있다"고 판단했던 바로 그 커밋이 예산 확대로 실제 Stage A에 도달해 추천된 것입니다. 나머지 198개 미분류는 콘솔에 찍힌 후보 목록에 자동 채점 커밋이 없다는 사실로 확인했습니다.

## 결론

동점 그룹 때문에 남은 예산을 쓰지 못하던 문제가 해결됐습니다. 개수 상한 200, 바이트 상한 110,000, 점수 계산은 손대지 않았습니다. `hm1n/Algorithm`처럼 점수가 몰린 저장소에서 자동 채점 커밋을 오추천하지 않으면서 예산을 최대한 활용하는 것을 실측으로 확인했습니다.
