# 이슈 #89 PR #104 Codex 1차 리뷰 반영

`hm1n/setting-llm-provider-2` 브랜치가 이번이 첫 PR이라(이전 커밋들도 develop에 병합된 적 없음),
Codex 리뷰가 #87·#88 시절 코드(`reducer.ts`)까지 포함해 인라인 코멘트 2건을 남겼습니다. 둘 다 도구
등급 P1입니다.

## 코멘트 수집

- `src/features/experience-block/request.ts:82-86` — 클라이언트가 보낸 `state`의 저장소 출처를
  스냅샷과 대조하지 않고, 주장 ID 중복과 `nextClaimSeq` 충돌도 통과합니다.
- `src/features/experience-block/reducer.ts:253-258` — 평가 검증 루프가 모델이 낸 평가만 확인하고
  `targetBlock`이나 영향받은 블록의 평가 누락은 거절하지 않습니다.

## 묶음과 재판정

**묶음 A(request.ts, state 무결성)를 P1로 유지했습니다.** `state`는 브라우저 JS 상태라 사용자가
개발자 도구로 고쳐 재전송할 수 있고, 검증되지 않은 저장소 인용이 "저장소 출처"로 표시될 수 있어
`AGENTS.md`의 "AI는 항상 실제 Repository의 커밋과 파일을 근거로 제시" 원칙을 직접 건드립니다. 설계
문서 3-2절이 인정한 "과거 상태의 최신성 보장 불가"(오래된 정보)와는 다른 결의 문제라고 판단했습니다.

같은 데이터 흐름을 다시 읽어 지적되지 않은 결함을 하나 더 찾았습니다. `state.display`의
`claimIds`도 실재하는 주장을 가리키는지 검증하지 않아, 조작된 요청이 완전히 지어낸 표시 문장을
그대로 돌려받을 수 있었습니다(`markDisplay`는 존재하지 않는 참조를 조용히 걸러낼 뿐 문장 자체를
지우지 않음).

**묶음 B(reducer.ts, 평가 누락)를 P2로 재판정해 후속 분리했습니다.** 지금 이 값을 읽는 소비자가
없어(#90 미착수) 관측 가능한 오동작이 당장 없고, 고치려면 `applyBlockUpdate`의 `context` 계약에
`targetBlock`을 추가해야 해 기존 호출부(테스트 18개, 측정 하네스 3곳, route.ts)를 함께 고쳐야
합니다. "수정 비용이 매우 작은" 예외에 해당하지 않는다고 봤습니다. 사용자에게 확인받아 진행했습니다.

## 반영

묶음 A를 커밋 d4001f8로 반영했습니다.

- `reducer.ts`의 `evidenceIndex`를 export해 `request.ts`가 재사용하도록 했습니다.
- 저장소 출처의 커밋·파일을 스냅샷과 대조합니다.
- 주장 ID 중복과 `nextClaimSeq`가 이미 쓰인 번호 이하인 경우를 거절합니다.
- `state.display`의 `claimIds`가 실재하는 같은 블록의 `active` 주장을 가리키는지 검증합니다.
- `isBlockRecord` 헬퍼가 검증 대상 블록 키를 콜백에 넘기도록 확장해 `display` 검증이 블록별 활성
  주장 집합을 참조할 수 있게 했습니다.

지적 4건(중복 ID, `nextClaimSeq` 충돌, 저장소 출처, display 참조)마다 회귀 테스트를 추가하고,
저장소 출처가 실재할 때 정상 통과하는 양성 테스트를 더해 총 5개를 넣었습니다
(`request.test.ts`, 9개 → 14개). 기존 테스트 하나(주장 상태 상한 테스트)가 새 `nextClaimSeq` 검증에
걸려 실패해, 픽스처의 `nextClaimSeq`를 실제로 일관된 값(2)으로 고쳤습니다. 전체 테스트 963개, lint,
typecheck 통과를 확인했습니다.

묶음 B는 `wiki/2026-09-11-PAAR-경험블록-후속-backlog.md`에 1번 항목으로 남겼습니다.
