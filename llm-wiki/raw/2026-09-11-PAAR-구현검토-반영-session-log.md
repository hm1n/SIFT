# PAAR 구현검토 P1 반영 기록

날짜는 2026-09-11입니다. `output/2026-09-11-PAAR-경험블록-구현검토.md`가 남긴 P1 다섯 묶음을 사용자
승인(`이대로 진행해`) 뒤 반영했습니다. 각 묶음은 검토 보고서의 판정을 그대로 신뢰하지 않고, 최소
`progress.ts`(P1-1)와 `use-experience-interview.ts`(P1-2, P1-3)는 실제 코드를 직접 읽어 재현 가능함을
확인한 뒤 착수했습니다.

## 커밋 순서와 이유

이슈 #90 구현 전체가 이 세션 시작 시점까지 한 번도 커밋되지 않은 상태였습니다. 묶음별로 "수정 전"과
"수정 후"를 분리한 히스토리를 남기기 위해, 먼저 원본 구현(측정 세션이 실측한 그대로의 상태)을
`7caed93 feat: 턴 진행과 블록 전환, 열 턴 자동 종료 구현`으로 커밋하고, 그 위에 묶음마다 커밋을
쌓았습니다.

- `79de4ff fix: 재질문 예산이 총 질문 횟수 기준으로 잘못 소진되던 결함 수정` (P1-1)
- `9b8809e fix: 성공한 다른 턴이 실패한 턴의 미반영 기록을 지우던 결함 수정` (P1-2)
- `899c92f fix: 겹친 블록 갱신 응답의 적용 경계와 언마운트 취소 누락 수정` (P1-3)
- `4c1c107 fix: 완료 대기 상태에서 보충 답변을 제출할 수 없던 결함 수정` (P1-4)
- `baf49c1 feat: 블록 갱신의 실패·충돌·응답 분류를 다음 질문 생성에 전달` (P1-5)

## P1-1. 재질문 카운팅

`recordResponse`가 `askedCount`(총 질문 횟수)로 재질문 소진을 판정하던 것을, 첫 `unknown`을 받은
시점의 `askedCount`(`firstUnknownAskedCount`)를 따로 기록해 그 뒤 한 번 더 물었는지로 판정하도록
바꿨습니다. 검토가 지적한 두 방향(provided 뒤 첫 unknown이 곧장 소진되는 것, unknown 뒤 unanswered가
반복돼도 소진되지 않는 것) 모두 새 로직으로 해소되는 것을 확인했고, 기존 회귀 테스트 4개와 새 테스트
2개(R1·R2) 모두 통과했습니다.

"다른 구체적 단서가 있을 때"라는 조건은 이번에 구현하지 않았습니다. 지금 계약에 그 조건을 판단할
신호가 없고, 신호를 새로 만드는 일은 모델 출력 계약을 또 넓히는 별도 작업이라 판단해 설계 문서
12절에 확인 필요로 남겼습니다.

## P1-2. 턴별 미반영 상태

단일 슬롯(`unreflectedRef: {turn, target} | null`)을 턴 ID 키의 `Map`으로 바꿔, 어느 턴이 성공하든
자기 턴만 지우게 했습니다. `endInterview`가 abort로 끊은 진행 중인 호출은 `inFlightRef`를 직접 읽어
동기적으로 미반영 등록하도록 바꿨습니다(`applyTurn`의 catch가 비동기라 타이밍 경합이 있었습니다).
열 턴 자동 종료도 `inner.endInterview()`를 곧장 부르는 대신 사용자 종료와 같은 정리 경로
(`retryAllUnreflected`)를 거치게 했습니다.

기존 테스트 중 "블록 갱신이 진행 중일 때 종료하면..." 하나가 깨졌는데, 이는 고친 동작을 그대로
검증하던 테스트라 기대값을 새 동작(미반영 등록 + 재시도 1회 더 나감)에 맞춰 갱신했습니다. R3·R6·R9를
새 회귀로 추가했습니다.

## P1-3. 비동기 취소 경계

`applyTurn`에 호출별 일련번호(`callSeq`)를 매겨, 응답이 왔을 때 그 사이 다른 호출이 이미 시작됐으면
(겹쳐 들어온 재처리 등) 적용하지 않고 조용히 버리게 했습니다. 이 작업 중 `inFlightRef` 정리를 처음에
turnId로만 판별하다가, 같은 턴을 재시도할 때 이전 시도의 `finally`가 새 시도의 기록을 지우는 경합을
스스로 만든 것을 발견해 `callSeq` 비교로 바꿨습니다(회귀 테스트를 쓰기 전에 코드 추적으로 잡았습니다).

언마운트 가드는 두 훅에 나눠 넣었습니다. `use-experience-interview.ts`는 자신의 `blockUpdateAbortRef`를
끊고 `applyTurn`·`onBeforeQuestion`의 이어지는 상태 갱신을 막는 `unmountedRef`를 뒀습니다.
`use-interview-stream.ts`는 `onBeforeQuestion`이 끝난 뒤 `start()`를 부르는 자리에 같은 성격의
`unmountedRef`를 별도로 뒀습니다. 기존 unmount effect(의존성 배열이 있는)에 얹으면 `start`가 바뀔
때마다 재실행돼 "매번 언마운트됨"으로 잘못 표시하므로, 빈 의존성 배열의 effect를 새로 분리했습니다.
R4·R5를 새 회귀로 추가했습니다.

## P1-4. 완료 대기 상태의 보충 답변

`canSubmitAnswer`가 "마지막 메시지가 질문"이어야 한다는 조건을 없애고 "마지막 메시지가 스트리밍
중이 아니어야 한다"만 남겼습니다. 답변 메시지는 스트리밍 상태가 없으므로 이 조건만으로 충분합니다.
`use-experience-interview.ts`에는 보충 답변이 다시 물을 거리를 만들면 `isReadyToFinish`를 되돌리는
코드를 함께 넣었습니다(기존에는 한 번 true가 되면 되돌리는 경로가 없었습니다). R7을 새 회귀로
추가했습니다.

## P1-5. 실패·충돌·응답 분류를 질문 생성에 전달

`InterviewLastOutcome` 타입을 `history.ts`에 새로 두고(블록 갱신 실패 여부, `targetResponse`, 아직
해소되지 않은 충돌의 관찰 문장), `use-experience-interview.ts`가 매 턴 끝에 "눈에 띄는" 결과가 있을
때만(반영 실패, `provided`가 아닌 응답, 충돌 존재) 이 값을 만들어 `onBeforeQuestion`의 반환값에
얹도록 했습니다. `use-interview-stream.ts`는 이 값을 `pendingTargetRef`와 같은 자리에서 같은 방식으로
받아 다음 질문 요청 본문에 싣고, 서버(`question-request.ts`)는 상한 있는 검증을 거쳐
`question-generation.ts`가 `focus`와 같은 방식으로 별도 메시지에 담습니다. `question-prompt.ts`에
이 메시지를 어떻게 쓸지 지시하는 규칙 한 줄을 더했습니다.

이 묶음은 나머지 넷과 성격이 다릅니다. 코드 결함 수정이 아니라 설계 9절이 이미 요구했지만 구현되지
않았던 계약을 새로 추가하는 것이라 프롬프트 계약이 커집니다. 요청 본문 상한(`MAX_INTERVIEW_STREAM_BODY_BYTES`)과
프롬프트 바이트 상한(`INTERVIEW_QUESTION_MAX_PROMPT_BYTES`)에 `INTERVIEW_LAST_OUTCOME_MAX_BYTES`
(관찰 최대 3개, 문장당 240바이트에서 유도)를 더했습니다. 단위 테스트로 계약(생성·검증·메시지 순서)만
확인했고 실제 모델 호출로 재실측하지 않았습니다. 이 맥락이 검토가 지적한 실제 사례(EventSource 충돌을
사실처럼 전제한 질문, 배제된 측정을 다시 물은 질문)를 얼마나 줄이는지는 유료 실측이 있어야 압니다.

## 검증

각 묶음 뒤 `npm run typecheck`, `npm run lint`, `npm test`를 돌렸고 매번 통과했습니다. 최종
`npm test`는 68개 파일 1,112개 테스트(원본 1,094개 + 이번 세션에서 추가한 18개)를 통과했습니다.
회귀 테스트는 검토 보고서의 재현 테스트(R1~R9)를 정식 테스트로 옮기거나 대응하는 새 테스트로
다시 썼고, `output/2026-09-11-PAAR-리뷰-재현.test.tsx.txt`의 임시 파일 형태는 그대로 두었습니다
(정식 테스트 파일에 흡수됐다는 점을 그 파일 자체에는 표시하지 않았습니다).
