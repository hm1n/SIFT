# 답변 입력 훅을 실제 route에 붙여 4턴을 돌렸습니다

이슈 #77의 `use-interview-stream.ts`를 실제 `/api/interview/stream`과 모델에 붙여 한 번 확인한 기록입니다. 결정은 `wiki/2026-09-08-꼬리질문-답변입력-대화누적-화면.md`에 있습니다.

## 1. 어떻게 돌렸는가

- 워크트리에서 `next dev -p 3117`을 띄웠습니다. 환경변수는 메인 체크아웃의 `.env`를 프로세스 환경에만 실었고 파일은 복사하지 않았습니다.
- 훅은 vitest jsdom 안에서 `renderHook`으로 띄우고 `fetchImpl`에 세션 쿠키를 붙인 실제 `fetch`를 넘겼습니다. 쿠키는 `encryptGitHubToken`으로 만들었습니다. route는 쿠키 존재만 확인하고 GitHub를 부르지 않으므로 토큰 값은 임의입니다.
- 근거는 `question-fixture.ts`의 `evidenceSnapshotFixture()`입니다. 실제 GitHub 응답으로 조립한 근거는 아닙니다.
- 답변 3개는 미리 써 두었습니다. seq를 done에 실은 이유, Last-Event-ID 재개를 테스트 스트림에만 연 이유, 측정을 하지 않았다는 답변입니다.
- 임시 테스트 파일은 저장소 루트에 두고 돌린 뒤 지웠습니다. 커밋하지 않았습니다.

## 2. 결과

| 턴 | 첫 청크 지연 | 마지막 seq | 오류 |
| --- | --- | --- | --- |
| 1 | 5,954ms | 8 | 없음 |
| 2 | 742ms | 9 | 없음 |
| 3 | 701ms | 7 | 없음 |
| 4 | 측정 안 함 | 9 | 없음 |

1턴의 지연에는 `next dev`의 첫 컴파일이 들어 있습니다. 서버 로그의 첫 요청은 6.3초 가운데 `application-code` 1,341ms였고 나머지 세 요청은 1.1~1.2초였습니다. 2026-09-08 앞선 확인의 685~905ms와 같은 자리입니다.

- 역할이 질문·답변·질문·답변·질문·답변·질문 순서로 쌓였습니다.
- 답변 제출 직후 `canSubmitAnswer`가 거짓이 되고 마지막 항목이 그 답변이었습니다.
- 매 요청의 `receivedSeq`가 0에서 다시 시작해 마지막 seq와 일치했습니다.
- `removedHistory`는 비어 있었습니다. 이력 6개는 상한 18개 안입니다.

## 3. 프롬프트 규칙은 이번에도 지켜지지 않았습니다

이슈 #77 범위가 아니라 문구는 손대지 않았습니다. 이슈 #79의 판정 기준에 그대로 들어가는 사례라 남깁니다.

- 꼬리 질문 3개가 모두 답변 요약으로 시작했습니다. "구분하셨군요", "전략으로 이해됩니다", "방침을 세우셨군요".
- 2턴과 3턴이 같은 것을 물었습니다. seq 불일치를 감지했을 때의 클라이언트 복구 전략입니다. 2턴 답변이 그 질문에 답하지 않고 재개 방침을 설명했는데, 모델이 앞 질문을 되돌리는 대신 같은 질문을 새 문장으로 다시 냈습니다.
- 4턴은 "운영 데이터가 없는 상황"이라는 사용자 답변을 그대로 전제로 삼았습니다. 이 사실은 저장소로 확인할 수 없습니다.

## 4. 하지 않은 것

- 브라우저에서 입력란을 눌러 보는 확인은 하지 않았습니다. 화면 흐름은 GitHub 로그인 세션을 거쳐야 인터뷰 화면에 도달하므로 jsdom 테스트로 대신했습니다.
- 이력 절단이 실제로 일어나는 10턴 대화는 돌리지 않았습니다. 절단은 훅 테스트가 상한 초과 한 쌍으로 고정합니다.
- 메시지가 쌓일 때의 렌더링 비용은 재지 않았습니다.
