# PAAR 경험 블록 설계 개정 (이슈 #87, #88)

날짜는 2026-09-11입니다. `raw/2026-09-11-블록갱신-프롬프트-2차-재실측-session-log.md`를 이어받습니다. 2차 재실측이 재지 못한 상황을 정리하다가 이슈 #87의 설계 자체를 고치기로 한 경위입니다. 결론은 `wiki/2026-09-11-PAAR-경험블록-설계-개정.md`에 있습니다.

## 1. 상황 목록

현재 블록 상태와 답변 종류로 나눠 13개를 적었습니다. 픽스처가 필요한 것, 설계로 이미 처리되는 것, 설계가 정해지지 않은 것으로 갈랐습니다.

| --- | --- | --- | --- |

## 2. 외부 검토

이 목록과 현재 설계를 정리해 다른 모델에게 검토를 요청했습니다. 질문 일곱 개였습니다. 잘못된 기대 동작이 있는지, 상황 2·3·5를 프롬프트만으로 보장할 수 있는지, 상황 7·8의 대안 네 가지 비교, 상황 6에서 무엇을 남길지, 상황 9의 사실 유실을 프롬프트로 고칠 수 있는지, 느슨한 인용과 확인 필요 표시의 상호작용, 빠진 상황입니다.

검토의 핵심 진단은 "1~2문장으로 압축한 블록을 다음 갱신의 유일한 기억으로 쓰는 것"이 문제라는 것이었습니다. 여기에 정보 보존, 정정, 충분성 판정까지 맡기면 한 번 빠진 정보를 복구할 수 없습니다. 제안은 원문, 주장, 표시 문장을 분리하고 주장 단위 변경 연산으로 바꾸는 것이었습니다.

받아들인 제안입니다.

- 상태 분리와 변경 연산. 언급되지 않은 주장은 유지하고 존재하지 않는 ID는 거절합니다.
- 상황 7·8은 블록 갱신 입력에 전체 이력을 넣는 것으로 풉니다. 질문 생성이 이미 전체 이력을 받으므로 가장 작은 수정입니다.
- 충분성과 이동을 분리합니다. 최소 턴은 두지 않습니다.
- 상황 6은 어느 한쪽을 확정하지 않고 충돌로 보존하며 확인 질문으로 넘깁니다.
- 상황 9는 "답변 전체를 거절"이 아니라 "지시는 따르지 않고 분리 가능한 진술은 보존"으로 문구를 바꿉니다. 보장은 없으므로 평가 항목으로 둡니다.
- 인용 존재 검증과 내용 검증을 구분해 표시합니다.
- 추가된 상황 여섯 개. 늦은 정정이 지나간 블록을 바꾸는 경우, 중복 제출과 응답 순서 역전, 종료 직전 갱신 실패, 충분하지 않지만 더 물을 이유도 없는 경우, 저장소 근거 안의 지시, 종료 후 편집으로 기존 인용이 무효가 되는 경우입니다.

접은 제안입니다.

- "이전 내용이 있는데 빈 출력이 오고 답변에 정정 표현이 없으면 이전 블록을 유지한다"는 키워드 규칙. 정정 키워드가 없는 철회를 놓치고, 인용문 속 철회를 오해하며, 일부 누락에는 효과가 없습니다.
- 한 호출에서 네 블록을 매번 다시 쓰는 안. 답변과 무관한 블록까지 변형할 범위가 커집니다.
- 다른 블록 정보를 별도 보관소에 두는 안. 분류 누락과 잘못된 배정 위험이 있고 구현이 큽니다.
- 질문 생성이 앞선 이력의 내용을 다시 묻게 하는 안. 이미 받은 명확한 정보를 저장하려고 제한된 턴을 씁니다. 충돌과 모호함의 재확인에만 씁니다.

## 3. 턴 분배

사용자가 이어서 물었습니다. 10턴은 러프하게 잡은 값이라 충분한지 재검토가 필요하고, 블록마다 N턴을 고정하면 내용이 완성될 때 넘어가야 하는지 N턴을 다 써야 하는지, 최소 턴을 두어야 하는지 모르겠다는 것이었습니다.

검토 결론입니다. 블록마다 고정 턴이나 최소 턴을 두지 않고 필요한 정보에 따라 이동하되 전체 질문 수에 상한을 둡니다. 10턴은 충분성이 검증된 값이 아니라 우선 실험할 상한입니다. 기존 설계의 "충분해도 최소 2턴"은 이미 확보한 정보에 질문을 더 하도록 강제합니다. 블록별 N을 두고 싶다면 할당량이 아니라 예산으로 두고, 일찍 충족하면 남은 예산을 다른 블록에 씁니다. 서버 판정은 "남은 질문 수가 다른 미확인 블록 수 이하이면 미확인 블록으로 이동"입니다. 기존의 "블록마다 두 턴 보장"보다 적게 예약합니다.

10턴이 충분한지는 실제 인터뷰를 돌려야 알 수 있습니다. 합성 답변 통과를 그 근거로 쓰지 않기로 했습니다.

## 4. 핸드오프와 구현 결정

검토 결과를 구현 엔지니어에게 넘길 핸드오프 문서로 정리했고, 코드와 대조해 계획을 세웠습니다. 대조에서 드러난 사실은 저장 계층이 없다는 것입니다. 대화는 훅의 React 상태로만 있고 서버는 매 요청에 스냅샷과 이력을 통째로 받습니다. 핸드오프의 "서버 규칙"인 주장 저장소, 상태 버전, 답변 ID 중복 방지, 재처리 경로는 모두 클라이언트 상태에 두어야 합니다.

사용자가 결정한 것입니다.

1. 영속 저장 계층은 넣지 않습니다. 훅이 원문·주장·표시 문장·버전·미반영 답변을 보관합니다. 검증과 상태 전이는 `src/features/experience-block/`의 공유 순수 함수로 두고, 서버가 검증과 리듀서 적용을 수행해 검증된 결과를 돌려줍니다. 훅에서만 검증하지 않습니다. 보존 범위는 현재 페이지 세션 안의 실패·재시도이고, 무상태 서버가 클라이언트가 보낸 과거 상태의 진위와 최신성을 보장하지 못한다는 한계를 문서에 적습니다.
2. 주장 연산과 영향받은 블록의 표시 문장을 같은 호출에서 받습니다. 서버가 주장을 이어 붙여 표시 문장을 만들지 않습니다. 같은 응답에서 추가한 주장을 참조할 수 있는 임시 ID 규칙을 둡니다. ID 검증은 의미적 타당성을 보장하지 않으므로 "유효한 주장을 참조하면서 근거 없는 수치를 덧붙이는 사례"를 평가에 넣습니다. "호출 분리 시 지연이 두 배"라는 설명은 "직렬 호출 추가로 지연이 증가할 수 있으며 실측이 필요하다"로 고쳤습니다.
3. 입력 순서는 고정 규칙, 근거 스냅샷, 전체 이력, 주장 상태·대상 블록·답변 ID·상태 버전입니다. 최신 답변은 이력에 있으므로 중복 삽입하지 않고 ID로 지정합니다. 명시 캐시 경계는 공급자 지원을 확인해 적용하고 캐시 적중 유지를 문서에 보장하지 않습니다. 입력 한도를 정의하고 초과 시 안내하며 조용히 잘라내지 않습니다.
4. 새 하위 이슈를 만들지 않고 #88의 평가 범위를 확장합니다. #87, #89, #90, #91은 각각 해당 부분을 고칩니다. #88에서 구현 검증과 실사용 검증을 구분해 기록합니다.
