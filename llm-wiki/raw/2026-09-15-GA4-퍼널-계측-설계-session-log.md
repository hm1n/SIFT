# 2026-09-15 GA4 퍼널 계측 설계와 1단계 구현 세션 로그

이슈 #125를 읽고 계획을 세워 1단계를 구현하기까지의 경위입니다. 확정된 계약은
`wiki/2026-09-15-GA4-퍼널-계측.md`에, 범위 밖으로 넘긴 항목은
`wiki/2026-09-15-GA4-계측-후속-backlog.md`에 있습니다.

## 1. 명세를 읽고 코드와 맞춰 본 결과

이슈 #125와 상위 이슈 #124, 노션 기능 정의서 `GA4 사용자 행동 계측`을 읽었습니다. **#124 이슈
본문과 노션 페이지 본문이 완전히 같았습니다.** 노션 쪽에 더 갱신된 내용은 없었습니다.

코드를 읽으며 명세와 어긋나는 곳을 넷 찾았습니다.

- 명세는 `stage`를 "`LoadingPhase`의 여섯 단계"라고 적었지만 `LoadingPhase`는 `step` 5종이고
  `details` 하나가 `phase`로 둘로 갈립니다. 6단계로 펴는 매핑은 화면
  (`repository-analysis-view.tsx`의 `checklistKeyFor`)에만 있었습니다.
- `empty_kind` 다섯 갈래 가운데 `no_final_candidates`는 `EmptyKind` 유니온 밖입니다.
- `user_id`를 위해 `page.tsx`가 쿠키를 복호화하면 지금 동작이 바뀝니다. `decryptGitHubSession`이
  만료·옛 형식·키 미설정에서 던지는데, 지금 페이지는 쿠키의 존재만 봅니다.
- `page.test.tsx`의 `next/headers` mock이 `has`만 제공해 `.get()`을 쓰는 순간 전부 깨집니다.

`error_kind`는 명세대로였습니다. `AnalysisError["kind"]`가 정확히 `GitHubFetchErrorKind` 6종 +
`CandidateGenerationErrorKind` 6종입니다.

그리고 **개인정보 처리방침이 존재하지 않는다**는 것을 확인했습니다. `src` 443개 파일에
`개인정보`·`privacy` 문자열이 0건이고 노션에도 이 프로젝트의 처리방침 페이지가 없습니다(검색에
걸린 것은 다른 프로젝트인 엔빵의 것). Task 3번 "처리방침에 적습니다"는 없는 문서를 만드는 일이었습니다.

## 2. 사용자와 합의한 결정 넷

### 2-1. 개인정보 처리방침은 후속으로 분리

없는 문서를 만드는 일이라 계측 이슈가 화면과 라우트를 늘리게 되고, GA4 문단만 있는 처리방침은
GitHub OAuth·Neon·LLM 전송을 수집하지 않는다는 오해를 만듭니다. backlog 1번에 적고 "운영 시작 전에는
닫혀야 하는 항목"으로 표시했습니다.

### 2-2. `login_result`는 콜백 쿼리로 (C안)

세 안을 놓고 논의했습니다.

- A: 명세 그대로 "세션 확인 후 첫 렌더". 비용 0이지만 로그인 성공 수가 페이지 로드 수가 됩니다.
- B: `sessionStorage` 플래그로 탭 세션당 1회. GA4 세션 경계와 어긋나고 저장소 접근이 실패할 수 있습니다.
- C: 콜백 성공 리다이렉트에 `?login=success`를 붙입니다.

C를 골랐습니다. `AGENTS.md`의 판별 기준("그 상태를 직접 나타내지 않는 대리 지표를 쓰지 않습니다")에
정확히 걸리는 문제였고, 실패가 이미 `?auth_error=`로 오고 있어 대칭이 됩니다.

접은 반론도 남깁니다. 기능 정의서가 "계측 하나 때문에 인증 경로의 표면적을 넓히는 일"이라며 세션
`GET` 라우트 추가를 거절했는데, C도 인증 경로를 건드립니다. 새 엔드포인트가 아니라 기존 리다이렉트의
쿼리 하나이고 그 자리에 이미 `auth_error`가 같은 방식으로 붙는다는 점에서 표면적 증가는 아니라고
판단했습니다.

URL에서 표시를 지우는 방법으로 `window.history.replaceState`를 먼저 검토했다가 접었습니다. Next.js
16.3.1 문서에 이 API에 대한 언급이 없어 App Router 내부 상태와 어긋날 위험이 있었습니다. 이 저장소가
이미 쓰고 있는 `router.replace("/")`로 갔습니다.

### 2-3. `candidate_confirmed`의 `duration_ms`는 후보 목록 첫 렌더 기준 (A안)

분석 시작 기준(B안)은 분석 대기 시간이 섞이고 그 시간은 `analysis_stage_done`이 따로 재므로 뺄셈이
필요해집니다. 첫 상세 열람 기준(C안)은 그 이벤트가 2차 범위(#126)라 기준점이 없습니다. 이 이벤트
자체는 이번 PR에 들어가지 않았고 결정만 backlog 2번에 남겼습니다.

### 2-4. 화면 개편 때문에 1·2단계로 나눔

사용자가 화면 레이아웃과 순서를 바꿀 예정이고 단계 수가 바뀌는지는 아직 정해지지 않았다고 했습니다.
붙이는 자리를 도메인 경계로 잡으면 12종 중 10종을 지금 할 수 있다고 판단해 나눴습니다.

- `repo_list_loaded`를 선택 화면이 아니라 `repository-client.ts`의 조회 함수에.
- `analysis_requested`와 `flow_id` 발급을 저장소를 고른 시점이 아니라 분석 시작 액션에.
- `login_view`는 로그인 화면이 "로그인 뒤 순서"를 바꾸는 개편의 사정권 밖이라 판단해 포함.

남은 둘은 `candidate_confirmed`와 `interview_started`입니다.

이 논의 중에 **#115와 #116이 퍼널을 우회하는 진입 경로를 만든다**는 것을 발견했습니다. 저장된
인터뷰 이어가기와 저장된 분석에서 후보 고르기입니다. backlog 3번에 적었습니다.

## 3. 구현에서 판단이 갈렸던 자리

### 3-1. 공통 파라미터를 우리 맵으로 들지 않음

처음에는 모듈 안에 `commonParams` 맵을 두고 매 전송에 합치려 했습니다. gtag의 `set`이 이미 같은
일을 하고, 맵을 따로 두면 두 곳이 어긋날 수 있어 `set`으로 갔습니다. `user_id`는 GA4 예약
파라미터라 이벤트 파라미터로 싣는 것이 문서화된 방식인지 확실하지 않았던 점도 이유입니다.

### 3-2. 측정 ID 형식 검사를 판정 함수에 넣음

측정 ID가 인라인 부트스트랩 스크립트 본문에 문자열로 박히므로 형식을 벗어난 값이 스크립트를 깨거나
코드를 끼워 넣는 통로가 됩니다. `JSON.stringify`로 감싸는 방법을 먼저 생각했지만 `</script>`를
막지 못합니다. 영숫자와 하이픈만 통과시키고 나머지는 값이 없는 것과 같이 다루기로 했습니다. 게이팅과
렌더링이 같은 판정을 보게 하려고 검사를 `resolveMeasurementId` 안에 넣었습니다.

### 3-3. 스크립트 전략

`next/script`의 `afterInteractive`로 부트스트랩까지 실으면 `login_view`가 그보다 먼저 일어나 유실될
수 있다는 것을 배선 중에 알았습니다. `beforeInteractive`는 Next.js 16.3.1 문서가 임계 스크립트로
한정하고 있어, 부트스트랩만 평범한 인라인 `<script>`로 두고 라이브러리만 `afterInteractive`로
나눴습니다. React 19가 인라인 `<script>`를 지우지 않는지 확신이 없어 프로덕션 빌드로 실측했습니다(4절).

### 3-4. 테스트가 예외 격리 결함을 잡음

`repository-flow.test.tsx`에 계측 모듈 mock을 넣었더니 관계없는 기존 테스트 둘이 깨졌습니다. mock이
`commitCountBucket`을 빠뜨려 `advanceAnalysisTracker`가 `TypeError`를 던졌고, 그 예외가 분석 상태
sink를 타고 올라가 `setState`에 닿지 못해 화면이 로딩에 멈춘 것이었습니다.

mock을 고치면 끝나는 문제였지만 **실제 결함이 드러난 것으로 봤습니다.** 이슈 #125의 제약이 "계측
코드에서 던진 예외가 화면으로 올라가지 않아야 합니다"이고, 계측은 상태를 화면에 반영하기 직전에
실행됩니다. 전송부(`ga.ts`)만 감싸 두면 상태 판정과 파라미터 구성은 보호되지 않습니다.

세 겹으로 고쳤습니다.

1. `events.ts`의 `trackEvent`와 공통 파라미터 세터를 try/catch로 감쌌습니다. `repo_list_loaded`가
   저장소 목록 조회 함수 안에서 나가므로, 거기서 던지면 계측 실패가 조회 실패가 됩니다.
2. 분석 화면의 `reportAnalysis` 전체를 감쌌습니다.
3. 회귀 테스트를 둘 넣었습니다. `events.test.ts`는 전송부가 던져도 `trackEvent`가 던지지 않는 것을,
   `repository-flow.test.tsx`는 `advanceAnalysisTracker`가 던져도 분석 결과가 그려지는 것을 봅니다.

## 4. 실측

프로덕션 빌드로 두 경우를 확인했습니다.

**측정 ID 없이 빌드하고 실행** — 서버가 보낸 HTML(17,000바이트)에 `googletagmanager`도 `dataLayer`도
`ga-bootstrap`도 0건이었습니다. 이슈 #125의 Definition of Done인 "측정 ID 없이 빌드하고 실행했을 때
네트워크 요청이 발생하지 않는 것"을 충족합니다.

**`NEXT_PUBLIC_GA_MEASUREMENT_ID=G-TEST12345`로 빌드하고 실행** — 인라인 부트스트랩이 HTML에 그대로
들어갔고(`window.dataLayer = window.dataLayer || [];...gtag('config', 'G-TEST12345');`) 라이브러리
태그도 `strategy: afterInteractive`로 실렸습니다. React 19가 인라인 `<script>`를 지우지 않는 것을
확인했습니다.

전체 스위트 1,434개 통과, typecheck와 lint 통과입니다.

브라우저 콘솔 작업이고 사용자가 맡기로 했습니다. 보고 시간대와 통화는 생성 시점에 정해야 소급되지
않는다는 것을 함께 전달했습니다.
