# PR #119 코드래빗 GitHub 자동 리뷰 반영 세션 로그

develop을 브랜치로 머지해 충돌을 해소한 뒤, CodeRabbit이 GitHub에서 자동 리뷰를 돌렸습니다. 인라인 지적 5건입니다. 앞의 두 라운드는 로컬 CLI로 돌린 것이고 이번은 GitHub 쪽 리뷰라 지적이 겹치지 않았습니다.

## 반영한 것

### 블록 버전이 오르지 않는 저장을 막지 못했습니다 (P1)

`appendTurn`이 `expectedBlockVersion`만 봤습니다. 저장된 버전과 기대 버전과 새 버전이 모두 같으면 저장이 성공하고 버전이 오르지 않습니다. 그 뒤로도 기대 버전이 같은 요청이 몇 번이고 성공합니다.

정의서의 동시성 설계가 이 검사 하나에 걸려 있습니다. "내가 알고 있던 `version`이 그대로일 때만 덮어쓴다"가 성립하려면 버전이 실제로 올라야 합니다. 오르지 않으면 다른 탭이 먼저 저장해도 막지 못하고 턴이 사라집니다. 등급표의 "데이터 손실"이라 P1으로 봤습니다.

`blockState.version`이 `expectedBlockVersion`보다 정확히 1 큰 값이 아니면 `version_conflict`를 돌려주게 했습니다. 결과 종류를 새로 만들지 않은 이유는 호출한 쪽이 할 일이 같기 때문입니다. 최신 내용을 다시 읽어 오면 됩니다.

### jsonb가 받지 못하는 값이 메모리 구현을 통과했습니다 (P2)

`unknown`으로 둔 칸은 표의 jsonb로 가는데, 메모리 구현은 `undefined`와 `bigint`와 함수와 순환 참조를 그대로 담았습니다. 테스트는 통과하는데 Postgres에서만 실패하는 상태였습니다. 메모리 구현 주석에 제가 적어 둔 "이 둘을 흉내 내지 않으면 테스트가 통과해도 실제 동작을 보장하지 못합니다"가 이 칸에는 적용되지 않고 있었습니다.

리뷰가 제안한 방법은 `JsonValue` 타입을 정의해 모든 jsonb 대응 필드에 적용하는 것이었습니다. 이 방법을 접었습니다. `ExperienceEvidenceSnapshot` 같은 기존 인터페이스는 재귀적인 `JsonValue`에 그대로 대입되지 않아 호출하는 쪽마다 캐스팅이 붙고, 캐스팅이 붙는 순간 검사가 무력해집니다.

대신 메모리 구현이 저장할 때 `JSON.parse(JSON.stringify(...))`를 한 번 거치게 했습니다. 타입이 아니라 실행 시점에 걸리므로 캐스팅으로 우회할 수 없습니다.

**지적되지 않은 결함을 하나 더 찾았습니다.** 이 수정 전에는 메모리 구현이 호출한 쪽의 객체를 참조로 붙들고 있었습니다. 호출한 쪽이 나중에 그 객체를 고치면 저장된 값이 함께 바뀝니다. 데이터베이스는 그렇게 동작하지 않으므로 이것도 같은 원인의 다른 단면입니다. JSON을 거치면서 사본이 남아 함께 해결됐고, 회귀 테스트를 따로 넣었습니다.

### 환경 파일 로드가 모든 오류를 삼켰습니다 (P2)

`apply-schema.mts`의 `loadLocalEnv`가 `catch {}`로 모든 오류를 넘겼습니다. 권한 오류로 `.env.local`을 못 읽은 상태에서 `.env`나 셸에 남은 `DATABASE_URL`이 있으면 엉뚱한 데이터베이스에 DDL을 적용하게 됩니다. `ENOENT`가 아니면 다시 던지게 고쳤습니다. 비용이 작아 같은 PR에서 반영했습니다.

제 새 코드에 같은 성격의 빈 `catch`가 더 있는지 확인했고, 이 한 곳뿐이었습니다.

## 분리한 것

### 로컬에서 프로덕션에 DDL을 적용할 수 있습니다 (P3)

이미 남겨 둔 backlog 3번과 같은 원인이라 거기에 합쳤습니다.

가드를 넣지 않은 이유를 적어 둡니다. `db/schema.sql`의 모든 문장이 `if not exists`라 지금은 여러 번 돌려도 결과가 같고 지울 것이 없습니다. 그리고 지금 프로덕션에 스키마를 적용하는 정당한 방법이 이 명령뿐이라, 프로덕션을 거부하는 가드는 의도한 사용까지 막습니다. 배포 흐름이 정해지기 전에 확인 절차를 붙이는 것은 근거 없이 형식을 늘리는 일입니다.

### `githubFetch`에 제한 시간이 없습니다 (P2)

이번 PR이 만든 결함이 아닙니다. `githubFetch`는 GitHub을 부르는 모든 경로가 쓰고, 이번 PR은 호출하는 곳을 하나 늘렸을 뿐입니다. 고치면 라우트 8곳의 동작이 함께 바뀌고, 제한 시간 값을 고르려면 커밋 목록 페이지네이션이 실제로 얼마나 걸리는지 재야 합니다. backlog 5번으로 분리했습니다.

## 그 밖에

스키마 스크립트를 다시 돌리면서 첫 호출 연결 타임아웃이 세 번째로 재현됐습니다. backlog 1번의 관찰과 같습니다.

`bigint` 회귀 테스트를 `1n` 리터럴로 썼다가 typecheck가 `target: ES2017`에서 막았습니다. 테스트는 통과했는데 `tsc`만 실패해서, 테스트만 돌리고 넘어갔으면 놓쳤을 자리였습니다. `BigInt(1)`로 바꿨습니다.
