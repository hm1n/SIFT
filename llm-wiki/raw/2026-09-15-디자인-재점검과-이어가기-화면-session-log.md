# 디자인 재점검과 이어가기 화면 세션 로그 (2026-09-15)

이슈 #115의 화면 구간입니다. 서버·클라이언트 배선은 앞 세션 로그(`2026-09-15-인터뷰-저장-복원-배선-session-log.md`)에 있습니다.

## 디자인 원본을 두 번 읽었습니다

### 1차: 무엇이 없는지 확인

사용자가 "UI 디자인이 사전에 필요한지 먼저 확인하라"고 해서 원본(`C:\Users\user\Desktop\Chat Interface Design`)을 먼저 읽었습니다. `App.tsx`는 그날 갱신돼 있었습니다.

있는 것과 없는 것이 갈렸습니다. 인터뷰 세션 행의 생김새(상태 기호, 제목, `PAAR n/4 · 날짜`)와 그 행이 놓이는 자리 둘(사이드바 Interviews, 워크스페이스 헤더의 Sessions 드롭다운)은 이미 있었습니다. 반면 저장된 인터뷰 목록을 **Repository 선택 화면 아래에 두는** 섹션, 삭제, 저장 실패·버전 충돌 안내는 없었습니다. 이슈 본문의 "확인 필요"에도 "목록 섹션의 디자인이 확정되지 않았습니다"라고 적혀 있었습니다.

사용자에게 셋을 물었고 이렇게 정해졌습니다. 목록 디자인은 원본에 먼저 넣어 주시기로, 진행도는 목록 행에 보이기로, 사이드바는 이번에 함께 채우기로 했습니다. 그동안 화면이 아닌 쪽(클라이언트 함수, 저장 대상 전송, 복원 배선, 확정 시점 저장)을 먼저 끝냈습니다.

### 2차: 갱신본 점검

사용자가 "UI 수정이 거의 완료됐다"고 해서 다시 읽었습니다. `App.tsx`가 137KB에서 154KB로 늘어 있었습니다.

요청한 셋이 모두 들어왔지만 **목록의 자리가 바뀌었습니다.** 선택 화면 아래 섹션이 아니라 사이드바로 갔고, 그 사이드바가 로그인 이후 모든 화면을 감쌉니다. 원본 주석이 "이 화면에 필요한 유일한 이동 수단은 사이드바"라고 이유를 적어 뒀습니다. 그리고 새 화면이 하나 생겼습니다. 사이드바에서 인터뷰를 고르면 대화로 바로 가지 않고 그 경험의 분석과 PAAR 진행 상태를 먼저 보는 `SessionReviewScreen`입니다.

이 점검에서 구현상의 구멍 둘을 찾았습니다. "다시 저장" 버튼이 누를 것이 없다는 것과, 인터뷰를 `completed`로 바꾸는 코드가 아예 없다는 것입니다. 둘 다 사용자 결정을 받아 앞 세션 로그의 구간에서 메웠습니다.

범위 밖 변경 셋(계정 삭제, 공개 랜딩 페이지, KO/EN 언어 선택기)도 함께 들어왔습니다. 별도 이슈로 두기로 하고 손대지 않았습니다.

## 화면 구현에서 정한 것

### 목록을 셸이 직접 그리지 않습니다

`AppShell`은 `components/shell`에 있는 공용 셸이고, 목록은 저장 계층의 값과 삭제 조작을 다루는 기능 쪽 화면입니다. 셸이 직접 그리면 공용 셸이 저장된 인터뷰의 모양을 알게 됩니다. 그래서 셸은 사이드바 Interviews 자리를 `interviews` 슬롯으로 열어 두고, `features/saved-interviews/saved-interview-list.tsx`가 그 안을 채웁니다. 슬롯이 비면 예전 빈 상태 문구를 그대로 그려 셸만 쓰는 화면도 깨지지 않습니다.

### 삭제는 화면에서 먼저 지웁니다

응답을 기다린 뒤에 지우면 누른 뒤에도 그 인터뷰가 목록에 남아 있어 사용자가 한 번 더 누릅니다. 먼저 지우고 요청을 보내되, 실패하면 목록을 다시 조회해 서버에 남아 있는 그대로를 보입니다. 지워지지 않았는데 지워진 것처럼 보이면 사용자가 지웠다고 믿고 떠납니다.

### 이어가기 화면의 PAAR 표시 범위

원본은 이어가기 화면에 블록 문장까지 그립니다. 그 패널은 이슈 #91의 범위이고 아직 저장소에 없습니다. 같은 값을 두 화면이 각자 그리면 #91에서 둘이 어긋나므로, 이번에는 블록마다 어디까지 왔는지를 기호(`✓`·`●`·`○`)로만 보입니다.

기술 토픽과 선정 이유는 근거 스냅샷에 없는 값이라 복원 응답에 후보 하나를 실어 해결했습니다(앞 세션 로그 참고). 저장된 분석이 오래전에 쓴 값이라 모양이 어긋날 수 있어, 화면은 후보를 찾지 못하면 "이 인터뷰는 그 후보의 분석 없이 저장됐다"고 알립니다. 없는 것을 있는 것처럼 그리지 않습니다.

### 이탈 확인을 조건부로 바꿨습니다

디자인 원본은 확인을 아예 없앴습니다. 저장이 있으니 잃지 않는다는 전제입니다. 그러나 저장이 꺼져 있거나 실패한 상태에서 나가면 실제로 잃습니다. 그래서 **저장되지 않은 턴이 남아 있을 때만** 묻고 문구도 "저장되지 않은 답변이 있습니다"로 바꿨습니다.

이 신호는 훅에서 흐름까지 네 층을 지나야 해서(`useExperienceInterview` → 스트림 화면 → 인터뷰 화면 → 후보 목록 → 분석 화면 → 흐름), 기존 `onInterviewActiveChange`와 같은 길로 콜백 하나를 더 흘려보냈습니다.

## 겪은 문제

### 이탈 확인이 걸리지 않았습니다

저장 실패 뒤에 사이드바의 Change repository를 누르면 확인 없이 나가 버렸습니다. 로그를 심어 보니 훅은 "저장되지 않은 턴 있음"을 올바로 올렸고, 흐름의 상태 갱신 함수도 불렸는데, **그 갱신으로 인한 재렌더가 클릭 전에 일어나지 않았습니다.** 저장 실패는 응답이 돌아오는 시점(act 밖)에 알려지므로 갱신이 다음 act까지 밀렸고, 클릭 핸들러는 직전 렌더의 값(거짓)을 보고 판단했습니다.

테스트에서만 보이는 타이밍처럼 보이지만 실제로도 같은 창이 있습니다. 응답이 돌아온 직후 다시 그리기 전에 사용자가 사이드바를 누르면 같은 일이 일어납니다. 그래서 테스트를 손보는 대신 판정에 쓰는 두 값(인터뷰 열림, 저장되지 않은 턴)을 상태에서 ref로 옮겼습니다. 두 값 모두 화면을 그리는 데 쓰지 않으므로 상태일 이유가 없었습니다.

### 접근성 이름이 겹쳤습니다

목록 행의 접근성 이름이 제목·저장소·진행도를 모두 이어 붙인 문자열이라, 삭제 버튼의 `Delete interview: <제목>`과 같은 정규식에 함께 걸렸습니다. 행을 `^제목`으로 고정해 가릅니다. 삭제 버튼 이름에 제목을 남긴 이유는 목록에 행이 여럿일 때 어느 인터뷰를 지우는 버튼인지가 이름만으로 갈려야 하기 때문입니다.

### 렌더 중 ref 갱신을 lint가 막았습니다

`fetchRef.current = fetchImpl`을 렌더 본문에서 하던 두 훅이 `react-hooks/refs`에 걸렸습니다. 효과 안으로 옮겼습니다. 같은 파일에서 "효과 안의 동기 setState"도 걸려서, 읽는 중 상태를 효과로 넣는 대신 결과에 요청 키를 함께 들고 있다가 키가 다르면 읽는 중으로 보게 고쳤습니다. 렌더에서 파생되므로 갱신이 한 번 줄고, 앞 인터뷰의 내용이 새 인터뷰 자리에 잠깐 비치는 일도 없습니다.
