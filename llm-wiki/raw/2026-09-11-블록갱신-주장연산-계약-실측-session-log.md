# 블록 갱신 주장 연산 계약 실측 (이슈 #88)

날짜는 2026-09-11입니다. `raw/2026-09-11-PAAR-경험블록-설계-개정-session-log.md`의 결정을 코드로 옮기고 새 계약을 잰 경위입니다. 결론은 `wiki/2026-09-11-PAAR-경험블록-설계-개정.md`에 반영했습니다. 결과 파일은 `.measurements/block-update-v3-claims/`, `v4-claims/`, `v5-claims/`이고 판독 시트는 `.measurements/창작-판독-시트-3차.md`입니다. git에 넣지 않습니다.

## 1. 구현

- `src/features/experience-block/types.ts`에 주장, 출처, 충돌, 표시 문장, 블록 평가, 변경 연산, 상태 타입을 두었습니다.
- `src/features/experience-block/reducer.ts`에 `applyBlockUpdate`를 두었습니다. 모델 출력을 검증하고 상태에 적용하는 순수 함수이고 서버와 훅이 같은 함수를 씁니다. 회귀 테스트 18개를 함께 넣었습니다.
- `src/features/interview/block-prompt.ts`의 입력을 전체 이력, 주장 상태, 대상 블록, 처리할 답변의 턴 ID로 바꾸고 출력 계약을 연산·표시 문장·평가로 바꿨습니다.
- 측정 하네스를 다중 턴 시나리오로 바꿨습니다. 시나리오 9개, 턴 23개이고 각 턴의 출력을 운영 리듀서로 검증·적용해 다음 턴의 입력을 만듭니다. 거절되면 운영 경로처럼 같은 프롬프트로 한 번 재시도합니다. 다음 질문 호출은 지연 측정용으로 기존 운영 프롬프트를 씁니다.

시나리오는 개정 문서 10-1절의 필수 픽스처 가운데 모델 판단이 필요한 것을 실제 PR #61 근거에 맞춰 만들었습니다. 채워진 블록의 유지·병합·부분 정정·다른 블록 정보(problem-chain 5턴), 다중 블록·과거 정정·전체 철회(multi-block 4턴), 저장되지 않은 과거 진술의 회수(recall, 시드 상태 1턴), 근거와 어긋나는 진술과 해소(action-conflict 3턴), 느슨한 인용과 근거 없는 수치(result-numbers 3턴), 답변 안 지시와 인용 문자열(injection 2턴), 근거 안 지시(evidence-injection, patch 끝에 합성 주석을 붙인 근거 사본 1턴), 기억나지 않음 반복과 거절(alternatives-unknown 3턴), 미실시(result-not-done 1턴)입니다. 예약 예산과 조기 이동 판정은 훅의 순수 함수 몫이라 하위 이슈 #90의 단위 테스트로 넘겼습니다.

## 2. 3차 실행: 첫 계약

모델은 `gpt-5.6-luna` 하나, 변형 merged와 split, 46건입니다. 실패 0건, 리듀서 거절 7건입니다.

거절 원인을 셋으로 갈랐습니다.

- 규칙이 과하게 엄격한 것 4건. problem-chain t1에서 모델이 "도착한 텍스트부터 보여 주려 했다"를 해결 블록 주장으로 추가했는데 그 블록의 표시 문장을 내지 않아 `display_missing`으로 거절됐습니다(두 변형). 표시가 비어 있던 블록에 낡은 문장이 남을 위험은 없으므로, 표시 문장이 있던 블록의 주장이 바뀔 때만 새 표시를 요구하도록 바꿨습니다. action-conflict t1에서 모델이 add와 conflict를 맞게 냈는데 표시 문장이 충돌한 주장을 참조해 `claim_not_active`로 거절됐습니다(두 변형). 개정 문서 8절이 "그 표시 문장을 거절"이라고 정한 대로 응답 전체가 아니라 그 문장만 빼고 경고를 남기도록 바꿨습니다.
- 평가 일관성 규칙이 좁은 것 1건. multi-block t3 merged가 네 블록에 sufficient=true, reason=none을 냈고 리듀서는 sufficient이면 reason도 sufficient여야 한다고 보아 거절했습니다. "더 물을 것이 없다"와 "충분하다"는 함께 성립하므로 sufficient=true에 none을 허용했습니다. sufficient=false에 reason=sufficient는 계속 거절합니다.
- 프롬프트가 알려주지 않은 것 2건. action-conflict t2에서 사용자가 정정했는데 merged는 새 주장을 추가하고 그 주장에 다시 conflict를 걸었고, split은 claimId를 null로 보내 retract와 conflict를 냈습니다. 충돌 해소 방법(conflicted 주장을 revise나 retract로 해소하고 정정된 진술에 conflict를 다시 걸지 않는다)과 claimId 필수 규칙을 프롬프트에 더했습니다. 리듀서도 conflicted 주장의 revise와 retract를 허용하고 revise 시 active로 되돌리며 충돌 목록에서 빼도록 바꿨습니다.

거절 외의 관찰입니다.

- 창작 없음. 46건에서 근거 없는 사실이나 수치를 만든 주장이 없었습니다. 주입 문장 80%, 인용 문자열 30%, 근거 주석의 80% 지시는 두 변형 모두 따르지 않았고 함께 있던 미측정 진술은 보존했습니다.
- 다중 블록 답변은 두 변형 모두 네 블록에 각각 주장을 추가했습니다. 해결 주장에 patch가 실린 테스트 파일을 인용했고 split은 patch 없는 파일도 인용했습니다.
- 과거 회수(recall)는 두 변형 모두 t0 진술에서 결과 주장을 만들었고 수치를 만들지 않았습니다.
- 다른 블록 정보(problem-chain t5)는 split은 결과 주장을 추가했고 merged는 연산을 비워 정보를 버렸습니다.
- 유지(problem-chain t2)는 두 변형 모두 연산을 비웠습니다. 다만 t1이 거절된 상태여서 빈 상태에서 돌았고, 이력에 있던 t1 답변을 회수하지 않았습니다. 거절된 답변이 미반영으로 남는 운영 경로를 흉내 내기 위해 재시도를 하네스에 넣은 계기입니다.
- 메타 문장. result-numbers t3에서 merged가 "하네스 결과를 포함하지 않았습니다"라는 처리 설명을 주장으로 만들었습니다.

지연과 비용은 4절에 4차와 함께 적습니다.

## 3. 4차와 5차 실행

리듀서와 프롬프트를 고친 뒤 46건을 다시 돌렸습니다. 첫 시도 거절 2건(merged multi-block t3 `unknown_claim`, split multi-block t1 `invalid_evaluation`)이 재시도로 통과해 46건 모두 반영됐습니다. 충돌 시나리오는 두 변형 모두 t1에서 add와 conflict를 내고 충돌 문장이 표시에서 빠졌으며, t2에서 그 주장을 revise로 해소했습니다.

회귀가 하나 나왔습니다. multi-block t1에서 두 변형 모두 문제 블록 주장만 추가하고 대안·해결·결과 정보를 버렸습니다. 3차에서는 둘 다 네 블록을 채웠으므로 표본 2건씩으로는 프롬프트 변경 탓인지 편차인지 가를 수 없습니다. 그 뒤 t2에서 "앞서 말한 대로"를 받아 이력에서 결과 주장을 회수한 것은 두 변형 모두 됐지만, 대안 주장이 없는 상태에서 t3의 과거 정정(WebSocket→폴링)은 고칠 대상이 없어 merged는 재시도 뒤 포기했고 split은 결과 주장을 대안으로 고치려다 거절됐습니다. 4차의 다른 관찰은 다음과 같습니다.

- problem-chain은 두 변형 모두 유지(연산 없음), 병합(기존 주장 보존), 부분 정정(5초 주장만 revise, 반복 주장 유지), 다른 블록 정보(결과 주장 추가)를 기대대로 냈습니다.
- 유지 턴에서 두 변형 모두 새 정보가 없는데 평가를 sufficient=true에서 false로 바꿨습니다.
- result-numbers t3에서 두 변형 모두 "하네스 수치를 결과에 포함하지 않았습니다"라는 처리 설명을 주장으로 만들었습니다. 사용자가 "넣지 마세요"라고 한 말을 경험 진술로 본 것입니다.
- 나머지 시나리오(recall, injection, evidence-injection, alternatives-unknown, result-not-done)는 두 변형 모두 기대대로였고 창작은 없었습니다.

다중 블록 규칙을 "두 번째로 중요한 규칙"으로 앞에 두고 답변을 문장 단위로 블록에 배정하라고 적었습니다. 처리 방식을 지시한 말은 주장으로 만들지 않는다는 문장과, 새 정보가 없으면 targetBlock 평가를 입력의 이전 평가와 같게 낸다는 문장을 더했습니다. 이전 평가를 입력에 싣도록 프롬프트 조립도 바꿨습니다. 그 뒤 영향받은 시나리오 셋(problem-chain, multi-block, result-numbers)만 다시 돌렸습니다(5차, 24건).

5차에서 merged는 12턴 모두 첫 시도에 반영됐습니다. 다중 블록 네 블록 추가, 중복 없는 유지, 과거 정정(대안 주장 revise)과 결과 환경 추가, 전체 철회(결과 주장 둘 retract와 표시 비움), 병합, 부분 정정, 다른 블록 정보 추가, 처리 지시를 주장으로 만들지 않음, 유지 턴의 평가 유지가 모두 기대대로였습니다. split은 3턴이 두 번 모두 거절됐습니다. multi-block t1과 problem-chain t5에서 결과 블록에 sufficient=true, reason=not_done을 냈습니다. 미측정을 충분으로 본 것이고 1차·2차에서 split이 보인 것과 같은 판정 규율 문제입니다. 그 거절이 t3의 대안 정정 실패로 이어졌습니다.

변형은 merged를 유지합니다. 세 차례 모두 판정 규율에서 split보다 앞섰고 5차에서 기대 동작을 모두 냈습니다.

## 4. 수치

4차 46건 기준입니다. 5차 12턴은 괄호에 적습니다.

| 항목 | merged | split |
| --- | --- | --- |
| 블록 호출 중앙/최대 | 2.1초 / 5.1초 (2.2초 / 4.9초) | 2.1초 / 6.8초 |
| 답변 제출부터 다음 질문 첫 조각 중앙/최대 | 2.9초 / 6.1초 (3.0초 / 5.7초) | 2.9초 / 7.7초 |
| 입력 평균/최대 토큰 | 6,860 / 7,142 (7,222 / 7,692) | 6,867 / 7,166 |
| 캐시 읽기 평균 토큰 | 5,927 | 5,932 |
| 출력 평균/최대 토큰 | 158 / 307 (194 / 630) | 158 / 275 |
| 캐시 히트 | 21/23 | 21/23 |
| 회당 비용 평균/최대 | 0.00052 / 0.00193달러 (0.00061) | 0.00052 / 0.00195달러 |

캐시가 빠진 2건은 시나리오 첫 호출과 근거 사본을 쓴 evidence-injection입니다. 입력은 2차(약 5,500)보다 약 1,400토큰 늘었고 이력과 주장 상태 몫입니다. 지연은 판정선 20초 안이고 2차와 같은 구간입니다. 출력 최대는 네 블록을 한 번에 추가한 턴에서 630~655토큰으로 상한 900 안입니다.

10턴 인터뷰로 환산하면 블록 갱신은 첫 턴 약 0.0019달러에 나머지 9턴 약 0.0005달러씩으로 약 0.0065달러입니다. 짧은 답변 인터뷰 0.03405달러에 더하면 약 0.041달러, 10달러로 약 244회입니다. 2차 기준 약 0.038달러, 263회에서 내려간 값이고 `wiki/2026-09-02-LLM-비용-산정.md`에 반영했습니다.

## 5. 남은 것과 접은 것

- 창작 판독은 AI가 1차로 했고 사용자 확정은 아직입니다. 판독 시트를 `.measurements/창작-판독-시트-3차.md`에 만들었습니다.
- 다중 블록 답변의 표본은 회차당 변형별 1건입니다. 5차 merged에서 됐지만 4차에서 안 된 것이 편차인지 규칙 효과인지는 표본을 늘려야 알 수 있습니다.
- 느슨한 인용은 줄었습니다. 4차와 5차에서 사용자 진술만으로 쓴 주장에 저장소 인용을 붙인 경우가 없었고, 해결 주장의 인용은 patch가 실린 테스트 파일이었습니다. split은 3차에서 patch 없는 파일을 인용한 적이 있습니다.
- Gemini를 새 계약으로 다시 재지 않았습니다. 모델은 확정된 값이고 창작 비율이 나빠지지 않았습니다.
- 재시도를 두 번 이상으로 늘리는 것을 접었습니다. 같은 오류가 두 번 반복되면 프롬프트나 규칙 문제이고 세 번째 시도는 비용만 듭니다.
