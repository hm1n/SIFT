# 화면 문구 레퍼런스 대조와 중앙화 세션 로그

2026-09-15. `2026-09-15-화면-문구-한국어-전환-session-log.md`를 이어받습니다. 1차 전환을 끝낸 뒤 같은 세션에서 이어진 작업입니다. 결론은 `wiki/2026-09-15-화면-문구-한국어-전환.md`의 "문구를 한 곳으로 모은 이유"와 "빈 상태 문구를 쓰는 기준" 절에 있습니다.

## 발단

1차 전환을 끝내고 사용자가 PAAR 카드의 `인터뷰가 아직 이 블록까지 오지 않았습니다.`를 지목하며 더 자연스러운 한국어 수정안을 요청했습니다.

## 세 번 틀린 제안

**1차 제안.** `아직 이 블록에 대해 묻지 않았습니다.` / `이 블록은 아직 이야기하기 전입니다.` / `아직 이 블록을 다루지 않았습니다.` 셋을 냈습니다. 사용자가 "후보 3개 다 너무 별로야. 번역체같아. **대화를 통해 블록을 채워 보세요.** 정도의 톤을 생각한 건데"라고 답했습니다.

셋 다 실패한 이유는 같습니다. 전부 **시스템이 무엇을 안 했는지 서술하는 문장**이었습니다. 원문(`The interview hasn't reached this block yet.`)의 구조를 그대로 두고 단어만 바꾼 것이라 번역체가 남았습니다. 문장의 주체와 목적을 바꿔야 했습니다.

**2차 제안.** 톤을 바꿔 `대화를 이어가면 이 블록이 채워집니다.` 등을 냈습니다. 사용자가 "대화를 진행하면 AI가 자동으로 이 블록을 채워 준다는 내용으로 몇 개 더"를 요청해 주체를 AI로 명시한 안을 다시 냈습니다.

**그 다음 질문이 이 세션의 전환점이었습니다.** 사용자가 "내가 참고하라고 한 파일 참고해서 UX 수정한 거 맞아?"라고 물었습니다.

## 확인해 보니 아니었습니다

레퍼런스 `App.tsx:1382`가 우리 `CARD_EMPTY_TEXT`와 정확히 같은 자리에 이미 한국어를 갖고 있었습니다.

```
{status === "empty" ? <p>{t.notStartedYet}</p>
  : <div>{block.content ? <p>{block.content}</p> : <p>{t.collectingInfo}</p>}</div>}

notStartedYet:  "아직 시작되지 않았습니다."
collectingInfo: "정보를 수집 중입니다..."
```

그리고 1차 전환에서 **읽지 않았던** `paar-interview-workspace.md`에는 더 나은 예시가 있었습니다.

```
│ ACTION                             ○  │
│ Not enough information yet.           │
│ 현재 AI가 구현 과정과 구체적인        │
│ 변경 내용을 확인하고 있습니다.        │
```

같은 문서 302행이 목표를 못박고 있었습니다. "사용자는 인터페이스만 보고도 **대화에 답하면 오른쪽 PAAR이 채워진다**는 관계를 이해할 수 있어야 합니다." 사용자가 두 턴에 걸쳐 요구한 것과 같은 내용이 스펙에 이미 있었습니다.

## 전수 대조

사용자가 전체를 뽑아 어긋난 곳을 다 찾으라고 지시했습니다. `TRANSLATIONS.ko` 76개 항목을 우리 코드와 맞췄습니다.

처음에는 스크립트로 자동 판정하려 했는데 실패했습니다. 문자열 포함 여부만 보니 주석과 AI 프롬프트에 우연히 같은 말이 들어 있는 경우를 "쓰고 있다"로 잘못 셌습니다(`아직 시작되지 않았습니다`가 `interview-stream-view.tsx`의 다른 문구 안에 들어 있고, `PAAR 경험`이 `block-prompt.ts`의 프롬프트에 있는 식). 자동 판정을 접고 항목별로 실제 렌더 자리를 확인하며 손으로 맞췄습니다.

결과를 다섯으로 갈랐습니다.

| 분류 | 건수 | 내용 |
| --- | --- | --- |
| A | 6 | 레퍼런스에 답이 있었는데 직접 번역 |
| B | 9 | 이슈 #128 결정으로 의도적으로 다름 |
| C | 1 | 레퍼런스 구현과 스펙이 서로 다름 |
| D | 5 | 띄어쓰기·어휘 수준의 미세 차이 |
| E | — | 레퍼런스에 대응이 없어 새로 쓴 오류 문구 |

C는 인증 오류 상태 코드입니다. `App.tsx`는 `연결 실패 / AUTH`로 번역했고 `product-flow-update.md`는 `ERROR / AUTH`로 적었습니다. 이슈 경계표가 스펙 쪽을 따랐으므로 코드를 그대로 두고 충돌 사실을 기록했습니다.

사용자가 A~E 전부 반영을 지시했습니다. B는 이슈에 기록된 사용자 결정이라 제 판단으로 뒤집지 않고 유지한 뒤 그 사실을 보고했습니다.

A1·A2에서는 레퍼런스 **구현**과 **스펙**이 갈렸습니다. `TRANSLATIONS.ko`의 `아직 시작되지 않았습니다.`는 그 자체가 상태 서술이라 사용자가 지적한 문제를 그대로 갖고 있습니다. 스펙을 따랐습니다.

E에서는 내부 용어가 화면에 새던 것을 걷었습니다. `출력 계약`, `시간 예산`, `라우트 전체`, `판단을 버렸습니다`, `이 스트림은`, `LLM`(→`AI`) 등 11건입니다. 오류 갈래 자체는 건드리지 않았습니다. 이 프로젝트는 오류 분기를 정밀하게 가르는 것이 설계의 핵심이라 문구만 고쳤습니다.

## 왜 놓쳤는지

번역 실력의 문제가 아니라 **대조할 방법이 없던 것**이 원인입니다. 문구가 39개 파일에 흩어져 있어 레퍼런스 표와 나란히 놓을 수 없었습니다. 표를 사전처럼 한 항목씩 찾아 쓰다 보니, 우리 쪽 영어가 더 길거나 구체적인 자리에서는 "대응 항목이 없다"고 판단하고 직접 번역했습니다. A의 여섯은 대응 항목이 **있었는데도** 그렇게 된 경우입니다.

## 중앙화 검토

사용자가 문구가 흩어져 있는지 묻고, 한 파일에서 UX를 계속 개선하는 방식을 검토해 달라고 했습니다.

실측했습니다. 화면 컴포넌트 18개 파일 207개, 서버·요청 계층 21개 파일 94개, 화면에 닿지 않는 내부 5개 파일 16개. 상수 테이블이 10여 개 있었지만 전부 그 문구를 쓰는 컴포넌트 파일 안에 있었고, JSX에 직접 박힌 문장이 59개, 서로 다른 파일에 복제된 문구가 14건이었습니다(`다시 시도` 6곳, `서버 설정 문제로 요청을 처리하지 못했습니다.` 4곳, `인터뷰 계속하기` 4곳).

**이슈 #128은 "번역 테이블 도입"을 이미 검토하고 기각했습니다.** 근거는 "KO 단일에서는 모든 참조가 한 단계 우회할 뿐 얻는 것이 없고, EN을 붙일 때 어차피 다시 잡는다"였습니다. 이 판단은 지금도 유효합니다. 다만 그것은 **다국어 대비**만 이유로 놓은 것이고, 지금 제기된 목적은 **문구를 계속 다듬을 자리를 만드는 것**이라 기각 사유가 다루지 않은 별개의 이득입니다. 이 구분을 분명히 하고 찬성 의견을 냈습니다.

반대 근거도 함께 적었습니다. 분기 조건(`clearsOnRetry`, `resumable`, `isSaved`)과 문구가 떨어지면 "이 문구가 언제 나오는가"를 읽으려고 두 파일을 오가야 합니다. 보간이 든 문구는 상수가 아니라 함수가 됩니다. 300개짜리 파일 하나는 그 자체로 탐색이 어렵습니다.

절충안으로 **한 파일이 아니라 화면 단위 6개 파일**을 제안했고 사용자가 이 이슈에서 진행하라고 승인했습니다.

## 중앙화 실행

`src/copy/`에 `shell.ts`, `auth.ts`, `repository.ts`, `candidates.ts`, `interview.ts`, `saved.ts`와 `README.md`를 만들었습니다.

담는 기준은 **그 문자열이 DOM에 닿는가**입니다. `error.message`를 그대로 그리는 자리가 둘뿐이라 그 둘로 흘러드는 서버 문구까지 담고, `kind`만 읽히는 오류의 원문은 도메인 코드 옆에 남겼습니다.

순환 참조가 걱정이었습니다. `copy/interview.ts`가 `features/interview/errors.ts`의 타입을 필요로 하는데 `errors.ts`도 문구를 필요로 합니다. 타입은 전부 `import type`으로 가져와 런타임 순환이 생기지 않게 했습니다. `evidence-verifiability.ts`처럼 파일 전체가 문구였던 것은 re-export만 남기고 판별 규칙 주석을 그 자리에 남겼습니다.

`code-panel.tsx`의 `STATUS_MARK`는 `{mark, label}` 구조였는데 `mark`(`A`/`M`/`D`)는 화면 기호이고 `label`만 번역 대상이라 둘을 갈랐습니다. 기호는 컴포넌트에, 이름은 `copy/interview.ts`에 뒀습니다.

작업 도중 lint가 미사용 import 3건을 잡았습니다(`InterviewStreamPhase`, `BlockUpdateFetchErrorKind`, `EvidencePatchOmittedReason`). 문구와 함께 타입 사용처가 옮겨 가면서 남은 것입니다.

## 회귀 방지 장치

문구를 모으는 것만으로는 같은 실수가 다시 납니다. 대조를 **테스트가 대신하게** 만들었습니다.

`src/copy/reference-ko.test.ts`가 `TRANSLATIONS.ko` 항목을 고정하고, 항목마다 우리가 그 문구를 쓰는지 의도적으로 다르게 쓰는지를 기록합니다. 쓰는 항목 33개는 `toContain`으로, 다르게 쓰는 항목 18개는 `not.toContain`으로 확인합니다. 후자가 중요합니다. 누가 레퍼런스 문구로 되돌리면 테스트가 깨지고, 그때 표의 사유부터 다시 보게 됩니다.

레퍼런스 저장소가 이 저장소 밖에 있어 테스트가 직접 읽을 수 없습니다. 값을 테스트 파일에 옮겨 고정한 것은 그 때문이고, 레퍼런스가 갱신되면 이 표도 손으로 갱신해야 합니다. 이 비용을 받아들였습니다.

**장치가 실제로 무는지 확인했습니다.** `PAAR_CARD_EMPTY_COPY.pending`을 레퍼런스 문구로 되돌려 보니 `'notStartedYet': 의도적으로 다르게 씁니다`가 실패했고, 되돌리니 51개가 다시 통과했습니다.

## 접은 대안

- **한 파일에 전부.** 300개를 한 파일에 넣으면 "어디 있는지 모르겠다"가 "어디쯤인지 모르겠다"로 바뀔 뿐이라고 보고 화면 단위로 나눴습니다.
- **`t()` 헬퍼와 키 기반 조회.** 키를 통해 문구를 찾는 구조는 다국어를 전제합니다. KO 단일에서는 타입이 주는 안전만 잃습니다. 이름 있는 상수를 그대로 export하는 쪽을 골랐습니다.
- **레퍼런스 파일을 테스트가 직접 읽기.** 저장소 밖 절대 경로에 의존하게 되어 다른 기계와 CI에서 깨집니다. 값을 옮겨 고정했습니다.
- **`request.ts`들의 검증 메시지도 함께 모으기.** 34건이 더 들어오지만 화면에 닿지 않습니다. 모으면 `src/copy/`의 판별 기준("DOM에 닿는가")이 흐려집니다.
