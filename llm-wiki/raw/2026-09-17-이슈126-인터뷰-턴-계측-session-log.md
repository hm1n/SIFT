# 이슈 #126 인터뷰 턴 단위 계측 세션 로그

## 1. 선행 조건이 순환이라는 것을 먼저 확인했습니다

이슈 #126은 "1차 계측 데이터로 인터뷰까지 도달하는 사용자가 있다는 것을 확인한 뒤에 시작한다"는
선행 조건을 달고 있습니다. 배포하고 데이터를 며칠 모은 뒤 시작하자고 계획을 세웠는데, 사용자가
"이벤트를 심어놔야 기록을 할 거 아니야"라고 지적했습니다.

배선된 이벤트를 세어 확인했습니다. 10종이고 전부 분석 단계에서 끝납니다.

| 이벤트 | 위치 |
| --- | --- |
| login_view | `login-screen.tsx:38` |
| login_start | `auth-transition.tsx:55` |
| login_result | `analytics-session.tsx:61` |
| repo_list_loaded | `repository-client.ts:22` |
| analysis_requested | `repository-flow.tsx:143` |
| analysis_stage_done·succeeded·empty·failed | `repository-analysis-view.tsx:137` |
| analysis_retried | `repository-analysis-view.tsx:230` |

퍼널의 마지막이 `analysis_succeeded`이고 그다음이 비어 있습니다. 도달 여부에 답할 이벤트는
`interview_started`인데 그것이 #125에서 미뤄 둔 2종 중 하나였습니다. 선행 조건을 확인하려면 그
조건에 답할 이벤트를 먼저 만들어야 한다는 것이 드러나 순서를 뒤집었습니다.

접은 대안은 `analysis_succeeded` 건수로 인터뷰 도달을 추정하는 것입니다. 그 값은 후보 화면까지 온
사용자 수이고, 이 프로젝트가 금지한 대리 지표 판별에 해당해 접었습니다.

## 2. 이슈 본문의 전제가 이미 바뀌어 있었습니다

이슈 Approach는 이탈 확인 대화의 두 선택지를 각각 이벤트로 남기라고 적고 있습니다.
`repository-flow.tsx:119`를 읽어 보니 `wasInterviewOpen && hasUnsavedRef.current`일 때만 확인 대화가
나타납니다. #115와 #127이 저장을 넣으면서 바뀐 것입니다.

확인 대화만 측정하면 저장되지 않은 답변을 버린 경우만 계산합니다. Goal인 "중도 종료가 몇 번째 턴에
몰리는지"에 답하지 못하므로, 이탈은 `navigate` 안의 이동 경로에서 계산하기로 했습니다.

접은 대안은 `InterviewScreen` 언마운트에서 계산하는 것입니다. prop 전달 40줄쯤이 사라지지만 Strict
Mode가 개발에서 두 번 마운트하므로 이벤트가 두 번 전송됩니다. 기존 `onInterviewActiveChange`가
언마운트 시점을 쓰면서도 문제가 없는 이유는 그 값이 멱등한 bool이기 때문입니다.

## 3. 후보 화면 3종을 제외했습니다

`experience-candidate-list.tsx:106`이 master-detail이라 `useState(() => items[0]?.candidate.sha)`로
첫 후보가 자동 선택됩니다. `candidate_detail_opened`를 `selectedSha` 변화에 연결하면 사용자가
아무것도 하지 않아도 1건이 전송됩니다.

`experience-candidate-detail.tsx:161`의 근거 목록 "View all"이 이 화면에서 펼칠 수 있는 유일한
것이고, 항목 수가 임계값을 넘을 때만 버튼이 나타납니다. `evidence_type` 디멘션의 값이 한 종류뿐이
됩니다.

코드보다 정의를 먼저 고쳐야 하는 일이라 backlog 2번으로 옮겼습니다.

## 7. PR #139 리뷰 1라운드에서 계측 값이 실제로 틀린 것을 실측했습니다

CodeRabbit이 `optionsRef.current.turnsUsed`가 요청 시점에 한 턴 뒤처진다고 지적했습니다. 두 턴짜리
프로브를 붙여 확인했습니다.

```
PROBE question_shown: [0,0]
PROBE answer_submitted: [1]
```

두 번째 질문도 턴 0으로 기록됩니다. `onBeforeQuestion`의 `.then()`이 `setTurnsUsed` 직후 같은 틱에
`start()`를 호출하는데, 옵션을 옮겨 담는 effect는 렌더가 끝난 뒤에 돌기 때문입니다.
`question_shown`의 턴이 오르지 않아 "질문이 몇 번째 턴에 나왔는지" 분포가 통째로 쓸 수 없습니다.

같은 지적의 다른 면이 하나 더 있었습니다. `READY_TO_FINISH_PROMPT`는 스트림 없이 삽입되므로
`questionShownAtRef`를 갱신하지 않습니다. 보충 답변의 `think_time_ms`에 앞 질문을 읽고 답한 시간이
들어가고, 턴으로 세지 않는 답변이 `turnsUsed + 1`로 기록됩니다.

둘 다 "계측 값을 사건과 함께 나르지 않고 주변 상태에서 읽는다"는 한 원인이라 한 묶음으로 고쳤습니다.
턴 값을 `InterviewQuestionOutcome`의 `ask`에 실어 요청과 함께 나르고, 완료 대기 안내를 넣는 그 한
곳에서 보충 답변 표시를 세웁니다. 두 결함마다 회귀 테스트를 하나씩 붙였고 고치기 전에 실패하는 것을
확인했습니다.

접은 수정이 하나 있습니다. `reportCompleted`를 `flushPendingSaves()` 뒤로 옮기라는 지적입니다.
이슈 Goal이 "그만둔 시점에 블록이 몇 개 채워져 있었는지"이고 지금 코드는 종료를 누른 순간의 값을
기록합니다. 그 값은 화면의 `PAAR n/4`와 같은 함수에서 나오므로 사용자가 본 것과 일치합니다. 정리
뒤로 옮기면 사용자가 본 적 없는 값을 기록하게 되고, 설계 9절이 구분한 "종료"와 "정리 완료"를 하나로
합치게 되어 접었습니다.
