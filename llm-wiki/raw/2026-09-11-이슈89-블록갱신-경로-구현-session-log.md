## 확인 필요 항목 해소: `@ai-sdk/openai` 캐시 옵션 노출 여부

핸드오프가 남긴 확인 필요 항목입니다. 웹 검색(ai-sdk.dev 공식 문서)과 설치한 패키지의 타입 정의를 직접
읽어 확인했습니다.

- `@ai-sdk/openai`는 설치되어 있지 않았습니다(`package.json`에 `@ai-sdk/google`, `@ai-sdk/groq`만 있었음).
  `npm view @ai-sdk/openai version`으로 최신 버전(4.0.65)을 확인해 `ai@^7.0.68`과 함께 설치했습니다.
- `node_modules/@ai-sdk/openai/dist/index.d.ts`를 읽어 `openaiLanguageModelResponsesOptionsSchema`에
  `promptCacheKey`, `promptCacheOptions: {mode: "explicit"|"implicit", ttl: "30m"}`,
  `promptCacheRetention`, `reasoningEffort`가 있음을 확인했습니다. `gpt-5.6-luna`도
  `OpenAIResponsesModelId` 유니온에 실제로 포함되어 있습니다.
- 측정 하네스(`block-update.measure.mts`)가 raw fetch로 쓴 `prompt_cache_breakpoint`(콘텐츠 파트 단위,
  근거 블록 뒤에만 경계를 두는 것)에 대응하는 옵션은 `.d.ts`에 없었습니다(`breakpoint`, `cache_control`,
  `cacheControl` 문자열로 grep해도 매치 없음). 즉 이 SDK 버전은 호출 단위 모드 전환만 가능하고, 근거
  블록 뒤에만 정확히 경계를 두는 세밀한 제어는 노출하지 않습니다.
- 결론: 서버 경로는 `providerOptions.openai.promptCacheOptions.mode: "explicit"`만 배선하고, 측정
  하네스가 20건 중 18건 히트를 낸 것과 같은 수준의 캐시 적중을 보장하지 않는다고 코드 주석과 위키에
  남겼습니다. 설계 문서(5절)가 "캐시 적중 유지를 보장하지 않는다"고 이미 못 박아 둔 원칙과 맞습니다.

## 구현

계획을 `EnterPlanMode`로 세우고 사용자 승인을 받은 뒤 진행했습니다. 계획 단계에서 결정이 필요했던
지점 하나를 `AskUserQuestion`으로 확인받았습니다.

**결정: 응답 계약.** 설계 문서 3-1절 "훅은 그 결과를 같은 리듀서로 다시 적용합니다"를 두 갈래로 해석할
수 있었습니다. (案 A) 서버가 계산한 새 `ExperienceBlockState` 전체를 응답에 실어 돌려주고 훅이 그대로
교체하는 안과, (案 B) 서버가 검증만 통과시킨 모델 원본 출력을 돌려주고 훅이 `applyBlockUpdate`를 자신의
로컬 상태에 대해 한 번 더 호출하는 안입니다. 案 B는 클라이언트 로컬 `nextClaimSeq`가 서버와 어긋나는
경합 상황에서 결국 서버 상태를 다시 신뢰해야 해서 案 A로 수렴한다고 판단해 案 A를 제안했고, 사용자가
그대로 확정했습니다.

파일 구성은 계획 파일(`C:\Users\user\.claude\plans\federated-exploring-forest.md`, 세션 종료 후 정리
대상)에 자세히 있고 요약하면 다음과 같습니다.

- `src/features/experience-block/llm-provider.ts`: OpenAI provider 생성. 로컬 전환은 기존
  `experience-candidates/llm-provider.ts`의 `requireLocalModel`/`resolveLocalLlm`을 그대로 재사용(export
  추가).
- `src/features/experience-block/errors.ts`: 요청 단계 거절 분류(`invalid_request` 등)와
  `block_update_rejected`(리듀서 거절)를 더한 상태 코드 표. `interview/errors.ts`와 같은 `Record`
  패턴으로 컴파일 타임에 누락을 잡습니다.
- `src/features/experience-block/request.ts`: 요청 본문 검증. 이력은 턴 단위(`BlockUpdateTurn`)라서
  질문 생성 경로의 메시지 단위 상한(`INTERVIEW_HISTORY_MAX_ITEMS`=18)을 그대로 못 쓰고, 마지막 답변까지
  이미 이력에 실린다는 설계 5절 전제에 맞춰 턴 상한을 `INTERVIEW_MAX_TURNS`(10)로 다시 유도했습니다.
  주장 상태(`state`)의 `display`·`evaluation`이 네 블록 키를 모두 갖추도록 검증하는데, 리듀서가
  `state.display[block]`류 접근을 그 전제로 짜여 있어 빠지면 undefined 접근으로 깨지기 때문입니다.
- `src/features/interview/block-prompt.ts`: 측정 하네스가 116건 호출에 실제로 검증한 JSON Schema
  리터럴을 `BLOCK_UPDATE_OUTPUT_JSON_SCHEMA`/`blockUpdateOutputSchema`로 옮겨 서버 경로와 공유합니다.
  측정 스크립트 자체는 고치지 않았습니다(수동 실측 스크립트이고 이번 이슈 범위 밖).
- `src/features/interview/llm-error.ts`: `NoObjectGeneratedError` 처리를 추가했습니다. 기존 주석이
  "스트리밍 호출이라 이 분류가 없다"고 적어 둔 이유가 블록 갱신 경로(구조화 출력)에는 적용되지 않아서
  주석도 함께 고쳤습니다.
- `src/app/api/interview/experience-block/route.ts`: `POST` 핸들러. 테스트 가능성을 위해 실제 로직을
  `handleExperienceBlockUpdate(request, {generate?})`로 분리해 `generate`를 주입할 수 있게 했습니다.
  `stream/question-route.ts`가 이미 쓰던 패턴(모듈 mock 대신 함수 주입)을 그대로 따랐습니다.
