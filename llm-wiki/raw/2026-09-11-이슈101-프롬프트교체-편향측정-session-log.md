## 프롬프트 교체

이슈 #101에서 확정한 다음 기준으로 교체했습니다.

> 각 입력은 PR 묶음 또는 단일 커밋입니다. 하나의 완결된 경험이라고 가정하지 마세요. 제공된 정보에서 기술적 선택이나 문제 해결을 확인할 단서가 있는 항목을 후속 diff 검토 대상으로 추천하세요. 변경 규모나 커밋 수만으로 설명 가치를 판단하지 마세요. 제공되지 않은 문제 상황, 선택 이유, 성과를 추정하지 마세요.

추천 상한과 전수 응답 계약은 기존 서버 검증과 맞아야 하므로 다음 지시를 뒤에 유지했습니다.

> 추천 개수는 최대 `candidateLimit`개까지입니다. 이 상한은 고르는 개수에만 걸리며 decisions 배열의 길이를 줄이는 데 쓰면 안 됩니다. 추천하지 않는 나머지는 미분류로 담으세요.

최소 1개 하한과 입력이 상위 후보이므로 고를 것이 없을 수 없다는 문장은 제거했습니다. 서버의 `candidateLimit >= 1` 검사는 상한의 유효성 검사이므로 바꾸지 않았습니다.

## 교체 후 측정

| 저장소 | Stage A 입력 | 5회 후보 수 | 전수 응답 계약 | `unknown_sha`·`schema_validation` |
| --- | ---: | --- | --- | --- |
| `hm1n.github.io` | 12개 | 4, 4, 4, 4, 4 | 5회 모두 충족 | 0회 |
| `Algorithm` | 1개 | 0, 0, 0, 0, 0 | 5회 모두 충족 | 0회 |

`hm1n.github.io`의 후보 네 개는 교체 전과 같았습니다. 프롬프트 교체가 이 표본의 유효 후보를 떨어뜨리지 않았습니다. `Algorithm`은 입력 한 개를 미분류로 반환해 후보 0개가 정상 결과가 되었습니다. 모든 회차가 전체 판단 단위를 정확히 한 번 반환했고 SHA 앞 7자리 식별자 때문에 발생한 오류는 없었습니다.

이번 모델과 고정 입력에서는 회차별 후보 분산이 없었습니다. 후보 수가 0을 포함해 매회 달라져야 한다는 기대보다, 근거가 있는 혼합 저장소와 근거가 부족한 대조군을 일관되게 갈랐는지가 더 직접적인 판정 근거가 되었습니다.

## 단일 커밋 편향 측정

| 저장소·종류 | 전체 | 평균 점수 | Stage A 입력 | 예산 제외 | 제외율 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `hm1n.github.io` PR 묶음 | 3 | 2.00 | 3 | 0 | 0% |
| `hm1n.github.io` 단일 커밋 | 9 | 0.78 | 9 | 0 | 0% |
| `Algorithm` 단일 커밋 | 435 | 0.0023 | 1 | 434 | 99.77% |

`hm1n.github.io`의 점수 분포는 PR 묶음이 4점·2점·0점, 단일 커밋이 2점 3개·1점 1개·0점 5개였습니다. PR 묶음은 `many_commits` 같은 규모 신호를 받을 수 있어 평균 점수가 더 높았지만 전체 12개가 예산 안에 들어와 실제 제외 차이는 없었습니다.

`Algorithm`은 workflow 추가 커밋 하나만 `infrastructure_added` 신호로 1점을 받았습니다. 나머지 434개는 모두 0점 동점이었습니다. 1점 단위가 먼저 들어간 뒤 0점 동점 묶음 전체가 입력 상한을 넘었기 때문에 `over_input_budget`으로 함께 제외되었습니다. 제외된 434개 가운데 433개는 BaekjoonHub 자동 채점 커밋이고, 나머지 하나는 `0759fe2` `Change default branch from 'master' to 'main'`입니다. 이 커밋은 workflow의 감시 브랜치를 한 줄 바꾼 변경이라 배포 브랜치 전환을 질문할 단서는 있지만, 이 diff만으로 문제 상황이나 선택 이유와 성과를 확인할 수 없어 이 표본에서 제외된 것은 받아들일 수 있다고 판단했습니다.

두 저장소 모두 상세 입력 순서를 역순으로 바꿔 다시 선별했을 때 선택된 `unitId` 집합이 달라지지 않았습니다. `hm1n.github.io`는 전부 선택됐고, `Algorithm`은 1점 단위와 0점 동점 묶음의 경계가 분명했기 때문입니다. 측정한 두 표본에서는 동점 입력 순서 편향이 결과로 나타나지 않았습니다.

## 결론과 문서 반영

- 새 프롬프트를 채택합니다. 혼합 저장소의 기존 후보를 유지하면서 근거가 부족한 입력의 후보 0개를 정상 결과로 만들었습니다.
- 20회 모두 전수 응답 계약을 지켰고 SHA 7자리 매칭 오류는 없었습니다.
- PR 묶음이 단일 커밋보다 높은 점수를 받기 쉬운 구조는 혼합 저장소의 평균 점수에서 확인됐습니다. 다만 이 표본에서는 입력 예산이 충분해 단일 커밋이 빠지지 않았습니다.
- `Algorithm`의 99.77퍼센트 제외는 종류 자체보다 434개가 모두 0점 동점이고 입력 상한이 200인 데서 생겼습니다. 이슈 #101의 Non-goal에 따라 점수식과 상한은 바꾸지 않습니다.
- 자동 커밋 도구 서명을 블랙리스트에 추가하는 문제와 점수식 변경은 별도 후속 판단으로 남깁니다.
- Notion의 `경험 후보 생성` 기능 정의서를 현재 계약에 맞게 갱신했습니다. 판단 단위를 경험 자체가 아닌 근거 범위로 정의하고, PR 묶음과 단일 커밋, 후보 0개, Stage A와 Stage B, Loading·Empty·Error 상태를 반영했습니다.
