# PAAR 경험 블록 턴 진행 실측 (이슈 #90 핸드오프 이어받음)

날짜는 2026-09-11입니다. `wiki/2026-09-11-PAAR-경험블록-턴진행-실측-핸드오프.md`가 남긴 실측 대상을
이어받았습니다. 결과 파일은 `.measurements/block-update-2026-09-11/`이고 git에 넣지 않습니다.

## 1. 준비

- `.env`가 없어 비어 있는 파일로 만들었습니다. `--prepare`는 `GITHUB_TOKEN`이 없어도 `gh auth token`으로
  대체되어 무료로 끝났습니다(공개 PR hm1n/demian #61, SHA `b62f0207...`).
- `--dry-run`으로 46건의 프롬프트 바이트만 먼저 확인했습니다. 실패 0건.
- 사용자가 `.env`에 넣어 준 OpenAI 키가 `OPEN_AI_API_KEY`로 저장돼 있었는데 측정 스크립트는
  `OPENAI_API_KEY`(언더스코어 없음)를 읽습니다. 이름이 다른 이유를 사용자에게 확인하니 오타였고,
  같은 값으로 `OPENAI_API_KEY` 줄을 추가했습니다. 다른 곳에서 `OPEN_AI_API_KEY`를 쓰는 코드는
  없었습니다(`src` 전체 검색 결과 0건).
- 이 확인 과정에서 실수로 `.env`를 `od -c`로 열어 키 값 일부가 세션 로그(대화)에 그대로 찍혔습니다.
  외부로 전송되지는 않았지만 사용자에게 바로 알렸습니다. 이후 파일 내용을 직접 출력하지 않고
  `grep -c`/`grep -n` 등 존재 여부만 확인하는 방식으로 바꿨습니다.

## 2. 시나리오 보강 (핸드오프 3번 항목)

핸드오프 문서가 지적한 대로 `block-update.measure.mts`의 모든 `ScenarioTurn`이 `targetElement`를
비워 둬 실행부가 기본값 `"a"`로만 돌고 있었습니다. 기존 시나리오 셋을 골라 `targetElement: "b"`를
추가했습니다.

- `problem-chain` t4(5초 수치를 어떻게 확인했는지 묻는 턴): `targetElement: "b"`
  (`기존 방식이 만든 구체적인 비용이나 한계`).
- `action-conflict` t3(순서·종료 처리를 묻는 턴): `targetElement: "b"`(`코드에서 확인되는 구체적인 구현`).
- `result-not-done` t1(결과를 어떻게 확인했는지 묻는 턴): `targetElement: "b"`(`그것을 확인한 방법`).

편집 도구(`smart_edit`)로 라인 치환을 하다가 첫 시도에서 `problem-chain` t3 줄을 통째로
`targetElement:"b"` 버전으로 덮어써 t4 줄이 사라지는 실수가 있었습니다. 바로 발견해 t3(원래대로)와
t4(targetElement 추가)를 복원했습니다. 두 번째 편집에서는 유니코드 이스케이프를 잘못 써 "첨부된"이
"첵부된"으로 들어간 오타가 있었고 다시 고쳤습니다. `--dry-run`으로 세 시나리오만 다시 돌려 프롬프트가
정상 생성되는 것을 확인한 뒤 `npm run typecheck`와 `npm run lint`를 통과시켰습니다.

## 3. 실행

`--out=.measurements/block-update-2026-09-11 --budget=1`로 46건(시나리오 12개 × 변형 2개, 일부
시나리오는 턴 수가 달라 정확히는 turnId 기준 23턴 × 2변형)을 실행했습니다. 실패 0건, 리듀서 거절
7건(재시도로 5건 통과, 2건은 재시도까지 실패), 총 비용 $0.0239(budget 1 대비 여유 큼).

## 4. 관찰

### targetResponse 분류 (핸드오프 2번 항목)

46건의 `targetResponse`를 사람이 기대한 반응과 대조했습니다. `unknown`(기억나지 않음 반복),
`refused`(명시적 거절), `not_done`(미실시·미측정 진술), `unanswered`(테스트 문자열 인용처럼 질문과
무관한 답), `provided`(직접 답)까지 다섯 값 모두 기대와 어긋난 사례가 없었습니다. 경계 사례 하나는
`problem-chain` t4로, 사용자가 "5초는 재지 않았고 체감입니다. 매 턴 반복된 건 맞습니다"라고 답해
반복 사실은 확인해 줬지만 정량치는 철회했는데, 두 변형 모두 `not_done`을 냈습니다(반복 사실만으로
`provided`를 줄 수도 있는 경계라 사람 판단으로 재확인할 가치가 있습니다).

### targetElement=b 겨냥 (핸드오프 3번 항목)

세 턴 모두 `targetElementPurpose`가 가리키는 의미로 반응했습니다. `result-not-done` t1("결과는 어떻게
확인했나요?" → b="확인한 방법")은 `not_done`, `action-conflict` t3("순서와 종료는 어떻게 처리했나요?" →
b="구체적인 구현")는 `provided`로 구현을 서술, `problem-chain` t4는 위 경계 사례입니다. 모델이 `a`
목적으로 되돌아가 엉뚱한 반응을 내는 사례는 없었습니다.

### 리듀서 거절 2건 (재시도로도 실패)

`merged-problem-chain-t1`과 `split-multi-block-t3`가 재시도 두 번 모두 `invalid_evaluation`으로
거절됐습니다. 두 경우 모두 모델이 targetBlock이 아닌 다른 블록(각각 action, alternatives)에 대해
`ops`는 냈지만(주장 추가·정정) 그 블록의 `evaluation`(또는 표시 문장)을 함께 내지 않았습니다. 이
가드(targetBlock·영향받은 블록의 평가 누락을 거절)는 `wiki/2026-09-11-PAAR-경험블록-후속-backlog.md`
1번 항목이 지적했던 결함을 막기 위해 이번 세션 코드에 이미 들어 있었고, 실측에서 실제로 두 번
작동했습니다. 다만 운영 경로의 재시도가 "같은 프롬프트로 한 번 더"이기 때문에 같은 누락이 그대로
반복돼 결국 그 턴의 정보(문제 답변 속 해결 정보, 결과 답변 속 대안 정정)가 버려졌습니다. 표본 46건
중 2건(4.3%)이라 재시도 프롬프트를 바꿀 가치가 있는지는 표본을 더 봐야 합니다. 후속으로 backlog에
남깁니다.

### 토큰·비용 변화 (핸드오프 4번 항목)

`targetElement`·`targetElementPurpose`(입력)와 `targetResponse`(출력) 추가로 캐시 히트 턴 기준 입력이
평균 6,860→7,303토큰(+443, +6.5%), 출력이 평균 158→191.7토큰(+34, +21%)으로 늘었습니다. 회당 비용은
평균 $0.00052→$0.000459로 오히려 소폭 낮아졌는데(표본 차이로 보이고 원가 구조상 입력 6.5% 증가가
출력 단가 우위를 상쇄하지 못할 정도는 아님), 어느 쪽이든 10턴 인터뷰 전체 비용에 끼치는 영향은
무시할 만합니다. `wiki/2026-09-02-LLM-비용-산정.md`에 반영했습니다.

## 5. 남은 것

  못했습니다.** 이 측정 하네스는 `block-update` 모델 호출 하나하나를 독립적으로 재현할 뿐
  `selectNextTarget`이 만드는 턴 배분·10턴 소진 흐름을 재현하지 않습니다. 핸드오프 문서가 이미 밝힌
  대로, 이 값은 `npm run dev`로 `useExperienceInterview`를 사람이 직접 돌리며 확인해야 합니다.
  `interview-screen.tsx`가 아직 없어 임시 테스트 페이지가 필요하고, 이 세션에서는 만들지 않았습니다.

  선행 세션(`raw/2026-09-11-블록갱신-주장연산-계약-실측-session-log.md`)처럼 별도 판독 시트를 만들어
  사람이 확정하지는 않았습니다.
