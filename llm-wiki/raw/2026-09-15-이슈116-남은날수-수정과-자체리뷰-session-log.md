## 1. `CRON_SECRET`을 어디서 확인하느냐는 질문

사용자가 물었습니다. 발급처가 있는 값으로 오해할 수 있는 이름이라 세 가지를 확인해 답했습니다.
Vercel Project Settings의 Environment Variables에 직접 넣는 값이고(`npx vercel env ls`는 이름만
보입니다), 로컬은 `.env`이며 이 워크트리에는 `.env`도 `.env.local`도 없고, 값이 없으면
`api/cron/purge/route.ts:25`가 401을 냅니다.

값 조건으로 셋을 들었습니다. 길고 무작위일 것(이 경로에는 호출 횟수 제한이 없습니다), ASCII만 쓸 것
(한글은 HTTP 헤더에 실리지 않고 공백·따옴표는 `.env` 파서와 셸이 다르게 읽습니다), 깃에는 들어가지
않는다는 것(`.gitignore:34`의 `.env*`). 생성 명령은 제가 돌리지 않고 사용자에게 넘겼습니다. 셸에
비밀값 원문을 찍지 않는 이 프로젝트의 규칙 때문이고, Claude Code 프롬프트에서 `!`로 돌리면 결과가
대화에 남는다는 점도 함께 알렸습니다. 사용자가 직접 생성해 Vercel에 넣었습니다.

## 2. 남은 날수가 91일로 보이던 문제

사용자가 화면 이미지와 함께 물었습니다. 오늘 진행한 인터뷰인데 배너가 `91 days until automatic
deletion`이라고 적혀 있었습니다.

`daysUntilDeletion`이 계산하는 자리는 하나뿐이고 `+1`을 하는 곳은 없었습니다.

```ts
return RETENTION_DAYS - Math.floor((now - opened) / DAY_MS);
```

방금 연 인터뷰는 `floor`가 0이라 90이 나와야 합니다. 91이 나오려면 `floor`가 `-1`이어야 하고, 그것은
`opened > now`일 때뿐입니다. 1밀리초만 앞서도 `floor(-0.00000001) = -1`입니다.

시간대 문제를 먼저 의심했습니다. 칸이 `timestamp`인데 KST 값을 UTC로 읽으면 9시간 앞서 보이고 그러면
정확히 `-1`이 나옵니다. `db/schema.sql:31`을 보니 `timestamptz`라 이 가설은 틀렸습니다.

남은 설명은 시계가 둘이라는 것입니다. `opened_at`을 찍는 것은 `neon-store.ts:367`의 `set opened_at =
now()`로 Neon 서버 시계이고, 날수를 세는 것은 `daysUntilDeletion`의 기본값 `Date.now()`로 브라우저
시계입니다. 이 PC 시계가 Neon보다 조금 느리면 방금 연 인터뷰가 미래로 보입니다.

고친 방법은 경과 시간을 0에서 자르는 것입니다.

```ts
const elapsed = Math.max(0, now - opened);
return RETENTION_DAYS - Math.floor(elapsed / DAY_MS);
```

시계를 맞추거나 서버가 남은 날수를 계산해 내려보내는 대안을 접었습니다. 앞은 우리가 통제할 수 없고,
뒤는 계산 자리를 늘리면서 얻는 것이 "90을 넘지 않는다" 하나뿐입니다. `retentionCutoff`는 90일보다
오래된 줄만 지우므로 보관 기간보다 큰 수는 어느 경우에도 사실이 아닙니다.

회귀 테스트는 `NOW + 2초`를 넣어 `RETENTION_DAYS`가 나오는지 봅니다. 기존 테스트 여섯은 모두 `NOW`
이하만 보고 있어 이 입력을 아무도 막지 않았습니다.

## 3. 자체 코드리뷰 1라운드

`110520d..HEAD`의 프로덕션 코드 약 1,800줄을 근본 원인별로 묶어 봤습니다. P0과 P1은 없었습니다.

### 고친 것 (P2 둘)

**`appendHistory` 주석이 코드와 반대였습니다.** `neon-store.ts`의 주석이 "블록 버전 조건이 없습니다"
라고 적고 그 이유까지 설명하는데, 같은 함수의 SQL에는 `and s.block_version = $4`가 있었습니다.
어느 쪽이 맞는지 `store.ts`의 `AppendHistory.expectedBlockVersion` 주석("저장된 값이 이와 다르면
쓰지 않습니다")과 in-memory 구현으로 확인했습니다. 둘 다 조건이 있는 쪽이라 조건을 남기고 주석을
고쳤습니다. 조건을 빼는 쪽은 접었습니다. 버전이 어긋났다는 것은 다른 탭이 이미 저장했다는 뜻이고 그
저장에 여기 붙이려는 턴이 들어 있어서, 빼면 같은 질문과 답변이 대화에 두 번 남습니다.

**선택 화면에서 적은 기여 항목이 저장된 분석 경로에서 조용히 버려집니다.** 한 원인이 세 곳에서
드러났습니다. (1) 저장된 분석을 찾으면 `contributionItems`를 쓰지 않고 그립니다. (2)
`repository-flow.tsx:172`의 `openAnalysis()`가 빈 배열을 넘기므로 그 화면에서 다시 분석하면 기여
항목 없이 돕니다. (3) 그렇게 저장된 새 분석이 그 저장소의 최신 분석이 됩니다.

세 가지를 다 고치는 것은 기여 항목을 다시 받는 자리를 만드는 일이라 이번 범위를 넘습니다. 비용이
아주 작은 (1)만 했습니다. `SavedAnalysisNotice`가 `contributionItems.length > 0`일 때 한 문장을 더
말합니다. 회귀 테스트는 적었을 때 뜨는 것과 안 적었을 때 안 뜨는 것 둘입니다.

### 후속으로 분리한 것 (P3 셋, backlog 13·14·15번)

- 분석 줄의 보관 기준이 `created_at`입니다. 인터뷰는 `opened_at`으로 "안 연 지 90일"을 재는데 분석만
  대리 지표입니다. 매일 열어 보는 분석도 90일이면 사라지고 남은 기간 표시도 없습니다. `repository_analysis`에
  칸을 더하는 스키마 변경이 필요해 미뤘습니다.
- `appendTurn`이 `opened_at`을 갱신하지 않습니다. 한 탭에서 90일 내내 대화만 이어간 인터뷰는 쓰는
  도중에 지워집니다. 사이드바에서 다시 열면 갱신되므로 실제로 닿기 어려운 경로라 미뤘습니다.
- `appendHistory`가 `progress`를 저장하지 않습니다. 모델이 실패한 턴의 재질문 예산이 복원 때
  되살아납니다. 그 턴은 블록에 반영되지 않았으니 예산을 쓴 것도 아니라 지금 동작이 틀렸다고 보기
  어렵습니다.

### 재검증 라운드를 돌리지 않은 이유

`AGENTS.md`는 재검증을 생략하지 말라고 하지만 그 목적을 "앞 라운드의 P0과 P1이 실제로 해결되었는지
확인"으로 한정합니다. 이번 라운드에 P0과 P1이 없었고 고친 둘이 주석과 안내 문구라 앞 수정이 새 문제를
만들 자리가 없습니다.
