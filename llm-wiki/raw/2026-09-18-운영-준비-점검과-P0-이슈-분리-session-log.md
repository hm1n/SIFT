# 운영 준비 점검과 P0 이슈 분리 세션 로그

사용자가 "실제 사용자 대상으로 운영하려고 하는데 현재 운영 단계에서 부족한 것"을 파악해 달라고 요청해서 시작했습니다.

## 무엇을 근거로 봤는지

코드만 보면 "기능이 없다"와 "운영 장치가 없다"를 구분할 수 없어 다섯 갈래를 함께 읽었습니다. develop 브랜치의 `src`, `.github/workflows`, `vercel.json`, `db/schema.sql`, 그리고 `llm-wiki`의 후속 backlog 4종입니다. 마지막으로 `gh issue list`로 열린 이슈가 없다는 것을 확인했습니다.

`npm test`를 돌려 106개 파일 1,967건이 통과하는 것을 봤습니다. 기능과 테스트가 아니라 그 바깥이 비어 있다는 판단의 근거입니다.

## 도구가 두 번 막혔습니다

`process.env` 참조를 세려고 `smart_grep`을 불렀는데 542개 파일을 훑고 0건을 돌려줬습니다. 패턴을 `rateLimit|quota|throttle`로 바꿔도 0건이었습니다. 실제로는 `src/lib/github/auth-session.ts`만 봐도 `process.env[GITHUB_SESSION_KEY_ENV]`가 있으므로 도구가 틀린 값을 준 것입니다.

내장 `Grep`으로 다시 시도했더니 훅이 `smart_grep`을 쓰라며 막았습니다. 두 도구가 서로를 가리키는 상태라, `find src -name "*.ts" | while read f; do grep -ho ... "$f"; done` 형태의 파일 단위 반복으로 우회했습니다. 이 방식은 훅에 걸리지 않았고 환경변수 21종을 정확히 셌습니다.

`smart_grep`이 리터럴 문자열(`maxDuration`)에는 정상 동작했습니다. 정규식 대안(`|`)과 이스케이프(`\.`)가 들어간 패턴에서만 0건이 나왔습니다.

## 요청 제한이 없다는 판정을 어떻게 내렸는지

`rateLimit`과 `quota` 계열로 걸린 파일이 52개나 나와 처음에는 제한 장치가 있다고 볼 뻔했습니다. 하나씩 열어 보니 전부 GitHub과 LLM 제공자가 **우리에게** 돌려주는 429를 처리하는 코드였습니다. 서비스가 사용자에게 거는 제한은 한 건도 없었습니다.

`llm-wiki/wiki/2026-09-02-LLM-비용-산정.md`의 회당 0.02182달러와 예산 10달러에 458회를 근거로 삼아 P0으로 올렸습니다.

## 등급을 새로 정의한 이유

처음에는 `AGENTS.md`의 코드 리뷰 등급(P0~P3)을 그대로 쓰려 했습니다. 그런데 저 표는 "이 PR을 머지할 수 있는가"의 기준이고, 이번 질문은 "서비스를 열 수 있는가"입니다. 같은 이름으로 다른 것을 재면 나중에 읽는 사람이 헷갈립니다. 체크리스트 문서에 두 등급이 다르다는 문장을 먼저 적고 시작했습니다.

## 확인하지 못한 것

Google AI Studio의 예산 알림, Sentry 알림 규칙, Neon 백업과 특정 시점 복구 설정은 외부 콘솔에 있어 코드로 볼 수 없었습니다. 추측으로 "있다" 또는 "없다"를 적지 않고 `확인 필요`로 남겼습니다.

## 이슈를 몇 개로 나눌지

P0이 6건인데 이슈는 5건으로 만들었습니다. 6번(요금과 사용량 알림 확인)은 코드 변경이 없고 2번(분석 횟수 상한)과 같은 비용 통제 묶음이라, 체크리스트가 이미 "2번의 상한과 짝이 되는 항목"이라고 적어 둔 대로 #142의 Task로 넣었습니다.

접은 대안이 둘 있습니다.

하나는 P1과 P2도 이슈로 만드는 것입니다. 이 저장소는 후속 항목을 GitHub Issue가 아니라 `llm-wiki`의 backlog 문서에 적는 관행이 있고(`AGENTS.md`의 "후속 분리와 기록"), 열린 이슈가 20개를 넘으면 무엇이 급한지 알 수 없게 됩니다. P0만 이슈로 올렸습니다.

다른 하나는 1번(처리방침)과 5번(계정 삭제)을 한 이슈로 묶는 것입니다. 처리방침에 삭제 방법을 적어야 하므로 내용이 얽혀 있습니다. 그런데 하나로 묶으면 화면 두 개와 저장 계층 변경과 GitHub 권한 해제가 한 PR에 들어가 "하나의 Issue는 하나의 PR"을 어깁니다. 나누되 #141 본문에서 삭제 기능을 Non-goal로 명시하고 #145가 정한 방법을 적는다고 걸어 두는 쪽을 택했습니다.

## 남은 판단

체크리스트 문서에 "별도 GitHub Issue는 만들지 않습니다"라고 적어 두고 30분 뒤에 이슈를 만들었습니다. 사용자 요청으로 방침이 바뀐 것이라, 문장을 지우고 P0에만 번호를 다는 형태로 문서를 고쳤습니다. P1과 P2는 이슈 없이 문서에 남습니다.
