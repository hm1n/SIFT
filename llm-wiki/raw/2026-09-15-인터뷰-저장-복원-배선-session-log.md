# 인터뷰 저장·복원 배선 세션 로그 (2026-09-15)

이슈 #115의 서버·클라이언트 배선을 만든 구간입니다. 화면은 다음 세션 로그(`2026-09-15-디자인-재점검과-이어가기-화면-session-log.md`)에 있습니다.

## 진행 순서

1. 목록 행의 `PAAR n/4`를 위해 저장 계층에 충분한 블록 수를 더했습니다.
2. 블록 갱신 요청에 저장 대상을 싣는 훅 배선을 넣었습니다.
3. 저장된 인터뷰의 목록·복원·삭제를 부르는 클라이언트 함수를 만들었습니다.
4. 저장된 대화와 블록과 진행 상태로 인터뷰를 시작하는 복원 배선을 넣었습니다.
5. 경험 확정 시점에 인터뷰 줄과 분석 축약본을 저장하게 했습니다.
6. 디자인 재점검에서 드러난 구멍 둘(저장만 다시 보내기, 종료 표시)을 메웠습니다.

커밋은 `6e392c0`, `d855284`, `4a67c1f`, `44fd617`, `621ab38`, `8e56b4d`입니다.

## 결정과 근거

### 진행도를 질의에서 센 이유

목록 행이 `PAAR 2/4`를 보이려면 충분하다고 평가된 블록 수가 필요합니다. 코드에서 세려면 목록 질의가 블록 상태를 통째로 실어 와야 하는데, 인터뷰 하나의 블록 상태에는 주장과 표시 문장이 모두 들어 있어 화면이 쓰지 않는 값이 목록 응답의 대부분이 됩니다. 그래서 Neon 구현은 `jsonb_each`로 평가 객체를 펼쳐 `sufficient`가 참인 것만 셉니다. 블록 이름 넷은 `BLOCK_KINDS`에서 만들어 질의문에 끼웁니다. 값이 컴파일 시점에 고정된 낱말이라 안전하고, 질의문에 다시 적으면 이름이 바뀔 때 한쪽만 남습니다.

`jsonb_typeof`로 모양을 먼저 보는 이유는 `jsonb_each`가 객체가 아닌 값을 받으면 오류를 내기 때문입니다. 칸을 더하기 전에 만들어진 줄이 그 경우입니다.

### 저장 대상을 훅이 만들게 한 이유

저장에 필요한 값 넷(인터뷰 식별자, 기대 블록 버전, 밀린 턴, 반영 전 진행 상태)은 모두 훅이 들고 있는 값입니다. 화면이 조립하게 하면 화면마다 같은 조립을 반복하고, 밀린 턴 목록처럼 훅 내부에서만 정확한 값을 화면이 추측하게 됩니다.

기대 버전을 화면의 `blockState.version`으로 쓰지 않는 것이 이 배선의 핵심입니다. 저장이 한 번 밀리면 화면의 버전만 오르고 저장된 버전은 그대로여서 둘이 어긋나고, 그 뒤의 모든 저장이 조건에 걸립니다. 훅은 **저장에 성공한 버전만** 올리는 ref를 따로 둡니다.

### 응답을 잃은 경우

블록 갱신 요청이 실패하면 그 턴을 밀린 턴으로 남깁니다. 서버가 이미 저장한 뒤 응답만 유실된 경우에도 그렇게 합니다. 다음 저장이 같은 턴을 한 번 더 보내지만, 그때는 저장된 블록 버전이 이미 올라 있어 조건부 갱신이 아무것도 쓰지 않습니다. 대화가 겹쳐 저장되는 대신 `version_conflict`가 되어 화면이 다시 불러오기를 묻습니다. 겹침을 막는 장치를 따로 만들지 않고 이미 있는 조건이 막는다는 사실을 확인한 것입니다.

### 인터뷰 줄이 생기기 전의 턴

확정 시점의 저장은 요청 하나를 기다려야 끝납니다. 그 사이에 사용자가 답할 수 있는데, 저장 대상이 없다고 해서 그 턴을 세지 않으면 줄이 생긴 뒤에도 그 턴만 영영 저장되지 않습니다. 그래서 저장 대상이 없어 저장하지 않은 턴도 밀린 턴으로 남깁니다. 다만 그때는 저장 상태 안내를 바꾸지 않습니다. 저장하지 않은 것은 실패가 아니기 때문입니다.

### 이어가기의 대상 선택

`selectNextTarget`에 `lastTarget`을 넘기지 않기로 했습니다. 직전 질문이 겨냥한 블록은 저장하는 값에 없습니다. 진행 상태의 `askedCount`가 가장 큰 요소를 직전 대상으로 보는 방법이 있지만, 그것은 상태를 직접 나타내지 않는 대리 지표이고 `AGENTS.md`가 금지합니다. 결과적으로 이어가기는 같은 블록을 이어가지 않고 아직 다루지 않은 블록을 먼저 묻습니다. 테스트를 쓰다가 이 동작을 처음 관찰했고(기대를 problem.b로 잡았다가 alternatives.a가 나왔습니다), 코드가 아니라 제 기대가 틀린 것이어서 테스트를 고쳤습니다.

### "다시 저장" 버튼이 누를 것이 없던 문제

디자인에 "다시 저장" 버튼이 있는데, 블록 갱신은 성공했고 저장만 실패한 턴에는 다시 보낼 요청이 없었습니다. 같은 답변으로 블록 갱신을 다시 부르면 모델을 한 번 더 호출하는 데다 같은 주장이 블록에 두 번 들어갑니다. 사용자에게 두 선택지(같은 route에 저장 전용 모드를 두기 / 버튼을 빼고 자동 복구에 맡기기)를 드렸고 전자를 택했습니다.

저장 전용 길은 `mode: "save_only"`로 갈립니다. 근거 스냅샷과 이력과 블록 상태를 그대로 받아 검증은 같은 함수로 하고, 모델 호출과 블록 적용만 건너뜁니다. 크기 검사를 두 길이 공유하도록 함수로 뽑았습니다. 저장 전용만 상한을 느슨하게 두면 블록 갱신이 거절한 크기가 저장으로 들어갑니다.

이 길이 `progress`를 반영하지 않고 그대로 저장하는 것이 일반 저장과 다른 점입니다. 반영은 그 턴의 블록 갱신이 성공할 때 이미 했고, 다시 반영하면 같은 답변의 반응이 두 번 기록됩니다.

반영까지 밀린 턴은 이 길로 보내지 않습니다. 그 턴은 블록 갱신 재시도가 저장까지 함께 하므로 둘 다 보내면 저장된 대화에 같은 질문과 답변이 두 번 들어갑니다. 화면의 버튼 하나가 두 갈래를 순서대로 처리하되, 재시도를 큐 밖에서 먼저 기다립니다. 큐 안에서 기다리면 그 재시도가 같은 큐를 기다리게 되어 서로 풀리지 않습니다.

### 인터뷰 종료 표시

표에 `status` 칸이 있는데 그 값을 `completed`로 바꾸는 코드가 아무 데도 없다는 것을 디자인 재점검에서 발견했습니다. 목록의 `✓` 기호와 "인터뷰 다시 보기" 버튼이 영영 나타나지 않을 상태였습니다.

끝내는 조작은 답변 제출과 함께 오지 않으므로 턴 저장에 얹을 수 없습니다. 사용자에게 두 선택지(종료 전용 요청 하나 두기 / 진행도로 판정하기)를 드렸고 전자를 택했습니다. 진행도 판정은 사용자가 중간에 끝낸 인터뷰를 영영 진행 중으로 남기므로 기호와 문구가 사실과 어긋납니다.

`PATCH /api/interviews/[id]`는 `status: "completed"`만 받습니다. 되돌리는 값을 받지 않는 이유는 끝낸 인터뷰를 다시 여는 조작이 화면에 없고, 받아 두면 쓰지 않는 경로가 남기 때문입니다. 질의는 `updated_at`을 건드리지 않습니다. 그 값은 "마지막으로 이어간 때"이고 목록 정렬 기준이라, 끝내는 조작이 대화를 이어간 것처럼 순서를 바꾸면 안 됩니다.

## 겪은 문제

### 가짜 블록 상태가 숨어 있었습니다

목록 진행도를 세는 코드를 넣자 기존 테스트 하나가 깨졌습니다. `blockState: { version: 1 } as never`로 모양이 없는 값을 넣고 있었고, 진행도가 `evaluation`을 읽으면서 그 거짓말이 처음 걸렸습니다. 방어 코드를 넣는 대신 테스트를 실제 모양으로 고쳤습니다. 저장 계층이 받는 값은 타입이 보장하는 값이고, 방어를 넣으면 다음에 같은 거짓말이 조용히 통과합니다.

### 실DB 검증에서만 확인할 수 있는 것

`jsonb_each`와 `jsonb_typeof`를 쓰는 식, 그리고 `update ... returning` 안의 부질의는 가짜 실행기로는 옳은지 알 수 없습니다. `scripts/verify-neon-store.mts`에 항목을 더해 실제 Neon에서 돌렸고 32개 항목이 모두 통과했습니다. `returning` 안에서 부질의가 도는 것도 이 실행으로 확인했습니다.

### Bash 도구가 백슬래시를 삼켰습니다

테스트 픽스처에 `patch: "@@ -1 +1 @@\n-old\n+new"`를 쓰려 했는데, 명령 문자열에서 `\n`이 실제 줄바꿈으로 바뀌어 문자열 리터럴이 두 줄로 쪼개지고 파싱 오류가 났습니다. `.join("\n")`으로 바꿔도 같은 일이 반복돼 `String.fromCharCode(10)`으로 우회했습니다. 이 도구로 파일을 쓸 때는 백슬래시 이스케이프를 피하는 편이 안전합니다.
