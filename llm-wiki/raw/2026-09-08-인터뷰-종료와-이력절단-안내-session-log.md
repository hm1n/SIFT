# 인터뷰 종료와 이력 절단 안내 세션 로그

## 1. 착수 시점의 상태

이슈 #77(PR #82)이 머지된 직후이고 워크트리 브랜치는 `develop` 끝인 `eb5e828`에 있었습니다. 이슈 #78이 얹을 자리를 코드에서 먼저 확인했습니다.

- `use-interview-stream.ts`가 `removedHistory`를 이미 내놓고 있었고 읽는 곳이 없었습니다.
- `interview-stream-view.tsx`의 `REQUEST_ERROR_GUIDANCE`에 `history_too_large` 항목이 없었습니다. `errors.ts`의 `RETRY_CLEARS`에는 이미 `false`로 들어 있었으므로 갈라 쓸 축은 서 있고 문구만 없는 상태였습니다.
- 종료 조작이 없었습니다. `interview-screen.tsx`의 "후보 목록으로" 버튼이 사실상의 종료이고, 그 버튼은 `experience-candidate-list.tsx`의 `backToList()`를 불러 확정 상태를 비웁니다. 대화가 사라진다는 안내가 없었습니다.

## 2. 사용자에게 물어 정한 것

이슈 #78의 "확인 필요" 두 항목과 핸드오프가 남긴 `beforeunload` 항목, 그리고 `history_too_large` 문구가 가리킬 조작을 함께 물었습니다. 정한 값과 접은 쪽을 적습니다.

### 작성 중이던 답변

정한 것은 종료 확인 문구에 "작성 중인 답변도 사라진다"를 함께 적고 그대로 버리는 쪽입니다.

접은 대안은 둘입니다. 답변이 비어 있지 않으면 "먼저 제출"과 "버리고 종료"를 갈라 묻는 안은 확인 대화의 분기를 둘로 늘리는 값을 치릅니다. 답변이 남아 있으면 종료를 잠그는 안은 사용자가 종료하려는데 못 하는 상태를 만듭니다.

### 종료한 인터뷰의 재시작

정한 것은 재시작 조작을 두지 않고 읽기 전용으로만 남기는 쪽입니다. 다시 하려면 후보 목록에서 경험을 다시 확정합니다.

접은 대안은 "새로 시작" 버튼으로 대화를 비우고 첫 질문을 다시 생성하는 안입니다. 저장이 없으므로 재시작은 첫 질문 재생성이 되는데, 그 조작이 종료 상태를 푸는 경로가 되어 `start`·`retry`·`submitAnswer` 잠금을 다시 열어야 합니다. `history_too_large`의 탈출구가 생기는 이점이 있었지만, 그 분류는 정상 경로에서 오지 않으므로 이점이 작았습니다.

### 페이지 이탈 경고

정한 것은 넣지 않고 후속 backlog에 두는 쪽입니다. 사용자가 우선순위를 높게 두라고 했으므로 backlog 6번에 그 사실을 적었습니다.

`beforeunload`를 넣는 안을 접은 이유는 이슈 #78의 Tasks에 없고 jsdom에서 다루기 까다로워 회귀 테스트 없는 코드가 하나 생기기 때문입니다.

### 이력 상한 초과 문구가 가리킬 조작

정한 것은 종료와 새 인터뷰를 가리키는 쪽입니다. 문구를 "대화를 줄여 주세요"로 끝내는 안을 접은 이유는 대화를 줄이는 조작이 화면에 없기 때문입니다. 원인만 알리고 조작을 권하지 않는 안도 접었습니다. 사용자가 다음에 무엇을 해야 하는지 알 수 없습니다.

## 3. 구현 순서

근본 원인별로 묶어 커밋 하나씩 만들었습니다.

1. `82b05ab` 훅의 종료 상태와 요청 잠금. `isEnded`·`endInterview()`를 더하고 `start`·`retry`·`submitAnswer` 세 자리를 막았습니다.
2. `5706b5a` 화면의 종료 조작과 확인 절차, 종료 후 읽기 전용.
3. `ca88786` 절단 안내를 빠진 자리에 그리기.
4. `5c033a7` `history_too_large` 문구 분리.

잠금을 훅에 둔 이유는 이슈 #77에서 화면 테스트가 `fireEvent.submit`으로 버튼 우회 경로를 잡아낸 일이 있었기 때문입니다. 종료는 요청을 시작하는 자리가 셋이라 같은 성격의 결함이 나기 쉬운 지점입니다. `start` 하나만 막으면 요청은 나가지 않지만 `retry`가 마지막 질문을 지우는 부수 효과는 남으므로 `retry`도 따로 막았습니다.

`InterviewStreamPhase`에 `"ended"`를 더하는 안을 접었습니다. 그 union은 스트림 수신부의 상태이고 종료는 사용자의 조작입니다. 스트림이 끝나지 않은 채 종료한 경우에 어느 값을 담을지 정할 수 없습니다. 대신 화면이 상태 문단에서 종료 문구로 갈라 그리고 `aria-busy`를 끕니다.

확인 절차에 `window.confirm`을 쓰는 안도 접었습니다. jsdom에서 전역을 갈아끼워야 하고 문구를 스타일링할 수 없습니다. 화면 상태 하나로 확인 단계를 그렸습니다.

## 4. 실패하고 고친 것

절단 안내를 넣은 뒤 종료 관련 화면 테스트 셋 가운데 "질문이 도착하는 중에 종료하면 준비 안내와 진행 표시를 걷는다"가 처음에 실패했습니다.

원인은 테스트가 잰 시점입니다. 답변 제출 뒤 `await waitFor(fetchImpl 2회)`를 먼저 기다렸는데, 그 사이에 상태가 `connecting`에서 `streaming`으로 넘어가 준비 안내가 이미 사라져 있었습니다. 준비 안내는 `connecting`과 `idle`에서만 나옵니다. 제출 직후에 안내를 확인하고 그 상태에서 종료하도록 순서를 바꿨습니다. 종료 뒤에 요청이 더 나가지 않는지는 그 다음에 `waitFor`로 확인합니다.
