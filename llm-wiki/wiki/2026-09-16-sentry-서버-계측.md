# Sentry 서버 계측과 오류 수집 경로

## 결론

**서버 오류를 `@sentry/nextjs`로 수집합니다.** 이슈 #136 범위입니다. 이슈 #81이 브라우저만
계측해 두어 배포 뒤에도 Sentry Issues에 오류가 한 건도 쌓이지 않았습니다. 원인은 세 가지였고 셋
다 이번에 막았습니다.

**수집 기준은 응답 status 하나입니다.** 오류 종류를 열거하지 않고 **status가 500 이상일 때만**
`captureException`을 부릅니다. 각 라우트가 이미 오류 종류를 status로 옮기고 있어 그 매핑을 한 번
더 베끼면 두 곳이 어긋날 자리가 생깁니다. 이 기준이면 401, 400, 413, 422, 404, 409는 자동으로
빠지고 500, 502, 503, 504만 남습니다.

**전송은 SDK의 `captureException`을 그대로 부릅니다.** 전송 함수를 직접 보관하고 꺼내 쓰는 장치를
한 번 만들었다가 지웠습니다. 아래 4절이 그 경위이고, 이번 작업에서 가장 오래 걸린 지점입니다.

**DSN이 없으면 초기화하지 않습니다.** 초기화하지 않으면 SDK에 client가 없고, client가 없는
`captureException`은 아무 일도 하지 않습니다. 5절에서 실측으로 확인했습니다.

## 왜 SDK만 붙여서는 0건인가

배포 커밋 `eae1708` 기준으로 확인한 세 가지입니다.

**1. 서버에 SDK가 없었습니다.** 저장소에 `instrumentation.ts`가 없고 `instrumentation-client.ts`
하나뿐이었습니다. 빌드 로그의 라우트 18개가 전부 `ƒ (Dynamic)`, 즉 서버 실행인데 그쪽에서
`Sentry.init`이 불린 적이 없습니다.

**2. 서버 오류가 예외로 던져지지 않습니다.** 라우트가 전부 최상위 `try/catch`로 오류를 잡아 타입
있는 응답으로 바꿉니다. Next.js의 `onRequestError`는 핸들러 밖으로 던져진 오류만 받으므로,
`instrumentation.ts`를 추가하는 것만으로는 여전히 0건입니다. 그래서 **실제 효과의 대부분은 각
라우트 catch에 붙인 `reportServerError`**이고 `onRequestError`가 잡는 것은 Server Component 렌더
오류처럼 라우트 밖에서 던져진 것입니다.

라우트의 `try/catch`를 걷어내 예외를 밖으로 흘리는 방법도 있었지만 채택하지 않았습니다.
`AGENTS.md`의 작업 원칙이 모든 핵심 흐름에 Error 상태를 요구합니다.

**3. 클라이언트 렌더 오류를 React 에러 바운더리가 삼킵니다.** `src/app`에 `error.tsx`도
`global-error.tsx`도 없었습니다. App Router 기본 바운더리가 오류를 잡으면 `window.onerror`가
일어나지 않아 Sentry 전역 핸들러가 보지 못합니다. `src/app/global-error.tsx`에서
`captureException`을 직접 불러 막았습니다.

## 배선한 자리

이슈 본문은 네 곳을 적었지만 같은 성격의 catch가 13개 파일 18곳에 있었습니다. 넷만 고치면 나머지
14곳이 그대로 조용합니다. 전부 배선했습니다.

전송을 얹는 방식은 자리마다 다릅니다. 판정을 한 자리에 모을 수 있으면 모았습니다.

| 방식 | 자리 | 이유 |
| --- | --- | --- |
| 오류 응답 생성 함수 안에서 전송 | `features/saved-interviews/errors.ts`의 `savedInterviewErrorResponseFor`, `interview/experience-block/route.ts`와 `interview/stream/route.ts`의 `errorResponse` | 같은 세 줄이 여러 번 반복되거나 오류 응답을 만드는 자리가 여럿입니다. 호출부마다 얹으면 새 catch가 생길 때 빠뜨릴 자리가 남습니다. |
| catch에서 응답을 감싸 전송 | GitHub 라우트 넷, Stage A, Stage B, cron purge | 오류 응답 생성 함수가 파일 밖 공용이거나(`lib/github/api-contract.ts`) 한 자리뿐입니다. |

`savedInterviewErrorResponse`처럼 오류 종류와 문구만 받는 함수가 많아, 그 함수 안에서 전송하면
원본 오류 객체를 잃어 스택트레이스가 남지 않습니다. 그래서 **판정은 만들어진 응답의 status로 하고
전송은 catch가 쥐고 있는 원본 오류로** 합니다. `reportServerError(error, response)`가 그 모양입니다.

지적되지 않았지만 함께 고친 것이 둘 있습니다. `features/saved-interviews/route-request.ts`와
`api/interviews/[id]/route.ts`가 각자 들고 있는 `requireUserId`입니다. 세션 쿠키는 있는데 암호화
키 설정이 없으면 500을 내는데, 이것이 조용하면 로그인 전체가 막힌 배포를 알 수 없습니다.

## 전송 함수를 직접 보관하지 않는 이유

처음 구현은 라우트가 SDK를 모르게 하는 쪽이었습니다. `report.ts`라는 파일을 따로 두고, 전송 함수를
`initSentryServer()`가 등록하면 라우트가 그것을 꺼내 쓰는 방식이었습니다. 라우트가 SDK를 import하면
jsdom 테스트가 깨지는 문제(6절)를 피하려는 것이었습니다.

**그 방식은 실제로는 동작하지 않았습니다.** 단위 테스트는 전부 통과했는데, 프로덕션 빌드를 띄워
5xx를 내 보니 응답은 503으로 정상인데 envelope가 한 건도 오지 않았습니다. 진단 로그를 넣어 확인한
결과입니다.

```
[diag] reporter registered                ← register()에서
[diag] reportServerError 503 NO REPORTER  ← 라우트에서
```

Next.js가 `instrumentation.ts`와 각 라우트를 서로 다른 번들로 만듭니다. 두 번들이 같은 파일을
import해도 모듈 인스턴스가 따로 생기므로 한쪽이 채운 값을 다른 쪽이 보지 못합니다.

이 문제를 등록 위치를 `globalThis`로 옮겨 한 번 고쳤습니다. 그러나 그 상태로 자체 리뷰를 돌리면서
방향을 되돌렸습니다. Sentry SDK가 자기 client를 `globalThis.__SENTRY__`에 두는 것과 똑같은 일을
직접 다시 만든 것이었기 때문입니다. **SDK를 그대로 부르면 이 문제 자체가 생기지 않습니다.** 장치를
지워 코드 110줄이 줄었고, 라우트가 SDK를 import하는 대가는 jsdom 테스트 한 곳에 mock 한 덩이를
넣는 것이었습니다.

번들이 갈린다는 실측은 남겨 둘 값어치가 있습니다. 서버에서 모듈 지역 상태로 무언가를 공유하려는
다음 시도가 같은 자리에서 막힙니다. 단위 테스트는 한 번들 안에서 돌아 이 결함을 잡지 못하므로,
확인 수단은 5절의 절차뿐입니다.

## 확인 절차

로컬에서 실제 전송까지 확인하는 절차입니다. Sentry 계정 없이 됩니다.

1. 가짜 수집 서버를 띄웁니다. 127.0.0.1:9999에서 POST 본문을 파일로 떨구는 HTTP 서버면 됩니다.
2. `npm run build`
3. `SENTRY_DSN="http://publickey@127.0.0.1:9999/1" CRON_SECRET="<아무 값>" npx next start -p 3123`
   - `DATABASE_URL`을 비워 둡니다. 그래야 다음 단계가 저장소 실패로 503을 냅니다.
4. 4xx가 전송되지 않는 것을 봅니다. `curl http://127.0.0.1:3123/api/cron/purge` → 401, envelope 0건.
5. 5xx가 전송되는 것을 봅니다.
   `curl -H "Authorization: Bearer <위 값>" http://127.0.0.1:3123/api/cron/purge` → 503, envelope 1건.
6. `SENTRY_DSN` 없이 3~5를 되풀이합니다. 5xx를 내도 envelope 0건이어야 합니다.

2026-09-16 결과입니다. 5단계의 envelope에 `"type":"DatabaseError"`와 한국어 오류 문구, 그리고
프레임이 달린 `stacktrace`가 실려 왔습니다. 4단계와 6단계는 0건이었습니다.

자체 리뷰로 전송 방식을 바꾼 뒤에 같은 절차를 한 번 더 돌렸습니다. 결과가 같았고, 6단계에서는 5xx를
세 번 내도 envelope이 0건이며 SDK가 경고도 남기지 않았습니다. DSN이 없을 때 조용한 것이 우리 코드가
아니라 SDK의 동작에 기대게 되었으므로 이 확인이 필요했습니다.

**비밀값 점검도 같은 envelope로 했습니다.** `cookie`, `authorization`, `Bearer`, cron secret 값
네 가지를 envelope 본문에서 찾아 전부 0건인 것을 확인했습니다. `sendDefaultPii: false`를
`Sentry.init`에 명시해 두었고 회귀 테스트가 그 값을 고정합니다. 기본값도 꺼짐이지만, 이 값이
켜지면 세션 쿠키에 든 암호화된 GitHub 토큰이 이벤트에 실리므로 기본값에 기대지 않습니다.

## 설정값

| 값 | 설정 | 이유 |
| --- | --- | --- |
| `dsn` | `SENTRY_DSN`, 없으면 `NEXT_PUBLIC_SENTRY_DSN` | 공개 DSN 하나만 설정한 배포에서도 서버 이벤트가 나갑니다. 서버 전용 이름을 따로 둔 것은 나중에 서버 이벤트를 다른 프로젝트로 나눌 때 배포 설정만 바꾸면 되게 하려는 것입니다. |
| `sendDefaultPii` | `false` | 위 5절. |
| `tracesSampleRate` | `0` | 서버 트랜잭션 샘플링 비율 조정은 이슈 #136의 Non-goal입니다. 이 값이 0이어도 `captureException`은 그대로 동작합니다. |

## 파일 경계

SDK를 import하는 파일은 둘입니다. `instrumentation.ts`와 `src/lib/sentry/server.ts`이고, 라우트 13개가
후자의 `reportServerError`를 부릅니다.

**그래서 라우트를 부르는 jsdom 테스트는 SDK를 가려야 합니다.** jsdom에서 서버 빌드를 로드하면
`@sentry/server-utils`의 번들러 플러그인이 `TypeError: The URL must be of scheme file`로 깨집니다.
지금 해당하는 파일은 `src/features/experience-block/save-contract.test.tsx` 하나이고, 훅과 라우트를
한자리에서 돌리는 테스트입니다. 파일 맨 위에 다음을 넣으면 됩니다.

```ts
vi.mock("@sentry/nextjs", () => ({
  init: () => undefined,
  captureException: () => undefined,
  captureRequestError: () => undefined,
}));
```

node 환경에서 도는 라우트 테스트 13개는 그대로 둡니다. 실제 SDK를 실어도 DSN이 없어 아무것도 나가지
않고, 전체 스위트 실행 시간도 늘지 않았습니다.

## 하지 않기로 한 것

이슈 #136의 Non-goal과 이번에 새로 분리한 것입니다. 후속 항목은
`wiki/2026-09-08-sentry-계측-후속-backlog.md`에 있습니다.

- Source Map 업로드와 Releases. 서버 스택트레이스가 minified 상태로 보입니다. backlog 1번과 7번입니다.
- Session Replay, Profiling, 커스텀 스팬과 메트릭, 알림 라우팅, 서버 트랜잭션 샘플링 비율 조정.
- `src/app/error.tsx`. `global-error.tsx`만 두면 렌더 오류가 헤더까지 포함한 화면 전체를 대체합니다.
  UX 변경이라 이번 범위에 넣지 않았습니다. backlog 18번입니다.
- 스트림 중간 실패, OAuth 실패, Stage A degrade 경로. status 기준에 걸리지 않는 자리들이고
  backlog 15~17번입니다.

## 확인 필요

- **배포 환경 도달 확인.** 위 5절은 로컬 `next start`입니다. Vercel의 서버리스 함수는 응답을 보낸
  뒤 동결될 수 있어 전송이 끝나기 전에 멈출 여지가 있습니다. backlog 14번입니다.
- **엣지 런타임.** 지금 라우트 16개가 전부 `runtime = "nodejs"`이고 `proxy.ts`도 없어 엣지에서 도는
  코드가 없습니다. `register()`는 런타임을 가르지 않으므로 엣지가 생기면 그대로 초기화되지만, 그
  경로를 실제로 확인하지는 못했습니다.
