# PR 없는 저장소의 커밋 묶음 방식 실험

2026-09-10 아이데이션 세션의 결론과 층 0 실측 결과를 담습니다. 실측 원본 수치는
`raw/2026-09-10-커밋-묶음-방식-층0-구조지표-실측.md`에 있습니다. 층 1과 층 2는 진행하지 않기로 했습니다. 6절 참조.

## 1. 문제

Stage A는 커밋이 아니라 WorkUnit(PR 묶음)을 판단 단위로 씁니다. `groupCommitsIntoWorkUnits`가 PR에
속하지 않은 커밋을 `no_pull_request` 사유로 전부 제외하므로 PR 없이 커밋만 올리는 저장소는 Stage A를
통과하는 묶음이 0개입니다. 경험 정리를 어려워하는 교육생은 PR도 잘 쓰지 않을 가능성이 높아, 서비스가
가장 도와야 할 사용자군이 첫 단계에서 걸러지는 구조입니다.

## 2. 이미 확인된 사실 (다시 검증하지 않음)

- 커밋 단위 판단은 실측으로 폐기됐습니다. 경험은 커밋 단위에 존재하지 않습니다.
  근거: `wiki/2026-08-24-경험-판단단위-PR-묶음-전환-검토.md` 3-4절.
- PR 없는 커밋의 폴백 묶음 규칙 다섯 개는 같은 문서 4-2절에서 한 번 측정됐습니다. 경로 겹침만 쓰면
  전이 병합으로 저장소 대부분이 한 묶음이 되고, 연쇄를 끊는 것은 시간 제한입니다.
- 과분할은 과병합보다 안전합니다. 과분할된 묶음도 일관된 작업이지만 과병합된 묶음은 무관한 작업이
  섞여 판단이 불가능합니다.

## 3. 결정

### 3-1. 정답 기준은 PR 복원이 아니라 "하나의 경험"

PR은 경험의 대리 지표이며 정답이 아닙니다. 릴리스 PR은 경험이 아니고(`resolvePullRequest`가 최소
번호를 고르는 이유), PR#113처럼 69일간 커밋 18개에 경험 세 개가 들어 있는 PR도 있고, 커밋 1개짜리
PR도 정답으로 세어집니다. 프로젝트 리뷰 규칙도 대리 지표로 판별하는 코드를 지적하도록 되어 있습니다.

판정 세 문항. **결과를 보기 전에 고정했으며 결과를 본 뒤 고치지 않습니다.**

1. 이 묶음 안의 커밋들은 한 문제(목표)를 향하는가.
2. 이 묶음만 보고 코드 근거가 있는 "왜 이렇게 했나" 질문을 하나 쓸 수 있는가.
3. 더 쪼개야 하는가, 더 합쳐야 하는가, 그대로가 맞는가.

PR 복원률(순도)은 PR 저장소에서만 참고 지표로 곁에 둡니다. 순위에 넣지 않고, 유독 낮은 방식이 있을
때 들여다보는 경보로만 씁니다.

### 3-2. 후보 묶음 방식

- 축 1 규칙 기반. 1-a 다중 신호 점수화(시간·경로·접두어·이슈 번호), 1-b 커밋 그래프(머지 커밋 부모
  사이. 현재 캐시로는 못 잼, 첫 회차 제외), 1-c 세션 경계(간격 N시간 이상이면 새 묶음. 파일 신호를
  안 써서 전이 병합이 원리상 없음).
- 축 2 LLM 개입. 2-a Stage A 앞 묶음 제안 단계, 2-b 규칙으로 과분할한 뒤 인접 묶음 쌍에 "같은
  작업인가"만 묻기. 2-b가 더 싸고 안정적일 가능성.
- 축 3 다른 단위(파일·모듈, 사용자 직접 수정)는 이번 범위 밖.
- 축 4 진단. 저장소 입력 시점에 PR 비율·머지 커밋·브랜치 수를 진단해 분석 방식을 안내. 어떤 방식을
  택하든 필요.

1차 추천 조합은 1-c와 1-a 변형을 규칙 층으로 두고 그 위에 2-b입니다.

### 3-3. 측정 설계: 세 층

- 층 0 구조 지표(LLM 없음): 방식별 묶음 수, 크기 분포, 최대 묶음, 1개짜리 비율, 묶음당 기간.
  목적은 붕괴 감지.
- 층 1 Stage A 심판(LLM): 층 0 통과 방식의 묶음을 현재 Stage A에 그대로 넣고 선정 후보 수와 점수
  분포, 상위 후보의 커밋 구성, 반복 실행 간 안정성을 봅니다. 방식 간 차이가 Stage A 자체 분산보다
  작으면 차이 없음. 온도 고정과 분산 측정은 `raw/2026-09-01-Stage-A-온도-고정-실측.md`,
  `raw/2026-09-01-Stage-A-후보-선정-분산-측정.md`를 따릅니다.
- 층 2 사람 판정(소량, 블라인드): 남은 두세 방식의 묶음을 섞고 방식 이름을 가린 뒤 3-1 세 문항으로
  판정. 표본은 Stage A 상위 후보 전부 + 하위 무작위 몇 개. 하위 표본은 필수.

## 6. 결정: PR 없는 커밋은 커밋 단위로 판단한다 (2026-09-10)

층 0 결과를 놓고 논의한 뒤 사용자가 정했습니다. 경위와 접은 대안은 `raw/2026-09-10-커밋-묶음-판단단위-결정-session-log.md`에 있습니다. PR 묶음을 판단 단위로 채택한 최초 근거는 `wiki/2026-08-24-경험-판단단위-PR-묶음-전환-검토.md` 3-4절입니다. 층 1과 층 2에서 묶음 규칙을 비교하는 계획은 접습니다.

근거는 두 가지입니다. 첫째, 시간 규칙에는 N이라는 조정값이 있고 그 값은 저장소마다 다르게 맞습니다. hm1n.github.io에서는 2시간이 맞았고 demian에서는 어떤 값도 맞지 않았습니다. 서비스는 사용자마다 N을 맞춰 줄 수 없으므로 한 사람에게 맞는 값이 다른 사람에게 틀리는 규칙은 서비스 규칙이 될 수 없습니다. 둘째, 작업 경계와 시간 경계는 관계가 없습니다. 자정을 넘겨 마무리한 작업과 아침에 시작한 새 작업을 어떤 N도 구분하지 못합니다. 커밋 단위에는 조정값이 없고, 틀렸을 때도 경험이 흩어져 후보가 빠지는 쪽으로만 틀립니다. 무관한 커밋이 섞여 잘못된 후보가 나가는 것보다 안전합니다.

8월 24일에 커밋 단위를 폐기한 근거(잡무 커밋 18개가 모여 하나의 경험이 된 PR#66)는 PR을 쓰는 팀 저장소의 사례입니다. PR 저장소는 PR 묶음을 그대로 쓰므로 그 결론은 유지되고, 이번 결정은 PR에 속하지 않은 커밋에만 적용됩니다.

### 6-1. 반영 결과

- `groupCommitsIntoWorkUnits`는 PR에 속하지 않은 커밋을 제외하지 않고 커밋 1개짜리 WorkUnit을 만듭니다. WorkUnit은 `kind: "pull_request" | "commit"` 판별 유니온이며 식별자는 `pr:번호` 또는 `commit:SHA` 형식입니다.
- 휴리스틱 점수는 단일 커밋도 의존성 추가, 인프라 추가, 변경 파일 수, 큰 삭제 같은 신호에 따라 달라집니다. 1개짜리 묶음이 모두 같은 점수라는 이전 설명은 틀렸습니다.
- `STAGE_A_MAX_UNITS` 200과 점수식은 유지합니다. 이 값들은 새 점수식을 만드는 것이 Non-goal인 이슈 #101에서 바꾸지 않고 편향만 측정했습니다.
- Stage A는 판단 단위를 하나의 완결된 경험으로 가정하지 않고 후속 diff 검토 대상으로 추천합니다. 근거가 없으면 후보 0개를 정상 결과로 반환합니다.
- Stage B는 PR 묶음을 여러 커밋으로 펼치고 단일 커밋은 한 개 그대로 처리합니다. 두 종류 모두 같은 통합 경로를 사용합니다.
- BaekjoonHub 같은 자동 커밋 도구 서명의 블랙리스트 추가 여부는 별도 후속 판단으로 남깁니다.

### 6-2. Stage A와 선별 편향 측정 결과 (2026-09-11)

근거와 전체 측정 경위는 `raw/2026-09-11-이슈101-프롬프트교체-편향측정-session-log.md`에 있습니다.

`hm1n.github.io`와 `Algorithm`을 프롬프트 교체 전후로 각각 5회 실행했습니다. 전체 20회가 전수 응답 계약을 지켰고 `unknown_sha`나 `schema_validation` 오류는 없었습니다. 혼합 저장소인 `hm1n.github.io`는 교체 전후 모두 네 후보를 유지했습니다. `Algorithm`은 최소 1개 강제 때문에 교체 전에는 workflow 추가 커밋 하나를 추천했지만 교체 후에는 5회 모두 후보 0개를 정상 반환했습니다.

### 6-3. 선별을 동점 그룹 일괄 처리에서 개별 예산 검사로 전환 (2026-09-11)

경위는 `raw/2026-09-11-Stage-A-개별-예산-선별-설계-session-log.md`와 `raw/2026-09-11-Stage-A-개별-예산-선별-구현-session-log.md`에 있습니다.

선별을 점수 내림차순으로 정렬한 항목을 하나씩 개별로 확인하는 방식으로 바꿨습니다. 점수식, 개수 상한 200, 바이트 상한 110,000은 그대로 두었습니다. 이제 선택 결과는 "N점 이상"이라는 단일 점수 경계로 설명되지 않습니다.

`Algorithm`을 3회 재측정한 결과 선별 입력묶음이 1에서 200으로, Stage A가 실제로 판단하는 묶음 수가 늘었습니다. 제외는 434에서 235로 줄었고 전부 `over_input_budget` 사유입니다. 후보는 기존 1개(`37ce5d2` workflow 추가 커밋)에 `0759fe2`(배포 기본 브랜치를 `master`에서 `main`으로 변경)가 추가돼 2개가 됐습니다. 이 커밋은 자동 채점 커밋이 아니라 실제 설정 변경이라, 예산 확대가 자동 채점 커밋을 오추천으로 끌어들이지는 않았습니다. `hm1n.github.io`는 12묶음 전체가 이미 예산 안에 들어오는 저장소라 이번 변경으로 결과가 바뀌지 않았습니다.

PR과 단일 커밋 사이의 점수 편향 자체(6-2절)는 이번 변경으로 해소되지 않았습니다. 예산이 충분해 제외로 이어지지 않는 저장소에서는 여전히 구조적 차이가 남아 있고, 이 차이를 다룰지는 별도 후속 판단입니다.
