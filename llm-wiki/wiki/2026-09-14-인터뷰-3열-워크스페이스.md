# 인터뷰 3열 워크스페이스와 코드 근거 패널

이슈 #98이 만든 인터뷰 화면의 현재 계약입니다. 배경은 `wiki/2026-09-10-디자인-개편-계획.md`에 있고, 앞 단계인 경험 후보 화면은 `wiki/2026-09-11-경험후보-master-detail-화면-개편.md`에 있습니다. 확인 가능·불가 구분의 원본 계약은 `wiki/2026-08-24-확인가능불가-구분-계약.md`이고, 스트리밍 렌더링 결정은 `wiki/2026-08-25-스트리밍-렌더링-측정과-전송-계약.md`입니다.

**이 문서는 `wiki/2026-08-25-인터뷰-화면-근거패널-배치.md`의 결정 1(근거 패널을 질문 아래 한 열로 둔다)을 대체합니다.** 같은 문서의 결정 2(화면에서 patch를 추가로 자르지 않는다)와 절단 알림·확인 수준 표시 경계는 그대로 유효합니다.

확인 날짜는 2026-09-14입니다.

## 1. 배치

왼쪽 코드 근거, 가운데 대화, 오른쪽 PAAR의 3열입니다. 한 열로 쌓던 배치를 바꾼 이유는 "코드를 보고 → 왜 그렇게 했는지 설명하고 → 경험으로 정리한다"는 이 제품의 핵심 동작이 세로 배치에서는 드러나지 않기 때문입니다.

| 열 | 기본 폭 | 한계 |
| --- | --- | --- |
| 코드 | 300px | 200~520px |
| 대화 | 남는 폭 | 최소 280px |
| PAAR | 280px | 220~480px |

양옆 두 열은 헤더 토글로 접히고 손잡이로 폭을 바꿉니다. 폭 계산은 열의 한계만 보지 않고 대화 열의 최소 폭까지 함께 봅니다. 한쪽을 넓히다가 대화 열이 최소 폭 아래로 밀리면 더 넓어지지 않습니다.

워크스페이스 폭이 708px(세 열 최소 폭 200 + 280 + 220에 손잡이 8을 더한 값)보다 좁으면 `[ CODE ] [ INTERVIEW ] [ PAAR 0/4 ]` 탭으로 바뀝니다. 판정 기준은 화면 폭이 아니라 `ResizeObserver`로 잰 워크스페이스 폭입니다. 사이드바 208px 때문에 화면 폭과 어긋나므로 미디어 쿼리를 쓰지 않았습니다.

**탭 모드에서도 세 열을 모두 DOM에 남깁니다.** 보이지 않는 열은 `visibility`로만 감춥니다. 대화 열을 떼면 스트림이 끊기고 대화 이력이 사라지기 때문이고(이슈 #98 Constraint), `display: none`을 쓰지 않는 이유도 같은 자리에 있습니다. 높이가 0이 되면 로그의 자동 스크롤이 하단을 잡지 못한 채 다시 나타납니다. `visibility: hidden`은 레이아웃을 남기면서 접근성 트리와 포커스에서만 뺍니다.

가운데 열의 `InterviewStreamView`는 렌더링 방식, 자동 스크롤, 낭독 경계를 그대로 둡니다. 바꾼 것은 CSS 높이 규칙 하나입니다. 한 열로 쌓던 시절의 `max-height: 60vh`는 열 높이와 무관한 값이라 열 아래가 비어 있어서, 로그가 열이 준 높이를 채우도록 `flex: 1; min-height: 0`으로 바꿨습니다. 같은 gap을 유지하려고 `.stream`의 grid를 flex로 바꿨습니다.

## 2. 코드 패널

`InterviewEvidencePanel`을 `CodePanel`로 대체했습니다. 스냅샷의 `커밋 → 파일` 구조를 `파일 → 커밋`으로 뒤집어(`evidence-files.ts`) 파일 트리와 diff 뷰어를 그립니다. 파일 하나를 고르고 그 파일이 어느 커밋에서 어떻게 바뀌었는지 넘겨 보는 것이 이 패널의 조작입니다.

- **파일 상태.** GitHub의 `status` 7종을 디자인의 added·modified·deleted 셋으로 좁힙니다. `renamed`와 `copied`는 이전 경로가 스냅샷에 없어 새로 생긴 파일과 구분해 보여 줄 수 없으므로 modified로 모읍니다. **여러 커밋에 걸친 파일은 언제나 modified입니다.** 스냅샷에 커밋 시간 순서가 없어(`EvidenceSnapshotCommit`에 날짜가 없고 배열 순서는 역할 순서입니다) added 뒤 deleted인지 그 반대인지 재구성할 수 없습니다. 순서를 모르는 채 한쪽을 고르면 실제와 어긋난 상태를 단정하게 됩니다.
- **디렉터리 트리.** 모든 디렉터리가 공유하는 앞 구간만 이름에서 덜어냅니다. 300px 폭에서 모든 줄이 `src/features/...`로 시작하면 정작 다른 부분이 잘려 나갑니다. 마지막 한 세그먼트는 남깁니다. 전부 덜어내면 묶음 이름이 사라집니다. 트리는 한 겹입니다.
- **patch 파싱.** `@@ -a,b +c,d @@` hunk 헤더로 old/new 줄 번호를 추적합니다. **절단된 patch가 정상 입력입니다.** hunk 헤더 없이 시작하거나 줄 가운데서 끊긴 입력이 들어오므로, 파싱에 실패해 빈 화면을 그리지 않고 아는 것만 붙이고 모르는 줄 번호는 null로 둡니다. 접두어까지 잘려 나간 줄은 버리지 않고 문맥 줄로 남깁니다. 버리면 사용자가 보는 diff가 조용히 짧아집니다.
- **줄 번호.** 추가된 줄은 변경 후 번호, 나머지는 변경 전 번호를 씁니다. 디자인 원본은 변경 전 번호만 써서 추가된 줄의 번호 칸이 비는데, 그러면 추가된 줄이 새 파일의 몇 번째 줄인지 알 수 없습니다.
- **diff 색.** 추가와 삭제를 색으로 가르지 않습니다. 배경 대비, `+`/`−` 기호, 왼쪽 표시선 셋으로 구분합니다(이슈 #98 Non-goal). 디자인 원본의 연초록·연분홍 배경은 옮기지 않았습니다.
- **FILE 모드.** 근거 스냅샷에 파일 전체 원문이 없어 비활성입니다. 자리를 없애지 않고 비활성 버튼으로 두되 왜 못 쓰는지를 접근성 이름에 남깁니다.

## 3. Loading·Error를 만들지 않은 이유

이슈 #98 Goal은 코드 패널의 상태 3개(`LOADING EVIDENCE`, `NO EVIDENCE`, `ERROR / EVIDENCE(Retry)`)를 요구했습니다. **셋 중 둘은 현재 아키텍처에서 도달할 수 없어 만들지 않았습니다.** 사용자와 착수 전에 확인한 결정입니다.

- `LOADING`: 근거 스냅샷은 `confirmExperienceSelection`이 확정 시점에 동기 순수 함수로 만듭니다. 관측할 진행 상태가 없습니다. 시간 같은 대리 지표로 가짜 전환을 만들지 않는다는 기존 결정(`experience-selection.ts`)을 그대로 따릅니다.
- `ERROR + Retry`: 스냅샷 생성 실패는 확정 단계에서 `EXPERIENCE_SELECTION_ERROR_COPY`로 갈려 후보 화면에 남습니다. 인터뷰 화면에 도달한 시점에는 재시도할 대상이 없습니다.
- `NO EVIDENCE`(파일 0개): `evidence-snapshot.ts`가 모든 커밋의 변경 파일이 0개인 근거를 `no_repository_evidence`로 미리 막습니다. 파일 트리가 비는 경우가 없습니다.

AGENTS.md의 "방어 코드를 추가할 때 그 코드가 실제로 도달 가능한지 확인합니다"와 "그 상태를 직접 나타내지 않는 대리 지표를 쓰지 않습니다"에 걸리는 자리라, 검증할 수 없는 분기를 만드는 대신 이 문서에 차이를 남깁니다.

실제로 도달하는 상태는 하나입니다. **선택한 파일의 그 커밋 patch 본문이 없는 경우(`NO DIFF BODY`)**이고, 이유를 예산 소진과 GitHub 미제공으로 갈라 보여 줍니다. 근거 로드가 비동기로 바뀌면 그때 세 상태를 추가합니다.

## 4. 확인 가능·불가 안내는 시각적으로만 숨깁니다

디자인의 `CodePanel`에는 확인 수준 안내의 자리가 없습니다. Constraint는 그 안내를 제거하지 말라고 합니다. 둘을 함께 만족시키려고 #97과 같은 방법을 씁니다. **DOM과 `aria-describedby` 연결은 남기고 화면에서만 감춥니다.** `aria-label`로 이름만 주거나 DOM에서 지우면 안내가 스크린리더에서 사라지고, 그것이 이슈 #47 PR #52 1차 리뷰의 P1이었습니다.

시각적으로 숨기는 것은 넷입니다. `REPOSITORY_VERIFIED_NOTICE`, `EVIDENCE_VERIFIABILITY_NOTICE`, `RELATED_COMMITS_VERIFICATION_NOTICE`, 그리고 `unverifiableItems` 목록(`What can't be confirmed from the Repository`)입니다. 앞 둘은 패널의 `aria-describedby`가 가리킵니다.

**patch 절단·미포함 안내는 여기 해당하지 않습니다.** 근거가 온전한지 판단하는 데 직접 쓰이므로 눈에 보이는 자리를 따로 만듭니다. 파일 단위 절단은 diff 뷰어 아래, 스냅샷 전체의 상한 절단은 패널 바닥입니다. 보는 자리가 달라 하나가 나머지를 감추지 않는다는 기존 결정을 유지합니다. 파일 단위 안내에 단계를 지목하지 않는 것도 그대로입니다. `evidence-snapshot.ts`가 Stage B 절단과 예산 절단을 한 boolean으로 합쳐 실어 오므로 화면이 출처를 가를 수 없습니다.

색인에서 찾지 못한 커밋은 diff 뷰어가 무엇을 확인할 수 없는지 말합니다(`Not found in the commit index — title, message, and PR info can't be confirmed.`). 제목이 비었다는 사실만 보여 주면 사용자는 그 커밋에 메시지가 없다고 읽습니다.

## 6. 렌더링 비용 측정

`streaming-render-cost.measure.mts` 2부는 합성 페이지를 `page.setContent`로 띄웁니다. 실제 앱을 로드하지 않으므로 그대로 다시 돌리면 배치를 바꿔도 정의상 같은 값이 나옵니다. 그래서 2부에 **한 열 배치와 3열 배치를 같은 코퍼스로 각각 재는 변형**을 넣었습니다. 두 배치의 차이는 로그가 놓이는 자리뿐이고 메시지 HTML·측정 절차·viewport는 같습니다. viewport는 3열이 성립하는 1440x900입니다.

2026-09-14 측정입니다. 로그 폭은 한 열 1231px, 3열 609px입니다.

| 메시지 | 한 열 append | 3열 append | 한 열 청크 | 3열 청크 |
| --- | --- | --- | --- | --- |
| 20 | 0.29 ms | 0.31 ms | 0.035 ms | 0.035 ms |
| 80 | 0.30 ms | 0.38 ms | 0.040 ms | 0.045 ms |
| 160 | 0.33 ms | 0.33 ms | 0.055 ms | 0.065 ms |

하단 자동 스크롤은 두 배치 모두 모든 크기에서 0.000ms입니다.

**회귀가 없습니다.** 두 배치의 차이는 최대 0.08ms이고, 같은 배치를 두 번 돌렸을 때의 차이(같은 날 두 실행에서 160개 append가 0.33ms와 0.40ms)보다 작습니다. 한 프레임 16.7ms에 비하면 어느 쪽도 의미 있는 비용이 아닙니다. 로그가 절반 폭이 되면 줄바꿈이 늘어 높이가 커지지만, 그 비용이 append와 스크롤에 드러나지 않습니다.

1부(Node에서 재는 Markdown 파싱·React 렌더·Highlighting)는 DOM이 없는 순수 JS 비용이라 배치와 무관합니다. 다만 실행 사이 편차가 큽니다. 같은 날 두 실행에서 메시지 80개 전체 리렌더가 165.98ms와 155.26ms, `createHighlighter` 최초 1회가 449.38ms와 97.81ms였습니다. 이 수치로 배치 변경의 영향을 판단하지 않습니다.

보존하는 것이 아니라는 점입니다. 그래서 색과 문구만 옮기고 다음 셋은 건드리지 않았습니다.

- 자동 스크롤(`use-auto-scroll.ts`)과 그 의존 키
- 낭독 경계: `role="log"`의 `aria-live="off"`, 상태 문단과 새 메시지 안내의 `aria-live="polite"`
- `InterviewMessage`의 `memo` 경계와 미완성 코드 블록을 highlight하지 않는 규칙

### 색

52개를 전부 `globals.css` 토큰으로 옮겼습니다. 남은 하드코딩은 6개이고 모두 이미 개편된 파일과 같은 값입니다.

- `#404040`(primary hover)과 `#d4d4d4`(secondary border)는 `button.module.css`와 같습니다.
- `#fdeaea`·`#a3272c`·`#7c3b3d`는 `experience-candidate-detail.module.css`의 `.selectionError`와 같습니다.
  토큰 9종 밖이지만 확인 실패를 알리는 의미색이라 같은 값을 씁니다.

초점 표시는 `rgba(109, 99, 232, .25)` 계열 세 가지를 `2px solid var(--color-foreground)` 하나로 통일했습니다.
`code-panel.module.css`·`button.module.css`와 같은 규칙입니다.

버튼 높이를 `44px`에서 `32px`로 줄였습니다. 개편된 화면의 버튼이 전부 32px이고 헤더 옆에서 44px 알약이
홀로 커 보였습니다. 44px을 정한 결정은 위키에 없어 근거를 확인하지 못했습니다. 터치 목표가 작아지는
변경이므로 여기 적어 둡니다.

### 문구

오류 상자에 그려지는 문장이 네 층에서 오기 때문에 화면 컴포넌트만 옮기면 상자가 반만 번역됩니다.
네 곳을 같이 옮겼습니다.

| 파일 | 무엇 |
| --- | --- |
| `interview-stream-view.tsx` | 상태 문구, 오류 안내, 절단 안내, 답변 입력, 종료 확인 (43개) |

| `api/interview/stream/route.ts` | 서버가 내려보내 화면이 그대로 그리는 `message` 8종 |

`llm-error.ts`는 `ExperienceCandidateOutputError`를 만들지만 `src/features/interview/` 소유이고 질문 생성
경로에서만 씁니다. 후보 생성 화면의 오류 문구는 `experience-candidates/errors.ts`가 따로 만들므로 영향이
없습니다.

절단 안내는 영어로 옮기면서 단수·복수 문제가 생겼습니다. "1 question-and-answer pairs ... were dropped"가
되었습니다. `candidate-period.ts`의 `pluralCount`를 재사용하고, 동사가 개수에 따라 바뀌지 않도록 주어를
이력 쪽으로 옮겼습니다. "the history sent with the next question drops N question-and-answer pair(s)
starting here"입니다.

### 남은 차이

- 디자인 원본의 메시지 행은 `YOU`·`AGENT` 라벨을 본문 왼쪽 고정폭 칸에 두고 오른쪽에 시각을 적습니다.
  여기서는 라벨을 본문 위에 그대로 두었습니다. DOM 구조를 바꾸는 변경이고 시각 데이터가 없습니다.

  highlight 전(회색)과 후(흰색)의 배경이 다릅니다. 테두리와 라운드와 여백은 두 경로에 같이 걸었습니다.
