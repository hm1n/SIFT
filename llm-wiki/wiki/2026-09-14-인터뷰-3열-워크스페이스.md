# 인터뷰 3열 워크스페이스와 코드 근거 패널

이슈 #98이 만든 인터뷰 화면의 현재 계약입니다. 배경은 `wiki/2026-09-10-디자인-개편-계획.md`에 있고, 앞 단계인 경험 후보 화면은 `wiki/2026-09-11-경험후보-master-detail-화면-개편.md`에 있습니다. 확인 가능·불가 구분의 원본 계약은 `wiki/2026-08-24-확인가능불가-구분-계약.md`이고, 스트리밍 렌더링 결정은 `wiki/2026-08-25-스트리밍-렌더링-측정과-전송-계약.md`입니다.

**이 문서는 `wiki/2026-08-25-인터뷰-화면-근거패널-배치.md`의 결정 1(근거 패널을 질문 아래 한 열로 둔다)을 대체합니다.** 같은 문서의 결정 2(화면에서 patch를 추가로 자르지 않는다)와 절단 알림·확인 수준 표시 경계는 그대로 유효합니다.

확인 날짜는 2026-09-14입니다.

## 1. 배치

왼쪽 코드 근거, 가운데 대화, 오른쪽 PAAR의 3열입니다. 한 열로 쌓던 배치를 바꾼 이유는 "코드를 보고 → 왜 그렇게 했는지 설명하고 → 경험으로 정리한다"는 이 제품의 핵심 동작이 세로 배치에서는 드러나지 않기 때문입니다.

| 열 | 기본 폭 | 한계 |
| --- | --- | --- |
| 코드 | 300px | 200~520px |
| 대화 | 남는 폭 | 최소 280px |
| PAAR | 280px | 220~480px |

양옆 두 열은 헤더 토글로 접히고 손잡이로 폭을 바꿉니다. 폭 계산은 열의 한계만 보지 않고 대화 열의 최소 폭까지 함께 봅니다. 한쪽을 넓히다가 대화 열이 최소 폭 아래로 밀리면 더 넓어지지 않습니다.

워크스페이스 폭이 708px(세 열 최소 폭 200 + 280 + 220에 손잡이 8을 더한 값)보다 좁으면 `[ CODE ] [ INTERVIEW ] [ PAAR 0/4 ]` 탭으로 바뀝니다. 판정 기준은 화면 폭이 아니라 `ResizeObserver`로 잰 워크스페이스 폭입니다. 사이드바 208px 때문에 화면 폭과 어긋나므로 미디어 쿼리를 쓰지 않았습니다.

**탭 모드에서도 세 열을 모두 DOM에 남깁니다.** 보이지 않는 열은 `visibility`로만 감춥니다. 대화 열을 떼면 스트림이 끊기고 대화 이력이 사라지기 때문이고(이슈 #98 Constraint), `display: none`을 쓰지 않는 이유도 같은 자리에 있습니다. 높이가 0이 되면 로그의 자동 스크롤이 하단을 잡지 못한 채 다시 나타납니다. `visibility: hidden`은 레이아웃을 남기면서 접근성 트리와 포커스에서만 뺍니다.

가운데 열의 `InterviewStreamView`는 렌더링 방식, 자동 스크롤, 낭독 경계를 그대로 둡니다. 바꾼 것은 CSS 높이 규칙 하나입니다. 한 열로 쌓던 시절의 `max-height: 60vh`는 열 높이와 무관한 값이라 열 아래가 비어 있어서, 로그가 열이 준 높이를 채우도록 `flex: 1; min-height: 0`으로 바꿨습니다. 같은 gap을 유지하려고 `.stream`의 grid를 flex로 바꿨습니다.

## 2. 코드 패널

`InterviewEvidencePanel`을 `CodePanel`로 대체했습니다. 스냅샷의 `커밋 → 파일` 구조를 `파일 → 커밋`으로 뒤집어(`evidence-files.ts`) 파일 트리와 diff 뷰어를 그립니다. 파일 하나를 고르고 그 파일이 어느 커밋에서 어떻게 바뀌었는지 넘겨 보는 것이 이 패널의 조작입니다.

- **파일 상태.** GitHub의 `status` 7종을 디자인의 added·modified·deleted 셋으로 좁힙니다. `renamed`와 `copied`는 이전 경로가 스냅샷에 없어 새로 생긴 파일과 구분해 보여 줄 수 없으므로 modified로 모읍니다. **여러 커밋에 걸친 파일은 언제나 modified입니다.** 스냅샷에 커밋 시간 순서가 없어(`EvidenceSnapshotCommit`에 날짜가 없고 배열 순서는 역할 순서입니다) added 뒤 deleted인지 그 반대인지 재구성할 수 없습니다. 순서를 모르는 채 한쪽을 고르면 실제와 어긋난 상태를 단정하게 됩니다.
- **디렉터리 트리.** 모든 디렉터리가 공유하는 앞 구간만 이름에서 덜어냅니다. 300px 폭에서 모든 줄이 `src/features/...`로 시작하면 정작 다른 부분이 잘려 나갑니다. 마지막 한 세그먼트는 남깁니다. 전부 덜어내면 묶음 이름이 사라집니다. 트리는 한 겹입니다.
- **patch 파싱.** `@@ -a,b +c,d @@` hunk 헤더로 old/new 줄 번호를 추적합니다. **절단된 patch가 정상 입력입니다.** hunk 헤더 없이 시작하거나 줄 가운데서 끊긴 입력이 들어오므로, 파싱에 실패해 빈 화면을 그리지 않고 아는 것만 붙이고 모르는 줄 번호는 null로 둡니다. 접두어까지 잘려 나간 줄은 버리지 않고 문맥 줄로 남깁니다. 버리면 사용자가 보는 diff가 조용히 짧아집니다.
- **줄 번호.** 추가된 줄은 변경 후 번호, 나머지는 변경 전 번호를 씁니다. 디자인 원본은 변경 전 번호만 써서 추가된 줄의 번호 칸이 비는데, 그러면 추가된 줄이 새 파일의 몇 번째 줄인지 알 수 없습니다.
- **diff 색.** 추가와 삭제를 색으로 가르지 않습니다. 배경 대비, `+`/`−` 기호, 왼쪽 표시선 셋으로 구분합니다(이슈 #98 Non-goal). 디자인 원본의 연초록·연분홍 배경은 옮기지 않았습니다.
- **FILE 모드.** 근거 스냅샷에 파일 전체 원문이 없어 비활성입니다. 자리를 없애지 않고 비활성 버튼으로 두되 왜 못 쓰는지를 접근성 이름에 남깁니다.

## 3. Loading·Error를 만들지 않은 이유

이슈 #98 Goal은 코드 패널의 상태 3개(`LOADING EVIDENCE`, `NO EVIDENCE`, `ERROR / EVIDENCE(Retry)`)를 요구했습니다. **셋 중 둘은 현재 아키텍처에서 도달할 수 없어 만들지 않았습니다.** 사용자와 착수 전에 확인한 결정입니다.

- `LOADING`: 근거 스냅샷은 `confirmExperienceSelection`이 확정 시점에 동기 순수 함수로 만듭니다. 관측할 진행 상태가 없습니다. 시간 같은 대리 지표로 가짜 전환을 만들지 않는다는 기존 결정(`experience-selection.ts`)을 그대로 따릅니다.
- `ERROR + Retry`: 스냅샷 생성 실패는 확정 단계에서 `EXPERIENCE_SELECTION_ERROR_COPY`로 갈려 후보 화면에 남습니다. 인터뷰 화면에 도달한 시점에는 재시도할 대상이 없습니다.
- `NO EVIDENCE`(파일 0개): `evidence-snapshot.ts`가 모든 커밋의 변경 파일이 0개인 근거를 `no_repository_evidence`로 미리 막습니다. 파일 트리가 비는 경우가 없습니다.

AGENTS.md의 "방어 코드를 추가할 때 그 코드가 실제로 도달 가능한지 확인합니다"와 "그 상태를 직접 나타내지 않는 대리 지표를 쓰지 않습니다"에 걸리는 자리라, 검증할 수 없는 분기를 만드는 대신 이 문서에 차이를 남깁니다.

실제로 도달하는 상태는 하나입니다. **선택한 파일의 그 커밋 patch 본문이 없는 경우(`NO DIFF BODY`)**이고, 이유를 예산 소진과 GitHub 미제공으로 갈라 보여 줍니다. 근거 로드가 비동기로 바뀌면 그때 세 상태를 추가합니다.

## 4. 확인 가능·불가 안내는 시각적으로만 숨깁니다

디자인의 `CodePanel`에는 확인 수준 안내의 자리가 없습니다. Constraint는 그 안내를 제거하지 말라고 합니다. 둘을 함께 만족시키려고 #97과 같은 방법을 씁니다. **DOM과 `aria-describedby` 연결은 남기고 화면에서만 감춥니다.** `aria-label`로 이름만 주거나 DOM에서 지우면 안내가 스크린리더에서 사라지고, 그것이 이슈 #47 PR #52 1차 리뷰의 P1이었습니다.

시각적으로 숨기는 것은 넷입니다. `REPOSITORY_VERIFIED_NOTICE`, `EVIDENCE_VERIFIABILITY_NOTICE`, `RELATED_COMMITS_VERIFICATION_NOTICE`, 그리고 `unverifiableItems` 목록(`What can't be confirmed from the Repository`)입니다. 앞 둘은 패널의 `aria-describedby`가 가리킵니다.

**patch 절단·미포함 안내는 여기 해당하지 않습니다.** 근거가 온전한지 판단하는 데 직접 쓰이므로 눈에 보이는 자리를 따로 만듭니다. 파일 단위 절단은 diff 뷰어 아래, 스냅샷 전체의 상한 절단은 패널 바닥입니다. 보는 자리가 달라 하나가 나머지를 감추지 않는다는 기존 결정을 유지합니다. 파일 단위 안내에 단계를 지목하지 않는 것도 그대로입니다. `evidence-snapshot.ts`가 Stage B 절단과 예산 절단을 한 boolean으로 합쳐 실어 오므로 화면이 출처를 가를 수 없습니다.

색인에서 찾지 못한 커밋은 diff 뷰어가 무엇을 확인할 수 없는지 말합니다(`Not found in the commit index — title, message, and PR info can't be confirmed.`). 제목이 비었다는 사실만 보여 주면 사용자는 그 커밋에 메시지가 없다고 읽습니다.

## 6. 렌더링 비용 측정

`streaming-render-cost.measure.mts` 2부는 합성 페이지를 `page.setContent`로 띄웁니다. 실제 앱을 로드하지 않으므로 그대로 다시 돌리면 배치를 바꿔도 정의상 같은 값이 나옵니다. 그래서 2부에 **한 열 배치와 3열 배치를 같은 코퍼스로 각각 재는 변형**을 넣었습니다. 두 배치의 차이는 로그가 놓이는 자리뿐이고 메시지 HTML·측정 절차·viewport는 같습니다. viewport는 3열이 성립하는 1440x900입니다.

2026-09-14 측정입니다. 로그 폭은 한 열 1231px, 3열 609px입니다.

| 메시지 | 한 열 append | 3열 append | 한 열 청크 | 3열 청크 |
| --- | --- | --- | --- | --- |
| 20 | 0.29 ms | 0.31 ms | 0.035 ms | 0.035 ms |
| 80 | 0.30 ms | 0.38 ms | 0.040 ms | 0.045 ms |
| 160 | 0.33 ms | 0.33 ms | 0.055 ms | 0.065 ms |

하단 자동 스크롤은 두 배치 모두 모든 크기에서 0.000ms입니다.

**회귀가 없습니다.** 두 배치의 차이는 최대 0.08ms이고, 같은 배치를 두 번 돌렸을 때의 차이(같은 날 두 실행에서 160개 append가 0.33ms와 0.40ms)보다 작습니다. 한 프레임 16.7ms에 비하면 어느 쪽도 의미 있는 비용이 아닙니다. 로그가 절반 폭이 되면 줄바꿈이 늘어 높이가 커지지만, 그 비용이 append와 스크롤에 드러나지 않습니다.

1부(Node에서 재는 Markdown 파싱·React 렌더·Highlighting)는 DOM이 없는 순수 JS 비용이라 배치와 무관합니다. 다만 실행 사이 편차가 큽니다. 같은 날 두 실행에서 메시지 80개 전체 리렌더가 165.98ms와 155.26ms, `createHighlighter` 최초 1회가 449.38ms와 97.81ms였습니다. 이 수치로 배치 변경의 영향을 판단하지 않습니다.

## 10. 3열이 셸 높이를 못 받던 원인 (같은 PR)

실물에서 세 열이 짧게 그려지고 아래가 비었습니다. 원인은 인터뷰 화면이 아니라 그 위 한 칸,
`repository-analysis.module.css`의 `.content`였습니다.

```css
.content { flex: 1; min-height: 0; padding: 24px 32px 32px; }   /* display가 없어 block */
```

`flex: 1`은 자기 자신이 부모에서 늘어나는 규칙이라 `.content`는 787px을 제대로 받았습니다. 그런데
`.content`가 블록 컨테이너라 그 안의 `interview-screen.module.css`의 `.screen { flex: 1 }`을 받아 줄
flex 부모가 없었습니다. 높이가 내용만큼으로 줄고, `.workspace`가 20px이 되었습니다.

`display: flex; flex-direction: column`을 더해 고쳤습니다. 셸 콘텐츠 787px 기준 실측입니다.

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| `.content` display | `block` | `flex` |
| `.content` 안쪽 높이 | 731px | 731px |
| 인터뷰 `.screen` | 64px (헤더만) | 731px |
| `.workspace`(3열) | 20px | 687px |

측정은 dev 서버가 내려주는 실제 CSS 청크 4개를 받아 같은 DOM 중첩을 만들고 `display`만 되돌려
비교했습니다. jsdom은 레이아웃을 계산하지 않아 회귀 테스트를 넣지 못했습니다.

높이를 받는 전체 사슬은 이렇습니다. 한 칸이라도 블록이면 거기서 끊깁니다.

```
html[height:100%] → body[flex column] → .shell[flex:1, flex] → app-shell .content[flex:1, flex column]
  → main.screen[flex:1, flex column] → .content[flex:1, flex column]  ← 여기가 끊겨 있었습니다
    → 인터뷰 .screen[flex:1, flex column] → .workspace[flex:1, flex] → .column
```

### 남은 것

`.content`의 패딩(위 24 / 아래 32 / 좌우 32) 때문에 워크스페이스가 787px 중 731px만 씁니다. 후보
master-detail은 테두리 있는 카드라 이 여백이 필요하지만, 인터뷰 3열은 디자인 원본에서 셸 가장자리에
붙습니다. 패딩을 `ExperienceCandidateList`의 후보 분기(`.state`)로 옮기면 갈라지는데, 그 분기의
`margin-top`·`border-top`과 함께 봐야 해서 이번에 손대지 않았습니다.


## 11. 메시지 블록이 화면 높이를 따라 늘어나던 결함 (같은 PR)

10절에서 높이가 제대로 내려가자 다음 결함이 드러났습니다. 대화가 짧을 때 메시지 블록이 창 높이를
따라 늘어났습니다. 창을 키우면 메시지도 같이 커졌습니다.

### 원인

`.log`는 grid 컨테이너이고 grid의 `align-content` 기본값은 `stretch`입니다. **남는 높이를 자동 크기
행에 나눠 줍니다.** 그전까지는 `.log`에 `max-height: 60vh`만 있어 컨테이너가 내용만큼만 자랐고,
남는 높이가 없어 이 동작이 드러나지 않았습니다. #98이 열 높이를 채우도록 `flex: 1; min-height: 0`으로
바꾸면서 남는 높이가 생겼습니다. #98이 만든 회귀입니다.

`align-content: start`를 더해 고쳤습니다. `experience-candidate-list.module.css`의 `.candidateList`가
같은 이유로 이미 같은 선언을 쓰고 있었습니다.

### 같은 원인이 한 곳 더 있었습니다

`display: grid`와 `flex: 1`을 함께 쓰는 자리를 전부 찾아 보니 셋이었고, 그중 하나가 아직 안 막혀
있었습니다. `experience-candidate-detail.module.css`의 `.body`입니다. 목록 패널이 `max-height: 640px`
라 내용이 짧은 후보에서는 상세 쪽에 남는 높이가 생기고, 문단 사이가 화면 높이를 따라 벌어집니다.
지적받은 줄만 고치지 않는다는 규칙에 따라 함께 고쳤습니다.

| 컨테이너 600px, 내용은 두 줄 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 대화 메시지 1 | 275px | 58px |
| 대화 메시지 2 | 288px | 71px |
| 후보 상세 문단 1 | 268px | 21px |
| 후보 상세 문단 2 | 268px | 21px |

측정은 10절과 같은 방식입니다. dev 서버의 실제 CSS 청크를 받아 `align-content`만 되돌려 비교했습니다.
jsdom은 레이아웃을 계산하지 않아 회귀 테스트를 넣지 못했습니다.

### 규칙

**`display: grid`인 컨테이너가 `flex: 1`로 남는 높이를 받으면 `align-content: start`가 함께 있어야
합니다.** 없으면 행이 늘어납니다. 이 저장소에서 그 조합은 지금 셋이고 모두 `start`입니다.

`keep-all`은 한국어를 어절 단위로 끊습니다. `anywhere`는 좁아진 대화 열에서 한 단어를 글자 단위로
갈랐습니다.

### 순환 표시를 CSS로 돌립니다

디자인 원본 `ThinkingRow`는 `setInterval`로 400ms마다 React 상태를 바꿉니다. 그대로 옮기면 질문이
도착하는 동안 내내 렌더가 한 번씩 더 돕니다. 스트리밍 중 리렌더 범위를 줄이는 것이 이 화면의 핵심
제약이라(AGENTS.md) 같은 모양을 keyframe 셋으로 만들었습니다. 렌더가 0이고
`prefers-reduced-motion`도 CSS에서 함께 처리됩니다. 칸마다 차는 시점은 다르고 비는 시점은 같아서
`animation-delay` 하나로는 만들 수 없고 keyframe이 셋 필요합니다.

### 정의되지 않은 CSS Module 클래스를 참조하면 조용히 드러납니다

12절에서 답변 칸 라벨을 `styles.visuallyHidden`으로 감췄다고 적었는데 실제로는 감춰지지 않았습니다.

`className={undefined}`는 속성 자체를 지웁니다. 타입도 통과하고 lint도 통과하고 테스트도 통과합니다.
감추려던 것이 감춰지지 않은 경우라 화면을 눈으로 보기 전에는 드러나지 않습니다. 실제로 사용자가
화면에서 `Answer`를 보고 물어서 알았습니다. 같은 경로로 생성 중 표시의 대체 문장도 드러나 있었습니다.

선언을 더해 고치고, 같은 종류가 다시 생기지 않도록 `src/css-module-class-reference.test.ts`를

일부러 선언 이름을 바꿔 실패하는 것을 확인했습니다. 저장소 전체에서 어긋난 참조는 이 하나뿐이었습니다.

고친 뒤 라벨은 1x1이고 `label.control`이 입력 칸을 가리켜 접근 가능한 이름 `Answer`가 남습니다.

### 답변 칸은 초점 표시를 두지 않습니다

디자인 원본은 composer에 `focus-within`으로 테두리를 진하게 합니다. 여기에 브라우저 기본 초점
테두리까지 겹쳐, 초점을 주면 테두리가 두 번 강조됐습니다. 사용자가 그 강조를 빼기로 해서 둘 다
걷었습니다. `focus-within` 규칙을 지우고 답변 칸에 `outline: none`을 명시했습니다.

**이 칸의 초점은 글자 커서만 알립니다.** `outline: none`을 보고 되돌리려는 사람이 나올 수 있어
적어 둡니다. 같은 화면의 다른 조작(Send, Retry, 종료, 새 메시지 보기, 로그 자체)은 2px 초점 표시를
그대로 씁니다. hover와 입력 상한 초과(`data-invalid`)의 테두리 변화도 초점이 아니라 남겼습니다.

실측으로 답변 칸은 초점 전후 테두리가 `rgb(229, 229, 229)`로 같고 outline이 `none`이며, Send 버튼은
`2px solid rgb(10, 10, 10)`이 나오는 것을 확인했습니다.

## 13. 높이 사슬의 진짜 출발점은 `body`였습니다 (같은 PR)

10절에서 `.content`를 flex 컨테이너로 고쳤지만 그것으로 끝이 아니었습니다. 코드 패널에서 변경 줄이
많은 파일(`package-lock.json`, +8576 −1923)을 고르니 diff가 자기 안에서 스크롤하지 않고 화면 전체가
늘어났습니다. 셸 콘텐츠가 1203px이 되어 문서에 스크롤이 생겼습니다.

### 원인

```css
html { height: 100%; }
body { min-height: 100%; display: flex; flex-direction: column; }   /* ← 여기 */
```

`min-height`는 아래 한계만 정합니다. 내용이 뷰포트를 넘으면 body가 같이 자랍니다. body가 자라면
`.shell`도 자라고, 그 아래로 `flex: 1; min-height: 0`을 줄줄이 걸어 둔 칸들이 **줄어들 이유를 잃습니다.**
줄어들 준비만 해 놓고 위에서 확정된 높이가 내려오지 않은 것입니다.

그래서 10절까지 고친 사슬은 내용이 짧을 때만 맞았습니다. `min-height: 100%`가 바닥을 잡아 주는
동안에는 뷰포트 높이로 보였고, 내용이 그 위로 올라가는 순간 전부 풀렸습니다.

`body`를 `height: 100%`로 바꿨습니다. 800줄 diff 기준 실측입니다.

| | 전 | 후 |
| --- | --- | --- |
| `body` | 16254px | **900px** (뷰포트) |
| 문서 스크롤 | 생김 | **없음** |
| `.shell` | 16210px | 856px |
| `.workspace` | 16110px | 756px |
| `.diffBody` | 9912px | 393px |
| `.diffBody` 자체 스크롤 | 있음 | 있음 |

diff를 5줄·800줄·12000줄로 바꿔 가며 재도 `body` 900px, `.workspace` 756px, `.diffBody` 393px이
그대로입니다. 파일 크기가 부모 높이를 바꾸지 않고 diff만 자기 안에서 스크롤합니다.

### 셸을 쓰지 않는 화면

로그인 화면은 `AppShell` 밖에 있어 body가 곧 스크롤 컨테이너입니다. `globals.css`의
`overflow-x: hidden` 때문에 body의 `overflow-y`가 `auto`로 계산되므로 내용이 뷰포트를 넘으면 body가
스크롤합니다. 뷰포트 380px에 600px짜리 카드를 넣어 확인했고, 스크롤이 살아 있고 카드 위쪽이 잘리지
않았습니다.

### 규칙

**`flex: 1; min-height: 0`은 위에서 확정된 높이가 내려올 때만 뜻이 있습니다.** 사슬의 출발점이
`min-height`면 중간을 아무리 고쳐도 내용이 길어지는 순간 전부 풀립니다. 11절의 grid 규칙과 함께
이 화면의 높이 계약 둘입니다.

## 15. diff의 추가·삭제를 색으로 가릅니다 (같은 PR, Non-goal 뒤집음)

**이슈 #98은 이것을 하지 않기로 했었습니다.** Non-goal에 `diff에 semantic 색을 넣는 결정. 우선
배경 대비와 +/- 기호, 왼쪽 표시선으로만 구분하고, 읽기 어렵다는 실측이 있을 때만 극히 절제된 색을
검토합니다`로 적혀 있었고 `code-panel.module.css` 머리 주석도 같은 근거를 달고 있었습니다.

실물을 띄워 놓고 본 사용자가 뒤집었습니다. 색 없이도 읽힐 것이라는 이슈 작성 시점의 전제가 실제
화면에서 맞지 않았습니다. 값은 디자인 원본(`Chat Interface Design/src/App.tsx`의 `DiffLineRow`)을
그대로 가져와 `globals.css` 토큰으로 올렸습니다.

```css
--color-diff-add: #16a34a;   --color-diff-add-surface: #f0fdf4;
--color-diff-del: #dc2626;   --color-diff-del-surface: #fef2f2;
```

원본에서 이 색이 쓰이는 자리는 셋이고 우리 쪽도 같은 셋이라 전부 맞췄습니다. diff 줄의 `+`/`−`
기호와 배경, 파일 트리의 `+42 −5`, diff 헤더의 `+42 −5`입니다. 집계 숫자는 `+`와 `−`가 같은
클래스를 쓰고 있어 `data-kind="add|del"`로 갈랐습니다. 순서 의존(`:first-child`)을 쓰지 않은
이유는 사이에 무엇이 들어오면 조용히 어긋나기 때문입니다.

### 색이 대신하게 된 표시 둘을 걷었습니다

| 걷은 것 | 이유 |
| --- | --- |
| add 줄의 왼쪽 세로 표시선 | 원본에서 그 자리는 `focused` 줄 표시입니다. 우리에겐 `focused` 개념이 없어 추가·삭제 구분에 전용하고 있었습니다. 정렬용 `transparent`만 남겼습니다. |
| del 줄 본문의 취소선 | 원본에 없습니다. 코드에 그어진 선이 `-`·`_`·`=`와 섞여 읽기를 해칩니다. 색 없이 삭제를 표시해야 했던 제약이 만든 것입니다. |

### 색만으로 가르지 않습니다

색으로만 정보를 전달하면 색각 이상과 흑백 출력에서 정보가 사라집니다. 걷어내지 않은 것이 그
역할을 합니다. `+`/`−` 기호가 `.diffMark`에 그대로 있고, 줄 번호가 add는 새 번호·del은 옛 번호를
보여 주며, DOM에 `data-type`이 남습니다. 색은 덧붙이는 신호이지 유일한 신호가 아닙니다.

### 테스트는 값이 아니라 관계를 고정합니다

jsdom은 CSS Module 선언을 적용하지 않아 렌더 결과에서 색을 읽을 수 없습니다.
`src/css-module-class-reference.test.ts`의 선례대로 소스를 읽습니다. 고정하는 것은 `#16a34a`라는
값이 아니라 둘입니다. **추가와 삭제가 서로 다른 토큰을 가리키는지**, 그리고 **색을 지웠을 때 남는
`+`/`−` 기호가 DOM에 있는지**. 두 번째는 이 결정이 한 번 뒤집힌 자리라 다음 사람이 "색이 있으니
기호는 지워도 되겠다"로 가는 것을 막기 위해서입니다. 색 규칙을 되돌려 실제로 실패하는 것을
확인했습니다.

이 끌어올리기가 이전에 감수하던 값을 없앴습니다. 10절 시점의 주석은 `종료했는지에 따라 묻지 않게
하려면 훅을 InterviewStreamView 밖으로 끌어올려야 하고, 종료한 뒤 한 번 더 묻는 값을 치르고 훅의
자리를 그대로 둔다`고 적고 있었습니다. 지금은 훅이 밖에 있습니다. 그런데도 **뒤로가기는 종료 뒤에도
계속 묻습니다.** 근거가 바뀌었기 때문입니다. 종료는 입력만 닫고 대화를 남기지만 뒤로가기는 그
대화까지 지웁니다. 사라지는 것이 남아 있는 한 확인을 걷지 않습니다.

블록이 다 차야 눌리는 원본의 잠금은 옮기지 않았습니다. 완료 개수가 언제나 0이라 지금 옮기면
인터뷰를 끝낼 수 없습니다. 블록 계약이 생기는 #89~#91에서 함께 붙입니다.

### 훅이 아는 사실을 화면이 따로 받지 않습니다

`InterviewStreamView`가 `stream`과 `hasSnapshot`을 따로 받고 있었습니다. prop 주석은 `두 값을 따로
받으면 서로 어긋난 조합을 넘길 수 있으므로 갈라지기 전의 사실을 받습니다`라고 적혀 있었는데, 한
단계 덜 간 것이었습니다. 그 사실과 `stream`이 여전히 따로 넘어와서, 스냅샷이 있는 훅의 `stream`에
`hasSnapshot={false}`를 붙일 수 있었습니다. 주석이 경계하던 바로 그 어긋남입니다.

`snapshot`을 실제로 받는 것은 훅이므로 판정을 `InterviewStreamState`로 올렸습니다.
`InterviewStreamView`의 prop은 `stream` 하나가 되고 어긋난 조합을 표현할 방법이 사라집니다.
**주석이 막던 것을 타입이 막습니다.**

같은 리뷰에서 함께 정리한 것은 셋입니다. `url`은 호출부 3곳이 전부 같은 상수를 넘기고 있어 훅
기본값으로 내리고 `DEFAULT_INTERVIEW_STREAM_URL` export를 지웠습니다. `.endConfirmButton`은
`.endButton`에서 `width: 100%`만 뺀 같은 선언인데 그 `width`는 부모 grid가 어차피 주므로 한
클래스로 합쳤습니다. `` `${useId()}-end-confirm` ``의 접미사는 id가 하나뿐이라 지웠습니다.

### 접으면 끝낼 수 없습니다

종료 조작이 PAAR 패널 안에 있으므로 헤더 토글로 그 열을 접으면 종료 버튼도 함께 사라집니다.
다시 펴야 끝낼 수 있습니다. 디자인 원본의 자리를 따른 결과이고, 테스트가 이 동작을 고정합니다.

## 17. `develop` 병합에서 #90과 겹친 자리 (같은 PR)

PR #118·#119가 `develop`에 들어가면서 이 브랜치와 8개 파일이 충돌했습니다. 원인은 둘로 갈립니다.

- **문구.** `develop`이 이 브랜치가 영어로 옮긴 자리에 한국어 문구를 새로 들여왔습니다.
- **훅 자리.** 이슈 #90이 `InterviewStreamView`에 훅을 하나 더 붙였는데, 이 브랜치는 16절에서
  그 훅을 화면 밖으로 뺐습니다.

### 훅 자리 — 두 설계가 정면으로 부딪혔습니다

`develop`은 `InterviewStreamView`가 `snapshot` 유무로 `useInterviewStream`과
`useExperienceInterview` 중 하나를 부르게 했습니다. 한 함수에서 훅을 조건부로 부를 수 없어
`TestStreamInterviewView`·`ExperienceInterviewStreamView`·`InterviewStreamBody` 셋으로 갈랐습니다.

**16절의 끌어올리기가 그 분할을 불필요하게 만듭니다.** 이 컴포넌트가 훅을 아예 부르지 않으면
조건부 호출 문제 자체가 없어집니다. 어느 훅을 쓸지는 `InterviewScreen`이 정하는데, 그 화면은
`snapshot`이 필수 prop이라 **언제나 `useExperienceInterview`** 하나입니다. 조건이 없습니다.

| | `develop` | 병합 결과 |
| --- | --- | --- |
| 훅을 부르는 곳 | `InterviewStreamView` 안, 두 갈래 | `InterviewScreen` 하나 |
| 컴포넌트 수 | 4 (`View`·`TestStream`·`Experience`·`Body`) | 1 (`View`) |
| 분기 조건 | `snapshot === undefined` | 없음 |

테스트는 두 경로를 다 봐야 해서 하네스가 `develop`이 하던 분기를 그대로 합니다. 실제 화면에는
없는 갈래가 테스트에만 남는 모양인데, 테스트용 스트림 경로를 계속 덮으려면 필요합니다.

엔드포인트 상수 `DEFAULT_EXPERIENCE_BLOCK_UPDATE_URL`은 `interview-stream-view.tsx`에서
`use-experience-interview.ts`로 옮겨 `blockUpdateUrl` 기본값으로 뒀습니다. 표시 컴포넌트가
엔드포인트를 들고 있을 이유가 없어졌고, 16절에서 질문 스트림 URL을 훅 기본값으로 내린 것과
같은 처리입니다.

### 호출 횟수가 밀린 테스트

#90은 답변 한 건마다 블록 갱신 호출을 하나 더 보냅니다. `fetchImpl` 호출 횟수와 `mock.calls`
인덱스를 쓰던 테스트가 전부 한 칸씩 밀렸습니다. 충돌로 표시된 것은 셋이고, **하나는 표시되지
않았습니다** — 이 브랜치가 나중에 추가한 단축키 테스트라 같은 줄을 건드리지 않았기 때문입니다.
병합 뒤 전체 스위트를 돌려서야 드러났습니다. 충돌 표식이 없는 자리에도 같은 원인이 있을 수
있다는 뜻입니다.

이력 상한 절단 테스트는 `develop` 쪽으로 갈았습니다. #90이 열 턴 자동 종료를 넣으면서 상한에
닿기 전에 인터뷰가 끝나 버려, 같은 자리의 테스트가 다른 것을 보게 됐습니다.

### 문구

9절의 기준(서비스 chrome은 영어)을 그대로 적용했습니다. `develop`이 들여온 화면 문구 7건을
영어로 옮겼습니다. `auth-session.ts`의 오류 2건, 후보 대체 제목, 답변 라벨, 다시 시도, 역할
라벨, 종료 안내입니다. 픽스처 데이터와 개발자 주석의 한국어는 그대로 뒀습니다.

`commitTitle`의 대체 제목은 양쪽이 다 바뀌어 있었습니다. `develop`은 `candidate.summary`를
먼저 쓰도록 기준을 바꿨고 이 브랜치는 문구를 영어로 옮겼습니다. 둘은 같은 자리의 서로 다른
층이라 **양쪽을 다 받았습니다** — 기준은 `develop`, 문구는 이 브랜치입니다.
