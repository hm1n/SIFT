# Neon 접속 계층과 세션 사용자 번호

이슈 #114가 확정한 계약입니다. 인터뷰 저장과 이어가기(#115)와 분석 결과 저장과 90일 자동 정리(#116)가 이 문서의 결정 위에서 시작합니다. 화면에서 보이는 동작은 이 작업으로 바뀌지 않습니다.

## 저장소

Neon Postgres를 씁니다. 프로젝트는 `steep-feather-35162878`(이름 `SIFT`, `aws-us-east-2`)이고 데이터베이스는 `neondb`, 역할은 `neondb_owner`입니다.

브랜치는 둘입니다.

| 브랜치 | 만든 주체 | 쓰는 곳 |
| --- | --- | --- |
| `production` (기본) | `neon link` | Vercel Production, 그리고 `neon link`가 써 준 로컬 `.env.local` |
| `vercel-dev` | Vercel 마켓플레이스 연결 | Vercel Development |

`vercel-dev`는 스키마를 적용한 뒤에 `production`에서 갈라져 나와서 표 두 개를 그대로 가지고 있습니다. 따로 적용할 필요가 없습니다.

Vercel 마켓플레이스는 새 프로젝트를 만드는 대신 이미 있는 이 프로젝트를 연결했습니다. 이슈 원안은 Neon 프로젝트가 없는 상태를 전제했지만, 실제로는 `neon link`로 먼저 만든 뒤에 연결했습니다. 새로 설치했다면 별개의 프로젝트가 생겨 표를 만든 쪽과 Vercel이 가리키는 쪽이 갈릴 수 있었습니다.

의존성은 `@neondatabase/serverless` 하나입니다. 이 드라이버는 연결을 붙잡지 않고 HTTP 한 번 왕복으로 질의를 끝내므로 서버리스 환경에서 연결 수가 고갈되지 않고, 요청 하나에 질의 하나인 이 서비스의 접근 패턴과 맞습니다.

`neon config init`이 함께 설치한 `@neon/config`와 `@neon/env`는 `devDependencies`에 둡니다. 런타임 코드가 `neon.ts`를 import하지 않으므로 프로덕션 번들과 무관하고, 이슈가 건 "새 의존성은 접속 드라이버 하나" 제약의 취지가 유지됩니다.

## 환경변수

| 이름 | 쓰는 곳 |
| --- | --- |
| `DATABASE_URL` | 애플리케이션 질의. 연결 풀을 거칩니다 |
| `DATABASE_URL_UNPOOLED` | `npm run db:schema`의 DDL. 없으면 `DATABASE_URL`로 내려갑니다 |

`neon link`가 로컬 `.env.local`에 써 주고, Vercel에서는 마켓플레이스 연결이 같은 이름으로 주입합니다. 2026-09-14에 Vercel 프로젝트의 Environment Variables에서 두 이름이 그대로 있는 것을 확인했습니다. `NEON_BRANCH`도 로컬에 함께 주입되지만 코드가 읽지 않습니다.

`getSql()`은 환경변수를 모듈 최상단이 아니라 호출 시점에 읽습니다. 최상단에서 읽으면 빌드 시점 값이 고정되고, 값이 없는 환경에서는 모듈을 import하는 것만으로 실패합니다. 값이 없거나 공백뿐이면 `DatabaseError`의 `config_missing`을 던집니다.

## 스키마 적용

마이그레이션 도구를 쓰지 않습니다. `db/schema.sql` 한 파일과 `npm run db:schema`(`scripts/apply-schema.mts`)로 적용합니다.

도구를 쓰지 않기로 한 이유는 둘입니다. 마이그레이션 도구는 "새 의존성은 접속 드라이버 하나" 제약을 깹니다. 그리고 표가 둘이고 아직 배포된 적이 없어 되돌릴 이력이 없습니다. 대신 모든 문장을 `if not exists`로 써서 여러 번 돌려도 결과가 같게 만들었습니다.

정의서 SQL과 다른 점이 하나 있습니다. 정의서의 `create index on ...`에는 인덱스 이름이 없어 Postgres가 이름을 자동으로 붙이고 `if not exists`를 쓸 수 없습니다. 그래서 인덱스 둘에 `repository_analysis_user_created_idx`와 `interview_session_analysis_idx` 이름을 붙였습니다. 표 정의는 정의서 그대로입니다.

스크립트는 Node가 `.mts`를 그대로 실행합니다. 기존 측정 스크립트의 `npx tsx` 관례와 다르고, 그래서 import 지정자에 `.ts` 확장자가 붙습니다. `tsconfig.json`의 `allowImportingTsExtensions`가 이것을 허용합니다.

## 저장 계층 인터페이스

`src/lib/db/store.ts`의 `SiftStore`입니다. 연산은 정의서의 "저장 시점" 표에서 그대로 옵니다.

라우트는 이 타입을 매개변수로 받고 기본값으로 실제 구현을 씁니다. `experience-block` 라우트가 `GenerateBlockUpdate`를 받는 방식과 같습니다. 테스트는 `createInMemoryStore()`를 넘겨 데이터베이스 없이 돕니다. 지금 `vitest` 스위트가 외부 상태 없이 도는 성질을 유지하기 위한 결정이고, 이 결정을 여기서 확정하지 않으면 후속 이슈마다 같은 질문이 반복됩니다.

두 가지 판정은 저장 계층 안에 둡니다.

- **읽기와 쓰기를 가리지 않고 모든 연산이 사용자 번호를 받습니다.** 정리 작업인 `purgeInterviewsOpenedBefore`만 예외입니다. 소유자 판정을 호출하는 쪽에 맡기지 않고 조회와 갱신 조건에 함께 넣습니다. 읽은 뒤에 비교하는 방식이면 비교를 빠뜨린 경로가 하나만 있어도 남의 데이터를 읽거나 씁니다. 남의 것은 `getInterview`에서 `null`, `deleteInterview`에서 `false`, `createInterview`에서 `null`, `appendTurn`에서 `not_found`입니다. 없는 경우와 남의 것인 경우를 구분하지 않습니다.
- 블록 버전이 어긋나면 아무것도 쓰지 않고 `version_conflict`를 돌려줍니다. 여러 탭 문제를 새 개념 없이 막습니다.

`appendTurn`은 덮어쓰지 않고 이어 붙입니다. 서버가 매 턴 받는 이력은 `trimInterviewHistory`를 지나 최근 것만 실려 올 수 있어서, 받은 그대로 덮어쓰면 저장된 대화의 중간이 사라집니다.

### 시간 칸 셋의 뜻이 각각 다릅니다

`interview_session`의 `created_at`, `updated_at`, `opened_at`을 하나로 합치지 않습니다.

| 칸 | 뜻 | 갱신하는 연산 | 쓰는 곳 |
| --- | --- | --- | --- |
| `created_at` | 만든 때 | 없음 | |
| `updated_at` | 마지막으로 이어간 때 | `appendTurn` | 목록 정렬과 화면 표시 |
| `opened_at` | 마지막으로 연 때 | `getInterview` | 90일 자동 정리의 기준 |

`getInterview`는 읽기이지만 `openedAt`을 갱신하고 갱신된 값을 돌려줍니다. 이 호출이 곧 인터뷰를 여는 것이기 때문입니다. 갱신하지 않으면 `opened_at`이 생성 시각에 한 번 박히고 영원히 그대로여서, 매일 여는 인터뷰도 만든 지 90일이면 자동 정리가 지웁니다.

둘을 하나로 합치지 않는 이유는 쓰임이 다르기 때문입니다. 목록에서 골라 읽기만 하고 답을 달지 않아도 사용자는 그 인터뷰를 쓰고 있으므로 정리 대상이 아니어야 합니다. 반대로 화면의 "마지막으로 이어간 시각"은 읽기만 한 것이 아니라 실제로 답을 단 때를 보여야 합니다.

Neon 구현체는 이 이슈에 없습니다. 첫 호출 지점이 생기는 #115에서 넣습니다.

## 세션 쿠키의 사용자 번호

평문 구조가 바뀌었습니다.

```
[형식 번호 1바이트][발급 시각 8바이트][GitHub 사용자 번호 8바이트][GitHub 토큰]
```

식별자로 아이디 문자열이 아니라 숫자 번호를 씁니다. 아이디는 사용자가 바꿀 수 있어서 문자열을 키로 삼으면 이름을 바꾸는 순간 자기 데이터를 잃습니다.

쿠키 수명 `GITHUB_SESSION_MAX_AGE_SECONDS`와 GCM 인증 태그가 평문 전체를 덮는 구조는 그대로입니다. 세 값 모두 변조되지 않습니다.

### 형식 번호가 필요한 이유

사용자 번호가 없던 형식의 쿠키는 복호화가 실패하지 않습니다. 암호화 키가 같고 인증 태그도 맞아서 유효한 값으로 통과하고, 바이트를 자르는 위치만 달라집니다. 그러면 토큰 앞부분을 사용자 번호로 읽고 토큰은 앞이 잘린 채 남아, 조용히 틀린 값으로 GitHub를 호출하게 됩니다. 형식 번호 한 바이트가 그 경우를 구분하는 유일한 근거입니다.

### 옛 형식 쿠키는 다시 로그인시킵니다

형식 번호가 맞지 않으면 기존 `auth_revoked`를 던집니다. 화면은 세션이 만료됐을 때와 같은 `reauthenticate`를 받으므로 새 화면이나 새 문구가 생기지 않습니다.

조용히 채우는 방법과 없는 채로 두는 방법을 접었습니다. 쿠키 수명이 8시간이라 옛 형식은 배포 후 8시간이면 저절로 사라집니다. 조용히 채우려면 세션 토큰을 읽는 라우트 8곳을 모두 고치고 발급 시각을 보존하는 경로를 새로 내야 하는데, 이슈가 손대지 말라고 한 수명 구조가 정확히 거기입니다. 없는 채로 두면 사용자 번호 타입이 영구히 nullable이 되고, 저장이 안 되는 세션을 화면에 설명하는 일이 #115로 넘어갑니다.

### 사용자 번호를 얻는 곳

OAuth 콜백이 토큰을 교환한 뒤 `fetchAuthenticatedUser`로 `GET /user`를 한 번 부릅니다. 응답의 `id`가 안전 정수 범위의 양수가 아니거나 `login`이 비어 있으면 `server_error`로 바꿉니다.

`/user` 실패는 `exchange_failed`로 돌려보냅니다. `config_missing`은 우리 OAuth 설정과 암호화 키가 없을 때만 씁니다. 두 갈래를 묶으면 GitHub이 잠시 답하지 않는 상황에 사용자가 서버 설정을 고치라는 안내를 받습니다.

## MCP 인증

Neon MCP는 장기 보관 API 키 없이 URL만 설정에 두고, 에이전트가 처음 쓸 때 브라우저로 로그인합니다. 도구 범위는 `?projectId=steep-feather-35162878`로 이 프로젝트에 고정됩니다.

처음에 `neon mcp -y`가 발급한 키는 계정 전체 범위였습니다. `--project-id`만으로는 범위가 좁아지지 않습니다. CLI가 설정에 남은 키를 재사용하기 때문이고, 서버에서 키를 폐기해도 마찬가지입니다. 범위를 좁히려면 설정 8곳에서 항목을 지우고 다시 발급하거나 `--oauth`를 써야 합니다.

## 첫 질의가 연결 단계에서 끊기는 관찰

2026-09-14에 `npm run db:schema`를 네 번 돌렸고, 한동안 쉬었다가 처음 부른 두 번이 모두 같은 오류로 죽었습니다. 두 번 다 곧바로 다시 돌리면 정상으로 끝났습니다.

```
ConnectTimeoutError: Connect Timeout Error
(attempted address: api.c-2.us-east-2.aws.neon.tech:443, timeout: 10000ms)
```

응답이 느린 것이 아니라 연결이 10초 안에 맺어지지 않는 단계입니다. Neon이 5분 유휴 후 컴퓨트를 내렸다가 다음 연결에서 깨어나는 동작과 시점이 맞지만 **원인은 확인하지 않았습니다.** 유휴 시간을 바꿔 가며 재현 조건을 재보지 않았습니다.

대응을 이번 이슈에서 하지 않았습니다. 지금 재시도 횟수나 타임아웃 값을 고르면 원인을 모르는 채 상수를 정하는 것이 됩니다. 실제 저장 호출이 생기는 #115에서 재현 조건을 먼저 재고 정합니다. 그때까지는 첫 질의가 이렇게 끊기면 사용자에게 저장 실패로 보인다는 점만 기록해 둡니다.

## 실제 로그인 확인

2026-09-14에 `npm run dev`로 GitHub 로그인을 한 번 돌려 확인했습니다. 확인은 임시 라우트가 `getGitHubSessionFromRequest`를 그대로 불러 사용자 번호와 토큰 길이만 돌려주는 방식으로 했고, 확인 뒤 라우트를 지웠습니다. 쿠키 값은 브라우저 밖으로 내보내지 않았습니다.

로그인한 뒤 사용자 번호 `44727850`과 토큰 길이 40이 나왔습니다. 콜백이 넣은 번호가 뒤 요청에서 그대로 읽히고 토큰도 잘리지 않는 것을 확인했습니다.

## 확인 필요

- 로컬 `.env.local`이 `production` 브랜치를 가리킵니다. Vercel의 Development 환경은 `vercel-dev`를 가리킵니다. 로컬 개발이 프로덕션 브랜치에 쓰게 되므로 로컬을 `vercel-dev`로 옮길지 정해야 합니다.
- 첫 질의 연결 타임아웃의 원인과 대응은 위에 적은 대로 #115에서 정합니다.
- `interview_session.status`에 들어갈 값의 목록을 정하지 않았습니다. 인터페이스는 `in_progress`와 `completed` 둘로 두었고 표에는 제약이 없습니다.
