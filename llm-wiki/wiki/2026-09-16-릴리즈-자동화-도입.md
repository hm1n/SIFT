# 릴리즈 자동화 도입

이슈 #132의 1단계입니다. `production-release` 스킬과 `create-release-note.yml`을 `Andbread_Frontend`에서 옮겨 와 릴리즈 PR 작성부터 태그·GitHub Release 생성까지를 자동화합니다. 첫 배포(`v0.1.0`)는 2단계이고 아직 하지 않았습니다.

## 역할 분담

스킬은 "무엇을 릴리즈할지"와 "릴리즈 노트 내용"까지 책임집니다. 태그와 Release는 만들지 않습니다. 배포가 끝난 것을 확인하고 태그·Release를 만드는 일은 워크플로우가 배포 이벤트를 받아 처리합니다. 사람이 태그를 직접 만들지 않는다는 것이 이슈의 제약입니다.

두 구간을 잇는 것은 릴리즈 PR 본문의 `<!-- release-note:start -->` / `<!-- release-note:end -->` 마커입니다. 워크플로우가 그 사이를 `release-notes.md`로 뽑아 `gh release create --notes-file`에 넘깁니다. 마커 구조와 `[release] vX.Y.Z` 제목 형식은 자동화의 입력 계약이므로 바꾸지 않습니다.

## 원본과 달라진 점

### 1. 서비스 이름

`엔빵`을 `SIFT`로 바꿨습니다. `SKILL.md` frontmatter, `README.md` 개요, `agents/openai.yaml`의 `short_description` 세 곳입니다. `src/app/layout.tsx`의 `metadata.title`이 `SIFT | Repository analysis`라 그 이름을 씁니다. 저장소 이름은 `SIFT`, Vercel 프로젝트 이름은 `sift`, `package.json`의 `name`은 `demian`으로 셋이 다릅니다.

### 2. 배포 이벤트 식별

원본은 `status` 이벤트를 받아 `target_url`이 `https://vercel.com/hm1n/nbread/`로 시작하는지로 배포를 식별합니다. 이 저장소에서는 쓰지 않습니다.

이슈 본문은 이 값을 `https://vercel.com/hm1n/demian/`로 바꾸라고 지시했는데, 그 근거인 `origin/main` 최신 커밋의 status는 2026-08-20 배포입니다. 그 뒤 Vercel 프로젝트 이름이 바뀌어 현재 배포는 `https://vercel.com/hm1n/sift/...`로 옵니다. 지시대로 넣으면 조건이 영원히 안 맞고, job이 조용히 skip되므로 실패가 드러나지도 않습니다.

이름을 `sift`로 고치는 대신 판별 기준을 바꿨습니다. preview 배포도 context `Vercel`, state `success`, 같은 프로젝트 URL, sender `vercel[bot]`으로 오기 때문에 `status` 이벤트로는 production을 가려낼 수 없다는 문제가 함께 있었습니다.

```
gh api repos/hm1n/SIFT/deployments
6471605847  env=Preview     ref=da3dee5  creator=vercel[bot]
5997496673  env=Production  ref=23d97f7  creator=vercel[bot]  state=success
```

Vercel이 GitHub Deployment를 environment까지 붙여 만들고 있어서, `deployment_status` 이벤트를 받고 `deployment.environment == 'Production'`을 확인하면 Vercel 설정을 바꾸지 않고 프로덕션 승격을 판별할 수 있습니다. 프로젝트 URL 접두어 가드는 되살리지 않고 제거했습니다. 한 번 깨진 대리 지표를 새 이름으로 바꿔 넣으면 다음 이름 변경 때 같은 사고가 납니다.

`sender.login == 'vercel[bot]'`은 그대로 뒀습니다. 이슈가 "확인 필요"로 남긴 항목인데, 최근 status의 `creator`와 deployment의 `creator`가 모두 `vercel[bot]`으로 확인됐습니다.

### 3. 병합 방식 명시

비교 범위 `latest_tag..origin/develop`은 릴리즈 PR을 merge commit으로 병합할 때만 성립합니다. squash나 rebase로 병합하면 태그 커밋이 `origin/develop` 이력에서 벗어나, 다음 릴리즈 범위에 이미 릴리즈한 변경사항이 다시 들어옵니다. 원본 문서에 이 전제가 적혀 있지 않아 `SKILL.md`의 `Release Range`·`Pull Request`와 `README.md`에 적었습니다.

## 트리거가 도는 브랜치

`deployment_status`와 `status`는 저장소 단위 이벤트라 **기본 브랜치**의 워크플로우 파일로 실행됩니다. 이 저장소의 기본 브랜치는 `develop`입니다. 원본 저장소의 실행 이력도 `head_branch=develop`으로 찍혀 있습니다. 이슈 Tasks의 "워크플로우 파일이 `main`에도 있어야 하는지 확인" 항목은 확인할 필요가 없습니다.

## 검증의 한계

CI가 없어 워크플로우를 병합 전에 실행해 볼 수단이 없습니다. 실제 동작은 첫 릴리즈에서 처음 확인됩니다. 대신 판별 조건이 되돌아가는 것만 `scripts/create-release-note-workflow.test.ts`로 잠갔습니다. 트리거 종류, environment 게이트, `EVENT_SHA` 배선, 프로젝트 이름 문자열 미사용, 최소 권한 범위를 검사합니다. 이번에 깨진 두 가지가 모두 "조건이 조용히 안 맞는" 형태였기 때문에, 값이 되돌아가는 것을 막는 것이 지금 넣을 수 있는 유일한 회귀 방어입니다.

자동화가 실패하면 태그를 손으로 만들지 않습니다. 원인을 고쳐 기본 브랜치에 반영한 뒤 Vercel에서 같은 커밋을 재배포하면 새 이벤트로 다시 돕니다. 태그·Release가 이미 있으면 워크플로우가 재실행하지 않고 빠져나갑니다.

## 2단계 전에 확인할 것

프로덕션 환경변수입니다. `main` 최신 배포가 이슈 #1 범위라 그 뒤에 생긴 값이 Vercel Production에 없으면 첫 배포가 깨집니다. 코드가 요구하는 값을 전수로 훑어 본 결과, `.env.example`에 없는 것이 셋입니다.

| 변수 | 읽는 곳 | 없으면 |
| --- | --- | --- |
| `GOOGLE_GENERATIVE_AI_API_KEY` | `experience-candidates/llm-provider.ts`의 `createGoogle()` 기본값 | 경험 후보 Stage A·B와 인터뷰 첫 질문 실패 |
| `OPENAI_API_KEY` | `experience-block/llm-provider.ts`의 `createOpenAI()` 기본값 | 인터뷰 블록 갱신 실패 |
| `GITHUB_OAUTH_CLIENT_ID` / `_SECRET` | `lib/github/oauth.ts` | 로그인 불가 |

앞의 둘은 SDK가 기본 이름으로 읽어서 코드에 `process.env` 표현이 없습니다. 그래서 예시 파일에도 빠졌고, 빌드와 배포는 성공한 뒤 경험 후보 생성과 인터뷰에서만 터집니다.

반대로 **Production에 있으면 안 되는** 값도 있습니다. `NEXT_PUBLIC_LLM_BASE_URL`이 로컬 전환 스위치라, Production 스코프에 남아 있으면 프로덕션 트래픽이 로컬 엔드포인트로 향합니다. 나머지 로컬 변수(`LLM_API_KEY`, `STAGE_A_MODEL`, `STAGE_B_MODEL`, `LLM_TIMEOUT_MS`, `LLM_TEMPERATURE`, `NEXT_PUBLIC_LLM_STAGE_B_MAX_*`)는 모두 `isLocalLlm()` 게이트 뒤라 스위치가 꺼져 있으면 무시됩니다.

## 첫 릴리즈의 예외

스킬은 `origin/main` 릴리즈 계보의 최신 `vX.Y.Z` 태그를 기준으로 범위를 잡는데 태그가 하나도 없습니다. 첫 릴리즈만 범위를 `origin/main..origin/develop`으로, 버전을 `v0.1.0`으로 지정합니다. 이 범위의 병합 PR은 병합 커밋 기준 53건으로, 이슈 본문의 54건과 하나 차이가 나므로 `gh pr list`와 대조해 확정해야 합니다.
