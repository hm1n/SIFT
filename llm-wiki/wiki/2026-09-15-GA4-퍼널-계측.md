# GA4 퍼널 계측

## 범위

이슈 #125의 1차 범위는 퍼널 이벤트 12종입니다. 이번 PR은 그중 **10종과 계측 기반**을 담습니다.
`candidate_confirmed`와 `interview_started`는 화면 개편 확정 뒤로 미뤘고 이유는
`2026-09-15-GA4-계측-후속-backlog.md` 2번에 있습니다.

## 모듈 경계

| 파일 | 하는 일 |
| --- | --- |
| `src/lib/analytics/ga.ts` | 측정 ID 판정과 gtag 호출. 이벤트 어휘를 모릅니다 |
| `src/lib/analytics/user-id.ts` | `githubUserId`를 HMAC으로 바꿉니다. 서버 전용입니다 |
| `src/features/analytics/events.ts` | 이벤트 이름과 파라미터 타입, 공통 파라미터 세터, 버킷 |
| `src/features/analytics/analysis-events.ts` | 분석 상태 전이를 이벤트로 옮기는 순수 함수 |
| `src/features/analytics/ga-script.tsx` | gtag 스크립트 두 조각 |
| `src/features/analytics/analytics-session.tsx` | `user_id` 설정과 `login_result` |

어휘를 `lib/`이 아니라 `features/`에 둔 이유입니다. 파라미터 값을 `LoadingPhase`나 `EmptyKind` 같은
화면 도메인 타입에서 유도하는데 그 타입이 `features/`에 있습니다. `lib/`이 `features/`를 가져오면
의존 방향이 뒤집히므로 전송부는 문자열과 원시값만 받습니다.

## 이벤트와 붙는 자리

| 이벤트 | 붙는 자리 | 파라미터 |
| --- | --- | --- |
| login_view | `LoginScreen` 마운트 | auth_error |
| login_start | `LoginLink` 클릭 | 없음 |
| login_result | 콜백이 붙인 `?login=success` 또는 세션 없는 `?auth_error=` | success, error_kind |
| repo_list_loaded | `fetchRepositoriesFromApi` 성공 | repo_count, duration_ms |
| analysis_requested | `RepositoryFlow`의 분석 시작 | contribution_item_count |
| analysis_stage_done | `AnalysisState` 단계 전이 | stage, duration_ms |
| analysis_succeeded | `AnalysisState` success | candidate_count, commit_count_bucket, duration_ms |
| analysis_empty | `AnalysisState` empty | empty_kind |
| analysis_failed | `AnalysisState` error | error_kind, recovery, stage |
| analysis_retried | 오류 화면의 재시도 | error_kind, retry_scope |

`repo_visibility`와 `repo_language`는 `analysis_requested`의 파라미터로 따로 싣지 않습니다. 분석을
시작할 때 공통 파라미터로 세우므로 그 이벤트부터 자동으로 붙습니다.

### 공통 파라미터

`user_id`, `flow_id`, `repo_visibility`, `repo_language`입니다. 우리 쪽에 맵을 따로 두지 않고 gtag의
`set`을 씁니다. gtag가 이미 같은 일을 하고, 맵을 두면 두 곳이 어긋날 수 있습니다. 스크립트가 아직
로드되지 않았어도 호출 순서가 `dataLayer`에 쌓이므로 뒤따르는 이벤트가 값을 놓치지 않습니다.

`flow_id`는 분석을 시작하는 순간 발급하고 저장소를 바꾸면 비웁니다. 재시도는 같은 값을 그대로
씁니다. 실패한 분석과 그 재시도는 한 번의 분석 시도입니다.

## 화면과 계측이 같은 분류를 보게 한 세 가지

계측 전용 문자열을 새로 짓지 않는다는 기능 정의서의 결정을 지키려고 세 곳을 옮기거나 고정했습니다.

**단계 어휘를 화면에서 도메인으로 옮겼습니다.** `LoadingPhase`는 `step` 5종이고 `details` 하나가
`phase`로 `commit_details`·`repository_metadata` 둘로 갈립니다. 6단계로 펴는 매핑이 Loading 체크리스트
안에만 있어서, 그대로 두면 화면 개편이 `analysis_stage_done`의 단계 이름을 함께 바꿉니다.
`ANALYSIS_STAGES`와 `analysisStageOf`를 `repository-analysis.ts`에 두고 화면과 계측이 같은 함수를 봅니다.

**Empty 갈래에 이름을 붙였습니다.** `no_final_candidates`는 `reason`을 함께 실어야 해서 `AnalysisState`의
별도 변형이고 `EmptyKind`에 들어 있지 않습니다. 화면 안내표와 `empty_kind`가 모두 다섯 갈래를 다뤄야
하므로 `AnalysisEmptyKind`로 묶었습니다.

**`auth_error`는 화면 안내표를 기준으로 거릅니다.** 주소창의 쿼리는 아무 값이나 들어올 수 있습니다.
`AUTH_ERROR_COPY`에 없는 값은 `unknown`으로 묶어 GA4 디멘션에 임의 문자열이 쌓이는 것을 막습니다.

## `login_result`를 세션 유무로 판정하지 않는 이유

기능 정의서의 발생 시점은 "세션 확인 후 첫 렌더"였습니다. 이 앱에서는 그 조건이 로그인 직후에만
성립하지 않습니다. 세션 쿠키가 8시간을 살고, 새로고침마다 성립하며, 로그아웃이 `router.refresh()`로
페이지를 다시 실행시킵니다. 그대로 두면 `login_result`가 로그인 성공 수가 아니라 페이지 로드 수를
셉니다. "세션이 있다"는 "방금 로그인했다"의 대리 지표입니다.

대신 OAuth 콜백이 성공 리다이렉트에 `?login=success`를 붙입니다. 실패는 이미 `?auth_error=`로 오고
있어 성공과 실패가 같은 방식으로 갈립니다. 표시는 한 번 읽고 `router.replace("/")`로 지웁니다.
실패 표시는 지우지 않습니다. 로그인 화면이 그 값으로 오류 안내를 그립니다.

## 스크립트를 두 조각으로 나눈 이유

부트스트랩(`dataLayer`와 `gtag` 정의)은 평범한 인라인 `<script>`이고 라이브러리 본체만 `next/script`의
`afterInteractive`입니다.

부트스트랩까지 `afterInteractive`로 두면 hydration이 얼마간 진행된 뒤에야 주입되는데, 로그인 화면이
마운트되며 보내는 `login_view`가 그보다 먼저 일어나 퍼널의 첫 마디를 통째로 잃습니다. 인라인
`<script>`는 서버가 그린 HTML 안에서 파싱 순서대로 실행되므로 hydration 전에 `window.gtag`가
존재합니다. `beforeInteractive`는 Next.js 16.3.1 문서가 봇 탐지기나 쿠키 동의 관리자 같은 임계
스크립트로 한정하고 있어 쓰지 않았습니다.

측정 ID가 없으면 두 조각 모두 그리지 않습니다. 2026-09-15 실측으로 서버가 보낸 HTML에
`googletagmanager`도 `dataLayer`도 들어 있지 않은 것을 확인했습니다.

## 예외 격리

계측 실패가 서비스 오류로 보이면 안 된다는 제약을 세 겹으로 지킵니다.

- `lib/analytics/ga.ts`의 gtag 호출을 try/catch로 감쌉니다. 측정 ID가 없거나 `window.gtag`가 없으면
  그냥 반환합니다. 광고 차단기로 스크립트가 막히는 경우는 오류가 아니라 정상 경로입니다.
- `events.ts`의 `trackEvent`와 공통 파라미터 세터도 감쌉니다. 이 함수들은 데이터 조회 함수 안에서도
  불리고(`repository-client.ts`), 거기서 던지면 계측 실패가 조회 실패가 됩니다.
- 분석 화면의 `reportAnalysis`도 감쌉니다. 이 경로는 상태를 화면에 반영하기 직전에 실행되므로 여기서
  던지면 `setState`에 닿지 못해 화면이 로딩에 멈춥니다.

세 번째는 구현 중 테스트가 실제로 잡아낸 경로입니다. 경위는 세션 로그에 있습니다.

## `user_id` 변환과 세션 복호화

`page.tsx`가 세션 쿠키를 복호화해 `githubUserId`를 얻고 `GA_USER_ID_HMAC_SECRET`으로 HMAC-SHA256
16진 문자열(64자)을 만듭니다. 비밀값이 없으면 null이고 계측만 익명으로 떨어집니다.

복호화를 try/catch로 감쌉니다. `decryptGitHubSession`은 만료된 쿠키, 옛 형식의 쿠키, 암호화 키가 없는
서버에서 모두 던집니다. 이 페이지는 지금까지 쿠키의 존재만 보고 화면을 갈랐고, 만료된 쿠키를 든
사용자는 화면을 받은 뒤 API 호출에서 재로그인 안내를 받습니다. 계측 때문에 그 경로가 서버 오류로
바뀌면 안 됩니다.

값이 없을 때는 gtag를 아예 부르지 않습니다. `gtag('set', { user_id: null })`을 부르면 gtag가 그
자리를 빈 문자열로 직렬화해 **이후 모든 이벤트에** `uid=`를 실어 보냅니다. 2026-09-15에 수집 요청을
가로채 확인했고, "로그인 전에는 붙지 않습니다"라는 기능 정의서의 정의와 어긋납니다. 한 번이라도 세운
뒤의 null은 그대로 보냅니다. 로그아웃은 새로고침 없이 서버 컴포넌트만 다시 그리므로, 지우지 않으면
앞 사용자의 `user_id`가 계속 붙습니다.

## 서버와 클라이언트 경계

`page.tsx`는 서버 컴포넌트입니다. 여기서 부르는 판정 함수는 `"use client"`가 붙은 파일에 두면 안
됩니다. Next.js가 클라이언트 모듈의 함수를 서버에서 부르는 것을 렌더 단계에서 500으로 끊습니다.

`AUTH_ERROR_COPY`와 `toAuthErrorParam`을 `src/features/auth/auth-error.ts`에 둔 이유입니다. 화면과
계측이 같은 표를 보되 어느 쪽도 경계를 넘지 않습니다.

**이 결함은 테스트로 잡히지 않습니다.** vitest는 모듈 그래프가 하나라 `"use client"` 지시어가 아무
경계도 만들지 않고, `next build`도 통과합니다. 서버를 띄우고 그 주소를 실제로 요청해야 드러납니다.
2026-09-15에 이 경로로 잡았습니다.

## 확인 절차

### 로그인 경계 네 건은 스크립트가 확인합니다

```
# .env.local에 NEXT_PUBLIC_GA_MEASUREMENT_ID를 두고
npm run build
npx next start -p 3125
npx tsx scripts/measure-ga-events.mts --url http://127.0.0.1:3125
```

`login_view`, `login_start`, `login_result`, 그리고 오류 화면의 `login_view`를 확인하고 기대와 다르면
종료 코드 1입니다. 기본은 가로채기라 확인용 히트가 실제 속성에 쌓이지 않습니다. `--send`를 주면
통과시킵니다.

이벤트와 파라미터를 수집 요청이 아니라 `window.dataLayer`에서 읽습니다. gtag가 클릭 직후의 이벤트를
`navigator.sendBeacon`으로 보내는데 Playwright가 그 본문을 읽지 못합니다. 전송이 실제로 일어나는지는
수집 요청 수로 따로 봅니다.

2026-09-15 실행 결과입니다.

```
수집 요청 4건
  event login_view {}
  event login_start {}
  event login_result {"success":false,"error_kind":"config_missing"}
  event login_view {"auth_error":"config_missing"}
```

### 나머지 여섯 종은 DebugView로 확인합니다

GitHub OAuth와 LLM 호출이 있어야 도달하므로 자동으로 확인할 수 없습니다.

1. 크롬에 Google Analytics Debugger 확장을 설치해 켭니다. 코드에 `debug_mode`를 넣지 않는 이유는
   그 값이 프로덕션 트래픽까지 디버그로 표시하기 때문입니다.
2. `.env.local`에 측정 ID와 GitHub OAuth, LLM 환경변수를 채우고 `npm run build`, `npx next start`를
   실행합니다.
3. GA4 관리 화면의 **관리 > 데이터 표시 > DebugView**를 엽니다.
4. 로그인하고 저장소를 골라 분석을 끝까지 돌립니다. `repo_list_loaded`, `analysis_requested`,
   `analysis_stage_done` 여섯 건, 그리고 `analysis_succeeded`나 `analysis_empty`나 `analysis_failed`
   가운데 하나가 도착하는지 봅니다. 실패했다면 재시도를 눌러 `analysis_retried`도 봅니다.
5. 각 이벤트를 눌러 파라미터를 펴고 금지 값(저장소 owner와 이름, 로그인 아이디, 커밋 SHA, 파일 경로)이
   없는지, `user_id`가 64자 16진 문자열인지 확인합니다.

### 등록한 맞춤 정의

디멘션(이벤트 범위)은 `flow_id`, `auth_error`, `success`, `error_kind`, `empty_kind`, `recovery`,
`stage`, `retry_scope`, `repo_visibility`, `repo_language`, `commit_count_bucket`입니다.

측정항목은 `duration_ms`(밀리초), `repo_count`, `contribution_item_count`, `candidate_count`입니다.
수치를 디멘션으로 등록하면 문자열로 취급돼 평균과 합계가 나오지 않습니다.

등록은 소급되지 않고 리포트 반영까지 하루에서 이틀 걸립니다. DebugView와 실시간은 등록과 무관하게
파라미터를 바로 보여주므로 이벤트가 제대로 나가는지는 등록을 기다리지 않고 확인할 수 있습니다.

2차 범위(#126)가 `turn`, `block`, `element`, `evaluation`, `verifiability`, `evidence_type`,
`answer_length_bucket`을 더 얹습니다. 그때 개수가 많으면 GA4 Admin API로 스크립트를 만드는 편이
낫습니다. 한도는 각각 50개입니다.

- 프로덕션(Vercel)에 `NEXT_PUBLIC_GA_MEASUREMENT_ID`와 `GA_USER_ID_HMAC_SECRET`을 넣어야 합니다.
  측정 ID는 빌드 시점에 인라인되므로 값을 넣은 뒤 다시 빌드해야 합니다. HMAC 비밀값은 프로덕션용으로
  따로 만들고, 값이 바뀌면 같은 사용자가 다른 사람으로 집계되므로 유출 사고가 아닌 한 교체하지 않습니다.
- GA4 향상된 측정이 `page_view`와 `scroll` 같은 자동 이벤트를 함께 보냅니다. 이 계측이 만든 것이
  아니고 퍼널 해석에 쓰지 않습니다.
