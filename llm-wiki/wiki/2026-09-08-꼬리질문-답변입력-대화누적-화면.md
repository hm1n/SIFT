# 꼬리 질문 답변 입력과 대화 누적 화면

이슈 #77의 결정과 근거를 기록합니다. 이슈 #76이 고정한 요청 계약 위에 답변 입력과 대화 표시를 얹었습니다. 인터뷰 종료와 이력 절단 안내는 이슈 #78, 프롬프트 문구와 모델 확정은 이슈 #79의 범위입니다.

## 1. 대화 상태

`use-interview-stream.ts`의 메시지에 `role`을 더했습니다. `question`은 모델이 만든 질문, `answer`는 사용자가 제출한 답변이며 `history.ts`의 `InterviewHistoryMessage["role"]`을 그대로 씁니다. 질문은 이전처럼 청크를 이어 붙이다가 `done`에서 확정되고, 답변은 제출 즉시 `isStreaming: false`인 확정 항목으로 들어갑니다.

메시지 갱신은 모두 `updateMessages` 하나를 거칩니다. 답변 제출 직후 같은 틱에서 요청 이력을 만들어야 하는데 React 상태는 다음 렌더까지 갱신되지 않으므로 ref에 같은 값을 함께 둡니다. 상태와 ref가 어긋나는 경로를 남기지 않으려고 `setMessages`를 직접 부르는 자리를 없앴습니다.

## 2. 요청 배선

다음 질문 요청은 확정된 메시지 전체를 `{ role, text }`로 바꿔 `trimInterviewHistory`를 통과시킨 뒤 `{ snapshot, history }`로 보냅니다. 첫 질문은 이력이 비어 있으므로 이슈 #76 이전과 같은 `{ snapshot }` 본문을 보냅니다. 절단 결과의 `removed`는 `removedHistory` 상태로 노출만 하고 안내는 이슈 #78이 얹습니다.

실제 생성 경로는 요청마다 새 스트림이므로 `start()`가 `lastSeq`와 버퍼를 0으로 되돌립니다. 앞 질문의 `seq`를 이어 쓰면 새 질문의 도착 순서 검증이 어긋납니다. 테스트용 스트림 경로는 이어받기를 유지하므로 되돌리지 않습니다.

## 3. 다시 시도의 범위를 좁혔습니다

이슈 #76까지 `retry()`는 실제 생성 경로에서 `setMessages([])`로 대화 전체를 지웠습니다. 첫 질문만 있을 때는 지울 것이 그 질문 하나여서 문제가 없었지만, 대화가 쌓인 뒤에는 사용자가 쓴 답변까지 사라집니다. 이제는 마지막 항목이 도착 중인 질문일 때 그 항목 하나만 빼고 같은 이력으로 다시 요청합니다. 첫 질문 실패 때의 동작은 결과적으로 같습니다.

## 4. 답변 제출 조건

`canSubmitAnswer`는 근거 스냅샷이 있고, `status`가 `done`이고, 표시 중인 오류가 없고, 마지막 항목이 확정된 질문일 때만 참입니다. 생성 중과 오류 표시 중에는 거짓이므로 다시 제출할 수 없습니다. 오류는 다시 시도로 풀어야 하고 그 다시 시도가 실패한 질문 하나만 다시 만듭니다.

`submitAnswer`는 훅 안에서 다시 판정합니다. 화면이 버튼만 잠그면 Enter 제출 같은 다른 경로가 그대로 통과합니다. 실제로 화면 테스트가 `fireEvent.submit`으로 이 경로를 잡아냈고, 훅에 판정을 옮겨 고쳤습니다. 같은 틱에 두 번 부르면 두 번째는 거짓을 돌려줍니다. 스트림의 첫 상태 콜백이 오기 전에는 `status`가 아직 `done`이므로 ref로 먼저 잠급니다.

근거 스냅샷이 없는 테스트용 스트림에서는 입력란 자체를 두지 않습니다. 그 경로는 대화를 받지 않으므로 답변이 아무 데도 가지 않습니다.

## 5. 답변 길이는 서버와 같은 자로 잽니다

화면 상한을 글자 수로 두지 않고 `interviewHistoryItemBytes`를 그대로 불러 `INTERVIEW_HISTORY_ITEM_MAX_BYTES`(4,500바이트)와 비교합니다. 서버 상한이 JSON 직렬화 바이트 기준이라 줄바꿈이 많은 코드 블록 답변은 같은 글자 수라도 두 배로 셉니다. 회귀 테스트는 `"a\n"`을 2,250번 반복한 답변을 씁니다. 글자 수 4,500자로 막았다면 통과시켰을 답변인데 직렬화하면 6,750바이트입니다.

이슈의 "확인 필요" 두 항목 가운데 답변 길이 상한은 이렇게 넘기지 못하게 막는 쪽으로 정했습니다. 넘긴 뒤 413으로 알리면 답변은 남지만 사용자가 어디를 줄여야 하는지 알기 어렵고, 막으면 입력란에서 바로 바이트 수와 상한을 봅니다. 페이지 이탈 경고는 종료 흐름과 함께 이슈 #78에서 정합니다.

## 6. 스크롤

`useAutoScroll`은 손대지 않고 `contentKey`만 `receivedSeq`에서 `${messages.length}:${receivedSeq}`로 바꿨습니다. 답변 제출은 청크가 아니라 `receivedSeq`가 움직이지 않는데 내용은 바뀝니다. 제출은 사용자의 행동이므로 위로 올려 둔 상태여도 `scrollToBottom`으로 내립니다. 위로 올려 읽는 중에 새 질문이 도착하는 경우는 기존 동작 그대로 자리를 유지하고 새 메시지 안내만 냅니다.

## 7. Loading과 낭독

"질문을 준비하고 있습니다" 안내는 질문 영역 한 곳에서만 나옵니다. 첫 질문이면 대화가 비어 있고 꼬리 질문이면 마지막 항목이 답변인데, 두 경우 모두 아직 자라나는 질문이 없다는 조건 하나로 판정합니다. 꼬리 질문에서는 문구를 "다음 질문을 준비하고 있습니다"로 바꿔 대화가 비어 있는 첫 질문과 구분합니다.

메시지에는 `aria-label`로 "AI 질문"과 "내 답변"을 붙여 누가 말한 것인지를 색이 아니라 글자로 구분합니다. 낭독 경계는 그대로입니다. `role="log"` 영역은 `aria-live="off"`이고 상태 문단과 새 메시지 안내만 낭독 대상입니다.

답변도 질문과 같은 Markdown 렌더러를 씁니다. 사용자가 코드 블록을 붙이는 경우가 있고, 답변은 제출 즉시 확정되므로 `memo`가 다시 파싱하지 않습니다. 메시지가 쌓일 때의 렌더링 비용은 재지 않았고 가상 스크롤도 넣지 않았습니다.
