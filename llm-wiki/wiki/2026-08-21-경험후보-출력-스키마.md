# 경험 후보 출력 스키마

## 목적과 범위

Stage B가 생성한 구조화 응답을 검증하고, 화면과 후속 상태 연결 단계에 근거가 확인된 경험 후보만 전달합니다. 출력 단계는 후보 선정 규칙이나 LLM 호출을 수행하지 않으며 점수, 가중치, 순위도 계산하지 않습니다.

Stage A는 이 계약을 쓰지 않습니다. 이슈 #101에서 Stage A가 판단 단위마다 판정을 돌려주는 구조로 바뀌면서 `stage-a.ts`의 `validateStructuredOutput`이 따로 검증합니다. 문서가 2026-08-21까지 두 Stage를 함께 묶어 서술한 것은 그 시점의 구조입니다.

근거는 GitHub 이슈 #15와 부모 기능 정의서인 GitHub 이슈 #12입니다. 후보 개수 상한과 부족 사유 규칙은 이슈 #108에서 바꿨습니다. 확인 날짜는 2026-09-11입니다.

## 출력 인터페이스

`ExperienceCandidateOutput`은 후보 목록과 후보 부족 사유로 구성됩니다.

| 필드 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| `candidates` | `readonly ExperienceCandidate[]` | 필수 | 검증을 통과한 경험 후보 목록입니다. 개수 상한은 호출부가 정합니다. 대표 SHA는 후보마다 달라야 합니다. |
| `insufficientCandidatesReason` | `string \| null` | 필수 | 후보를 더 채우지 않은 이유입니다. 후보가 0개이면 반드시 존재합니다. 1개 이상이면 `null`일 수 있습니다. |

후보 개수 상한은 고정값이 아닙니다. Stage B는 입력 판단 단위 수와 `STAGE_B_MAX_CANDIDATES`(20) 중 작은 값을 상한으로 씁니다. 클라이언트가 응답을 다시 검증할 때는 요청에 실어 보낸 Stage A 후보 수를 상한으로 씁니다.

상한이 3으로 고정되어 있던 동안에는 입력 판단 단위가 1~2개인 저장소에서 "서로 다른 묶음에서 3개"와 "부족 사유 `null`"을 동시에 만족할 방법이 없어 `schema_validation`으로 실패했습니다. 부족 사유를 후보 0개에만 묶은 것도 같은 이유입니다. 사유를 필수로 소비하는 유일한 지점은 `repository-analysis.ts`의 non-null 단언이고 그 분기가 후보 0개입니다.

상한을 올린 것이 하한을 만드는 것은 아닙니다. 근거가 없으면 후보를 적게 고르는 쪽이 정상이고 프롬프트도 개수를 채우지 말라고 지시합니다.

각 `ExperienceCandidate`는 다음 근거 필드를 포함합니다.

| 필드 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| `sha` | `string` | 필수 | 경험을 대표하는 커밋 SHA입니다. |
| `relatedShas` | `readonly string[]` | 필수 | 같은 PR에 속해 근거를 보강하는 관련 커밋 SHA 목록입니다. |
| `evidence` | `string` | 필수 | 실제 커밋과 파일을 근거로 한 후보 선정 설명입니다. |
| `citedFilePaths` | `readonly string[]` | 필수 | 근거에서 인용한 Repository 파일 경로입니다. |
| `source` | `"contribution_match" \| "automatic_recommendation"` | 필수 | 사용자 기여 항목 매칭 후보와 자동 추천 후보를 구분합니다. |

## 화면 근거 출처

후보 목록은 `ExperienceCandidateListItem`으로 변환하며 각 항목이 후보, SHA로 찾은 커밋, `origin`을 함께 가집니다. `origin`의 타입인 `EvidenceOrigin`은 MVP에서 `"repository"` 한 값만 사용하고, 화면은 출처별 라벨 맵으로 이를 표시합니다. 이후 보조 메모가 범위에 포함되면 `"user_note"` 같은 값을 유니온과 라벨 맵에 추가할 수 있으며, 후보 생성 경로를 나타내는 `ExperienceCandidate.source`와 근거의 출처를 나타내는 `origin`은 서로 다른 필드입니다. `origin`은 근거의 출처만 나타내며 LLM이 작성한 `evidence` 문장 안 주장의 검증 여부를 나타내지 않습니다. Repository 확인 가능·불가 구분은 이슈 #47에서 다룹니다.

## 검증과 오류 계약

`createExperienceCandidateOutputSchema`는 Stage B의 `generateObject` 호출에 전달할 JSON Schema를 만드는 팩토리입니다. 모듈 상수가 아니라 팩토리인 이유는 후보 개수 상한이 호출마다 다르기 때문입니다. `validateExperienceCandidateOutput`은 이미 역직렬화된 값을 같은 계약으로 검증하며 상한을 인자로 받습니다. JSON Schema의 `maxItems`와 런타임 검증의 상한은 같은 값을 써야 하므로 회귀 테스트로 고정합니다. 정의되지 않은 필드와 빈 문자열은 허용하지 않습니다.

JSON 텍스트를 직접 받던 `parseExperienceCandidateOutput`은 이슈 #108에서 지웠습니다. AI SDK가 역직렬화를 맡은 뒤로 호출부가 없었습니다.

Stage B는 상한을 두 번에 나눠 적용합니다. 모델 응답을 검증할 때는 입력 커밋 수를 상한으로 쓰고, 판단 단위 상한은 `dedupeCandidatesByWorkUnit`이 같은 Pull Request 후보를 합친 뒤에 적용합니다. 정리 전에 개수를 재면 모델이 같은 묶음에서 둘 이상 고른 응답이 정리에 닿기 전에 거부됩니다.

출력 계약은 프로덕션과 로컬 제공자 모두에게 같은 문장으로 알려줍니다. 2026-08-25까지는 로컬 제공자에만 붙였습니다. Gemini가 스키마만 보고 계약을 지켰기 때문인데, 판단 단위가 1~2개인 저장소가 들어오면서 Gemini도 부족 사유를 채우지 않아 실패했습니다.

검증 실패는 `ExperienceCandidateOutputError`로 변환합니다. `kind`는 출력 구조 위반인 `schema_validation`과 입력에 없는 SHA인 `unknown_sha`를 구분합니다. 원래 오류는 `cause`로 보존합니다. JSON 문법 오류인 `json_parse`는 이 모듈이 더 이상 만들지 않지만, 다른 기능이 쓰고 있어 오류 종류 자체는 남아 있습니다.

## SHA 무결성과 책임 경계

`assertCandidateShas`는 대표 커밋 `sha`와 모든 `relatedShas`를 해당 Stage에 전달된 입력 SHA 집합과 대조합니다. 입력에 없는 SHA가 하나라도 있으면 `unknown_sha` 오류를 던져 전체 결과를 거부하며, 유효한 후보만 부분적으로 통과시키지 않습니다.

Stage B의 `assertCandidateEvidence`는 SHA 검증에 더해 관련 SHA가 대표 커밋과 같은 PR에 속하는지 확인합니다. 대표 커밋이 어느 Pull Request에도 속하지 않으면 관련 커밋도 있을 수 없으므로 `relatedShas`는 비어 있어야 합니다. 이 분기를 따로 두지 않으면 빈 `pullRequests`에 대한 `every`가 항상 `true`를 돌려주어, 관련 커밋의 소속과 무관하게 전부 거부됩니다. 인용 파일 경로는 Repository 파일 트리 또는 해당 후보의 대표·관련 커밋 변경 파일에 존재해야 합니다. 관계나 경로가 하나라도 맞지 않으면 각각 `unrelated_sha`, `unknown_file_path` 오류로 전체 결과를 거부합니다.

프롬프트 문장은 이 판정과 한 줄씩 대응시킵니다. 인용할 경로가 있는 커밋은 `relatedShas`에 먼저 넣어야 한다는 관계를 문장에 적지 않으면, 모델이 `relatedShas`를 비운 채 같은 묶음의 다른 커밋 파일을 인용해 `unknown_file_path`로 거부됩니다. 실측은 `raw/2026-09-11-Stage-B-후보-개수-상한과-출력-계약-session-log.md`에 있습니다.

관련 커밋은 GitHub PR 소속 정보만 근거로 합니다. 시간 근접성, 파일 경로 중복, 커밋 메시지의 이슈 번호로 관계를 추정하지 않습니다. 실제 후보 선정, 프롬프트 구성, LLM 호출, route handler와 후보 화면 연결은 후속 이슈의 책임입니다.
