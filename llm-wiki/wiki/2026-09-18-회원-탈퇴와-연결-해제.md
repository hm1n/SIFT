# 회원 탈퇴와 GitHub 연결 해제

## 문서 목적

이슈 #145가 만든 삭제 경로의 계약을 적습니다. 무엇이 어느 순서로 지워지는지, 권한 해제가 실패하면 무엇이 남는지, 그 사실을 사용자에게 어떻게 알리는지가 범위입니다. 운영 준비 체크리스트 P0 5번을 닫는 작업입니다.

## 왜 필요했는가

지울 수 있는 것이 인터뷰 한 건씩(`DELETE /api/interviews/[id]`)과 90일 미열람 자동 정리(`src/app/api/cron/purge/route.ts`)뿐이었습니다. 두 가지가 빠져 있었습니다.

- 인터뷰를 하나씩 지워도 `repository_analysis`에 근거 스냅샷이 남습니다. 그 안에 비공개 Repository의 코드 변경이 들어 있고, 그 줄은 `purgeAnalysesWithoutInterviews`가 90일 뒤에나 걷어갑니다.
- 로그아웃은 쿠키만 지웁니다(`src/app/api/auth/session/route.ts`). 사용자 쪽에서는 연결을 끊은 것처럼 보이지만 GitHub에 발급된 토큰은 그대로 살아 있습니다.

개인정보 처리방침 8번에 적을 권리 행사 방법이 전자우편 요청뿐이었던 것도 같은 원인입니다. 작성지침 16번은 권리 행사 절차가 수집 절차보다 어렵지 않아야 한다고 요구합니다. 로그인이 한 번의 클릭이므로 삭제 요구도 한 번의 클릭으로 닿아야 합니다.

## 삭제 계약

| 항목 | 값 |
| --- | --- |
| 경로 | `DELETE /api/account` |
| 대상 판정 | 세션 쿠키의 `github_user_id`뿐입니다. 본문을 읽지 않습니다 |
| 지우는 것 | 그 사용자의 `repository_analysis` 전부와, `on delete cascade`로 딸린 `interview_session` 전부 |
| 함께 하는 것 | GitHub OAuth grant 해제, 세션 쿠키 삭제 |
| 성공 응답 | `200 { deleted: <지운 분석 수>, revoked: <boolean> }` + 세션 쿠키를 지우는 `Set-Cookie` |
| 세션 없음 | `401 { error: { kind: "unauthorized" } }`. 저장 계층과 GitHub을 건드리지 않습니다 |
| 저장소 실패 | `503 storage_failed`. 권한 해제를 부르지 않고 쿠키도 남깁니다 |

본문을 읽지 않는 것이 이 계약의 핵심입니다. 요청이 대상을 지정할 수 있으면 남의 번호를 적어 보낼 자리가 생기고, 그 자리를 막는 검사를 한 곳에서 빠뜨리면 남의 데이터가 사라집니다. 읽지 않는 편이 검사보다 확실합니다.

`deleted`는 지운 분석 수입니다. 인터뷰 수를 따로 세지 않습니다. cascade로 지워지는 줄은 `returning`에 오지 않아 한 문장으로는 셀 수 없고, 인터뷰는 분석 없이 존재할 수 없으므로 `deleted`가 0이면 그 계정에 저장된 것이 하나도 없었다는 뜻입니다. 빈 계정을 가르는 데는 이 값만 있으면 됩니다.

CSRF 토큰을 두지 않습니다. 세션 쿠키가 `SameSite=Lax`라 교차 사이트 요청에는 실리지 않고, HTML form은 `DELETE`를 보낼 수 없습니다.

## 순서: 데이터 삭제 먼저, 권한 해제 나중

이슈가 "권한 해제가 실패해도 데이터 삭제는 끝나야 한다"고 정했으므로 실패해도 되는 쪽을 뒤에 둡니다.

순서를 바꾸면 토큰이 죽은 뒤에 삭제가 실패하는 경우가 생깁니다. 그때 사용자는 데이터가 남은 채로 아무것도 할 수 없는 상태가 됩니다. 반대 순서에서는 최악의 경우가 "데이터는 지워졌고 권한이 남은 상태"이고, 그 상태는 사용자가 GitHub 설정에서 스스로 끝낼 수 있습니다.

저장소 삭제가 실패하면 쿠키도 남깁니다. 지우지 못한 채로 로그아웃시키면 사용자가 다시 로그인하기 전까지 무엇이 남았는지 볼 수 없고 다시 시도할 자리도 사라집니다.

## GitHub grant 해제

| 항목 | 값 |
| --- | --- |
| 엔드포인트 | `DELETE https://api.github.com/applications/{client_id}/grant` |
| 인증 | Basic. username이 `client_id`, password가 `client_secret`입니다 |
| 본문 | `{"access_token": "<세션의 사용자 토큰>"}` |
| 성공 | 204. 본문이 없습니다 |
| 효과 | 문서 원문: "Deleting an application's grant will also delete all OAuth tokens associated with the application for the user" |

토큰 하나만 지우는 `DELETE /applications/{client_id}/token`을 쓰지 않습니다. 그 호출은 지금 브라우저의 세션만 끊고 다른 기기에서 받아 둔 토큰은 남기므로, 권한을 끊었다고 말할 수 없습니다.

문서가 밝히는 상태 코드는 204와 422뿐이라 나머지는 이 서비스가 정했습니다.

| 응답 | 판정 | 근거 |
| --- | --- | --- |
| 204 | 해제 | 문서가 정한 성공입니다 |
| 404 | 해제 | 지울 grant가 없는 경우입니다. 사용자가 GitHub 설정에서 이미 해제했거나 토큰이 이미 죽은 것이고, 어느 쪽이든 권한이 남지 않는다는 목표는 이뤄져 있습니다 |
| 429 | 실패(`rate_limit`) | 1차 요청 한도입니다 |
| 403 + `x-ratelimit-remaining: 0` | 실패(`rate_limit`) | 1차 요청 한도입니다 |
| 403 + `Retry-After` 또는 본문에 `secondary rate limit`·`abuse detection` | 실패(`rate_limit`) | 2차 요청 한도입니다 |
| 401 | 실패(`invalid_credentials`) | client id와 secret이 틀린 경우입니다. 사용자 토큰 문제가 아니라 서버 설정 문제이고 다시 시도해도 같습니다 |
| 그 밖의 403, 422, 5xx | 실패(`rejected`) | 사용자가 할 일은 같습니다 |
| 전송 실패 | 실패(`network`) | |
| 환경변수 없음 | 실패(`config_missing`) | GitHub을 부르지 않습니다 |

요청 한도 판별을 `src/lib/github/rate-limit.ts`로 옮겼습니다. `commits.ts`의 `classifyErrorResponse`를 그대로 쓸 수 없는 이유는 그 함수가 404를 `repo_not_found`로, 401을 `auth_revoked`로 옮기기 때문입니다. 이 경로에서 둘의 뜻이 다릅니다. 판별을 양쪽에 따로 두면 GitHub이 헤더나 문구를 바꿀 때 한쪽만 고치게 됩니다.

`GITHUB_OAUTH_CLIENT_ID`와 `GITHUB_OAUTH_CLIENT_SECRET`을 읽는 자리를 `oauthAppCredentials()` 하나로 모았습니다. 로그인은 값이 없으면 던져야 하고(사용자가 할 수 있는 일이 없는 서버 설정 문제입니다) 이 경로는 없어도 데이터 삭제를 끝내야 해서, 두 경로가 없을 때 하는 일이 다릅니다. 그 차이는 각자 정하고 이름만 한 곳에 둡니다.

## 저장 계층

`SiftStore.deleteUserData(githubUserId)`를 더했습니다. Neon 구현은 한 문장입니다.

```sql
delete from repository_analysis where github_user_id = $1::bigint returning id
```

인터뷰를 먼저 지우고 분석을 지우는 두 문장으로 나누지 않습니다. 드라이버가 HTTP 한 번에 한 문장을 보내고 그 한 문장이 한 트랜잭션이라, 나누면 앞 문장만 성공한 채로 끝날 수 있습니다. 그때 남는 것이 근거 스냅샷을 든 분석입니다. `purgeAnalysesWithoutInterviews`가 한 문장을 쓰는 것과 같은 이유입니다.

메모리 구현은 cascade를 손으로 흉내 냅니다. 흉내 내지 않으면 지운 분석에 딸린 인터뷰가 메모리에 남아 목록과 복원에 계속 보입니다.

실제 Postgres에서 도는지는 `scripts/verify-neon-store.mts`가 봅니다. 이 검사만 사용자 번호를 따로 씁니다. 사용자 번호를 조건으로 지우는 유일한 연산이라 다른 검사가 쓰는 번호로 돌리면 그 번호로 심은 줄이 한 번에 사라지고, 뒤에 올 검사가 근거를 잃습니다. 지우기 전에 그 번호에 남은 줄이 없는지 먼저 확인합니다. 번호는 무작위로 고른 것이라 데이터베이스가 예약해 주지 않으므로, 이미 쓰이고 있는 번호였다면 이 연산이 남의 줄을 지웁니다(PR #127 리뷰가 지적한 위험과 같습니다).

## 화면

진입점은 계정 메뉴입니다. 로그인한 뒤 모든 화면에서 한 번의 클릭으로 닿습니다. 레퍼런스 디자인(`Chat Interface Design/src/App.tsx`)의 계정 메뉴에 있는 `Delete account` 자리이고, 디자인 개편 backlog 3번이 MVP 범위 밖으로 미뤄 둔 항목입니다.

대화상자를 띄우지 않고 메뉴 본문을 확인 단계로 갈아 끼웁니다. 저장된 인터뷰 목록의 삭제 확인이 같은 방식이고 레퍼런스도 그렇습니다. 확인 단계에서는 취소에 초점을 둡니다. 되돌릴 수 없는 쪽에 초점을 두면 Enter 한 번으로 지워집니다.

상태 넷을 함께 그립니다.

| 상태 | 화면 |
| --- | --- |
| 기본 | 계정 메뉴의 `회원 탈퇴` 항목. 로그아웃과 색으로도 가릅니다 |
| Loading | 확인 단계의 버튼이 `탈퇴 중…`으로 바뀌고 둘 다 잠깁니다. 이때는 바깥 클릭으로 메뉴가 닫히지 않습니다. 닫히면 실패 안내가 갈 자리가 사라집니다 |
| Empty | 지울 데이터가 없던 계정입니다. 응답의 `deleted`가 0이면 로그인 화면이 "지울 데이터가 없어 GitHub 연결만 해제했습니다"를 그립니다 |
| Error | 메뉴 안에 안내와 `다시 시도`를 그립니다. 실패 원인은 말하지 않습니다. 사용자가 할 수 있는 일은 원인과 무관하게 같습니다 |

끝나면 결과 표시를 주소에 실어 로그인 화면으로 보냅니다(`/?withdrawn=done`). 화면에 남아 있을 수 없습니다. 쿠키가 이미 사라져서 그 화면이 보내는 다음 요청은 모두 401로 답합니다. `auth_error`가 쓰는 방식과 같고, `AnalyticsSession`의 주소 정리는 `?login=` 표시가 있을 때만 돌아서 이 표시를 지우지 않습니다.

표시는 넷입니다. 사용자가 알아야 할 것이 지울 데이터가 있었는지와 GitHub 연결이 실제로 끊겼는지, 둘이기 때문입니다.

| 표시 | 뜻 |
| --- | --- |
| `done` | 지웠고 해제했습니다 |
| `empty` | 지울 것이 없었고 해제했습니다 |
| `done_kept` | 지웠지만 연결이 남았습니다 |
| `empty_kept` | 지울 것이 없었고 연결도 남았습니다 |

연결이 남은 두 표시에는 GitHub 설정의 승인된 앱 목록(`https://github.com/settings/applications`)으로 가는 링크를 함께 그립니다. 남았다는 사실만 알리고 끝내면 사용자가 할 수 있는 일이 없습니다.

응답 본문을 읽지 못한 경우에는 `done_kept`로 둡니다. 두 값 모두 사용자에게 더 많은 일을 시키는 쪽입니다. 반대로 두면 연결이 남았는데도 끊겼다고 알리게 되고, 탈퇴는 되돌릴 수 없어 다시 물어볼 수도 없습니다. 200을 받았다면 삭제는 이미 끝났으므로, 본문을 읽지 못한 것을 실패로 보여 사용자가 지워진 데이터를 다시 지우려 하게 만들지도 않습니다.

## 문구

레퍼런스의 한국어 `계정 삭제`를 쓰지 않고 `회원 탈퇴`로 정했습니다. 2026-09-18에 사용자와 정했습니다.

- `계정 삭제`는 이 서비스가 하는 일보다 큽니다. 지울 회원 레코드가 없고(`db/schema.sql`의 표는 둘뿐입니다) GitHub 계정도 그대로 남습니다.
- `로그아웃`은 이미 다른 항목입니다. 되돌릴 수 있는 것과 되돌릴 수 없는 것이 한 이름을 쓰면 안 됩니다.
- `데이터 전체 삭제`도 후보였지만, 사용자가 보는 결과로는 데이터가 모두 사라지고 서비스가 GitHub에 접근할 수 없게 되는 것이라 일반적으로 말하는 회원 탈퇴와 같습니다. 회원 레코드가 없다는 것은 내부 사정입니다.

확인 단계에서 "다시 로그인하면 빈 상태로 시작합니다"는 넣지 않기로 했습니다. 같은 날 사용자가 정했습니다.

어긋남 사유는 `src/copy/reference-ko.test.ts`의 대조 표에 `deleteAccount`, `deleteAccountConfirm`, `deleteAccountWarning` 셋으로 적었습니다.

- 처리방침 3번 파기 절차: 이용자가 화면에서 직접 지우는 경로를 적었습니다.

- 이용약관 2번 계정과 GitHub 권한: 이용을 끝내는 방법을 적었습니다. 가입이 없다고만 적힌 절에 종료 방법이 없으면 짝이 맞지 않습니다.

시행일은 바꾸지 않았습니다. 두 문서 모두 2026-09-18 시행이고 이 갱신도 같은 날이라, 공개 전의 첫 버전 안에서 문장이 늘어난 것입니다.

## 테스트로 고정한 것

- 저장 계층: 분석과 딸린 인터뷰가 함께 사라지는 것, 다른 사용자의 줄이 남는 것, 인터뷰가 붙지 않은 분석도 지워지는 것, 저장한 적 없는 사용자가 0을 받는 것, 두 번 불러도 되는 것. 메모리와 Neon 두 구현에 같은 항목을 두었습니다.
- 소유자 판정: `neon-store.test.ts`의 연산 표에 `deleteUserData`를 넣어 사용자 번호를 질의에 싣는지 함께 봅니다. 표에 넣지 않으면 연산이 늘 때 같은 누락이 다시 생깁니다.
- grant 해제: Basic 인증 헤더와 본문 모양, 상태 코드 여덟 갈래, 자격이 없으면 GitHub을 부르지 않는 것.
- 라우트: 본문으로 대상을 지정해도 남의 데이터가 남는 것, 해제가 다섯 가지 이유로 실패해도 데이터는 지우고 `revoked: false`를 돌려주는 것, 저장소 실패에서 해제를 부르지 않고 쿠키를 남기는 것, 세션이 없으면 아무것도 지우지 않는 것.
- 화면: 확인 없이 요청이 나가지 않는 것, 표시 넷이 응답에서 만들어지는 것, 실패 안내와 다시 시도, 탈퇴 중 잠김과 바깥 클릭 무시, 메뉴를 닫으면 확인 단계가 사라지는 것.
- 로그인 화면: 표시별 문구, 연결이 남은 표시에만 붙는 해제 안내 링크, 표에 없는 값과 프로토타입 키를 안내로 취급하지 않는 것.

## 손으로 확인하는 절차

단위 테스트로 덮지 못하는 것은 실제 GitHub과 Neon을 상대로 봐야 합니다.

1. 로컬에서 로그인해 분석을 한 번 저장하고 인터뷰를 하나 만듭니다.
2. 계정 메뉴에서 회원 탈퇴를 누르고 확인합니다.
3. `/?withdrawn=done`으로 이동하고 안내가 보이는지 봅니다.
4. Neon 콘솔에서 두 표에 그 사용자 번호의 줄이 없는지 봅니다.
5. `https://github.com/settings/applications`에서 SIFT가 목록에 없는지 봅니다.
6. 다시 로그인하면 권한 승인 화면이 다시 나오는지 봅니다. grant를 지웠으므로 나와야 합니다.

`npx tsx scripts/verify-neon-store.mts`는 4번을 질의 수준에서 자동으로 확인합니다.

## 후속으로 뗀 것

- **로그아웃은 토큰을 무효로 만들지 않습니다.** 이슈 Goal이 권한 해제를 탈퇴에만 걸어 두었고, 로그아웃마다 grant를 지우면 다음 로그인마다 권한 승인 화면을 다시 봐야 합니다. 쿠키가 사라진 뒤에도 토큰은 발급 후 8시간 안에서 살아 있습니다. 2026-09-18에 사용자와 이번 범위 밖으로 정했습니다.
- **권한 해제 실패가 Sentry로 가지 않습니다.** `reportServerError`는 5xx 응답만 보내고 이 요청은 200입니다. 지금은 서버 로그(`console.error`)에만 남습니다. 실패가 실제로 얼마나 일어나는지 봐야 할 시점에 전송 경로를 넓힙니다.
- **오류 봉투와 세션 helper의 이름이 `saved-interviews`에 있습니다.** 계정 라우트가 `savedInterviewErrorResponseFor`와 `requireSession`을 그 모듈에서 가져옵니다. 베끼지 않으려면 지금은 이 방법뿐이고, 이름을 옮기려면 참조하는 라우트 넷과 이 문서들을 함께 고쳐야 합니다.
- **`.env.example`에 OAuth 환경변수가 없습니다.** 운영 준비 체크리스트 P1 11번과 같은 항목입니다. 이번 경로가 `GITHUB_OAUTH_CLIENT_SECRET`에 새로 의존하지만, 로그인이 이미 같은 값을 쓰고 있어 이번 작업이 새로 만든 문제는 아닙니다.
