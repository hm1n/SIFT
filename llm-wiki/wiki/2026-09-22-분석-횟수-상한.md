# 분석 횟수 상한

사용자 한 명이 하루에 돌릴 수 있는 저장소 분석 횟수에 상한을 둔 계약입니다(이슈 #142). 서비스가
사용자에게 거는 첫 번째 제한입니다. 그 전까지 저장소 전체에서 `rateLimit`과 `quota` 계열 문자열이
걸리는 곳은 모두 GitHub과 LLM 제공자가 서비스 쪽에 돌려주는 429를 처리하는 코드였고, 반대 방향의
제한은 하나도 없었습니다.

## 확정

**하루 3회입니다. 한국 시간 자정에 초기화합니다. 막는 자리는 Stage A 라우트입니다.**

| 항목 | 값 | 자리 |
| --- | --- | --- |
| 상한 | 3회 | `DAILY_ANALYSIS_LIMIT`(`src/features/usage-limit/quota.ts`) |
| 세는 단위 | 세션의 `github_user_id` | `getGitHubSessionFromRequest` |
| 초기화 | 한국 시간 자정 | `analysisUsageDate` |
| 검사 자리 | `POST /api/candidates/stage-a` | `src/app/api/candidates/stage-a/route.ts` |
| 저장 자리 | `analysis_usage` 표 | `db/schema.sql`, `SiftStore.consumeAnalysisQuota` |
| 초과 응답 | 429 `usage_limit_exceeded` | 같은 라우트 |
| 남은 횟수 조회 | `GET /api/usage/analysis` | `src/app/api/usage/analysis/route.ts` |
| 화면 안내 | 선택 화면 푸터, 분석 화면 오류 | `repository-select-screen.tsx`, `repository-analysis-view.tsx` |

## 1. 상한을 분석에 둔 이유

분석과 인터뷰 둘 다 모델을 부르고 회당 비용도 비슷합니다. 분석 한 번이 **0.02182달러**이고 인터뷰
10턴이 약 **0.0205달러**입니다(`wiki/2026-09-02-LLM-비용-산정.md`). 비용만으로는 어느 쪽을 막아도
같습니다.

갈린 지점은 **서버가 1회 비용에 천장을 보장하는지**였습니다. 상한이 돈을 막으려면 `횟수 × 1회
비용`이 성립해야 하고, 그러려면 1회 비용이 서버가 지키는 값이어야 합니다.

분석은 보장합니다. 묶음 200개, 프롬프트 110,000바이트, 커밋 30건, patch 총량 60,000자가 모두
라우트에서 강제되므로 저장소가 아무리 커도 한 번이 **0.03833달러**를 넘지 않습니다.

인터뷰는 보장하지 않습니다. 10턴 상한인 `INTERVIEW_MAX_TURNS`는 화면 훅
(`src/features/experience-block/use-experience-interview.ts:709`)에만 있고,
`/api/interview/stream`과 `/api/interview/experience-block`은 본문 크기와 프롬프트 바이트만 보고
턴 수를 세지 않습니다. 화면을 거치지 않으면 같은 인터뷰로 모델을 몇 번이든 부를 수 있습니다.
따라서 "하루 인터뷰 n개"로 막아도 그 n개가 얼마인지 정해지지 않습니다.

막히는 자리도 갈립니다. 분석 상한은 흐름의 맨 앞에서 막으므로 사용자가 아직 아무 비용도 쓰지 않은
상태입니다. 인터뷰 상한은 분석을 끝내고 후보를 고른 뒤에 막으므로 돈은 이미 쓴 뒤입니다.

## 2. 상한 값 3의 근거

분석 회당 최대 비용이 0.03833달러이고 인터뷰 한 건이 약 0.0205달러이므로, 한 사용자가 하루에 쓸 수
있는 최대 금액은 다음과 같습니다.

| 상한 | 분석만 | 분석 + 같은 수의 인터뷰 | 예산 10달러를 혼자 비우는 데 걸리는 날 |
| --- | --- | --- | --- |
| 3회 | **0.115달러** | 0.176달러 | **87일** (분석만 기준) |
| 5회 | 0.192달러 | 0.294달러 | 52일 |
| 10회 | 0.383달러 | 0.588달러 | 26일 |

3을 골랐습니다. 한 사람이 하루 만에 예산을 비울 수 없고, 사용량 알림이 도착해 손을 쓸 시간이
남습니다.

정상 사용자가 이 값에 거의 닿지 않는 이유는 재사용 때문입니다. 같은 저장소를 다시 열면
`openRepository`(`src/features/repository-analysis/repository-analysis-view.tsx`)가 저장된 분석을
그대로 그리고 모델을 부르지 않으므로 횟수를 쓰지 않습니다. 3회는 **새 저장소 셋을 분석하거나 "다시
분석"을 세 번 누르는 것**을 뜻합니다.

인터뷰 비용은 위 표에 참고로만 넣었습니다. 이번 상한이 인터뷰를 막지는 않습니다.

## 3. 세는 규칙

**세는 것은 Stage A 라우트에 도달해 모델을 부르기 직전까지 간 요청입니다.**

- 저장된 분석을 다시 그리는 경로는 세지 않습니다. 모델을 부르지 않기 때문입니다. 이 구분은 GA4
  계측이 겪은 것과 같은 문제입니다(`wiki/2026-09-15-GA4-계측-후속-backlog.md` 7번).
- 형식이 어긋나 422나 413으로 거절된 요청은 세지 않습니다. 모델을 부르지 않아 비용이 없고, 그런
  요청이 횟수를 먹으면 사용자가 아무것도 얻지 못한 채 상한에 닿습니다.
- 세션이 없어 401로 거절된 요청은 셀 사용자 자체가 없습니다.
- **모델이 실패한 시도는 셉니다.** 검사를 모델 호출 앞에 두었기 때문입니다. 뒤에 두면 그 사이에
  들어온 요청이 함께 통과해 상한을 넘깁니다. 실패한 호출도 입력 토큰을 소비하므로
  (`wiki/2026-09-02-LLM-비용-산정.md` 7절) 비용이 든 것은 사실입니다.
- 라우트 안의 복구 호출(`selectWithRecovery`, 최대 2회)은 따로 세지 않습니다. 사용자가 시작한
  분석은 한 번이고 복구는 그 한 번을 끝내려는 시도입니다.

## 4. 저장 자리

표를 새로 만들었습니다. `repository_analysis`의 줄을 세지 않은 이유는 90일 자동 정리 때문입니다.
정리 작업이 지운 분석만큼 횟수가 줄어, 90일 전에 분석한 사용자가 상한을 다시 받게 됩니다. 이슈
#142의 Constraint "90일 자동 정리가 세는 값을 지우면 안 됩니다"가 이것입니다.

```sql
create table if not exists analysis_usage (
  github_user_id bigint  not null,
  usage_date     date    not null,
  run_count      integer not null,
  primary key (github_user_id, usage_date)
);
```

검사와 증가는 **한 문장**입니다. 읽어서 비교한 뒤에 올리면 두 요청이 같은 값을 읽어 둘 다
통과합니다. 블록 버전 판정을 `update ... where`에 넣은 것과 같은 이유입니다.

```sql
insert into analysis_usage (github_user_id, usage_date, run_count)
values ($1::bigint, $2::date, 1)
on conflict (github_user_id, usage_date)
do update set run_count = analysis_usage.run_count + 1
  where analysis_usage.run_count < $3::int
returning run_count
```

줄이 없으면 1을 넣고 1을 돌려줍니다. 상한 아래이면 1을 올리고 올린 값을 돌려줍니다. 상한에 닿아
있으면 `where`가 거짓이라 아무것도 쓰지 않고 돌려주는 줄도 없습니다. 호출하는 쪽은 줄이 없는 것을
초과로 읽습니다.

**상한이 0 이하인 경우만 이 문장으로 막지 못합니다.** 줄이 아직 없으면 `on conflict` 가지로 가지
않아 조건을 보지 않기 때문입니다. 두 구현 모두 질의 전에 막습니다.

## 5. 초기화 기준

한국 시간 자정입니다. `usage_date`에 들어가는 날짜를 애플리케이션이 계산해 넘깁니다.

데이터베이스의 `current_date`를 쓰지 않습니다. Neon은 UTC로 돌기 때문에 그 값으로 날짜를 가르면
한국 시간 오전 9시에 횟수가 초기화됩니다. 사용자가 밤에 상한에 닿고 자정을 넘겨도 아홉 시간을 더
기다려야 하므로 "내일 다시" 안내가 틀린 말이 됩니다.

`toLocaleDateString`에 시간대를 넘기는 방법도 쓰지 않습니다. 그 함수는 실행 환경의 ICU 자료에
기대는데 서버리스 런타임마다 자료가 달라 같은 입력에 다른 문자열이 나올 수 있습니다. 고정 시차
아홉 시간을 더하고 `toISOString`에서 앞 열 자를 자릅니다.

## 6. 오류 계약

기존 `kind`와 상태 코드 조합은 바꾸지 않았습니다. 종류를 하나 더했습니다.

```json
{
  "error": {
    "kind": "usage_limit_exceeded",
    "message": "오늘 분석할 수 있는 3번을 모두 썼습니다. 내일 다시 분석할 수 있습니다.",
    "retryable": false
  }
}
```

상태 코드는 **429**입니다. 사용자 입력 문제이므로 5xx로 만들지 않습니다. `reportServerError`를
지나지 않으므로 Sentry Issue에도 남지 않습니다. 제공자 쪽 한도인 `llm_rate_limit`(503)과는 다른
종류입니다.

해제 시각을 값으로 싣지 않습니다. 화면이 소유한 문구가 "내일"이라고 말하고 그 문구가 곧 해제
시점입니다. 시각을 싣던 `resetAt`과 `limit`은 어느 화면도 읽지 않아 2026-09-22 자체 리뷰에서
걷어냈습니다. 실제 시각을 그리기로 하면 그때 다시 넣습니다.

**저장 계층이 실패하면 분석을 막습니다.** 세지 못하는 동안 열어 두면 그 시간만큼 비용이 다시
무제한이 됩니다. 이 실패는 실제 장애이므로 `server_error` 500으로 돌려주고 Sentry에도 남깁니다.

## 7. 화면

디자인 원본은 `Chat Interface Design/src/App.tsx`의 `RepoSelectScreen`입니다. 두 자리에 그립니다.

**Repository 선택 화면의 푸터**가 기본 자리입니다. 선택한 저장소 이름 아래 한 줄이 붙어 `오늘 분석
2/3회 사용`을 알리고, 상한에 닿으면 문구가 `오늘의 분석 횟수를 모두 사용했습니다. 내일 다시
시도해주세요.`로 바뀌면서 분석하기 버튼이 함께 비활성됩니다. 색만으로 가르지 않습니다. 문구와 버튼
상태가 함께 바뀝니다.

이 자리에 필요한 값은 횟수를 늘리지 않고 읽어야 하므로 `GET /api/usage/analysis`를 따로 두었습니다.
응답은 `{ used, limit }` 둘뿐입니다.
Stage A의 검사에 얹을 수 없습니다. 그 검사는 곧 한 번을 쓰는 것이라 화면을 그리는 것만으로 횟수가
줄어듭니다. 경로를 `/api/analyses/usage`에 두지 않은 이유는 그 아래에 `[id]`가 있어 정적 구간과
동적 구간이 한 자리에서 겹치기 때문입니다.

**세 가지 상태를 나눕니다.** 읽는 중에는 안내를 그리지 않습니다. 읽었으면 값을 그립니다. 읽지
못했으면 안내를 접고 **분석은 막지 않습니다.** 읽지 못한 것을 막힌 것으로 보면 조회가 한 번
실패했다는 이유로 아직 횟수가 남은 사용자까지 분석을 시작하지 못합니다. 반대로 열어 두면 남지 않은
사용자가 한 번 헛걸음하고 429를 받습니다. 틀렸을 때 잃는 것이 적은 쪽을 골랐습니다. 목록 조회와
따로 읽는 것도 같은 이유입니다. 한 요청에 묶으면 횟수를 읽지 못한 것만으로 목록까지 오류 화면이
됩니다.

**분석 화면의 오류 상태**가 두 번째 자리입니다. 선택 화면이 버튼을 미리 막아도 다른 탭이 먼저
썼거나 화면을 열어 둔 사이에 상한에 닿으면 429가 여기까지 옵니다. 상태 코드는 `ERROR / LIMIT`이고
동작 버튼을 그리지 않습니다. `RecoveryAction`에 `wait`를 더했습니다. 기존 셋 중 맞는 것이
없습니다. 다시 시도하면 또 막히고, 다시 로그인해도 같은 사용자이며, 다른 Repository를 골라도 상한은
사용자 단위입니다.

**화면이 막는 것은 상한을 집행하는 것이 아닙니다.** 헛걸음을 줄이는 것입니다. 집행은 끝까지 Stage A
라우트가 합니다.

색은 디자인의 red-500(`#ef4444`) 대신 `--color-danger: #dc2626`을 씁니다. `#ef4444`는 흰 배경에서
대비가 3.8:1이라 작은 글자의 기준 4.5:1에 못 미치고 이 문구는 9~11px입니다. amber를 내린 것과 같은
이유입니다.

## 9. 남은 위험

- **Stage B 라우트가 열려 있습니다.** `/api/candidates/stage-b`는 로그인 세션만 있으면 직접 부를 수
  있고 횟수를 세지 않습니다. 회당 비용은 Stage B가 **0.01744달러**로 Stage A(**0.00282달러**)의 여섯
  배입니다. Stage A만 막으면 더 비싼 쪽이 열린 채 남습니다.
- **인터뷰 턴 상한이 클라이언트에만 있습니다.** 1절에 적은 사실입니다. 상한 유무와 별개로 서버가
  인터뷰 비용에 천장을 씌우지 못한다는 뜻입니다.
- **저장된 인터뷰 수 상한이 없습니다.** `wiki/2026-09-15-인터뷰-저장-후속-backlog.md` 6번입니다.
