# 이슈 #90 실측 핸드오프

이슈 #90("턴 진행과 블록 전환, 열 턴 자동 종료")의 구현은 이번 세션에서 끝났습니다. 이 문서는
유료 LLM 호출이 필요해 이 세션에서 하지 않은 실측을, 다른 세션이 이어서 할 수 있도록 남기는
핸드오프입니다. 구현 자체를 다시 설명하지 않고, 무엇을 재야 하는지와 어떻게 재는지만 적습니다.

## 지금 상태

브랜치는 `hm1n/feature-experience-block`이고 커밋은 아직 없습니다. `npm run typecheck`, `npm run lint`,
`npm test`(68개 파일, 1094개 테스트) 모두 통과했지만 전부 합성 데이터·모킹된 fetch 기준입니다. 실제
모델 호출은 한 번도 없었습니다.

바뀐 파일과 새 파일은 `git status --short`로 확인합니다. 핵심은 세 가지입니다.

- `src/features/experience-block/progress.ts` — 다음 질문 대상을 고르는 순수 함수와, 손으로 고른 임시
  운영값(`PROGRESS_CONFIG`).
- `src/features/experience-block/use-experience-interview.ts` — 답변마다 블록 갱신을 부르고 다음 대상을
  정해 `useInterviewStream`에 넘기는 훅.
- `src/features/interview/block-prompt.ts`, `src/features/interview/measurement/block-update.measure.mts` —
  블록 갱신 프롬프트에 `targetElement`·`targetResponse`를 추가한 부분과 그 측정 하네스.

## 실측이 필요한 이유

`progress.ts` 코드 주석에 이미 표시해 뒀듯, 이번 구현의 몇몇 값은 실제 인터뷰 데이터 없이 손으로
정했습니다. 설계 문서 10절은 이걸 "구현 검증"과 "실사용 검증"으로 나눕니다. 이번 세션이 끝낸 것은
구현 검증(회귀 픽스처, 상태 전이, 단위 테스트)뿐이고, 실사용 검증(10턴의 충분성, 재질문 횟수의
적절성, 사용자 피로와 중도 종료)은 실제 인터뷰를 돌려야만 잴 수 있습니다. 합성 답변 테스트 통과를
턴 수 충분성의 근거로 쓰지 않는다고 설계 문서와 코드 주석에 이미 명시했습니다.

## 실측 대상 목록

### 1. `PROGRESS_CONFIG` 두 값의 적절성

`src/features/experience-block/progress.ts:21-26`

```ts
export const PROGRESS_CONFIG = {
  maxAsksAfterUnknown: 2, // 같은 요소에서 unknown을 이 횟수(최초 질문 포함)만큼 받으면 포기
  unvisitedBlockReserve: 1, // 미확인 블록 하나에 예약하는 질문 기회
} as const;
```

- `maxAsksAfterUnknown=2`가 너무 인색해서(재질문 1회만 허용) 캐낼 수 있었던 정보를 놓치는지, 아니면
  너무 후해서 같은 걸 두 번 물어 사용자를 피로하게 하는지 실제 답변으로 확인합니다.
- `unvisitedBlockReserve=1`이 부족해서 마지막 블록(대개 result)이 한 번도 못 물어보고 10턴을 다 쓰는
  경우가 생기는지, 반대로 과해서 앞 블록을 덜 파고드는지 확인합니다.
- 판단 기준은 "10턴 안에 네 블록 모두 최소한의 정보를 얻었는가"와 "같은 질문을 반복한다고 느꼈는가"
  둘입니다. 둘 다 사람이 실제로 답하거나, 최소한 사람처럼 다양하게(모른다/거절/무관한 대답 포함)
  답하는 시나리오로만 판단할 수 있습니다.

### 2. `targetResponse` 분류 정확도

블록 갱신 모델은 이제 답변마다 `provided`·`unknown`·`not_done`·`refused`·`unanswered` 중 하나를
`targetResponse`로 냅니다(`src/features/experience-block/types.ts`의 `TARGET_RESPONSES`,
`src/features/interview/block-prompt.ts`의 "반응 규칙"). `progress.ts`의 재질문·거절 추적은 이 값을
그대로 신뢰합니다. 모델이 이 분류를 잘못 내면(예: 무관한 대답을 `unknown`으로 잘못 분류) 재질문
예산이 실제와 다르게 소진됩니다. 실측에서 답변 유형별로 이 분류가 맞는지 눈으로 확인합니다.

- `provided`: 겨냥한 요소에 직접 답한 경우.
- `unknown`: "기억이 안 난다"류.
- `not_done`: 아직 안 했거나 해당 없음.
- `refused`: 답변 거절.
- `unanswered`: 질문과 무관한 대답(설계에 없던 값으로, 이번 구현에서 `unknown`과 구분하려고
  추가했습니다 — 이 구분이 실제로 유의미한 차이를 만드는지도 함께 봅니다).

### 3. `block-update.measure.mts` 시나리오가 `targetElement`를 실제로 바꾸지 않음

`src/features/interview/measurement/block-update.measure.mts`의 `ScenarioTurn`은 `targetElement?:
BlockElement`를 받지만, 지금 있는 시나리오는 전부 이 필드를 비워 둬서 실행부가 기본값 `"a"`로만
돌립니다(파일 안 `targetElement: turn.targetElement ?? "a"` 자리). 즉 지금 측정 하네스는 각 블록의
요소 `b`(`BLOCK_ELEMENT_PURPOSES`의 두 번째 절)를 겨냥한 질문을 한 번도 실행해 보지 않았습니다.
요소 `b`를 겨냥했을 때도 모델이 `targetElementPurpose`를 프롬프트에 준 대로 따라가는지, 아니면
요소 `a` 쪽 정보만 계속 채우는지 확인이 필요합니다. 기존 시나리오 중 두세 개를 골라 `targetElement:
"b"`를 준 턴을 추가하는 방식이 제일 쌉니다.

### 4. 토큰·비용·지연 변화

`targetElement`·`targetElementPurpose`가 턴 JSON에 더해지고 `targetResponse`가 출력 스키마에
더해지면서 입력·출력 토큰이 늘었습니다. `llm-wiki/wiki/2026-09-02-LLM-비용-산정.md`의 기존 산정치를
이번 변경 이후 수치로 갱신해야 하는지, 늘어난 폭이 무시할 만한지 확인합니다.

## 실행 방법

```bash
# 1. 공개 PR 근거 준비(한 번만, 무료)
npm exec --yes --package=tsx -- tsx --env-file=.env src/features/interview/measurement/block-update.measure.mts --prepare

# 2. 프롬프트 바이트만 확인(무료)
npm exec --yes --package=tsx -- tsx --env-file=.env src/features/interview/measurement/block-update.measure.mts --dry-run

# 3. 실제 호출(유료). budget은 1이나 2만 허용됩니다.
npm exec --yes --package=tsx -- tsx --env-file=.env src/features/interview/measurement/block-update.measure.mts --out=.measurements/block-update-<날짜> --budget=1
```

`.env`에 모델 제공자 키가 필요합니다(`gpt-5.6-luna`·`gemini-3.1-flash-lite` 중 `--models=`로 고른 것).
`GITHUB_TOKEN`이 없으면 `gh auth token`으로 자동 대체합니다. 출력은 공개 PR 근거와 합성 사용자
답변만 남기고 키·원시 요청 헤더는 저장하지 않습니다(스크립트 상단 주석 참고).

`use-experience-interview.ts`가 만드는 10턴 자동 종료 흐름 전체를 실제 모델로 재현하려면
측정 스크립트를 그대로 쓰기보다, 이 훅을 브라우저에서 직접 돌리며(개발 서버 `npm run dev`) 사람이
번갈아 가며 답하는 편이 설계 10절이 요구하는 "실제 인터뷰"에 더 가깝습니다. 측정 스크립트는 리듀서
검증·프롬프트 품질 확인에는 적합하지만, 사람이 실제로 느끼는 피로도나 중도 종료 충동은 재지
못합니다.

- 분류 오류나 토큰 증가처럼 즉시 고치지 않고 후속으로 미룰 것은
  `llm-wiki/wiki/2026-09-11-PAAR-경험블록-후속-backlog.md`에 추가합니다.
- 실측 경위와 라운드 수는 `llm-wiki/log.md`에 남깁니다(이 프로젝트의 표준 절차,
  `AGENTS.md`의 "Code Review 반영 절차" 참고).
