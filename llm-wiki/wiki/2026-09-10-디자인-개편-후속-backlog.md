## PR #102 재검증에서 분리한 항목

14. **internal Repository의 visibility 오분류.** `RepositorySummary.visibility`는 GitHub 응답의 `private` 불리언만 보고 `public`과 `private` 둘로만 나눕니다. GitHub Enterprise Cloud 조직의 internal Repository는 `private: false`이면서 `visibility: "internal"`이라 화면이 이를 `public`으로 잘못 표시합니다. Codex 재검증이 도구 등급 P1로 지적했고, 프로젝트 기준으로는 P2로 판정해 분리했습니다. 판정 근거는 셋입니다. 이 서비스는 개인 개발자의 GitHub 계정을 대상으로 하고 GHEC 조직 전용 기능이라 발생 빈도가 낮습니다. 이슈 #95 Non-goal이 Organization 전환·필터를 범위 밖으로 뒀습니다. `visibility` 표시는 제품 스펙이 "과도하게 강조하지 마세요"라고 규정한 보조 정보입니다. 제대로 고치려면 `RepositorySummary.visibility`를 `"public" | "private" | "internal"`로 넓혀야 하고, 이 필드는 `AppShell`의 `ShellRepository.visibility`와 이름을 맞춘 계약이라 함께 넓힐지 판단이 필요합니다. 화면의 PRIVATE 라벨도 internal 표시를 어떻게 할지 정해야 합니다.
15. **Repository 목록 조회 실패 시 부분 결과 보존.** `fetchUserRepositories`는 두 번째 이후 페이지에서 HTTP 오류, JSON 파싱 실패, 배열이 아닌 응답 중 무엇이 나든 이미 모은 목록을 버리고 오류만 던집니다. Codex 재검증이 JSON 파싱 실패 경로의 테스트 공백을 P2로 지적했고, 회귀 테스트는 이번 PR에 추가했습니다. 다만 실제로 부분 목록을 오류 객체에 보존하는 일은 분리했습니다. 지금 이 값을 읽는 소비자가 없어 추가해도 쓰이지 않는 필드가 되고, 커밋 조회의 `GitHubFetchError<TCommit>`처럼 공유 계약에 태우려면 `errors.ts`, `api-contract.ts`의 `SerializedGitHubError`까지 넓혀야 합니다. 소비자가 생기면(예: 부분 목록이라도 보여 달라는 요청) 그때 계약을 넓힙니다.
