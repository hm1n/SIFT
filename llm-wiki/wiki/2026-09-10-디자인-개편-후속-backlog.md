## #93에서 분리한 항목

8. **TopHeader의 사용자명과 이니셜.** 세션 쿠키에 GitHub 사용자 정보가 없어 #93은 로그인 여부만 그립니다. #94에서 정했습니다. #94 Constraint가 세션 쿠키 계약을 바꾸지 않는 것이라 쿠키에 사용자 정보를 넣을 수 없고, 남는 방법은 layout에서 매 요청 GitHub `/user`를 조회하는 것인데 모든 페이지에 왕복 한 번이 붙습니다. #94에서는 넣지 않았습니다. #95에서 판단한 결과 목록 API에 묶는 방법은 쓸 수 없습니다. 목록은 클라이언트가 렌더 뒤에 가져오고 `TopHeader`는 layout 서버 컴포넌트가 그리므로 목록 응답에 `/user`를 실어도 헤더에 닿지 않습니다. 남는 선택지는 쿠키 계약 변경이나 layout의 `/user` 조회 둘이고, 디자인 개편 안에서는 넣지 않습니다.

## #95에서 분리한 항목

9. **기여 문장을 항목으로 풀어내기.** 선택 화면의 textarea는 디자인대로 한 문장 placeholder를 쓰지만 항목 경계는 줄바꿈이라 한 문장이 항목 하나가 됩니다. Stage A의 `contributionItem` 대조는 입력 집합과 정확히 일치해야 하므로 문장 하나로는 분류가 거칠어집니다. 쉼표·마침표 분리는 어색한 조각을 만들어 접었습니다. Stage A 프롬프트가 문장을 항목으로 풀어 돌려주게 하거나 대조를 완화하는 일은 Stage A 쪽 작업입니다.
10. **목록 페이지네이션의 누락.** `/user/repos`의 커서는 page 번호라서 조회 도중 목록이 바뀌면 경계에서 항목이 빠질 수 있습니다. 중복은 `id`로 걸러내지만 누락은 남습니다. GraphQL의 커서나 조회 뒤 개수 대조 같은 방법은 실제 누락이 관찰되면 검토합니다.
11. **되돌아갈 때 선택 보존.** 분석 화면에서 "다른 Repository 선택"으로 돌아오면 목록을 다시 조회하고 이전 선택과 기여 입력을 보존하지 않습니다. 디자인 `handleChangeRepo`와 같은 동작이지만, 기여 문장을 길게 쓴 뒤 Repository를 바꾸는 사용자는 다시 써야 합니다. 보존이 필요하다는 피드백이 있으면 흐름 컴포넌트의 상태로 올립니다.
12. **archived·fork 표시와 필터.** 목록 응답에 archived와 fork 여부를 싣지 않고 화면에도 표시하지 않습니다. 이슈 Non-goal의 Organization 전환·필터와 같은 묶음입니다.
13. ~~**비공개 Repository 접근 scope.**~~ 해결되었습니다. PR #73은 OAuth scope를 `read:user` 하나로 정해 비공개 Repository를 지원하지 않았습니다. ## PR #102 재검증에서 분리한 항목

14. **internal Repository의 visibility 오분류.** `RepositorySummary.visibility`는 GitHub 응답의 `private` 불리언만 보고 `public`과 `private` 둘로만 나눕니다. GitHub Enterprise Cloud 조직의 internal Repository는 `private: false`이면서 `visibility: "internal"`이라 화면이 이를 `public`으로 잘못 표시합니다. Codex 재검증이 도구 등급 P1로 지적했고, 프로젝트 기준으로는 P2로 판정해 분리했습니다. 판정 근거는 셋입니다. 이 서비스는 개인 개발자의 GitHub 계정을 대상으로 하고 GHEC 조직 전용 기능이라 발생 빈도가 낮습니다. 이슈 #95 Non-goal이 Organization 전환·필터를 범위 밖으로 뒀습니다. `visibility` 표시는 제품 스펙이 "과도하게 강조하지 마세요"라고 규정한 보조 정보입니다. 제대로 고치려면 `RepositorySummary.visibility`를 `"public" | "private" | "internal"`로 넓혀야 하고, 이 필드는 `AppShell`의 `ShellRepository.visibility`와 이름을 맞춘 계약이라 함께 넓힐지 판단이 필요합니다. 화면의 PRIVATE 라벨도 internal 표시를 어떻게 할지 정해야 합니다.
15. **Repository 목록 조회 실패 시 부분 결과 보존.** `fetchUserRepositories`는 두 번째 이후 페이지에서 HTTP 오류, JSON 파싱 실패, 배열이 아닌 응답 중 무엇이 나든 이미 모은 목록을 버리고 오류만 던집니다. Codex 재검증이 JSON 파싱 실패 경로의 테스트 공백을 P2로 지적했고, 회귀 테스트는 이번 PR에 추가했습니다. 다만 실제로 부분 목록을 오류 객체에 보존하는 일은 분리했습니다. 지금 이 값을 읽는 소비자가 없어 추가해도 쓰이지 않는 필드가 되고, 커밋 조회의 `GitHubFetchError<TCommit>`처럼 공유 계약에 태우려면 `errors.ts`, `api-contract.ts`의 `SerializedGitHubError`까지 넓혀야 합니다. 소비자가 생기면(예: 부분 목록이라도 보여 달라는 요청) 그때 계약을 넓힙니다.

## #96에서 분리한 항목

16. **후보 생성 오류(LLM·diff 재조회·Stage A/B)의 영어 번역.** `repository-analysis.ts`의 `toCandidateGenerationError`와 `DIFF_REFETCH_GUIDANCE`가 만드는 오류 6종 이상은 아직 한국어입니다. #96은 GitHub 조회 오류 5종(+ partial_failure)과 Empty 5종만 영어로 옮기기로 사용자가 결정했습니다. 이 범위까지 넓히면 `repository-analysis-view.test.tsx`·`experience-candidate-list.test.tsx`·`repository-flow.test.tsx` 세 파일 이상을 함께 고쳐야 해서 PR 크기가 커집니다. Empty·Error의 액션 버튼 라벨은 오류 종류와 무관하게 이미 전부 영어라, 번역이 끝나기 전까지는 버튼은 영어인데 제목·설명은 한국어인 혼용 화면이 남습니다.
17. **AppShell과 Loading 체크리스트의 중복된 Change repository 버튼.** #96에서 `AppShell`을 처음 실제 화면에 배치하면서, 사이드바의 `← Change repository`와 Loading 체크리스트 자체 푸터의 `← Change repository`가 Loading 중에는 동시에, 같은 접근성 이름으로 뜨게 됐습니다. 디자인 원본의 `AppShell`과 `AnalyzingScreen`도 각자 같은 버튼을 그려 이 중복은 디자인 자체의 특성이지만, 스크린리더 사용자가 같은 이름의 버튼 두 개를 만나는 문제는 남습니다. #97 이후 접근성 리뷰에서 다룹니다.
