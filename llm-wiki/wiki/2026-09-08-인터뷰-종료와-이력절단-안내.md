# 인터뷰 종료와 이력 절단 안내

이슈 #78의 결정을 기록합니다. 이슈 #77이 만든 답변 입력과 대화 표시 위에 종료 조작, 이력 절단 안내, 이력 상한 초과 안내를 얹었습니다. 요청 계약과 절단 규칙은 손대지 않았습니다.

## 1. 종료 판정은 훅에 있습니다

`use-interview-stream.ts`가 `isEnded`와 `endInterview()`를 내놓습니다. 종료는 되돌릴 수 없고 종료한 훅은 더 이상 요청을 보내지 않습니다.

판정을 화면에 두지 않은 이유는 요청을 시작하는 자리가 셋이기 때문입니다. 답변 제출은 Enter로도 불리고, 다시 시도는 오류 안내 안의 버튼에 걸려 있고, `start`는 마운트 시점에 자동으로 돕니다. 화면이 버튼을 잠그는 것으로는 앞의 둘을 막지 못합니다.

막는 자리는 세 곳입니다.

- `start`: 모든 요청이 이 함수를 지나므로 여기서 한 번 막으면 요청 자체가 나가지 않습니다.
- `retry`: 실패한 질문을 지우는 일이 요청보다 먼저 일어납니다. 이 갈래를 열어 두면 종료한 대화의 마지막 질문만 사라지고 새 질문은 오지 않습니다.
- `submitAnswer`: `canSubmitAnswer`가 거짓이 되지만 그 값을 읽는 `canSubmitRef`는 렌더 뒤 effect에서 갱신됩니다. 종료와 같은 틱에 들어온 제출은 아직 참인 값을 읽으므로 `isEndedRef`를 먼저 봅니다.

종료 상태도 상태와 ref를 함께 둡니다. ref는 상태를 바꾸는 자리에서 같이 바꿉니다.

## 2. 종료가 대화에 하는 일

진행 중인 요청을 끊고, 버퍼에 남은 청크까지 화면에 반영한 뒤 도착 중이던 메시지를 닫습니다.

받은 만큼을 지우지 않는 이유는 사용자가 이미 읽고 있던 내용이기 때문입니다. 닫지 않으면 도착 중 표시가 영영 남습니다. 닫아도 요청 이력으로 쓰이지 않으므로 상한을 다시 재지 않습니다.

`isLastQuestionTooLong`은 지웁니다. 그 판정이 뜻하는 것은 "이 질문으로는 대화를 이어갈 수 없다"이고 화면은 그 자리에서 다시 시도를 권하는데, 종료한 대화에는 다시 시도가 없어 사용자가 할 수 있는 일이 없습니다.

**종료한 인터뷰를 같은 화면에서 다시 시작하는 조작은 두지 않았습니다.** 저장이 없으므로 재시작은 첫 질문 재생성입니다. 그 조작을 두면 종료 상태를 푸는 경로가 생기고, 1절의 세 잠금을 다시 열어야 합니다. 다시 하려면 후보 목록으로 돌아가 경험을 다시 확정합니다. 대화가 사라지는 시점은 그 복귀이며 종료가 아닙니다.

## 3. 종료 화면

종료 조작은 대화 영역 안, 답변 입력 아래에 둡니다. 생성 중에도 누를 수 있습니다. 질문을 기다리다 그만두는 것을 막을 이유가 없고 종료가 진행 중인 요청을 끊습니다.

한 번 확인을 받습니다. 확인 문구는 사라지는 것을 모두 적습니다. 작성 중인 답변, 그리고 후보 목록으로 돌아갈 때의 대화입니다. 작성 중이던 답변은 어디에도 보내지 않으므로 남겨 둘 자리가 없고, 확인 문구가 그 사실을 알린 뒤 버립니다. 확인 단계는 화면 상태입니다. 훅에는 확정된 종료만 알립니다. 확인 단계를 훅에 두면 종료하지 않은 상태가 두 가지가 되고 1절의 잠금이 어느 쪽을 봐야 하는지 갈립니다.

종료한 뒤 그리는 것은 다음과 같습니다.

- 상태 문단이 "인터뷰를 종료했습니다. 대화는 읽기 전용입니다."로 바뀝니다. 낭독 대상은 이슈 #77과 같이 상태 문단과 새 메시지 안내뿐이므로 종료 사실은 이 자리에서 알립니다. `InterviewStreamPhase`에 값을 더하지 않았습니다. 그 union은 스트림 수신부의 상태이고 종료는 사용자의 조작입니다. 섞으면 스트림이 끝나지 않은 채 종료한 경우에 어느 쪽을 담을지 정할 수 없습니다.
- 답변 입력이 있던 자리에 다음에 무엇이 일어나는지를 적습니다. 종료 사실은 상태 문단이 이미 말했으므로 되풀이하지 않습니다. 이 자리는 "지금 사용자가 할 수 있는 일"을 그리는 자리이므로 새 자리를 만들지 않았습니다.
- 오류 박스를 걷습니다. 그 박스의 조작은 다시 시도 하나이고 종료한 뒤에는 요청을 보내지 않습니다.
- 준비 중 안내와 `aria-busy`를 걷습니다. 종료가 요청을 끊었으므로 준비하던 질문은 오지 않습니다.

## 4. 절단 안내는 빠진 자리에 그립니다

`removedHistory`가 비어 있지 않으면 첫 질문·답변 쌍 바로 뒤에 안내를 넣습니다. `trimInterviewHistory`가 첫 쌍을 남기고 그 다음부터 빼므로 빠진 구간의 시작이 언제나 그 자리입니다.

**절단은 화면의 대화를 자르지 않습니다. 잘리는 것은 요청 이력뿐입니다.** 빠진 질문과 답변도 화면에 그대로 남아 있으므로, 대화 밖에 안내를 두면 사용자가 어느 대목이 빠졌는지 알 수 없고 AI가 자기 답변을 무시했다고 읽습니다. 안내는 몇 쌍이 빠졌는지, 화면에는 남아 있지만 AI가 보지 못한다는 것, 첫 쌍과 최근 대화는 계속 실린다는 것을 적습니다.

오류 안내와 같은 자리에 두지 않았습니다. 오류는 사용자가 조작해서 풀어야 하는 상태이고 절단은 이미 일어난 일을 알리는 것입니다. 같은 자리에 두면 다시 시도 버튼이 절단에도 달린 것처럼 보입니다.

이 안내는 낭독되지 않습니다. `role="log"` 영역이 `aria-live="off"`이고 안내가 그 안에 있습니다. 자동 스크롤은 하단을 따라가므로 화면으로도 바로 보이지 않습니다. 이 항목은 `wiki/2026-09-08-꼬리질문-요청계약-후속-backlog.md` 7번입니다.

## 5. 이력 상한 초과 안내

`REQUEST_ERROR_GUIDANCE`에 `history_too_large` 문구를 넣었습니다. `body_too_large`와 갈라 씁니다. `clearsOnRetry`가 둘 다 거짓이지만 사용자가 할 수 있는 일이 다릅니다. 본문 상한은 근거가 정하므로 손댈 자리가 없고, 이 실패는 대화를 줄이면 풀립니다.

**대화를 줄이는 조작은 두지 않았습니다.** 그래서 "대화를 줄여 주세요"로 끝내지 않고 실제로 있는 조작인 종료와 새 인터뷰를 가리킵니다. 없는 조작을 권하면 사용자는 같은 요청을 반복합니다.

절단은 클라이언트가 하므로 정상 경로에서는 이 분류가 오지 않습니다. 남은 도달 경로는 항목 하나가 항목 상한을 넘는 경우인데, 답변은 입력이 막고 질문은 `isLastQuestionTooLong`이 먼저 잡습니다. 그래도 문구를 둡니다. 서버가 이 분류를 실제로 내보내고, 항목이 없으면 기다리면 풀린다는 뜻의 일반 문구가 나갑니다.

## 6. 페이지 이탈 경고는 넣지 않았습니다

`beforeunload`를 걸지 않았습니다. 이슈 #78의 Tasks에 없고, jsdom 테스트에서 다루기 까다로워 회귀 테스트 없는 코드가 하나 생깁니다. 새로 고침과 탭 닫기로 대화가 사라지는 것은 여전히 경고 없이 일어납니다. 이 항목은 `wiki/2026-09-08-꼬리질문-요청계약-후속-backlog.md` 6번이고 우선순위가 높습니다.

## 7. 확인 범위

종료 조작과 확인 절차, 종료 후 읽기 전용, 절단 안내의 자리, 상한 초과 문구는 jsdom 화면 테스트와 훅 테스트로 확인했습니다. 절단 안내 테스트는 `INTERVIEW_HISTORY_MAX_ITEMS / 2 + 1` 턴을 실제로 돌려 요청 이력이 상한으로 잘린 것과 안내의 자리를 함께 봅니다.

`npm run test`(47개 파일, 883개), `npm run lint`, `npm run typecheck`, `npm run build`가 통과합니다. 브라우저에서 눌러 본 확인은 하지 않았습니다. 인터뷰 화면에 닿으려면 GitHub 로그인 세션과 저장소 분석이 필요하고, 이번 변경은 모두 클라이언트 상태입니다.
