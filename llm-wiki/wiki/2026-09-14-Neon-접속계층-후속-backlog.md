# Neon 접속 계층 후속 backlog

이슈 #114와 PR #119에서 범위 밖으로 분리한 항목입니다. 2026-08-20 코드 리뷰 전략에 따라 새 GitHub Issue를 만들지 않고 이 문서에서 추적합니다.

## 1. ~~첫 질의가 연결 단계에서 끊기는 원인과 대응~~ (2026-09-15 해소)

`npm run db:schema`를 한동안 쉬었다가 처음 부르면 연결이 10초 안에 맺어지지 않아 `ConnectTimeoutError`로 죽고, 곧바로 다시 돌리면 성공합니다. 2026-09-14에 두 번 관찰했습니다.

```
ConnectTimeoutError: Connect Timeout Error
(attempted address: api.c-2.us-east-2.aws.neon.tech:443, timeout: 10000ms)
```

PR #119 리뷰에서 지수 backoff 재시도를 넣으라는 지적을 받았지만 반영하지 않았습니다. 원인을 확인하지 않은 상태에서 재시도 횟수와 간격을 고르면 근거 없는 상수를 정하는 것이 되고, `AGENTS.md`의 "추측성 최적화를 먼저 적용하지 않습니다"에 어긋납니다. 수동으로 돌리는 개발 스크립트라 다시 실행하면 되는 점도 있습니다.

**2026-09-15에 #115에서 재고 원인을 갈랐습니다. 프로덕션 코드에 재시도나 타임아웃 상수를 넣지 않기로 했습니다.**

같은 프로세스에서 단계를 나눠 잰 표본이 결정적이었습니다.

```
dns 11057ms | tcp 214ms | tls 203ms | query 646ms
```

연결 자체는 빠르고 이름 풀이에서 11초가 걸렸습니다. undici의 10초 connect timeout이 DNS 구간까지 덮으므로 이 표본이 곧 관찰된 오류입니다. 유휴 시간을 바꿔 가며 잰 결과도 scale-to-zero와 맞지 않았습니다. 0초 뒤 실패(10,696ms), 60초 뒤 성공(1,267ms), 360초 뒤 성공(1,300ms), 900초 뒤 실패(10,685ms)로 유휴 시간과 무관했습니다. DNS만 55회 따로 재니 중앙값 1ms에 11초를 넘긴 것이 2회였습니다.

원인은 Neon이 아니라 **로컬 이름 풀이가 간헐적으로 멈추는 것**입니다. 여기에 재시도를 넣으면 관찰되지 않은 원인에 상수를 고르는 일이 되고 `AGENTS.md`의 "추측성 최적화를 먼저 적용하지 않습니다"에 어긋납니다. #115의 저장 경로는 이 오류를 `DatabaseError`(`query_failed`)로 분류해 화면이 "잠시 뒤 다시 시도" 안내를 하고 대화는 그대로 잇습니다. 실제로 검증 스크립트 실행 중에 한 번 나서 그 경로가 도는 것을 확인했습니다.

Vercel 로그에 같은 오류가 나오면 그때 다시 봅니다. 그 환경은 이름 풀이 경로가 다르므로 여기서 잰 값이 그대로 적용되지 않습니다.

## 2. 테스트가 환경변수를 정리할 때 원래 값을 되돌리지 않습니다

`auth-session.test.ts`, `callback/route.test.ts`를 비롯한 여러 테스트가 `afterEach`에서 환경변수를 무조건 `delete`합니다. 실행하기 전에 셸에 그 값이 있었으면 잃습니다.

이들은 `beforeEach`에서 값을 확정해 두기 때문에 **결과가 환경에 따라 달라지지는 않습니다.** PR #119에서 같은 성격의 지적을 받은 `client.test.ts`는 값이 없다는 것을 전제로 판정해서 실제로 셸에 따라 실패했고, 그래서 그 파일만 고쳤습니다.

나머지는 이번 PR이 만든 것이 아니고 지금 깨지지도 않아 분리합니다. 고칠 때는 저장했다가 되돌리는 방식을 한 곳에 모으는 편이 낫습니다.

## 3. ~~로컬 `.env`가 프로덕션 브랜치를 가리킵니다~~ (2026-09-15 해소)

**2026-09-15에 이 워크트리의 `.env`를 `vercel-dev` 브랜치로 옮겼습니다(사용자 결정).** 파일 이름은 `.env.local`이 아니라 `.env`였고, 워크트리에는 없어서 메인 체크아웃의 값을 복사한 뒤 `DATABASE_URL`·`DATABASE_URL_UNPOOLED`·`NEON_BRANCH` 셋만 바꿨습니다. 사용자 지시로 다른 워크트리와 메인 체크아웃의 `.env`는 건드리지 않았으므로, 그쪽에서 `npm run db:schema`를 돌리면 여전히 프로덕션에 적용됩니다.

아래는 결정 당시의 기록입니다.

`neon link`가 써 준 값이라 `production`을 가리킵니다. Vercel의 Development 환경은 `vercel-dev`를 가리킵니다. 지금은 로컬에서 데이터베이스에 쓰는 애플리케이션 코드가 없지만, 실제 저장이 시작되면 로컬 개발이 프로덕션 브랜치에 씁니다. #115에서 어느 쪽으로 맞출지 정해야 합니다.

애플리케이션보다 먼저 걸리는 것이 `npm run db:schema`입니다. PR #119 리뷰에서 이 점을 지적받았습니다. 지금 로컬에서 이 명령을 돌리면 프로덕션 브랜치의 스키마가 바뀝니다.

이번에 막지 않은 이유는 두 가지입니다. `db/schema.sql`의 모든 문장이 `if not exists`라 지금은 여러 번 돌려도 결과가 같고 지울 것이 없습니다. 그리고 지금 프로덕션에 스키마를 적용하는 정당한 방법이 이 명령뿐이라, 프로덕션을 거부하는 가드를 넣으면 의도한 사용까지 막습니다. 배포 흐름이 정해지기 전에 확인 절차를 붙이는 것은 근거 없이 형식을 늘리는 일입니다.

`schema.sql`에 `drop`이나 `alter ... type`처럼 되돌릴 수 없는 문장이 들어가는 시점이 경계입니다. 그때는 대상 브랜치를 명시적으로 받게 고쳐야 합니다.

## 5. `githubFetch`에 요청 제한 시간이 없습니다

`src/lib/github/commits.ts`의 `githubFetch`가 `AbortSignal` 없이 `fetch`를 부릅니다. GitHub이 응답을 끝내지도 실패하지도 않으면 호출한 쪽이 계속 기다립니다. PR #119 리뷰가 OAuth 콜백의 `fetchAuthenticatedUser` 경로를 짚어 지적했습니다.

이번 PR이 만든 결함이 아닙니다. `githubFetch`는 커밋 목록, 커밋 상세, Repository 목록, Repository 정보 등 GitHub을 부르는 모든 경로가 씁니다. 이번 PR은 호출하는 곳을 하나 늘렸을 뿐입니다.

고치면 라우트 8곳의 동작이 함께 바뀝니다. 제한 시간 값을 고르려면 가장 오래 걸리는 경로인 커밋 목록 페이지네이션이 실제로 얼마나 걸리는지 재야 합니다. 근거 없이 상수를 고르면 정상 요청을 끊게 됩니다. 별도 작업으로 다룹니다.

## 4. `getSql({ unpooled: true })`의 폴백

`DATABASE_URL_UNPOOLED`가 없으면 `DATABASE_URL`로 내려갑니다. PR #119 재검증에서 폴백 없이 `config_missing`으로 처리하라는 지적을 받았지만 반영하지 않았습니다.

HTTP 드라이버는 문장 하나가 곧 트랜잭션 하나라 DDL을 풀 연결로 보내도 깨지지 않습니다. 지금 스키마에는 세션 상태를 쓰는 DDL이 없고, 폴백은 값이 하나만 주입되는 환경을 위한 의도된 동작이며 `.env.example`에도 적혀 있습니다. 실패 시나리오를 댈 수 없어 P3으로 분리했습니다.

세션에 걸쳐야 하는 DDL(예를 들어 advisory lock을 쓰는 마이그레이션)을 넣게 되면 그때 폴백을 없애야 합니다.
