# Sentry 클라이언트 계측

## 결론

**브라우저의 Core Web Vitals 다섯 개와 클라이언트 런타임 오류를 `@sentry/nextjs`로 수집합니다.**
Issue #81 범위이고 서버 사이드 트레이싱, Session Replay, Profiling, Source Map 업로드는 각각
후속으로 분리했습니다.

**DSN이 없으면 `Sentry.init`을 부르지 않습니다.** 판정과 초기화는 `src/lib/sentry/client.ts`의
`initSentryClient` 하나가 담당합니다. 값이 비어 있거나 공백뿐이면 초기화를 건너뛰고 false를
돌려줍니다. DSN 없는 프로덕션 빌드에서 envelope 요청이 0건인 것을 실측으로 확인했습니다.

초기화를 `instrumentation-client.ts`가 아니라 이 모듈에 둔 이유입니다. 그 파일은 import만으로
SDK를 초기화하는 부수 효과 파일이라 테스트가 로드할 수 없고, 이슈 #81의 제약도 jsdom에서 그
파일을 로드하지 않도록 요구합니다. 초기화를 함수로 떼면 SDK를 mock해서 DSN 판정과 예외 격리와
실험 옵션 배선을 모두 회귀 테스트로 고정할 수 있습니다.

**`Sentry.init`과 통합 생성을 try/catch로 감쌉니다.** 이 코드는 hydration 전에 실행되므로 여기서
던진 예외는 앱 초기화를 막습니다. 잘못된 DSN 하나는 `dsnFromString`이 `console.error`만 남기고
던지지 않는 것을 확인했지만, 그 사실은 초기화 전체가 어떤 입력에도 던지지 않는다는 근거가
아닙니다.

**CLS는 standalone span으로 보냅니다.** 기본값으로 두면 이 프로젝트에서 CLS를 사실상 잡지
못합니다. 아래 3절이 근거입니다.

## 수집 대상과 전송 경로

Sentry SDK가 지표를 싣는 경로가 지표마다 다릅니다. 프로덕션 빌드에서 실제 envelope를 열어
확인한 결과입니다.

| 지표 | 전송 경로 |
| --- | --- |
| LCP, FCP, TTFB | pageload 트랜잭션의 measurement |
| INP | `ui.interaction.click` span의 measurement |
| CLS | `ui.webvital.cls` standalone span의 measurement |

`browserTracingIntegration`은 `@sentry/nextjs`의 기본 통합입니다. 따로 켜지 않아도 들어가고,
실제 스위치는 `tracesSampleRate`가 0보다 큰지 하나입니다. 이 값이 0이면 Web Vitals가 아예 오지
않습니다.

## CLS를 standalone span으로 보내는 이유

`@sentry/browser` 10.73.0의 `webVitalsIntegration`은 standalone span 옵션이 꺼져 있을 때 CLS를
pageload 트랜잭션의 measurement로만 싣습니다. 그 트랜잭션은 로드 직후 idle 시점에 끝나므로,
끝난 뒤에 생긴 레이아웃 변화는 어디에도 기록되지 않습니다.

이 앱은 라우트가 `/` 하나이고 저장소 분석부터 인터뷰까지 전부 같은 페이지의 상태 전이입니다.
스트리밍이 화면을 미는 시점은 로드보다 수십 초에서 수 분 뒤입니다. 즉 기본값으로는 Issue #81의
Goal인 "스트리밍이 일어나는 경로의 CLS 조회"가 성립하지 않습니다.

실측으로 확인했습니다. 기본값에서 로드 직후의 시프트는 pageload measurement로 잡혔고 3초 뒤의
시프트는 사라졌습니다. `browserTracingIntegration`에 `_experiments.enableStandaloneClsSpans`를
켜면 두 경우 모두 `ui.webvital.cls` span으로 옵니다.

이 옵션은 SDK가 `_experiments`로 분류한 실험 기능입니다. 다음 메이저 업그레이드에서 이름이
바뀔 수 있으므로 SDK를 올릴 때 함께 확인해야 합니다. 옵션은 `Sentry.init`이 아니라
`browserTracingIntegration`의 인자로 넘겨야 동작합니다.

## `tracesSampleRate`를 1로 두는 근거

트래픽 규모가 정해지지 않았습니다. 표본을 줄일 근거가 없는 상태에서 낮추면 초기 데이터가
얇아져 이후 최적화의 전후 비교가 어려워집니다. `AGENTS.md`의 작업 원칙이 추측성 조정을
금지하므로 전량 수집으로 시작하고 실사용 이벤트 양을 본 뒤 낮춥니다.

값은 `SENTRY_INITIAL_TRACES_SAMPLE_RATE` 상수 하나입니다. 환경변수로 빼지 않았습니다. 조정
근거를 문서에 남기고 상수를 고치는 편이 값의 출처를 추적하기 쉽습니다.

## 초기화 비용

`instrumentation-client.ts`는 hydration 전에 동기로 실행되므로 이 시간이 그대로 첫 상호작용을
미룹니다. Next.js는 개발 환경에서 이 파일의 실행이 16밀리초를 넘으면 경고합니다.

**기준을 넘습니다.** 측정값입니다.

| 항목 | 값 |
| --- | --- |
| Next.js 개발 환경 경고값, 3회 | 42, 22, 24밀리초 |
| 프로덕션 `Sentry.init` 구간, 10회 중앙값 | 26.1밀리초 |
| 프로덕션 `Sentry.init` 구간, 10회 범위 | 21.5~33.3밀리초 |

파일 전체 비용이 `Sentry.init` 비용과 거의 같습니다. 남은 코드가 환경변수 하나를 읽는 것뿐이라
초기화가 전부를 차지합니다.

**옵션을 줄이지 않았습니다.** Issue #81의 제약이 추측으로 옵션을 조정하지 말고 측정값을 남기라고
정하고 있습니다. 무엇을 줄이면 얼마가 줄어드는지는 아직 재지 않았으므로 후속 항목으로 넘겼습니다.

## 첫 로드 JS 증가분

같은 프로덕션 빌드에서 `instrumentation-client.ts`만 뺐다 넣어 비교했습니다. 비압축 바이트입니다.

| 빌드 | 첫 로드 static JS |
| --- | --- |
| Sentry 클라이언트 포함 | 1,422.2 KB |
| `instrumentation-client.ts` 제거 | 1,195.9 KB |
| 증가분 | 226.3 KB, 18.9퍼센트 |

이 프로젝트의 핵심 챌린지가 렌더링 성능이므로 계측 도구가 지표 자체를 밀어낼 수 있습니다.
전송 바이트가 아니라 비압축 크기라는 점에 주의합니다.

## Source Map과 Release

Source Map 업로드는 `sourcemaps.disable`로 명시해 끕니다.

**`release: { create: false }`를 넣습니다.** 이 옵션은 Release 생성만 막는 것이 아니라 release
이름 자체를 없앱니다. `resolveReleaseName`이 `create !== false`일 때만 `getSentryRelease()`와 Git
revision을 탐색합니다.

```js
const shouldCreateRelease = userSentryOptions.release?.create !== false;
return shouldCreateRelease
  ? userSentryOptions.release?.name ?? getSentryRelease() ?? getGitRevision()
  : userSentryOptions.release?.name;
```

켜 두면 auth token이 없어도 커밋 SHA가 `_sentryRelease`로 클라이언트 번들에 인라인되고 모든
이벤트에 release 값이 붙습니다. 이슈 #81의 Non-goal이 Releases를 범위 밖으로 두었으므로 값이
붙지 않아야 합니다.

이 옵션을 "도달 불가능한 설정"으로 판단해 뺐던 것을 2026-09-08에 정정했습니다. 경위와 실측은
`raw/2026-09-08-sentry-release-주입-정정-session-log.md`에 있습니다.

프로덕션 빌드는 auth token이 없다는 경고를 남기고, 이 옵션으로도 그 경고는 막히지 않습니다.
`handleRunAfterProductionCompile`이 `createRelease()`를 조건 없이 부르고 그 안에서 auth token
검사가 `create` 값보다 먼저 반환하기 때문입니다. 경고는 Releases 후속 작업에서 auth token을
넣으면 사라집니다.

`silent`는 켜지 않습니다. 경고 하나를 지우려고 Sentry 빌드 로그를 전부 끄면 이후의 실제 경고까지
가려집니다.

## 환경변수

`NEXT_PUBLIC_SENTRY_DSN` 하나입니다. `.env.example`에 있습니다.

**빌드 시점에 있어야 합니다.** `NEXT_PUBLIC_` 접두사가 붙은 값은 Next.js가 빌드 시점에 클라이언트
번들로 인라인합니다. 런타임 환경변수로 주입하면 브라우저가 읽지 못합니다. 배포 대상이 무엇이든
DSN은 빌드 파이프라인에 들어가야 합니다.

`.gitignore`의 `.env*` 규칙이 `.env.example`까지 무시하므로 `!.env.example` 부정 규칙을 함께
넣었습니다. 이것 없이는 예시 파일이 커밋되지 않습니다.

## 확인 절차

`scripts/measure-sentry-web-vitals.mts`가 절차를 담고 있습니다. 프로덕션 빌드를 띄우고 Playwright가
Sentry ingest 요청을 가로채 envelope 내용을 확인합니다. 실제 Sentry 프로젝트 없이 전송 경로를
확인할 수 있게 하려는 것입니다.

모드가 둘입니다. `on`은 DSN을 넣은 빌드에서 지표 다섯 개가 모두 오는지 봅니다. `off`는 DSN을 뺀
빌드에서 envelope 요청이 0건인지 봅니다. **기대와 다르면 종료 코드가 1입니다.** 확인 절차가 실패를
확정하지 못하면 절차가 아닙니다.

판별은 지표마다 어떤 span에 어떤 measurement로 와야 하는지를 고정해 그 조합이 같은 item에 있을 때만
통과시킵니다. 지표를 전역으로 합쳐 세거나 op 문자열에 지표 이름이 들어 있는지로 판별하면 값이 없는
span만 와도 통과하므로 쓰지 않습니다.

고정 대기로 도착을 추정하지 않습니다. pageload envelope가 실제로 도착한 뒤에 레이아웃을 밀고, 기대
조합이 모두 모일 때까지 제한 시간 안에서 기다립니다.

같은 스크립트가 커밋 SHA가 클라이언트 청크에 release로 인라인되지 않았는지도 확인합니다. 프로덕션
빌드 산출물을 읽어야 하는 검사라 vitest 스위트에 넣을 수 없고, 이 절차가 이미 프로덕션 빌드를
전제하므로 여기에 둡니다.

CLS와 INP는 관측 조건이 LCP와 다릅니다. CLS는 레이아웃이 실제로 밀려야 하고 INP는 실제 상호작용이
있어야 합니다. 스크립트는 클릭을 실제 링크로 하고, 레이아웃 시프트는 pageload 트랜잭션이 끝난 뒤에
요소를 넣어 만듭니다. 후자는 앱이 만든 시프트가 아니므로 **CLS 수치를 성능 근거로 쓰지 않습니다.**
스크립트가 확인하는 것은 값의 크기가 아니라 전송 경로입니다.

## 확인 필요

- **Sentry organization과 project 이름, DSN 발급 주체.** 실제 DSN이 없어 Sentry Performance 화면에서
  지표를 최종 확인하지 못했습니다. envelope 단계까지만 확인된 상태입니다.
- **배포 대상 환경.** 주입 방식은 위 환경변수 절에서 정해졌지만 대상 자체는 정해지지 않았습니다.

## 하지 않기로 한 것

- **`useReportWebVitals`로 직접 전송하지 않습니다.** 수신과 시각화 백엔드를 따로 만들어야 하고,
  Sentry SDK가 같은 `web-vitals` 라이브러리를 내장합니다.
- **`@sentry/browser`를 직접 초기화하지 않습니다.** `@sentry/nextjs`가 App Router 계측과
  `next.config.ts` 통합을 제공합니다.
- **Next.js 16.3의 `instrumentationClientInject`를 쓰지 않습니다.** 플러그인이 자체 client
  instrumentation을 주입하는 통로이지만 `@sentry/nextjs` 10.73.0은 이 기능을 쓰지 않습니다. 루트
  `instrumentation-client.ts`를 직접 씁니다. SDK를 올릴 때 주입 방식으로 바뀌면 `Sentry.init`이 두
  번 불릴 수 있으므로 함께 확인해야 합니다.
- **Web Vitals 수치를 보고 최적화하지 않습니다.** Issue #81은 계측만 다룹니다.
