# GA4 계측 후속 backlog

## 문서 목적

Issue #125를 구현하면서 이번 범위 밖으로 넘긴 항목을 기록합니다. 별도 GitHub Issue는 만들지
않습니다. 확정된 설정과 이벤트 계약은 구현이 끝난 뒤 `wiki/`의 GA4 계측 문서에 남깁니다.

## 1. 개인정보 처리방침이 아직 없음

Issue #125의 Task 3번은 "개인정보 처리방침에 GA4 사용 사실과 수집 항목, 거부 방법을 적습니다"입니다.
그런데 적어 넣을 문서 자체가 없습니다.

2026-09-15에 확인한 사실입니다.

- `src` 443개 파일에 `개인정보`, `privacy`, `Privacy` 문자열이 한 건도 없습니다. 처리방침 라우트도
  화면도 없습니다.
- 노션 워크스페이스 검색에 이 프로젝트의 처리방침 페이지가 없습니다. 검색에 걸리는 처리방침은
  다른 프로젝트인 엔빵의 것입니다.
- 로그인 화면에 `By continuing you agree to our terms` 문구가 있지만 링크가 걸려 있지 않습니다
  (`src/features/auth/login-screen.tsx`).

### 이번 PR에서 하지 않는 이유

없는 문서를 새로 만드는 일이라 계측 이슈가 화면과 라우트를 늘리게 됩니다. `AGENTS.md`의 MVP 범위는
Repository 입력부터 꼬리 질문까지이고, 처리방침 화면은 그 목록에 없습니다. "이 범위를 벗어나는
기능은 먼저 논의 없이 추가하지 않습니다"에 걸립니다.

내용으로 봐도 GA4 문단만 있는 처리방침은 쓸 수 없습니다. 이 서비스는 GitHub OAuth 토큰을 암호화해
쿠키에 담고(`src/lib/github/auth-session.ts`), `github_user_id`를 Neon에 저장하며(`db/schema.sql`),
커밋과 diff를 LLM 제공자에게 보냅니다. 처리방침은 이 넷을 함께 적어야 의미가 있고, GA4 한 항목만
적힌 문서는 나머지를 수집하지 않는다는 오해를 만듭니다.

### 남는 위험

노션 기능 정의서의 "동의 배너를 만들지 않습니다"라는 결정은 **"대신 개인정보 처리방침에 GA4 사용
사실과 수집 항목과 거부 방법을 적어 고지와 선택권을 채웁니다"를 전제로** 성립합니다. 처리방침이
없는 상태로 계측만 켜면 고지도 선택권도 없이 수집만 하는 것이 됩니다.

지금은 실사용자가 없어 당장 문제가 되지 않습니다. **운영을 시작하기 전에는 닫혀야 하는 항목입니다.**

### 해야 할 일

- 처리방침 화면 또는 문서의 위치를 정합니다.
- 수집 항목을 적습니다. GA4 이벤트와 파라미터 목록, HMAC으로 변환한 `user_id`, GitHub OAuth 토큰과
  사용자 번호, Neon에 저장하는 항목, LLM 제공자에게 보내는 커밋과 diff입니다.
- 거부 방법을 적습니다. 기능 정의서가 정한 대로 구글이 제공하는 애널리틱스 차단 브라우저
  부가기능을 안내합니다.
- 로그인 화면의 `terms` 문구에 링크를 겁니다.

## 2. 화면 흐름이 확정되지 않아 2단계로 미룬 이벤트 2종

`candidate_confirmed`와 `interview_started`입니다. #125를 두 PR로 나눴고 1단계 PR은 나머지 10종과
인프라를 담습니다.

미룬 이유는 이 둘만 화면 구조에 직접 붙기 때문입니다. `candidate_confirmed`는 후보 목록과 상세의
확정 액션 자리에 붙고, `interview_started`는 인터뷰 진입 경로에 붙습니다. 나머지 10종은 도메인
상태나 액션 경계에 붙어 레이아웃과 순서가 바뀌어도 흔들리지 않습니다.

2026-09-15 기준으로 화면 레이아웃과 단계 순서를 바꾸는 개편이 예정되어 있고 단계 수가 바뀌는지는
아직 정해지지 않았습니다. 퍼널 계측에서는 화면 순서가 곧 이벤트 목록이므로, 단계가 늘거나 줄면
**코드보다 먼저 기능 정의서의 이벤트 표와 이슈 #125의 "12종"을 고쳐야 합니다.**

2단계에서 확정할 값입니다.

- `rank`는 화면에 보이는 위치가 아니라 Stage B가 준 순서입니다. 화면에 정렬이나 필터가 붙어도 값의
  뜻이 바뀌지 않게 하려는 것입니다.
- `duration_ms`는 후보 목록 첫 렌더부터 확정까지입니다. 후보를 고르는 데 걸린 시간을 재려는
  것이고, 분석 대기 시간은 `analysis_stage_done`이 따로 잽니다.
- 재선택하면 `candidate_confirmed`가 다시 나가고 기준점은 후보 목록 첫 렌더에 고정합니다. 두 건은
  `rank`로 구분됩니다.

## 3. 저장 경로가 퍼널을 우회함 (#115, #116)

이슈 #115와 #116이 들어오면 **퍼널을 거치지 않고 인터뷰나 후보 화면에 도달하는 경로**가 생깁니다.

- #115는 Repository 선택 화면 아래에 저장된 인터뷰 목록을 두고 거기서 바로 인터뷰를 이어갑니다.
  이 경로는 `analysis_requested`, `analysis_stage_done`, `analysis_succeeded`, `candidate_confirmed`를
  하나도 거치지 않습니다. `flow_id`도 "분석 한 번을 묶는 값"이라는 정의로는 발급할 자리가 없습니다.
- #116은 저장된 분석으로 후보 화면을 다시 그립니다. `candidate_confirmed`는 나가는데 그 앞의 분석
  이벤트가 없습니다.
- #115 본문이 "지금 `RepositoryFlow`는 선택이 없으면 목록, 선택하면 분석이라는 두 갈래뿐"이고
  "이 이슈의 실제 작업량은 이쪽에 있습니다"라고 적고 있습니다. `flow_id` 발급과 계측 배선이 들어가는
  바로 그 컴포넌트가 갈라집니다.

### 그때 리포트에서 보이는 증상

인터뷰 시작 수가 후보 확정 수보다 커집니다. 저장된 인터뷰를 이어간 사용자가 분석과 후보 확정 없이
인터뷰에 도달하기 때문입니다.

### 지금 하지 않는 이유와 그때 할 일

기능 정의서가 "이 목록에 답하지 않는 이벤트는 넣지 않습니다"라고 정하고 있고, 지금은 저장 경로가
존재하지 않아 아무도 발생시키지 않는 파라미터를 만들게 됩니다.

#115와 #116을 구현할 때 진입 경로를 가르는 파라미터 하나를 넣습니다. 새 분석인지, 저장된 분석에서
고른 것인지, 저장된 인터뷰를 이어가는 것인지를 구분하는 값입니다. 재작업이 아니라 파라미터 추가이고,
그때 `flow_id`의 수명도 저장 경로까지 확장할지 함께 정합니다.

이슈 #122가 GitHub 요청 전송 실패에 1회 재시도를 넣습니다. 화면은 바뀌지 않지만 `analysis_failed`가
"재시도까지 실패한 것"만 세게 됩니다.

계측 코드는 고칠 것이 없습니다. #122 머지 전후로 실패율을 비교할 때 이 사실을 알고 봐야 합니다.

## 5. 자체 코드리뷰가 남긴 P3 둘

PR을 열기 전 1단계 구현 전체(커밋 13개)를 한 번 리뷰했습니다. P1 하나(`flow_id` 발급이 계측
try/catch 바깥에 있어 보안 컨텍스트가 아닌 곳에서 분석 시작을 막던 문제)와 P2 하나(Loading
체크리스트가 `ANALYSIS_STAGES`와 따로 배열을 들고 있던 문제)는 같은 PR에서 고쳤습니다. 남은 둘입니다.

### 5-1. `GA_MEASUREMENT_ID_ENV`는 소비자가 없습니다

`src/lib/analytics/ga.ts`가 내보내지만 참조하는 곳이 없습니다. 값을 읽을 때는
`process.env.NEXT_PUBLIC_GA_MEASUREMENT_ID`를 그대로 써야 Next.js가 빌드 시점에 치환하므로, 이
상수는 앞으로도 쓰일 자리가 없습니다. 지우거나, `.env.example`과 문서가 같은 이름을 가리킨다는
사실을 확인하는 테스트에서 실제로 쓰는 것 중 하나를 골라야 합니다.

### 5-2. 로그아웃이 분석 공통 파라미터를 남깁니다 — 해결됨

CodeRabbit이 같은 곳을 짚어 PR #129에서 함께 고쳤습니다. `clearAnalysisFlow`가 한 번도 세운 적 없을
때 아무 일도 하지 않도록 `flowApplied` 가드를 넣고(`user_id`와 같은 방식), `AnalyticsSession`이
세션이 없을 때 부르게 했습니다. 세션 유무는 `userId`가 아니라 `signedIn`으로 봅니다. HMAC 비밀값이
없으면 로그인 중에도 `userId`가 null이라 대리 지표가 됩니다.

### 5-3. 실패 단계를 tracker가 아니라 오류가 싣게 하기

`analysis_failed`의 `stage`는 `AnalysisTracker`가 기억하는 직전 단계입니다. 실패가 일어난 단계를
직접 나타내는 값이 아니라, 화면 상태가 어디까지 갔는지로 미루어 보는 값입니다.

지금은 결과가 어긋나지 않습니다. `route-client.ts`가 각 요청 **전에** 그 단계의 진행률을 보고하므로
(`:54` 커밋 상세, `:65` 저장소 메타데이터) tracker의 단계와 `analyzeRepository`의 `failureContext`가
같은 순서로 움직입니다. CodeRabbit이 PR #129에서 이 둘이 어긋나는 경우를 지적했지만 그 줄 때문에
재현되지 않았습니다.

어긋날 수 있는 구조인 것은 맞습니다. 보고 시점을 요청 뒤로 옮기거나 새 단계를 추가하면서 보고를
빠뜨리면 계측만 조용히 틀립니다. `AnalysisError`가 자기 실패 단계를 싣고 `advanceAnalysisTracker`가
그 값을 그대로 쓰는 쪽이 곧습니다. `AnalysisError`의 형태를 바꾸는 일이라 이 이슈 범위를 넘습니다.
