# 꼬리 질문의 대화 프롬프트 전략

## 결론

**근거 전량을 매 턴 다시 싣습니다(설계 A).** 인터뷰가 길어져도 모델은 매 호출에서 근거 본문을
그대로 봅니다. 대안 셋(근거 폐기, 축약 근거, 캐싱)을 실측으로 비교한 뒤 고른 값이고 비교표는
`raw/2026-09-03-꼬리질문-근거-재전송-비용-비교-session-log.md`에 있습니다.

**이 결정의 이유는 비용이 아니라 근거 원칙입니다.** 가장 비싼 A와 가장 싼 B의 차이가 인터뷰 한 번에
0.0106달러입니다. 예산 10달러로 218회냐 355회냐의 차이이고 어느 쪽도 이 서비스의 제약이 아닙니다.
반면 B는 근거 본문 없이 대화만 보고 질문을 만들므로 근거에 없는 파일과 수치를 지어낼 자리가
생깁니다. `AGENTS.md`가 "AI는 항상 실제 Repository의 커밋과 파일을 근거로 제시한다"고 적은 전제를
1센트와 바꾸는 교환이므로 하지 않습니다.

## 1. 매 턴 모델에 실리는 것

API가 상태를 갖지 않으므로 "대화를 잇는다"는 것은 매 호출에 이력을 다시 싣는다는 뜻입니다. 배치는
첫 질문 경로와 같은 모양을 이어받습니다.

| 자리 | 내용 | 매 턴 |
| --- | --- | --- |
| system | `renderInterviewQuestionSystemPrompt()`에 꼬리 질문 규칙을 더한 값 | 같습니다 |
| contents[0] (user) | `renderInterviewEvidencePrompt(snapshot)` | 같습니다 |
| contents[1..] | `model` 자리에 지난 질문, `user` 자리에 지난 답변이 번갈아 | 턴마다 두 개씩 늘어납니다 |
| 마지막 | 방금 제출한 사용자 답변 | 이 답변에 이어 다음 질문을 만듭니다 |

근거를 system이 아니라 첫 user 메시지에 두는 이유는 두 가지입니다. 첫 질문 경로가 이미 그 배치이고
(`buildInterviewQuestionPrompt`는 `system`과 `evidence`를 갈라 냅니다), 접두사가
`system + 근거`로 고정되어야 나중에 캐싱을 얹을 때 캐시가 맞습니다.

**근거 스냅샷은 인터뷰 도중 갱신하지 않습니다.** 경험을 확정할 때 만든 값을 그대로 씁니다. 중간에
다시 조립하면 확인 수준 표시와 patch 절단 여부가 턴마다 달라져, 앞 턴에서 "확인 불가"로 물은 것을
뒤 턴에서 사실로 전제하는 일이 생깁니다.

## 2. 시스템 프롬프트에 더할 규칙

첫 질문의 규칙 여섯 개(`RULES`의 role, count, grounding, verifiability, quality, format)는 그대로
씁니다. 꼬리 질문에만 필요한 규칙은 대화가 생겨서 새로 열리는 실패에 대응합니다.

| 새 규칙 | 막으려는 실패 |
| --- | --- |
| 직전 답변에서 사용자가 실제로 말한 것과 말하지 않은 것을 갈라, 말하지 않은 부분을 묻습니다 | 답변을 읽지 않고 근거만 보고 물어 같은 질문이 반복되는 것 |
| 이미 물은 것을 다시 묻지 않습니다. 대화에 이미 나온 질문의 답을 다시 요구하지 않습니다 | 이력이 길어질수록 앞 턴과 겹치는 질문 |
| 사용자 답변에 담긴 주장은 근거와 대조합니다. 근거로 확인되지 않는 주장은 사실로 전제하지 말고 확인하는 형태로 묻습니다 | 사용자 답변이 새로운 "근거"로 승격되는 것 |
| 답을 대신 쓰지 않습니다. 사용자의 답변을 요약하거나 평가하지 않고 다음 질문만 냅니다 | 인터뷰어가 아니라 첨삭자가 되는 것 |

마지막 규칙은 첫 질문의 `role`·`format`과 겹쳐 보이지만 겹치는 자리가 다릅니다. 첫 질문에는 평가할
답변 자체가 없습니다.

**2026-09-08 실제 인터뷰에서 네 규칙 가운데 셋이 깨졌습니다.** 4턴 인터뷰를 두 번 돌려 꼬리 질문
6개를 사람이 읽었습니다. 직전 답변을 이어받는 규칙만 지켜졌고, 나머지 셋은 다음과 같이 깨졌습니다.
요약과 평가를 금지한 규칙은 6개 전부가 어겼습니다. 사용자가 말하지 않은 측정 도구를 모델이 사실로
단정했습니다. 2턴의 하위 항목과 3턴의 본 질문이 같은 것을 물었습니다. 기록은
`raw/2026-09-08-꼬리질문-실제-인터뷰-동작확인-session-log.md`에 있습니다.

규칙 자체는 그대로 두고 문구만 다시 봅니다. 무엇이 깨지는지를 알았으므로 변형 비교의 판정 기준이
생겼습니다.

**문구는 실측 없이 확정하지 않습니다.** 첫 질문에서 같은 지시를 한 문단에 두느냐 갈라 두느냐만으로
전수 응답률이 0/3에서 3/4로 갈린 적이 있습니다(`wiki/2026-08-25-Stage-A-청크-폐기와-점수-선별-전환.md`).
`INTERVIEW_QUESTION_PROMPT_VARIANT`가 그래서 남아 있고 꼬리 질문도 같은 방식으로 변형을 비교합니다.

## 3. 상한 계약 (2026-09-04 확정)

**손으로 고른 값은 지원 턴 수 하나뿐이고 나머지는 전부 거기서 유도됩니다.**

`INTERVIEW_MAX_TURNS = 10`입니다. 이 값을 비용 실측이 선 자리에 맞췄습니다. 2026-09-03 측정이
인터뷰를 10턴으로 두고 회당 0.03866~0.04583달러와 캐싱 손익분기 2.0시간을 냈으므로, 코드가 그보다
긴 인터뷰를 허용하면 위키에 적힌 회당 비용이 더 이상 상한이 아니게 됩니다. 실제 인터뷰 길이 분포를
보면 이 값을 다시 봅니다.

| 상한 | 값 | 유도 |
| --- | --- | --- |
| 근거 스냅샷 | 5,250토큰 (`EVIDENCE_SNAPSHOT_MAX_INPUT_TOKENS`) | 그대로 둡니다. 근거는 인터뷰 내내 고정이고 턴 수와 무관합니다 |
| 이력 항목 수 | 18개 (`INTERVIEW_HISTORY_MAX_ITEMS`) | `2 × (턴 수 - 1)`. 마지막 턴 요청에는 지나간 9턴의 질문과 답변만 실립니다 |
| 이력 항목 하나 | 4,500바이트 (`INTERVIEW_HISTORY_ITEM_MAX_BYTES`) | 실측 상단 답변 1,500자 × 한국어 한 글자 3바이트. 질문에도 같은 값을 씁니다 |
| 이력 항목을 재는 단위 | JSON 직렬화 바이트 | 요청 본문 상한과 같은 대상을 재야 합니다 |
| 이력 전체 | 81,000바이트 (`INTERVIEW_HISTORY_MAX_BYTES`) | 항목 수 × 항목 하나 |
| 프롬프트 바이트 | 98,978바이트 (`INTERVIEW_QUESTION_MAX_PROMPT_BYTES`) | 근거 15,750 + 시스템 1,934 + 이력 81,000 + 구분자 38 + 허용 오차 256 |
| 요청 본문 | 146,536바이트 (`MAX_INTERVIEW_STREAM_BODY_BYTES`) | 기존 근거 몫 64KB + 이력 81,000 |

본문 상한은 근거 몫을 건드리지 않고 이력 몫을 더하기만 했습니다. 그래야 상한이 커지기만 하고, 지금
통과하는 첫 질문 요청의 통과 여부가 바뀌지 않습니다.

이력 전체 바이트를 따로 검증하지 않습니다. 항목마다 상한이 걸리고 항목 수에도 상한이 걸리므로 전체
바이트는 두 값의 곱을 넘지 못합니다. 같은 이유로 절단도 항목 수만 봅니다.

**항목 바이트는 원본 UTF-8이 아니라 JSON 직렬화 바이트로 셉니다.** 이력이 겨루는 상대가 요청 본문
상한이므로 같은 대상을 재야 합니다. 원본으로 재면 줄바꿈이 많은 답변에서 실제 요청 크기를 절반으로
보게 되고, 항목 상한과 항목 수 상한을 모두 지킨 이력이 본문 상한에서 거절됩니다. 그러면 클라이언트가
자른 결과가 받아들여진다는 보장이 사라져 절단을 클라이언트가 맡는 계약이 성립하지 않습니다. 근거
스냅샷의 patch 예산이 같은 이유로 이미 `serializedByteLength`를 씁니다. 한글은 이스케이프되지 않으므로
실측 상단 구간인 1,500자 한국어 답변은 재는 방식과 무관하게 그대로 들어갑니다.

경위와 접은 대안은 `raw/2026-09-04-꼬리질문-이력-상한과-요청-계약-session-log.md`에 있습니다.

### 이력이 상한을 넘을 때

**가장 오래된 질문·답변 쌍부터 제외합니다.** 근거와 첫 질문·첫 답변은 남깁니다. 첫 턴이 그 인터뷰가
무엇을 묻고 있는지를 정하기 때문입니다.

요약으로 접는 방식은 지금 넣지 않습니다. 요약은 LLM 호출을 하나 더 쓰거나 규칙 기반으로 잘라내야
하고, 어느 쪽도 "무엇을 잃었는지"를 사용자에게 알리기 어렵습니다. 잘라내기는 잃은 것이 분명합니다.
**요약이 필요한지는 실제 인터뷰 길이 분포를 본 뒤에 판단합니다.** 지금 정할 근거가 없습니다.

제외가 일어나면 사용자에게 알립니다. 앞부분을 잊은 채 질문이 이어지면 사용자는 AI가 자기 답변을
무시했다고 읽습니다. 그래서 절단 함수(`trimInterviewHistory`)가 뺀 항목을 값으로 돌려줍니다.

**항목 하나가 항목 상한을 넘는 경우는 절단으로 풀지 않습니다.** 항목 안을 자르면 무엇을 잃었는지
보이지 않게 됩니다. 입력 단계에서 막고, 그래도 오면 서버가 거절합니다.

## 4. 실패와 재시도

- 답변 제출은 서버를 거치지 않습니다. 저장 계층이 없으므로 답변은 화면 상태에 들어가고 그 자리에서
  다음 요청의 입력이 됩니다.
- 질문 생성이 실패하면 이력은 그대로 두고 그 질문만 다시 만듭니다. 실제 생성 스트림은 이어받을 수
  없으므로 재시도는 처음부터 다시 생성합니다(`use-interview-stream.ts`의 `resumeMode: "restart"`).
- 오류 분류는 첫 질문 경로의 것을 그대로 씁니다. 이력 누적으로 새로 열리는 갈래는 하나이고
  `history_too_large`로 두었습니다(2026-09-04). `body_too_large`와 가른 이유는 본문 상한이 근거와
  이력을 합친 값이라 사용자가 손댈 자리가 없는 반면, 이력 초과는 대화를 줄이면 풀리기 때문입니다.
  재시도로 풀리지 않는다는 점만 같습니다.
- 이력의 모양이 어긋난 요청은 `invalid_request`입니다. 질문으로 시작해 두 역할이 번갈아 나오고
  답변으로 끝나야 합니다. 마지막이 질문인 이력을 그대로 실으면 모델이 자기 질문에 이어 또 질문을
  만듭니다.
- 종료는 사용자만 정합니다. AI가 답변 품질을 보고 끝내지 않습니다.

## 5. 비용

설계 A 기준 인터뷰 10턴의 총액입니다. 전체 분석과 첫 질문 0.02182달러를 포함합니다. 2026-09-08에
꼬리 질문 시스템 프롬프트로 다시 잰 값입니다.

| 답변 길이 | 인터뷰 한 번 | 예산 10달러 |
| --- | --- | --- |
| 200자 | 0.03893달러 | 256회 |
| 600자 | 0.04112달러 | 243회 |
| 1,500자 | 0.04610달러 | 216회 |

`wiki/2026-09-01-네-경로-LLM-모델-확정.md` 3-4절이 환산으로 적었던 267회와 가깝습니다. 꼬리 질문이
붙으면 10달러 가능 횟수가 458회에서 216~256회로 내려갑니다.

시스템 프롬프트는 첫 질문 297토큰, 꼬리 질문 417토큰입니다. 규칙 넷이 턴마다 120토큰을 더합니다.
2026-09-03 값은 이 몫이 빠져 있었고 정정 경위는
`raw/2026-09-08-꼬리질문-근거-재전송-비용-재측정-session-log.md`에 있습니다.

**모델은 `gemini-3.1-flash-lite`로 확정했습니다.** 2026-09-09 실측이고 경위는
`raw/2026-09-09-꼬리질문-모델-확정-session-log.md`에, 1차 리뷰로 정정된 수치는
`raw/2026-09-09-꼬리질문-모델-확정-리뷰-1차-session-log.md` 6절에 있습니다. 판정 기준인 첫 청크 지연으로는 두
후보가 갈리지 않았고(120건 모두 판정선 20초 안, 최대 1,087밀리초) 비용과 질문의 성격으로 골랐습니다.

**위 표의 값이 낮아졌습니다.** 실제 usage로 다시 내면 인터뷰 한 번이 0.03405~0.03445달러이고
10달러에 290~293회입니다. 위 표는 캐시 읽기를 계산에 넣지 않은 값입니다. 갱신된 값은
`wiki/2026-09-02-LLM-비용-산정.md` 3·4절에 있습니다.

**출력 상한을 함께 정했습니다.** `INTERVIEW_QUESTION_MAX_OUTPUT_TOKENS = 900`이고 이력 항목 상한
4,500바이트에서 유도했습니다. 토큰 상한만으로는 바이트가 지켜지지 않아 스트림에서 누적 바이트를
세고 상한에서 끊습니다(`toItemBoundedTextStream`).

## 6. 캐싱은 얹지 않습니다

접두사가 `system + 근거`로 고정되므로 캐싱을 얹을 자리는 준비되어 있습니다. 2026-09-03에는 이득이
시간에 달려 있고 그 시간을 몰라 미뤄 두었습니다. 손익분기는 근거 크기와 무관하게
`0.225 × 꼬리 질문 횟수` 시간으로 유도됐고 10턴이면 2.0시간이었습니다.

**2026-09-09에 확인한 결과 명시적 캐싱을 배선하지 않습니다.** 확인한 것은 둘입니다.

**암묵적 캐싱이 `gemini-3.1-flash-lite`에 자동으로 걸립니다.** 응답의
`usage.inputTokenDetails.cacheReadTokens`를 매 호출 읽었고 그 모델의 호출 60건 중 47건에서 값이 잡혔습니다. 최대
12,203토큰이고 4,068토큰 안팎의 배수로 올라갑니다. 인터뷰가 길어질수록 캐시가 덮는 몫이 커집니다.
`gemini-3.5-flash-lite`는 같은 접두사를 열 번 연속 보낸 단독 실행에서도 0건이라 순서 효과가
아닙니다.

**명시적 캐싱의 최소 토큰은 1,024입니다.** 작은 본문으로 `cachedContents`를 만들어 보고 거절 메시지
`Cached content is too small. total_token_count=51, min_total_token_count=1024`에서 읽었습니다. 두
모델 모두 같고 8,000자 본문으로는 두 모델 모두 캐시가 만들어졌습니다. 우리 접두사 5,043토큰은 조건을
넘깁니다.

**조건을 넘기는데도 배선하지 않는 이유는 이미 같은 절감을 받고 있기 때문입니다.** 암묵적 캐싱에는
스토리지 요금이 붙지 않으므로 손익분기를 따질 필요가 없습니다. 명시적 캐싱을 얹으면 관리할 것
(생성·TTL·삭제)이 늘고 요금이 붙는데 절감은 이미 들어와 있습니다.

**대신 보장이 아닙니다.** 걸리는지는 제공자가 정하고 우리가 켜고 끌 수 없습니다. 위 47/60이 그
비율입니다. 비용 문서의 값은 이 비율이 유지될 때의 값이고, 걸리지 않으면 정가로 돌아갑니다.
