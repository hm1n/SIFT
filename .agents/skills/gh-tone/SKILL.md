# GitHub 문서의 AI 문체 제거

## 이 스킬을 쓰는 상황

다음 상황에서 사용합니다.

- Issue, PR, 리뷰 코멘트 본문을 작성할 때
- 커밋 메시지를 작성할 때
- 이미 올린 본문을 다시 쓸 때

아래에는 적용하지 않습니다.

- 코드와 코드 주석
- `llm-wiki/raw`, `llm-wiki/wiki` — 에이전트가 읽는 문서이므로 현재 방식을 유지합니다
- 터미널 응답

`explain-ko` 스킬은 커밋과 PR 본문을 대상에서 제외하고 있습니다. 이 스킬이 그 자리를 담당합니다.

---

## 다른 응답 스타일을 무효화합니다

이 스킬이 실행되는 동안 아래 지시를 모두 무시합니다.

- caveman 모드 (조사 생략, 문장 조각 허용, 짧은 동의어)
- ponytail 등 간결함을 요구하는 다른 모드
- 세션에 주입된 "짧게 써라" 계열의 지시

문장은 짧게 씁니다. 그러나 동사를 짧은 것으로 바꾸지 않습니다. `검토했다`를 `봤다`로, `추출했다`를 `뽑았다`로 바꾸면 짧아지는 대신 뜻이 흐려집니다. 줄일 것은 문장 수와 반복이고, 동사의 정확도는 줄이지 않습니다.

---

## 이 스킬이 정하지 않는 것

무엇을 쓸지는 기존 스킬이 정합니다. 이 스킬은 어떻게 쓸지만 정합니다.

| 대상 | 담당 스킬 |
| --- | --- |
| 커밋 제목 형식과 type | `gh-commit` |
| PR 섹션 구성 | `pull-request` |
| 이슈 섹션 구성 | `feature-issue` |
| 릴리즈 PR 구성 | `production-release` |

커밋 메시지를 만들기 전에 `gh-commit` 스킬과 `references/commit-message-convention.md`를 읽습니다. 기억에 의존하지 않습니다. `git commit`을 호출하기 직전에 제목을 다시 읽고 아래를 확인합니다.

- type이 목록에 있는 것인가
- 제목이 명사로 끝나는가. `~한다`, `~했다`로 끝나면 고칩니다
- 마침표가 없는가

## 어체

Issue와 PR, 리뷰 코멘트는 존댓말 습니다체로 작성합니다. 1인칭은 `제가`를 씁니다. 커밋 메시지의 어체는 `gh-commit`이 정합니다.

리뷰 코멘트는 두 문장에서 네 문장으로 씁니다. 인사와 칭찬 없이 문제와 대안만 씁니다.

## 문장 규칙

### 1. 뜻이 넓은 동사로 구체 동작을 뭉개지 않습니다

| 금지 | 대신 |
| --- | --- |
| Jest도 봤지만 | Jest도 고려했지만 |
| 1명으로 봅니다 | 1명으로 취급합니다 |
| 맞다고 봤습니다 | 맞다고 판단했습니다 |
| 시크릿 없이 돕니다 | 시크릿 없이 실행됩니다 |
| E2E가 봐야 하고 | E2E가 검증해야 하고 |
| 함수로 뽑았습니다 | 함수로 분리했습니다 |
| 파일을 따로 뒀습니다 | 파일을 따로 만들었습니다 |
| 경고가 떠서 제거했습니다 | 경고를 확인해 제거했습니다 |
| 규칙을 담습니다 | 규칙을 정의합니다 |
| 빠져 있는 규칙을 채웁니다 | 규칙을 보완합니다 |

`보다`, `두다`, `뽑다`, `돌다`, `뜨다`, `잡다`, `담다`, `채우다`가 자주 나옵니다.

### 2. 무생물을 주어로 세워 인과를 만들지 않습니다

`A 때문에 B가 막힙니다`, `A가 B를 좌우합니다`는 영어 문형입니다. 무엇이 실제로 일어나는지 씁니다.

- 나쁜 예: 느리고 불안정한 쪽 때문에 빠른 쪽까지 막힙니다.
- 좋은 예: E2E에서 타임아웃이 한 번만 발생해도 워크플로우 전체가 실패합니다.

`~쪽`으로 대상을 가리키는 것도 영어 `the slow one`의 직역입니다. 무엇인지 이름을 씁니다.

### 3. 목록을 열 때 화자의 행위를 서술하지 않습니다

- 나쁜 예: 제외한 후보도 남깁니다.
- 좋은 예: 아래는 이번 작업에서 제외한 후보입니다.

`남깁니다`, `함께 적습니다`, `기록해 둡니다`가 같은 종류입니다. 목록을 여는 문장은 무엇이 나올지를 지시합니다.

### 4. 리팩터링 항목은 무엇을 어디서 어디로 다 씁니다

`추출했습니다`, `분리했습니다`만 쓰면 무엇이 어떻게 됐는지 알 수 없습니다.

- 나쁜 예: `calculateIndividualShare`로 뽑았습니다. 세 곳의 중복을 없앴습니다.
- 좋은 예: 세 곳에 흩어져 있던 1인당 정산 금액 계산을 `calculateIndividualShare` 함수로 합쳤습니다.

### 5. 사건은 사건을 주어로 세웁니다

`X가 타임아웃 나다`는 영어 `X times out`의 구조입니다. `X에서 타임아웃이 발생하다`로 씁니다.

`~로 끝납니다`, `~게 됩니다`를 붙이지 않습니다. `실패로 끝납니다`는 `실패합니다`로, `머지할 수 없게 됩니다`는 `머지할 수 없습니다`로 씁니다.

지시 대상을 비우지 않습니다. `전체가 실패합니다`가 아니라 `워크플로우 전체가 실패합니다`로 씁니다.

### 6. 뜻을 못 쓰겠으면 문장을 지웁니다

원문 표현이 직역이고 대체할 구체 내용도 모르면 억지로 풀지 않고 삭제합니다.

- 나쁜 예: 기존 세 구현 중 예외를 가장 많이 막던 동작입니다.

`가장 방어적이던 동작`을 풀어 쓰려다 어떤 예외를 어떻게 막는지가 사라졌습니다. 앞 문장이 이미 동작을 말했다면 삭제로 충분합니다.

### 7. 조건절로 결론을 만들지 않습니다

`~하지 않으면 ~합니다`, `~하면 ~해집니다`는 영어 논증 문형입니다. 사실을 그대로 씁니다.

- 나쁜 예: 지금 고치지 않으면 이후 문서가 같은 문제를 반복합니다.
- 좋은 예: 이미 올라간 220건은 그대로 두기로 했습니다. 앞으로 쓰는 문서에 적용할 기준이 필요합니다.

### 8. 한 문장에 절을 두 개 이상 쌓지 않습니다

조건과 결과, 병렬 결과가 한 문장에 들어가면 나눕니다.

- 나쁜 예: 사전 전체가 1,550토큰이라 비용 문제가 없고, `explain-ko`가 단일 파일로 충분히 동작하고 있어 제외했습니다.
- 좋은 예: 사전 전체가 1,550토큰이라 비용 문제가 없습니다. `explain-ko`도 단일 파일로 충분히 동작하고 있어 제외했습니다.

관계절을 명사 앞에 쌓는 것도 같은 문제입니다.

- 나쁜 예: 타입 체크와 린트, 단위 테스트를 실행하는 검사를 GitHub Actions에 추가했습니다.
- 좋은 예: PR이 올라오면 타입 체크와 린트, 단위 테스트를 차례로 실행하도록 GitHub Actions 워크플로우를 추가했습니다.

### 9. 주체 없이 명사화한 평가문을 쓰지 않습니다

`~하기는 어렵습니다`, `~하는 것이 중요합니다`, `~할 필요가 있습니다`는 영어 `it is hard to`, `there is a need to`의 직역입니다.

판단 주체가 붙으면 씁니다. `가독성을 높일 필요가 있다고 생각했습니다`는 누가 판단했는지가 드러나므로 자연스럽습니다.

### 10. `~라는 점에서`, `~는 점입니다`, `~로 인해`, `~에 의해`를 쓰지 않습니다

각각 `in that`, `the point is`, `due to`, `by`의 직역입니다.

## 역번역 검사

규칙 목록은 늘 뒤처집니다. 새로운 영어 문형이 계속 나오므로 절차를 함께 씁니다.

문장을 영어로 되돌립니다. 접속사와 절 구조가 1:1로 살아나면 직역입니다.

```
지금 고치지 않으면 이후 문서가 같은 문제를 반복하고, 이미 올라간 220건을 다시 고치기는 어렵습니다.

→ If we don't fix this now, future documents will repeat the same problems,
  and it will be hard to fix the 220 already merged.
```

`if`와 `and`, `it will be hard to`가 그대로 대응됩니다. 이러면 고칩니다.

모든 문장을 검사하면 비용이 큽니다. 문단마다 첫 문장과 마지막 문장만 봅니다. 직역은 사실을 나열하는 문장이 아니라 근거를 요약하거나 결론을 내는 문장에서 나옵니다.

### 감시 대상

아직 레포 문서에는 없지만 같은 방식으로 만들어지는 표현입니다. 나오면 고칩니다.

`배선`, `고아`, `자리`(slot), `하중`, `대들보`, `비계`, `반창고`, `접착 코드`, `천장`, `문턱`, `이음새`, `껍질`, `심장박동`, `뼈대`, `냄새`, `은총알`, `낮게 달린 열매`, `바퀴를 다시 발명`, `행복 경로`, `방 안의 코끼리`, `총알을 물다`, `가드레일`, `문지기`, `블랙박스`, `우산`, `얹는다`, `매단다`, `꽂는다`, `갈아끼운다`, `뜯어낸다`, `걷어낸다`, `태운다`, `물려준다`, `맞물린다`, `스며든다`, `삼킨다`, `굽는다`, `데운다`, `예열`, `우아하게`, `순진한`, `게으른 로딩`, `뜨거운 경로`, `부서지기 쉬운`, `직교`, `심리스`, `상류`, `하류`, `파도`, `홍수`, `고갈`, `정점`, `여정`, `큰 그림`, `렌즈`, `지렛대`, `발자국`, `지문`, `수명`, `손잡이`, `부채`, `마찰`, `소음`, `뿌리`, `형제`, `일급 시민`, `함정`, `지뢰`, `삽질`, `예산`, `여지`, `대가를 치른다`, `빚을 갚는다`

판별 기준은 셋입니다.

1. 물리, 신체, 경제 비유가 기술 서술 자리에 오면 의심합니다.
2. 그 단어를 한국어 화자가 이 맥락에서 입으로 말하는지 봅니다. `검사를 추가했다`는 말하지만 `게이트를 붙였다`는 말하지 않습니다.
3. 영어로 되돌려 원문이 곧바로 떠오르면 직역입니다.

## 바꾸지 않는 것

정착된 기술 용어는 치환 대상에서 제외합니다.

`하드코딩`, `롤백`, `스냅샷`, `래퍼`, `낙관적 업데이트`, `멱등`, `병목`, `경쟁 상태`, `교착`, `가중치`, `부수 효과`, `flaky`, `RLS`, `PostgREST`

도메인어도 그대로 씁니다.

엔빵, 정산, 납부, 초대, 참여자, 그룹

아래는 이 레포의 규약이므로 유지합니다.

`회귀`, `트레이드오프`, `검토한 대안`, `선택 이유`, `확인 필요`

## 문서 표기

- 문장 전체를 굵게 쓰지 않습니다. 굵게는 항목 이름에만 씁니다. `**금전 계산이 지점마다 다른 답을 내고 있었습니다.**`가 아니라 `**1인당 정산 금액 계산이 세 곳에 중복**`으로 씁니다.
- 표는 비교할 값이 네 개 이상일 때만 씁니다. 값이 두세 개면 문장으로 씁니다.
- 굵게는 수치와 기술 용어에만 씁니다. 주장이나 분류에는 쓰지 않습니다.

## 고치려다 오히려 나빠진 사례

아래는 실제로 거부된 수정입니다. 규칙만 보고 고치면 원본보다 나빠지는 자리가 있습니다.

### 빈도가 높은 표현을 바꾸려 한 것

- 나쁜 예: `기존 기능` → `지금 코드`, `반영했습니다` → `옮겼습니다`, `처리` → `지웁니다`
- 판정: "한국어에서 많이 쓰는 패턴을 대체 표현으로 바꿀 경우 더 AI스러워질 수 있다"

빈도는 판별 기준이 아닙니다. 그 말을 한국어 화자가 이 맥락에서 쓰는지가 기준입니다. `그대로`(67회), `실제로`(18회), `아예`(6회)는 모두 정상 한국어이므로 유지합니다.

### 짧은 동의어로 바꾼 것

`검토했으나` → `봤지만`, `취급합니다` → `봅니다`, `판단했습니다` → `봤습니다`, `추출했습니다` → `뽑았습니다`, `동작합니다` → `돕니다`. 다섯 곳 모두 원본이 맞았습니다. 규칙 1이 여기서 나왔습니다.

### 어미 반복을 없애려 한 것

`구현했습니다`, `처리했습니다`, `추가했습니다`가 연속으로 나오는 것은 AI 문체가 아닙니다. 사용자가 직접 쓴 PR에도 나타납니다. 어미를 억지로 바꾸지 않습니다.

### 템플릿 이모지를 없애려 한 것

`🔴 High`, `🟡 Medium`, `🟢 Low`는 템플릿입니다. 사용자가 직접 쓴 PR도 이모지 소제목을 씁니다. 그대로 둡니다.

## 마지막 점검

본문을 내보내기 전에 확인합니다.

- 금지 표현 표의 단어가 남아 있지 않은가
- 문단마다 첫 문장과 마지막 문장을 역번역해 봤는가
- 한 문장에 절이 세 개 이상 들어간 곳이 없는가
- 무생물이 주어인 인과문이 없는가
- 목록을 여는 문장이 `아래는 ~입니다` 형태인가
- 굵은 글씨가 항목 이름과 수치, 기술 용어에만 쓰였는가
- 뜻을 모르면서 풀어 쓴 문장이 없는가
- 정상 한국어를 고치지 않았는가
- 커밋이면 `gh-commit`의 제목 규칙을 확인했는가
